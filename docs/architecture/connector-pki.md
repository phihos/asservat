# Connector certificate issuer adapter

C-04/C-21 under TASK-03, S-01 and REQ-FED-001. The initial adapter reuses the selected OpenBao provider/client for a narrow PKI `sign/<configured-role>` operation. It adds no mandatory service beyond the selected key provider, generates no private key and does not activate the certificate in the peer registry. Other PKI adapters remain possible behind the same port.

The coordinator must supply a current `CertificateIssuePermit` for the exact claimed bootstrap/key, verified claim-audit digest and trust revision, with at most five seconds of validity inside the original enrollment deadline. It is an internal checked value, not a public credential. The adapter revalidates the identity-free CSR, expected public key, fixed installation/cluster/issuer-epoch scope and permit before and after provider I/O. It uses explicit HTTPS credentials and origin, no ambient proxy/namespace/token, no redirects and no automatic signing retry. Response size is at most 32 KiB; errors contain no provider body or secret.

The requested certificate expiry is fixed at thirty minutes after the original claim, truncated to certificate second precision. A retry cannot request thirty more minutes from its new execution time. The role must issue the [peer certificate profile](peer-identity.md), ignore CSR subject/SAN requests, restrict allowed URI SANs, allow only client authentication/digital signatures, emit explicit non-CA constraints and bound backdating. The adapter independently verifies the returned chain, exact identity, public key and expiry, rather than trusting role configuration or provider metadata. No returned private key is accepted.

An ambiguous provider result is not peer authority. The [enrollment coordinator](enrollment-activation.md) now implements bounded attempts, encrypted claim/certificate audit and atomic current registration before returning an active identity. Token issuance, renewal/revocation producers and actual bootstrap ingress remain pending. No implementation may call this adapter from an unauthenticated user request or treat a caller-created permit as proof.

## Provider review and tests

The existing pinned fixture image reports OpenBao v2.7.1, digest `sha256:6d2b93856e3fcf7b18ad855a0b51eaba474dc8b79cf554379ea32034797d2acf`; this was read from its actual image labels. [OpenBao's CSR SAN advisory](https://github.com/openbao/openbao/security/advisories/GHSA-g892-p242-8g86) affects versions before 2.6.2. The selected fixture is newer; the Asservat adapter also forbids incoming CSR identities and the role disables CSR SAN use. The role's explicit non-CA behavior is documented in [OpenBao's issue discussion](https://github.com/openbao/openbao/issues/81). These primary references explain settings; they do not qualify our integration by themselves.

The real-service test creates an owned synthetic PKI root and a sign-only role, signs a client-generated CSR, validates the result, completes an actual TLS client handshake, checks fixed retry expiry, rejects wrong key/epoch/audit/deadline and tests provider role/token denial. That run passed with exit 0 in `test/results/connector-pki-integration-check.log`; `test/results/context-storage-environment.json` records unchanged source hashes and successful owned-fixture cleanup. The existing two-cluster context/storage tests also passed in the same fixture. Its first attempt failed before tests because a temporary directory underscore produced an invalid Kind cluster name; the harness now normalizes that generated name, and the original failure is retained in `test/results/context-fixture-name-regression.log`.

The provider fixture is ephemeral dev mode with a synthetic root credential and a TLS bridge to its isolated backend network. This passing result does not qualify persistent CA custody, operator PKI policy, audit retention, root rollover, HA/restore or deployed ingress.
