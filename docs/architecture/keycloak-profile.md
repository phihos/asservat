# Keycloak reference identity profile

The maintainer selected Keycloak as the first supported and tested provider for browser sign-in and MCP access. This provider remains operator-managed; the official Helm chart does not install Keycloak automatically.

Partial C-02/C-21, TASK-07, S-01/S-02 and REQ-AUT-001. [ADR-053](../decisions/053-keycloak-access-profile.md) adds an explicitly selected provider profile while retaining the stricter generic RFC 9068 profile. `oidc.Trust.Profile` is trusted bootstrap configuration, not client input. Both profiles reuse the existing bounded HTTPS/JWKS and signature verification.

Keycloak access tokens require header `typ=JWT`, signed claim `typ=Bearer`, `azp` and the one pinned resource audience. If `client_id` exists, it must equal `azp`. ID and refresh tokens cannot substitute; delegation, impersonation and proof-of-possession remain unsupported. Ordinary Keycloak group names/paths never confer access. Only the dedicated `asservat_groups` list supplies stable IDs, and an absent list produces no group membership. Malformed/null/duplicate/oversized claims fail verification.

The reference realm uses built-in protocol mappers: an explicit API audience and a multivalued User Attribute mapper for `asservat_group_id`, with aggregation enabled, outputting `asservat_groups` only in access tokens. Configure group attributes to their native group UUIDs. Protect the attribute against user writes, restrict user/group/client/mapper administration, disable unmanaged attributes and never recycle group identifiers. This is installation automation, not per-developer setup. A future installer must validate and explain the effective configuration; setting a qualification flag alone cannot establish these properties.

Console sharing ([ADR-232](../decisions/232-concrete-evidence-share.md) increment 2) needs `evidence:share` in the browser session's token: add it as a default client scope of the console client. The console's login request does not name it. MCP clients request it as an optional scope.

Retain Keycloak's `basic` client scope, which supplies the stable `sub`; replacing default scopes with only Asservat operation scopes yields tokens without a subject and must fail verification. The human client uses authorization code plus S256 PKCE, with direct password grants, implicit flow and service accounts disabled. Workload credentials use a separate confidential client with browser/password flows disabled. Group membership is recomputed on refresh; its accepted lifetime remains bounded from the original access-token `iat`, never from verification time. Existing signed JWTs do not gain immediate offline revocation when a provider session is closed. Protected Asservat policy remains checked on every service call and can revoke a client/subject independently.

`make identity-integration` creates one owned loopback TLS Keycloak 26.8.0 fixture, synthetic users/groups and temporary credentials, runs the product verifier, and deletes the container and credential files. It uses a pinned image digest. Test administration is confined to the fixture; product verification has no realm-admin credential or Admin API dependency. The fixture's embedded development database is not a production deployment recommendation. Local qualification passed on 2026-10-10: `test/results/identity-provider.log` and `identity-provider-environment.json` record exit 0, unchanged source and no cleanup failures. The test exercises actual authorization-code/S256 exchange, code replay and wrong-verifier denial, ID/refresh token rejection, refresh rotation, stable group rename/add/removal, permitted ordinary profile edits with rejected authority-attribute self-assignment, separate human/service clients and disabled-user refresh denial. Earlier failed fixture configurations are preserved as `identity-provider-failure-01` through `-06`; no failed run is counted as passing. The canonical files now hold the 2026-10-16 ADR-193 run (`test/results/adr193-identity-3/`), which adds an owned S3 store and the fleet issuance subtest; the previous canonical files are kept in `test/results/identity-provider-20261012/`. The first valid access token lacked `sub` when `basic` was omitted, and was correctly rejected.

Public browser sessions, discovery/configuration acceptance, refresh coordination, step-up, workload/client provisioning diagnostics and MCP transport authorization remain separate integration requirements. No public collection or evidence route is enabled by this profile.

[Background policy identity research](../research/background-identity.md) withdraws the earlier mandatory directory-reader recommendation. Standard login/session refresh is the accepted human path; [ADR-059](../decisions/059-unattended-policy-authority.md) separates recurring team execution from the creator's SSO session. Team policies survive creator departure under current delegated authority. No directory/offline credential implementation is required; public policy execution remains gated on runtime qualification.

Research checked 2026-10-10: the [26.8.0 release](https://www.keycloak.org/2026/10/keycloak-2680-released) documents mandatory actor claims on impersonation; these are rejected by this adapter. The [built-in group mapper](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/mappers/GroupMembershipMapper.java) emits names/paths, while the [attribute mapper](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/mappers/UserAttributeMapper.java) supports aggregation. [Provider administration guidance](https://www.keycloak.org/docs/latest/server_admin/index.html#_groups) describes group attributes; the fixture verifies behavior rather than treating source review as an integration result.

The 2026-10-10 hierarchy extension passed real Keycloak tests: ancestor IDs, direct/inherited deduplication, parent rename, slash-containing names and removal retain correct stable UUID assertions. `test/results/identity-hierarchy.log` and its environment report record exit 0, unchanged source and complete cleanup. A future directory adapter must preserve these same semantics, including ancestors, rather than parsing a group path.

The [browser session continuation](browser-sessions.md) now qualifies the confidential client, actual HTTP session flow, encrypted SQL/OpenBao credentials, coordinated refresh and Keycloak back-channel logout. The owned provider uses a pinned loopback HTTPS listener with a fixture-only trusted certificate; no workstation network/firewall setting is changed. These are measured components, not protected deployment acceptance or approval step-up.
