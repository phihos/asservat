# Protected download worker configuration

[ADR-070](../decisions/070-protected-worker-configuration.md) implements the current administrator configuration path for REQ-DEP-003, REQ-DLD-003 and REQ-CAP-003. C-14 owns the private worker lifecycle/consumer ports, C-08 the encrypted audit/acknowledgement ports, C-21 the Kubernetes/SQL/object adapters, C-20 the closed wire DTO and C-24 the pure values. This introduces no public entity, HTTP endpoint, container permission or evidence approval.

## Kubernetes source

The [wire schema](../../specs/contracts/worker-configuration.schema.json) defines exactly one `worker-profile.json` ConfigMap value: installation/worker cluster, recovery epoch, increasing revision, suspension, namespace/account/PriorityClass/control ConfigMap references, immutable image digest, bounded registry references and CPU/memory/runtime ceilings. Control data, root keys, credentials and executable scripts cannot be embedded through extra fields. The separately referenced immutable `worker.json` protocol is implemented in the [worker startup](worker-startup.md); protected deployment/issuer bootstrap remains pending.

`WorkerConfigurationAdmission` protects CREATE/UPDATE/DELETE of the exact named ConfigMap in the exact namespace. Only the independently configured Kubernetes administrator users/groups may mutate it. `WorkerConfigurationProtection` checks a pinned policy UID/generation, binding UID/resourceVersion, complete expected specifications, observed generation and absence of CEL type warnings. It verifies the probe's real identity and named UPDATE RBAC before requiring an exact policy denial of a dry-run UPDATE. A missing guard, failed type checking, API error or ordinary RBAC denial is unavailable protection.

The reader has only named source/policy/binding and namespace reads. The trusted probe has named update capability solely to exercise admission; production RBAC need not include patch/delete. The actual fixture additionally uses those verbs to verify their admission denial. Neither identity selects administrators from the source data. Mutating admission, policy management and initial pin provisioning must remain installation-administrator operations; this guard does not defend against a cluster administrator disabling their own controls.

The source obtains protection, reads and canonically validates the exact ConfigMap twice, rechecks protection, and returns one observation ending within five seconds of its first read. Missing fields, aliases, unknown/duplicate fields, malformed references, changed namespace/ConfigMap identity, inconsistent revisions or expired reads fail. The original observation deadline is never recomputed from the last API call.

## Persistence and audit

`WorkerConfigurations` stores a current head plus immutable `download_worker_configuration_revision` snapshots under migration 26. Keys are installation, worker cluster and ConfigMap UID. Snapshot data contains configuration and independently measured protection digest, not bearer credentials, private keys or evidence. Same-revision content changes and rollback fail. Revision count is bounded to 1024; polling the same revision does not grow history.

The observer role can stage revisions and refresh their original observed/fresh-until timestamps. It cannot acknowledge encrypted audit. The audit role can attach one exact receipt but cannot change a snapshot or head. Runtime readers can lock/read current state but cannot accept profiles, alter revision, refresh freshness or acknowledge audit. Native immutable-row/monotonic-head triggers supplement these column-level privileges. Recovery is locked before staging or current checks; SQL time is checked again after blocking locks.

`WorkerConfigurationObserver.Observe` stages a fresh protected observation, reuses any acknowledged receipt, otherwise writes and authenticates a create-only encrypted S3 snapshot through the existing envelope codec and acknowledges it separately. An acknowledgement is historical; it cannot renew freshness or reactivate a superseded head. Source-read failure attempts to fence only observations at or before that read's start, preserving a newer successful observer's result. The original five-second deadline remains the backstop if fencing fails.

## Consumers and rollout

The dispatcher SQL path checks current recovery, original permission/retention/session authority and the exact current profile before and after effect work, including after child locks. The Job driver requires a `WorkerConfigurationGuard` and caps creation/observation by its returned original deadline. Missing configuration cannot be bypassed with an otherwise valid constructor profile. Audit receipt lookup, recording an already observed Job and known termination/cleanup remain historical operations and do not need a new active profile.

[Hub-wide routing](worker-routing.md) resolves the exact stored worker profile through a read-only application facet, while existing effect facets retain their constructor-profile match. Worker identity lookup returns `DownloadWorkerIdentity` with the original intersected configuration/SQL-observation/worker deadline. The dispatched TokenReview adapter caps its proof by that value, including time already spent in profile lookup. Existing key-binding/spend checks still require that proof to be fresh after SQL locks. No new proof or key grant may arise from an expired profile, and no reader turns the old deadline into another five seconds.

This version uses one current revision per enrolled source. Rollout or suspension denies old-profile dispatch/binding/new identity proofs; existing finite proofs expire at their original cutoff. It neither rewrites old worker identity nor refunds uncertain capacity. Confirmed cleanup remains available using the old immutable profile. The eventual supervisor must retire interrupted workers and make permitted retries visible; continuous supervision, issuer/control runtime, graceful profile draining and installation bootstrap are separate unfinished work.

## Qualification

The missing-projection regression is retained in [worker-config-before-custody.log](../../test/results/worker-config-before-custody.log). SQL tests exercise actual roles, revision history/audit gating, stale-profile rejection, suspension, explicit fencing and expiry behind locks with explicit synthetic Kubernetes/recovery inputs. The real Kubernetes test installs the actual native guard, uses distinct reader/probe identities, reads the protected ConfigMap and projects it through SQL/encrypted S3 audit before running the real Job driver. Its installation recovery root, audit wrapping keys, worker executable/registry and peer certificate remain fixture inputs. Both suites passed with unchanged tested sources and complete cleanup. Actual exits, detailed coverage and fixture boundaries are recorded in [implementation progress](../implementation-progress.md); these results do not qualify installer bootstrap or a public download service.
