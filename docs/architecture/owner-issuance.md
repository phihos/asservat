# Hub owner certificate issuance

[ADR-079](../decisions/079-owner-certificate-issuance.md) implements the provider boundary for REQ-FED-001, REQ-DEP-003, REQ-DLD-003 and REQ-CAP-003. C-04 owns `OwnerCertificateIssuer`; C-24 owns the immutable permit/result and renewal arithmetic; C-21 owns CSR, X.509 and OpenBao adapters. No public browser/MCP/worker contract or SQL schema changes. This uses [accepted owner configuration](owner-configuration.md) and the existing [TLS identity profile](hub-owner-discovery.md).

## Period and permit

`OwnerCertificateWindow(now)` derives a UTC twenty-minute period and its exact end. The following period may be prepared during the last minute. This is independent of process uptime and permits a healthy long-lived hub to renew without restarting. A later retry of the same attempt cannot alter its stored `CertificateNotAfter`. The issuer enforces that expiry against the original `CheckedAt`; it does not derive a new expiry after provider I/O.

`OwnerCertificatePermit` binds the consumed attempt ID, exact installation/cluster/issuer/Pod/process, single server/client purpose, CSR public-key digest, enrollment-audit digest, accepted configuration observation, current recovery observation, epoch/ordinal, original checked time and signing deadline. It admits only ordinals one or two and a signing interval of at most five seconds, clipped to the original configuration/recovery deadlines. Suspension, issuer/scope mismatch, missing audit digest and stale observations deny issuance. These structural validations are not cryptographic capabilities: only the trusted [enrollment coordinator](owner-registration.md) may construct a permit after actual proof and irreversible SQL spend.

The lifecycle must enforce finite concurrent registrations, per-period signing budgets, registration revocation, active-certificate slots, bounded history and cleanup. The provider adapter cannot enforce installation-wide concurrency or prove that an attempt was durably spent. Do not expose it directly to worker/user requests, use a test permit as production authority, or persist its caller's private key.

## Provider operation and verification

`kms.OwnerCertificateIssuer` fixes one provider/mount/role and purpose through private bootstrap. It uses the existing explicit HTTPS client with no ambient proxy, redirects or automatic retries. Validate an identity-free signed CSR and its key digest before I/O. Set the canonical owner URI explicitly. Server requests additionally send the deterministic DNS SAN as the OpenBao `alt_names` string; client requests omit it. The optional fresh-install [ADR144 profile](../decisions/144-cluster-local-observations.md) derives one additional common server SAN from the same accepted original Service/issuer identity. Both names use the existing one signing attempt, key, period and provider byte bounds. Legacy omission keeps the original request and leaf shape. The profile must be selected by the independently pinned constructor and current permit; received SANs cannot select it. Pass an absolute second-precision `not_after`, never a relative TTL that a retry could extend. Role configuration must disallow caller CSR identities and extra usages.

Only the configured sign path is used. The response has a 32 KiB bound, no private-key field, a DER leaf up to 16 KiB and at most three additional certificates; the combined DER bound remains 32 KiB. Standard PEM/X.509 parsing owns cryptography. Provider errors are sanitized. Retain the permit's deadline through the response and final validation.

`OwnerPeerVerifier.CheckOwnerCertificate` verifies the actual CSR key, strict existing leaf profile and configured certificate chain without pretending that issuance completed a network handshake. It additionally requires the same result under the current accepted configuration's roots. The returned leaf must match the exact Pod/process, purpose, requested expiry and at most one minute of backdating. Unsupported additional names/usages or changed expiry fail. Deep-copy result bytes before returning. A CA close to expiry cannot produce a full-period certificate: issuance must fail until qualified trust permits the requested period; do not silently shorten the certificate or extend the CA.

TLS peers still require an actual TLS 1.3 handshake and current X.509 revalidation through the original verifier. Certificate issuance alone neither activates a registry entry nor authorizes a forwarding request.

## Qualification and next composition

[ADR-081 enrollment proof](owner-enrollment-proof.md) now implements the pre-Ready token/CSR/workload observation. Its current configuration and workload guard remain separate from trusted historical installation and durable owner registration, signing spend and certificate activation.

[ADR-080 workload protection](owner-workload-protection.md) now adds native namespace admission and current enforcement proof. It does not establish historical workload integrity or finish the Pod/token/CSR enrollment proof below. Protected installation before credential/workload launch remains mandatory.

Unit tests cover stable renewal boundaries, long-running processes, exact CSR key, identity/purpose/deadline, removed current roots, stale configuration/recovery, suspension, missing audit, malformed/oversized chains, owned output buffers and the provider request's DNS field type. The HTTP fixture rejects with 429 and verifies exactly one POST, bounded sanitized failure and no unaudited request. Existing actual mutual-TLS negatives remain applicable to the extracted shared verifier.

The owned real-provider fixture creates separate OpenBao client/server roles and credentials, signs actual CSRs, opens mutual TLS with both resulting leaves, and checks identity, expiry, purpose, forbidden role/root changes and credential revocation. Its accepted configuration/recovery/enrollment/spend inputs are synthetic. It tests provider issuance, not durable activation, deployment admission or a public download. Actual exits, initial failures, source hashes and cleanup are recorded in [implementation progress](../implementation-progress.md).

[ADR-082](owner-registration.md) now supplies durable enrollment, pre-I/O signing spend, encrypted issue audit, current activation and bounded renewal history/retirement. Next compose native Pod proof and protected workload/issuer/bootstrap with the private credential channel, forwarding and supervised native byte delivery. The local static-key CA alternative remains a separate required backend under the accepted small-deployment plan.

Initial enrollment must not call the routable `OwnerEndpoint` reader as its ownership proof: that reader requires a Ready Pod and Ready EndpointSlice, while the service may need its first certificate before becoming Ready. Keep an independent, bounded Pod-bound-token/CSR and accepted workload membership proof for enrollment, and retain readiness requirements for actual forwarding. A matching ownerReference alone is insufficient protection against a namespace writer creating a Pod with the privileged account; protected workload/account creation and mutation remain installation prerequisites. Do not fix bootstrap by publishing unready endpoints or weakening the route reader.
