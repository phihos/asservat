# Complete retention source selection

C-01 owns the complete source set under REQ-PRV-002/004; C-21 supplies its Kubernetes adapter. A capture or download caller selects a target, never which retention sources should apply. Missing configuration cannot become an implicit hub-only configuration.

The initial adapter reads one immutable installation ConfigMap per enrolled target cluster. Its single `topology.json` value follows the [versioned schema](../../specs/contracts/retention-topology.schema.json) and [example](../../examples/retention-topology.json). It names the permission authority root, target cluster, exact hub source and an explicit local source or `null`. Source references bind cluster identity, control-namespace incarnation and qualified protection digest. Exactly one hub source is mandatory; a local source belongs to the target cluster and cannot duplicate the hub source. Source role comes from these fixed positions, never policy status or a request.

Protected installation/enrollment composition must independently accept the ConfigMap name, UID and canonical content digest, along with the control namespace UID already pinned by its reader. Kubernetes [immutable ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/#immutable-configmaps) prevent later data edits and reversal of immutability. UID pinning rejects deletion/recreation. Canonical content pinning rejects an incorrectly provisioned initial object; successful GET or `immutable: true` alone is not acceptance of its contents. Metadata-only changes do not change topology identity.

`RetentionTopologies` builds a private, bounded routing map from those accepted installation pins. It accepts at most 1,024 distinct target/name entries, copies its inputs, and has no fallback route or discovery through workload requests. Each read preserves its original five-second deadline, rechecks namespace identity around the GET, requires immutability and exact schema/content/root/target identity, and returns the complete source set. Deleting an object, unknown target, malformed/mutable data or delayed read fails closed. This route is configuration, not enrollment or permission to enumerate a cluster.

Installers should generate the object and pins together as part of existing cluster enrollment. App maintainers do not write hashes, select policy sources or approve topology when requesting captures. Changing source identities is a protected installation migration: stop affected new operations, drain prior policy history/catch-up, qualify the replacement source and restore continuity, then replace the accepted pin. A runtime reader cannot approve a new pin by discovering its current value. Changing ordinary retention maxima continues through the existing guarded policy CRD and does not replace topology.

`AcceptedRetentionReader` combines this topology with the independent SQL source-read facet and protected selector facts. It checks the complete set again after selector I/O. An accepted topology does not make a missing/stale/unaudited source Ready. Current fleet/recovery checks and the final operation transaction still apply. Protected pin provisioning/migration, historical selector qualification and the public workflow remain implementation work; tests explicitly supply their installation acceptance inputs.

Unit/race tests cover explicit hub-only and hub/local configuration, omitted local decision, mismatched target/root/source, extra or aliased fields, bad content/digest, changed namespace/object identity, mutable data, missing objects, original read expiry, immutable routing inputs and unknown-target refusal. Real API qualification is recorded in the implementation progress log when completed.

The [final retention effect contract](retention-effects.md) now requires the complete accepted source proof inside the SQL effect transaction. Its real SQL/S3 qualification and repository gates pass; it adds no public approval or policy-source selection step.
