# Retention policy observation and matching

C-15/C-21/C-24 under REQ-PRV-001–003 and S-01/S-02. These components read policy configuration, match protected selector facts and enforce API write boundaries. They do not make raw API observations production collection authority.

`RetentionClient` lists every EvidenceRetentionPolicy in one fixed enrolled control namespace using consistent bounded Kubernetes pagination. It pins namespace UID before and after the read, validates exact offline schemas, rejects malformed/deleting/duplicate/partial sources, and retains the original five-second freshness. A stable snapshot digest binds source cluster, control namespace, origin, policy IDs, generations and definitions; status and resource-version churn do not alter policy identity. API reads and schema validation prove neither historical provenance nor write protection.

The hub/local origin is set by protected installation wiring, never by a CRD author. Exactly one hub baseline with empty scope is required by the matcher. A local empty-scope policy applies locally and cannot become that baseline. The configured source topology must be complete before matching; callers cannot omit a local control namespace to avoid its ceiling. The initial composition supports one hub source and one optional local source for the target cluster. Same-cluster installations can use a single protected control source.

Matching ANDs namespace/workload/cluster dimensions and ORs cluster IDs. Every selector key in a potentially applicable policy needs a current protected metadata observation, including proof of an absent value. Unprotected or incomplete labels fail resolution even when the observed value would not match the narrower policy. The matcher accepts at most 64 applicable policy references and returns independent rule slices. The existing resolver then applies the shortest maxima and defaults, largest deletion budget and complete policy provenance. No classification or deadline extension comes from metadata/status.

`EvidenceRetentionPolicy` now has a generated structural CRD with named rule-list identity, bounded selectors and a native rule that deletion budget leaves positive usable time. Its bounded status reports phase/generation, optional exact policy digest, backend compatibility, outstanding lease age and cluster acknowledgements. Status is informational and cannot authorize reads or collection. Actual status reconciliation remains pending.

Native API admission separates retention administrators, scoped retention delegates and status writers. A delegate must preserve all delegated cluster/label dimensions on both old and new objects; it cannot create an installation baseline, move another scope into its own, delete another scope or write status. Ordinary maintainers/source administrators receive no implicit retention-authoring privilege. Policy protection is scoped to the configured control namespace; resources elsewhere are not accepted configuration. Runtime guards must separately pin that namespace's UID because native CEL does not expose it for these resource checks.

## Current source enforcement continuation

`RetentionGuard` now checks the exact protected installation plan, policy UID/generation, binding UID/resource version, Deny action, type-check status and control-namespace incarnation. It rechecks these around a schema-valid synthetic dry-run request. A separately credentialed ordinary probe must first pass native create RBAC and must be outside all administrator, delegate and status-writer identities. Only the exact structured denial from the pinned retention policy counts; an unrelated refusal, a missing guard or an administrator probe does not. No retention resource or collection is persisted. The returned five-second interval starts before the first API request, so blocking I/O consumes the interval.

Permission and retention guards share the exact installed-policy checker; they retain different plans, resources, negative controls and trust outputs. `PolicyProtectionReader` exposes `SourceProtection` to C-15. It proves current write enforcement only: accepted initial values, protected namespace/workload selector keys, complete source topology, cluster restore/continuity and propagation are still separate mandatory facts. A source cannot declare itself protected through CRD status.

Race-enabled tests pass in `test/results/retention-guard-unit.log`: warn-only/replaced/untyped guards, wrong causes, privileged probes, RBAC-only denials, unexpected admission success, namespace replacement, changes during the probe and expired observations all fail closed. The real Kubernetes test passed in `test/results/retention-guard-kubernetes-check.log`: ordinary negative control, administrator/delegate/status and RBAC-only rejection, dry-run nonpersistence, changed binding rejection and rejection after restoring the same binding value with a new resource version. The source-hashed report records observation/admission exit 0, unchanged source and no cleanup failures. This qualification still does not accept historical policy values or selector metadata.

## Accepted-source composition and ordered policy history

The subsequent [durable checkpoint implementation](retention-checkpoints.md) adds initial-value reviews, SQL process epochs and encrypted acceptance audit. It preserves original observation deadlines across restart. The subsequent context catch-up and finite-observation facets derive source readiness under [ADR-056](../decisions/056-retention-watch-watermark.md); production topology/selector wiring remains required for complete policy resolution.

`AcceptedRetentionReader` now joins the C-01 topology/source read ports with protected selector facts. The configured hub/local set is mandatory; a missing local source cannot silently become a hub-only plan. Both passes check source origin, protected guard digest, accepted revision, complete/ready state and original deadlines (30 seconds for accepted sources since the ADR-200 revision of 2026-10-23, migration 00075; raw LIST, guard and selector observations keep five seconds). A source or topology change during metadata I/O fails the read. Protected selector keys include absent values. No metadata read is needed when no selector affects the result. These consumers use the separately implemented durable C-01 checkpoint and source-read facets; they do not accept raw Kubernetes state as authority.

Retained resolution is a separate port that receives original and subsequently applied policy references from the custody/lifecycle ledger. It follows those UIDs regardless of current labels, detects revision rollback and unions the references into each signed shortening decision. Current matching adds new applicable rules. A deleted override cannot lengthen the retained ledger. Public callers cannot supply substitute origins, purpose or classification.

`RetentionClient.RetentionPolicyList` additionally preserves the complete LIST cursor and each policy's opaque resource version without placing them in the semantic snapshot digest. `WatchRetentionPolicies` uses the existing bounded Kubernetes JSON stream framing and strict policy decoder. A finite watch begins at the exact cursor, with no selectors or automatic history reset. ERROR/410, malformed events and replacement namespace identity fail closed.

C-01's `RetentionJournal` processes each transition serially, requires exact acceptance of a frozen checkpoint before the next transition, and never coalesces a lower-then-higher maximum. A later complete LIST can refresh freshness only when both rules and per-object versions agree with processed history and the durable watch cursor has reached that LIST watermark. Equal final state alone misses a policy added and deleted between LISTs. Bookmarks move the watch cursor without renewing completeness. Generation gaps, rewritten same-generation definitions, unexpected deletion bodies and UID/name replacement poison the journal. This journal is not SQL acceptance or restore qualification; guarded initial review, exclusive controller epoch, durable transition/audit/catch-up records and reconciliation of existing artifacts remain necessary before a source is Ready.

Unit/race tests cover complete hub/local composition, changed topology/guard, unprotected absence, stale input after I/O, retained origin matching and lower-then-raise watch history. The real Kubernetes stream test passed in `test/results/retention-watch-kubernetes-check.log` (exit 0; admission run 11.007 seconds). It lowered and restored the baseline through the real API, rejected a final LIST before processing history, and observed both exact limits in order under a read/watch-only role. The source-hashed report records unchanged source and no cleanup failures. `test/results/retention-watch-gates.log` records passing Go/race/import/sqlc/spec/architecture/design checks. The test acknowledges journal checkpoints synthetically; it does not establish SQL source acceptance or production retention authority.
