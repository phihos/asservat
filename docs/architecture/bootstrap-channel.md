# Bootstrap credential delivery

C-04/C-21 under TASK-03 and REQ-FED-001. `BootstrapCredentials` stores a credential for a durably reserved internal slot in a configured operator secret channel. The initial adapter uses the already-selected OpenBao client/provider's KV-v2 engine. It creates no new service dependency and returns only the slot/profile reference, purpose-bound secret digest and version. No secret appears in a browser/MCP operation result, SQL row, audit record or log.

## Stored format and retry rules

The private stored format is `asservat-bootstrap-secret/v1`. A `binding` object contains `format`, `installationID`, `bootstrapID`, `clusterID`, `peerID`, `issuerEpoch`, `deliveryProfile`, `requestSHA256`, `notBefore` and `notAfter`. Its sibling `secret` is 32 CSPRNG-generated bytes encoded as canonical unpadded base64url. All IDs and the original at-most-five-minute deadline are assigned by the issuance reservation, not by an enrollment client. Current creation/read authority lasts at most five seconds within that deadline. Preview never creates a slot or secret.

Bootstrap fixes the HTTPS provider, credentials, KV mount, prefix, installation and delivery-profile name. The path is `<mount>/data/<prefix>/<installation UUID>/<bootstrap UUID>`. No token/request-selected URL or provider namespace is accepted. The adapter reads the current record first, conditionally creates a missing record with `cas: 0`, and resolves the result with one read. It never retries the POST, overwrites an existing record or refreshes its binding/deadline. An unknown write result retains the original slot identity; a retry must resolve that same record. Only version 1 is accepted, with exact binding and strict owned-field spelling. Record size is at most 16 KiB; response errors never include provider bodies or credentials.

The issuer role has only `create` and `read` on the configured data prefix. It has no update, list, metadata change, delete, destroy or undelete authority. This uses KV-v2's create/update distinction and CAS behavior. Soft deletion remains reversible; it is not proof of credential destruction. Those provider semantics are documented in the [OpenBao KV-v2 reference](https://openbao.org/docs/secrets/kv/kv-v2/). Domain checks enforce the original token expiry independently of provider deletion timestamps, and a deleted or replacement version is rejected.

A stored credential is initially inactive. Only the eventual current SQL issuance transaction, after encrypted issuance audit, may create its claimable bootstrap slot. Operators may have access to the configured channel before activation; possession of an inactive token grants no enrollment. The UI must wait for the issuance receipt before presenting the install handoff. This is not another user approval.

## Verification and remaining composition

`test/results/bootstrap-channel-regression.log` records failing field-case substitution tests. The fix compares canonical JSON against the owned typed record because Go's ordinary struct decoder accepts case-insensitive field names. The race tests then passed in `test/results/bootstrap-channel-unit.log`, including a dropped POST response recovered by one read with no duplicate POST.

The actual OpenBao run passed in `test/results/bootstrap-channel-integration-check.log`: eight concurrent callers resolved one version-1 credential; the digest matched the provider-held secret; mutation/destroy/metadata operations were forbidden; changed binding/expiry, replacement version, deleted value, expired instruction and revoked provider credentials denied. `test/results/fleet-environment.json` records pinned images, source hashes, unchanged sources, exit 0 and complete owned-fixture cleanup. The same run included enrollment SQL/audit, current registry and combined OpenBao/TLS/SQL/S3 activation tests.

`make fleet-integration` runs those owned provider/SQL/S3 fixtures without creating Kubernetes clusters. `context-integration` still owns its separate two-cluster context tests. Shared role SQL under `test/fixtures/sql/` is explicitly synthetic and must never be applied to an operator installation.

The [SQL reservation facet](bootstrap-reservation.md) now supplies finite issuance intent/counters. The channel adapter does not implement issuance audit/finalization, production secret-channel qualification, credential destruction/finite metadata cleanup, provider backup horizons, trust/recovery production or public enrollment ingress. Credentials in the provider's backups still need a bounded encrypted retention policy. No evidence collection or disclosure is enabled here.

[Audited bootstrap issuance](bootstrap-issuance.md) now composes reservations, credential delivery, encrypted issuance-intent audit and current atomic activation, with real PostgreSQL/S3/OpenBao tests. This supersedes the issuance-producer gap stated above; protected trust/recovery, provider lifecycle qualification and public ingress remain pending.
