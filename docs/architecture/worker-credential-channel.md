# Worker credential channel

Current installed composition is revised by [ADR-219](../decisions/219-shared-approved-acquisition.md)
and [ADR-221](../decisions/221-admitted-worker-identity-enrollment.md): one closed
acquisition parent selects native download or approved pod-status. Certificate
enrollment uses the exact admitted worker and its own bounded HTTP request,
without a human certificate-owner registry/locator/relay. Native-operation
ownership and each purpose's current key/evidence authority remain separate.
The older certificate-routing components and their tests below are historical
component evidence, not the installed certificate path. Shared composition
qualification is still pending.

[ADR-072](../decisions/072-worker-credential-channel.md) completes the process-key/transport components of [worker enrollment](worker-enrollment.md). C-14 owns the live control operation; C-20 owns the closed wire and handler; C-21 owns process cryptography, the TLS client and projected-token reader; C-24 owns the minimized credential target and common renewal arithmetic. These are acquisition and control responsibilities within I-13, not a new always-on service or a public API.

## Control binding

`WorkerEnrollmentExchange` is the private ingress port. `WorkerEnrollmentOperation` binds the existing coordinator, current human credential, exact download scope and admitted `WorkerCredentialTarget` to a live control request. Installation ID is independent of the permission-root ID. The operation intersects the parent deadline, original worker deadline and thirty seconds. [ADR-074](worker-request-routing.md) retains parent cancellation during proof/provider/audit I/O and through response write using a mandatory-close `WorkerEnrollmentDelivery`. It never persists the credential. The active request owner must release the operation after use; lifetime checks do not promise Go heap erasure.

`WorkerProofFactory` creates an independent attester for each token buffer. The buffer is cloned for the operation, each attester read returns a fresh owned copy, and those byte buffers are cleared after use. The current proof must match installation, session, worker, acquisition Pod, original creation time and deadline. Existing ADR-071 checks additionally require current scope, configuration, TokenReview, SQL budget/audit and independent activation. Neither a client certificate nor a caller-selected download ID supplies the human credential.

Runtime routing must associate this operation with the already authenticated browser/MCP control request through the configured connector/hub path. A worker cannot register an arbitrary callback or select an actor. An unavailable, expired or disconnected request owner denies enrollment; a new authenticated operation can retrieve the same audited certificate. [The process-local owner registry](worker-request-routing.md) now checks current human/SQL worker binding and bounds concurrent ownership. Federated rendezvous and public owner registration remain unimplemented; an in-memory test binding is not a production substitute. Ordinary sign-in/refresh remains at the existing browser/OAuth boundary; no directory reader or offline token is introduced.

## Private wire and listener

`POST /internal/download-worker/v1/enroll` uses TLS 1.3 and [worker-enrollment.schema.json](../../specs/contracts/worker-enrollment.schema.json). Request JSON contains format, installation/session/worker IDs, a canonical 32-byte base64url nonce and an identity-free DER CSR. Authorization is a single `Bearer` dedicated Pod JWT, at most 16 KiB. This token is only a proof input; the current attester actually verifies it. Reject cookies, extra credential fields, duplicate/case-aliased/missing JSON fields, trailers, content encodings, arbitrary paths/query strings and oversized bodies. JSON is not accepted as authorization.

The response echoes the format/IDs/nonce and includes DER leaf plus a required array of at most three chain certificates. Each certificate is at most 16 KiB; the combined DER ceiling is 32 KiB. Request JSON is at most 16 KiB and response JSON at most 48 KiB. Cryptographic parsing and period/identity checks are mandatory beyond schema validation. Errors have empty bodies and never echo token/CSR/provider diagnostics. Responses are no-store and nosniff.

The listener must have finite header/idle/read/write/connection limits, a header ceiling sufficient for the bounded projected token (20 KiB configured), independently pinned server credentials and private routing. The handler admits at most sixteen concurrent requests (deployment settings may lower this); saturation returns 429 without entering the enrollment service. It retains original request/owner/socket deadlines through response flush, interrupts blocked writes on owner cancellation and joins deadline callbacks before socket reuse. Global endpoint/PKI limits across replicas must additionally narrow this bound. Do not log Authorization, raw requests, private keys or complete responses.

[ADR-204](../decisions/204-installed-downloads.md) decision 9 serves this listener in the installed `hub-api`, only when a download worker profile is configured. The owner port (`pool.Port`, 9443) is split by ClientHello: the exact process name stays the owner relay; the pool's fixed serving name (`OwnerBootstrapServerName`, already in every owner server leaf) without h2 reaches `transport/worker.Serve` (TLS 1.3, HTTP/1.1, no client certificate, 20 KiB headers, one request per socket, forty-second absolute socket lifetime, joined shutdown), and with h2 reaches the worker native path. One raw pre-TLS ceiling, the sum of the three servers' socket bounds, covers sockets still being classified or handed off. Enrollment goes through the owner runtime's exact-owner forwarder and SQL locator, so any ready replica can receive it. The native path attaches only an operation that this exact process owns, on a path whose connector cluster is the hub cluster; it never forwards to another replica.

## Process key and renewal

`mtls.WorkerCredentials` takes a fixed HTTPS endpoint, separately pinned server and issuer roots, a trusted worker target, a token reader and clock. It creates one ECDSA P-256 private key and identity-free CSR. It uses verified endpoint DNS/IP, no ambient proxy/system-root fallback/cookie jar, bounded timeouts and one simultaneous connection. Each actual enrollment opens a fresh TLS handshake before sending the Pod token, so an expired server certificate cannot survive through a previously established keep-alive connection. POST bodies are not replayable and redirects are refused. Responses must match their request and contain a trusted client-only acquisition certificate for that exact Pod and public key, within the original anchored certificate period. A request crossing the one-minute preparation boundary may return either valid adjacent period. The response cannot change original timing pins.

`Enroll` returns the already installed current-period credential without HTTP work, serializes actual enrollment and bounds caller retry frequency after failures. A failed renewal preserves an earlier credential only through that credential's original expiry; it never changes SQL activation or evidence authority. The fixed `mtls.NewProjectedWorkerToken` reader reopens `/run/asservat/identity/token` for each attempt, follows Kubernetes projection rotation through a single opened regular file and enforces token size/syntax. It does not accept a public path or default service-account token fallback.

`GetClientCertificate` provides a TLS 1.3 callback. Renewed snapshots share only the owner signer and keep their own finite certificate deadline. `Close` cancels an active enrollment, prevents new enrollment and disables previously returned signers. It does not serialize or persist the private key and does not promise heap zeroization. Consumers must close their own established transports on shutdown; current effects still check activated registry identity, Pod proof, permission, privacy, recovery and lease deadlines on reused connections.

## Verification boundary

Real local TLS tests exercise the production client/handler, actual CSR/key/certificate checks, mTLS use, renewal, wrong key/role/Pod/installation/expiry/usages, malformed responses, redirects, uncertain reply without replay, concurrency, cancellation and closed/expired signer snapshots. These use an explicit test issuer/token verifier. The composed SQL/S3 case uses the actual current authorizer, separate enrollment/audit/activation credentials and encrypted audit with a process-generated worker key; its Kubernetes proof and CA remain test fixtures. See [implementation progress](../implementation-progress.md) for actual exits and source/cleanup evidence.

[ADR-073 startup](worker-startup.md) subsequently adds the typed public configuration, credential-phase executable and finite renewal supervisor. Still required: protected private listener/endpoint/issuer initialization, active browser/MCP-to-connector routing, deployment-wide admission, native connection supervision, local CA and public native-file delivery. Neither these TLS tests nor earlier independently qualified Kubernetes/PKI tests establish a fully composed public download.
