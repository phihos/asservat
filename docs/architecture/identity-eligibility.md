# Initial identity and ordinary eligibility boundary

Scope: C-02 identity, C-03 authorization, C-21 protocol adapters and C-24 values; partial REQ-AUT-001/002, REQ-PER-001/006/008, TASK-07 and S-01/S-02. The [identity verification record](../research/identity-foundation.md) and [protected settings continuation](../research/identity-settings-foundation.md) distinguish tested components from missing provider/configuration integration. This boundary returns eligibility, not an execution permit or disclosure authorization.

## Credential verification

The initial internal adapter supports an RFC 9068 JWT access-token profile with RS256, one resource audience and a configured HTTPS issuer/JWKS endpoint. It uses the selected go-oidc verifier and go-jose JWK parsing. Library verification alone is insufficient: Asservat additionally checks the access-token media type, exact issuer, resource audience, `client_id`, consistent optional `azp`, required timestamps/token ID and finite scope/group claims. ID tokens, opaque tokens, encrypted tokens and delegation/proof-of-possession profiles are unsupported by this first adapter. They are not silently accepted as another credential kind.

This is a qualification profile, **not a new requirement that every production IdP use this exact token layout**. The separately selected [Keycloak profile](keycloak-profile.md) now passes a real-provider synthetic fixture; other named providers and operator-specific realms remain unqualified. Before exposing login/MCP, implement and test the selected provider's actual access-token distinction, discovery/resource mapping, human/workload classification, group refresh and session behavior. Add explicit provider adapters when needed; do not accept an ID token or guessed email/group display name to avoid configuration work. An installer should supply tested provider presets and actionable diagnostics, with no per-developer mapping step when a qualified group policy covers the organization.

Protected role bootstrap selects issuer, audience, JWKS URL, certificate trust and key-cache maximum. Token fields cannot choose endpoints, algorithms or key URLs. Requests use verified HTTPS without ambient proxies, cookies, forwarded bearer tokens or redirects. There is no online discovery in this component; the future configuration owner must resolve and pin approved discovery results. The verifier rejects untrusted TLS certificates and public keys unsuitable for its fixed algorithm. Where `key_ops` is present, the initial profile accepts only verification use.

| Input/work | Initial bound |
| --- | --- |
| Compact token / decoded header / decoded claims | 32 KiB / 2 KiB / 24 KiB |
| Header / claims JSON | 64 / 2048 tokens, depth 4 / 8; duplicate keys, invalid Unicode and ambiguous field aliases rejected |
| JWKS response | 128 KiB, 8192 JSON tokens, depth 8, at most 32 keys |
| Signature keys | RSA public keys, 2048–8192 bits; private/symmetric material rejected |
| Per-issuer key cache | One bounded snapshot; configured lifetime 1 second–5 minutes; no expired-key fallback |
| JWKS refresh | Serialized, at most one attempt per second; no per-attacker-key cache |
| Verification/request deadline | At most 5 seconds; expiry rechecked after network/signature work |
| Signed groups / scopes | At most 256 stable IDs / 64 scopes |

Key-cache age starts before fetching. A slow response cannot grant a fresh lifetime at completion. An observed clock rollback during verification fails closed. A failed refresh cannot revive expired keys; an independently still-fresh cached key remains usable within its existing deadline. This does not provide instant bearer-token revocation or qualify production clock behavior. Explicit issuer/client/configuration revocation belongs to the current policy checks below.

## Organization eligibility and current policy

`identity.Service` obtains verified claims from `TokenVerifier`, then asks `PolicyReader` for the current accepted installation policy for that exact issuer. A valid signature alone is insufficient. The policy must admit a stable user/workload subject or a qualified group and the registered client. Client IDs and resource audiences remain distinct.

The initial client mapping requires an explicitly qualified human-only or workload-only issuance configuration. Mixed clients need a separately qualified mapping, never a human default. Group-based eligibility requires a provider guarantee that the signed group list is complete, uses stable IDs and is refreshed at token issuance, including refresh-token issuance. The RFC 9068 profile requires an explicit groups array, which may be empty. The Keycloak profile uses a qualified dedicated stable-ID mapper and treats its absent output as an empty group set; ordinary group names/paths are never a fallback. Provider configuration must establish complete membership semantics in both cases. A refreshed `iat` with stale embedded groups fails provider qualification. No qualification flag may come from a token or public caller.

The policy snapshot is valid for at most 60 seconds, normally 30; group assertions for at most five minutes from their original issuance. Effective identity expiry is the earliest token, key snapshot, policy and group deadline. Verification cannot reset these clocks. Policy reads occur on each service call; client removal or organization ineligibility cannot be bypassed by a still-valid signature. The reader must return immutable snapshots and current accepted revisions, not re-stamp a stale watch/cache as fresh.

`IdentityPolicyClient` now implements `PolicyReader` by reading a single enrolled administrator-protected ConfigMap through the Kubernetes API. Its data contains only `identity.json`, validated against the [identity settings contract](../../specs/contracts/identity-settings.schema.json); the [example](../../examples/identity-settings.json) illustrates the shape, not provider qualification. Role bootstrap pins the object name/UID and issuer. The adapter checks namespace identity before/after, rejects replacement/deletion, unknown fields, duplicate clients, unqualified identity classes and invalid group bounds, and returns a 30-second snapshot whose clock starts before I/O. It does not refresh by re-stamping cached data. Current reads reflect client/group removal. ConfigMap revision is explicit; its canonical content digest changes independently of a revision typo. Protected installation write authority and actual provider/group behavior still require qualification. No SQL permission editor, public permission CRUD API, tenant abstraction or permissive development identity is added.

## Ordinary permissions and retained audiences

`authorization.Evaluator` resolves the identity, obtains a complete current permission projection for the exact cluster/namespace/workload/pod identity, and checks ordinary target entitlement before looking up evidence. An unauthenticated or ineligible caller cannot use this path to probe artifact metadata. It rechecks all deadlines after potentially blocking reads. Errors expose bounded reason codes, not token claims or downstream error text.

The first facet covers ordinary context eligibility, approved metadata/extract reads and their native-download eligibility. Maintainers may request context; readers and owner teams may read/download permitted approved evidence; an approver role alone confers neither collection nor reading. Reads need `evidence:read`; downloads also need `evidence:download`; context needs `evidence:capture`. There is no team-lead restriction or extra approval introduced for ordinary approved downloads.

Explicit denies subtract the named role's operations. Unknown, stale or incomplete authoritative denies block eligibility. A stale unrelated allow can be ignored when another current assignment suffices. Current projections have bounded allow/deny rows and finite source decisions, never a catch-all fallback. The future source adapters must implement namespace metadata, exact SAR and explicit bindings under their existing qualification rules; supplying an internal `Projection` value is not proof that those checks ran.

Evidence reads additionally intersect current assignments with the immutable audience in committed, verified evidence. Match issuer, subject/group, role, assignment ID and source UID/digest exactly; preserve namespace/workload/pod incarnation. A new owner team cannot read old evidence through new ownership alone. Removing and restoring a team under a new assignment ID does not revive an old assignment. New members of the same still-authorized stable team may read within the existing freshness bounds. Multiple original teams remain independently eligible. Creator identity grants no special access.

`Result.ContributingAssignments` explains why this caller qualifies. It is **not the complete default audience for a new capture**: acceptance must separately resolve all eligible retained audience/owner assignments, including other teams, and enforce the 32-assignment artifact bound. Do not populate a manifest by copying only the caller's matching groups. The implemented `Evaluator.ContextEligibility` facet now obtains one current permission snapshot and returns both caller eligibility and the separate complete default audience. It includes other current reader/maintainer/owner assignments, preserves multiple owner teams, excludes approver-only assignments and exact denied subjects, intersects all included deadlines, and rejects more than 32 assignments without truncation. Later reads still evaluate overlapping group membership and current denies. It performs no artifact lookup or acquisition.

Read preflight may inspect a larger bounded current projection before intersecting it with the artifact's original audience. Additional assignments created later must not block an existing legitimate reader merely because a new capture would exceed its audience ceiling. Final retained evidence still has at most 32 original assignments; no new reader is added by this distinction.

Raw operations, shares, approvals, step-up authentication, local collection ceilings, capacity, accepted execution, durable audit and actual disclosure are outside this initial facet. They must be composed before any effect. A SQL `ProjectionReader` now exists behind qualified configuration acceptance. `AudienceReader` remains unimplemented and must never treat `stored_unpublished` receipts as a published artifact. No collector, catalog, browser route, MCP tool or download endpoint is enabled here.

The [permission continuation](permission-observation.md) corrects deny freshness in the evaluator: `DeniesObservedAt` / `DeniesFreshUntil` independently bound the complete set to at most five seconds, including an empty set. Each deny row has the same maximum. This deadline intersects every eligible result and is rechecked after blocking evidence lookup; the positive projection's maximum 60-second age does not extend it. Concrete Kubernetes observation readers now exist, but protected acceptance and assignment lifecycle still separate their output from this evaluator's `ProjectionReader`.
