# Initial database schema preparation

C-21 owns the immutable embedded `migrations/*.sql` package and PostgreSQL runner. The private bootstrap composes it with the actual current Kubernetes preparation root. `initial-schema` reads `/run/asservat/initial-schema/deployment.json`, the existing current administrator/probe token files, and `postgres-ddl.json`. The latter is a fixed protected SQL credential projection. It is never mounted into `initial-prepare`, `initial-install` or runtime processes.

The plan must explicitly contain `schemaInitialization: asservat-initial-schema/v1` and the qualified handover capability. Before any declarative target creation, `Root.Schema` must be complete. Older plans omit both new fields and retain their existing bytes. The one root record stores public attempt/bundle/database/role identities and original times, with no passwords, token hashes, user data or per-retry rows.

The current root guard and administrator are checked before and after SQL work. Each root read, claim and completion can shorten the current step's deadline; none can extend it. Goose may already hold the previous context during its lock callback, so a shorter observation cancels that original context as well. A detached context is used only for bounded advisory unlock, never authority or successful response validation.

The initial SQL state must have no user relations/functions and no preexisting Goose history. After claim, interrupted migration resumes only the original exact applied prefix on the original database OID/postmaster. Each migration and version insertion share one transaction. Failed/unknown commit does not claim rollback: the next invocation reads the original history and performs no reset/down migration. The qualified PostgreSQL18 metadata shape requires its one immediate primary key on `id` and four enforced NOT NULL constraints, as well as the exact column/identity/default definitions; PostgreSQL18 represents NOT NULL constraints in [`pg_constraint`](https://www.postgresql.org/docs/18/catalog-pg-constraint.html). The history begins with applied version0; duplicate, foreign, future, down or reordered entries reject. All operational rows must remain empty before completion. Final tables must match the existing first-installation inventory exactly.

Goose `ApplyVersion` is used instead of `Up`/`UpByOne`, which perform an unlocked `HasPending` check. The standard metadata table is separately created in one original transaction, and the supplied Store rejects Goose's automatic metadata create/delete methods. Only the exact compiled filesystem is available; no SQL or directory comes from the caller. A process owns at most one SQL connection and cannot run concurrent local migrations. A busy original advisory lock returns unavailable rather than taking over.

The DDL role and setup manager are distinct. A protected bootstrap producer establishes the manager's original name/OID/password/finite interval before the final plan; this schema facet does not create/reset those credentials. It installs exactly the union of the three existing initial-role grant sets, with grant option so the manager can create the original finite preparation/audit/activation identities. Extra grants, ownership and inherited memberships reject the active setup stage. SQL administration remains part of the trusted installation boundary, not an application privilege.

After child roles exist, PostgreSQL gives their creator unavoidable ADMIN memberships. The separate read-only completion verifier consumes the protected completed root, exact embedded bundle/schema history, original table owner and database incarnation using the original manager connection. It does not require a pristine operational database, issue grants or claim recovery readiness. A fully completed installation bypasses active schema/setup constructors and uses the existing protected passive history path. Manager retirement cannot be reversed by replay.

An active `initial-prepare` invocation with this capability performs that read-only completion check after selecting the passive path and before creating any preparation effects. A mismatched incarnation fails at the static `schema-completion` phase. This is a constructor prerequisite, not permission retained for the later activation. The completed schema's bundle digest, head, database OID and postmaster start time are copied into the exact protected activation projection and therefore into its existing plan digest. The capability and binding must appear together; incompatible compiled bundles, incomplete roots and silent legacy adoption reject. Older profiles omit both fields and preserve their serialized bytes.

The schema-bound preparation, audit acknowledgement and activation facets independently compare the actual PostgreSQL incarnation inside their existing transactions. Preparation checks after table locks and before commit; acknowledgement checks around its immutable receipt mutation; activation retains its existing before/after checks. Thus a database restart between constructor preflight and a later SQL effect cannot authorize a new claim for the replacement incarnation. No transaction may adopt it, replace the witness or clear recovery. The fully passive historical path deliberately remains separate: it reports the original installation disposition without claiming current recovery readiness and does not load retired setup credentials.


The command has a fifteen-minute process limit; the root has no arbitrary expiry. A lost root/SQL reply resumes the same plan after current verification. Changed incarnation, bundle or unknown/foreign state is a specific reconciliation blocker, not permission to adopt a new root or erase the database. No credential lifetime is refreshed. Supplied DDL credentials remain operator-managed and must be removed from the runner after joined completion; this facet does not pretend to revoke externally owned credentials.

Qualification scope is recorded separately. Unit tests cover embedded source restrictions, original ordered history, deadline shortening through the already-passed Goose context, legacy omission and closed root validation. The [real PostgreSQL run](../../test/results/initial-schema-metadata-after.log) passes actual embedded migration execution, prefix resume, lost root completion, exact grants, altered constraints, foreign history and locked-owner denial with a clearly synthetic root port. It does not by itself prove native Kubernetes authority or the actual mounted `initial-schema` command. Helm/runtime enablement remains off until the protected input producer and intended command are qualified.

The [composed empty-database run](../../test/results/initial-schema-handover-first.log) additionally uses native Kubernetes root/guard observation and the actual protected schema loader, followed by the original activation Pod, encrypted audit and full handover cleanup. Bootstrap identities, manager and provider inputs remain fixture-supplied; schema loading runs in the test process. This healthy path does not test a database restart between schema completion and activation. Carrying the original completed schema binding through active preparation and the final SQL effects is a separately tracked correction in [implementation progress](../implementation-progress.md).

Dependencies: runtime now imports the established Goose Provider version already used by the repository toolchain. Only its library packages and required runtime helpers are imported; unrelated database driver executables are not linked. The exact module diff and qualification commands belong in the frozen handoff.

The schema-consumption follow-up has focused failing-before/passing-after decoder and producer regressions, deadline/record tests and integration source coverage. Its isolated SQL case provisions the real bounded role union, rejects mismatched original database/postmaster bindings without creating activation rows, and accepts only the original claim. The [schema50 composed run](../../test/results/initial-schema-handover50.log) also passes: it injects a mismatched original postmaster pin before the actual mounted constructor, requires rejection specifically at `schema-completion`, restores the exact fixture root under a new resource version, then continues through the original activation Pod and passive reopening. Its terminal report records unchanged source and complete lab cleanup. This is an incarnation mismatch test, not a physical server restart or recovery qualification; bootstrap/manager/provider roots remain explicit fixture inputs.
