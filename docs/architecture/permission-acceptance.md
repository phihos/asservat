# Permission acceptance and durable assignment history

C-01 owns acceptance, C-03 consumes narrowed current projections, C-08 publishes control audit, and C-21 implements SQL/Kubernetes/object-store ports. This implements parts of REQ-PER-001/002/006/008 and REQ-DB-001. It is not a public collection or permission-authoring API.

## Transactions and continuity

`PermissionStore` accepts complete, bounded input from a qualified configuration reconciler. Kubernetes remains the authoring authority. Each stream is pinned to a protected installation root, trust digest and exclusive finite controller epoch. A root row lock serializes changes. Database time is checked after waiting for locks and again after writes; process time is not SQL authority. Ambiguous replies retry the original request ID and exact normalized input, without renewing observation time or issuing another assignment.

A new epoch first suspends the projection. An expired leader cannot renew it or accept later work. A trust change retires old assignments. A routine restart retains candidate history while waiting for a complete current observation: it must not make every old artifact permanently inaccessible merely because a process restarted. Exact unchanged resource versions can demonstrate no intervening object write within the same qualified cluster incarnation. Changed versions need verified continuous transition history; a relist with matching final values does not provide it. A generation jump, reversed generation, changed effective scope, removed role/subject, replacement UID or an unverified metadata observation change retires the old assignment. Namespace metadata has its own observation version, separate from the PermissionSource resource version.

Fresh assignments use SQL-generated random UUIDs. Retired IDs are never reused. Equivalent assignments retain their original authorizing digest for matching encrypted artifact provenance. The frozen audit event captures transitions before later source updates can change those facts. Controller restore and cluster-incarnation checks must precede any continuity claim; this store cannot infer an API-server restore from final object values.

The first complete SQL projection uses a five-second observation interval, including an empty deny set. This conservative common interval is within the existing positive/deny maxima. `RefreshPermissions` renews only a newly observed identical complete projection; it appends no audit or assignment record for a polling heartbeat. It is not replay of an old snapshot. Changed configuration uses a new acceptance transaction. Missing or stale deny configuration fails closed.

The scope digest is computed from actual normalized scope, kind, effect and expiry, and independently checked by the adapter. A caller-supplied claim of equivalent scope cannot preserve an assignment. Bounds are 1,024 effective bases, 4,096 current assignments, and 256 rows for a selected pod; overflows fail with a narrowing diagnostic rather than dropping an owner or deny. A PermissionSource spanning namespaces has separate basis keys while retaining the original source UID in evidence provenance.

## Audit before new access

An acceptance transaction stores an immutable event payload in an outbox and applies retirement/denial immediately. Outbox insertion alone cannot activate a new allow. The audit publisher writes `authority/v1/<root UUID>/<event UUID>/record` with conditional creation, authenticated encryption and a dedicated audit KMS/object role, then reads and cryptographically verifies the whole stored record before acknowledging its pinned receipt in SQL. The encrypted format is `asservat-authority-audit/v1`; it is deliberately separate from artifact manifests. Tink's existing AES-256-GCM-HKDF streaming suite wraps a fresh per-record key through the KMS port. Plaintext control records are bounded to 8 MiB and never written to local scratch.

Two pending events are fetched per bounded publisher batch. A lost PUT or acknowledgement reply can replay the same event. Randomly different ciphertext from a retry cannot replace an existing record; the stored record must authenticate as the exact frozen event. An acknowledged SQL receipt cannot be changed. Assignment and acceptance references have deferred audit foreign keys so a missing audit row cannot silently remove a deny from a joined projection.

Read projection requires a current controller lease and complete observation. New allows also require the bootstrap event, assignment activation event and current epoch checkpoint to be acknowledged. Out-of-order audit publication cannot skip the original reviewed baseline. Denies apply before audit delivery. Retention and backup policy for the SQL history and encrypted audit namespace must be qualified with the restore horizon before runtime composition; an unlimited outbox is not a production storage policy.

## Kubernetes write guard

Generated AccessBinding and PermissionSource CRDs translate the existing JSON contracts to structural schemas. Conditional rules have explicit reviewed CEL translations; changing a source conditional without updating that translation fails `make permission-crd-check`. The `/status` subresource and printer columns support ordinary kubectl/GitOps workflows. Unknown-field handling follows the Kubernetes API: use strict field validation in clients rather than claiming every server defaults to strict rejection.

The native admission-policy builder uses authenticated Kubernetes usernames/groups and protected installation delegation envelopes. A delegated writer is limited to exact cluster, namespace name/UID, optional workload identities, roles and issuer allowlists. Both old and new objects are checked on updates; deletion checks the existing scope. PermissionSource trust configuration requires an administrator. Status writes require the dedicated controller identity. Resource RBAC remains required in addition to content validation.

Native CEL does not expose namespace UID through `namespaceObject.metadata`. The guard limits the namespace name; the reconciler separately pins its UID before and after reading configuration. The installed guard and binding must be qualified and pinned. Neither a source's `reviewRef` nor the mere existence of a policy proves enforcement, trusted historical values or safe bootstrap. The live guard reader checks pinned policy/binding identities, exact expected enforcement settings and current type-check status, then verifies a synthetic dry-run denial using a separate non-administrator probe identity. A SelfSubjectAccessReview first confirms native resource permission, so an RBAC refusal cannot impersonate admission enforcement. Structured policy causes are checked for both HTTP 403 and 422. Namespace identity and guard state are reread before returning the original five-second deadline. No probe persists a binding or starts collection. The explicit-binding reconciler now composes live guard checks, complete lists, ordered watches and SQL acceptance. Namespace inheritance and runtime installation qualification remain separate work.

Kubernetes provides authenticated request variables and fail-closed validation through ValidatingAdmissionPolicy; bindings must enforce `Deny`. Policies cannot protect their own admission-registration resources, so installation RBAC and current guard qualification remain part of the trust boundary. See the [upstream policy reference](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/) and [API reference](https://kubernetes.io/docs/reference/kubernetes-api/admissionregistration/validating-admission-policy-v1/). Structural CRDs do not directly accept every JSON Schema keyword; the generated translation and real API-server tests are necessary. See the [upstream CRD documentation](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/).


## Bootstrap and continuous reconciliation

Migration 00003 records the first accepted baseline by an immutable authority-audit reference. For a guarded empty installation no value review is needed. A non-empty baseline requires a finite administrator review, read from an explicitly enrolled ConfigMap name/UID in protected installation configuration. The five data fields are `format: asservat-permission-bootstrap/v1`, `reviewer`, `bindingsSHA256`, `reviewedAt` and `expiresAt`; review lifetime is at most one hour. The review binds the cluster, control namespace incarnation and sorted binding UID/spec-digest pairs. Status and unrelated metadata do not force a new review. The reader pins namespace/object identities before and after I/O and returns its original five-second deadline. Source `reviewRef` fields cannot choose the review object. The ConfigMap's write protection must be established by installation RBAC; a reviewer string is provenance, never authority.

SQL checks initial review validity after obtaining its lock and again before commit. The frozen encrypted audit carries minimized review identity, digest, actor label and dates. Ordinary restart retains initialization; a changed installation trust digest requires new qualification. Upgrading from the prior foundation intentionally suspends existing streams until this prerequisite is established. An exact ambiguous-commit replay remains resolvable after the original deadline and cannot renew authority.

`BindingReconciler` starts one fenced controller epoch, checks the live guard around its full list and obtains the initial review when needed. It processes every watched binding transition in order through SQL. A → B → A therefore retires the original assignment even when the final subject list matches. Queued events remain bounded; no per-event durable work queue is created. Clean finite watch completion reconnects from the last processed opaque resource version. Compaction, malformed history, changed trust or failed acceptance ends the epoch; cancellation attempts bounded suspension, with existing five-second authority expiry remaining effective if SQL is unavailable.

A one-second complete-list poll renews deny completeness only if it exactly agrees with the processed journal. A newer list never replaces unprocessed watch history; the coordinator catches up or expires. Watch bookmarks cannot renew this deadline. Identical projection refreshes create no additional audit records. The controller lease is renewed separately, with no extension of source observation authority. Kubernetes documents opaque resource versions, finite watch sessions and required relisting after expired history in its [API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/).

The same run reconciles namespace-metadata inheritance ([ADR-242](../decisions/242-namespace-permission-inheritance.md)) and accepts decision-time sources ([ADR-245](../decisions/245-decision-time-permission-sources.md)); see the sections below. No public handler or collector is enabled by constructing this service. Source scope identity qualification, protected installation composition, complete audit backlog/retention limits and recovery fencing remain prerequisites for deployment.

## Immutable versions in current receipt checks

Current Allows require complete acknowledged receipts for the original reset, initial review and assignment activation events. Each receipt binds the exact root/event key, nonempty non-`null` version, ETag, byte count and SHA256. The selected-assignment query carries only receipt metadata within its existing 257-row overflow check; it does not duplicate the full audit body per assignment or add per-assignment reads. A missing or foreign-root receipt cannot remove a current Deny: the audit join preserves the assignment row and disables only Allows. Current publication and download transactions repeat the reset/initial receipt checks after their existing locks.

Retained historical acknowledgements with missing versions cannot authorize current access. Source refresh and exact acceptance replay cannot repair them, synthesize a version or renew an old operation. Historical record parsing, retirement and immediate complete Denies remain separate. These checks preserve original input/audit bytes, role grants and deadlines. Component and actual SQL/S3 qualification are recorded separately in [implementation progress](../implementation-progress.md).

## Namespace metadata inheritance (ADR-242)

With a `NamespaceObserver` for the hub cluster, `BindingReconciler` also accepts `namespaceMetadata` PermissionSources (value map, `administratorManaged`). A separate goroutine LISTs the cluster's namespaces for the keys of those sources and follows them with two-second watch sessions resumed from the last delivered cursor; its own Kubernetes client and limiter keep a large LIST off the binding reconciler's budget. The coordinator applies each delivery to a `NamespaceJournal` (only namespaces carrying an observed key, values as SHA-256 digests) and, when the derived grants or observation change, accepts the batch before reading the next delivery. If the binding list is not current at that moment, continuity is dropped and the next acceptance compares exact namespace resourceVersions. Each granted namespace becomes one whole-namespace allow basis with `ObservationVersion` = the namespace resourceVersion, merged after the explicit bases (`BindingJournal.Prepare`), in source UID order and within the batch budget.

`PermissionStore` treats a PermissionSource basis as equivalent when its generation/spec digest show at most one spec transition (its resourceVersion alone does not matter) and its namespace resourceVersion is unchanged or the batch claims a continuous watch. Batch fields `UnavailableSources`/`SourcesUnavailable` keep a source's assignments without renewing their basis; the projection skips a PermissionSource allow whose basis lags the stream sequence, and capacity SQL already requires the current sequence. The batch's minimized `Namespaces` observation (no resourceVersions) is part of the projection digest and of the authority audit event; the impact preview reads it from the record of the stream's current sequence. The first acceptance of a new stream carries the reviewed explicit baseline only.


## Decision-time sources (ADR-245)

The reconciler also accepts supported `kubernetesExec`/`kubernetesAccessReview` sources of every cluster as `PermissionBatch.ReviewSources` (no subjects; at most four per cluster). `AcceptPermissions` keeps them in `permission_review_source` (epoch, `seen_sequence`, generation, spec and authority digests, minimized parameters, the accepting audit event): an equivalent version — one spec transition, same authority digest — keeps its row's original accepting event and the per-principal assignments; any other change, a generation jump or removal retires every `permission_review_assignment` of the source in the same transaction and records `ReviewRetirements` in the audit event; `SourcesUnavailable` keeps rows without renewing them. A trust change retires them with all other assignments.

hub-api's `AccessReviews` (C-03) asks the target cluster's connector (`review-access` on the ADR-179 query frames) and records the outcome through `postgres.AccessReviews` under the stream's share lock and the source row lock: an allowed review mints the (source, principal) assignment once and upserts the Pod's decision (recorded resource attributes, `decided_at`, `fresh_until ≤ decided_at + maxDecisionAgeSeconds ≤ 60 s`); a refusal only ends an existing decision. `permissionProjection` adds the fresh decisions of the exact Pod from current, acknowledged sources as `Reviewed` User allows (≤ 32, newest first, allow-only), so admission facets, execution, catalog, download and explain need no new port. `defaultAudience` admits a reviewed allow only as the capturing human's own. Read paths repeat the caller's recorded reviews before their permission read; capture and explain review the resolved Pod. Every decision change (first allow, revocation, restoration) appends one `permission-review` event to the authority outbox in the same transaction; the existing publisher encrypts and acknowledges it. Capacity enrollment scopes also come from recorded allowed maintainer decisions (migration 00096 rewrites the two capacity scope functions in place).
