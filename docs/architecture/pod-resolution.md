# Pinned pod resolution

This is the initial C-05/C-21/C-24 execution-identity facet for REQ-TGT-001/002/003/006, TASK-02/05 and S-01/S-02. It observes an already selected whole pod; it does not discover targets, authorize a user or admit collection.

`targets.PodResolver.ResolvePod` takes an enrolled cluster UUID, namespace name/UID, workload kind/name/UID and pod name/UID. The transport is fixed by bootstrap. Deployment resolution checks the pod's controlling ReplicaSet and that ReplicaSet's controlling Deployment, including exact API versions, names and UIDs. StatefulSet resolution checks its direct controlling reference. The initially supported direct-Pod form must be unowned: an owned pod must resolve through its actual supported workload, preserving workload-level capacity and permission scope. Other owner families need a separate explicit resolution profile; they cannot silently use per-pod budgets.

The adapter checks namespace identity, reads the pod and its owner chain, resolves the node UID and boot ID, then rereads pod, owner chain, node identity and namespace. A replacement, owner move, node move, node recreation/reboot, deletion, malformed ownership or lost read authority returns no resolution. It uses a single five-second request deadline, bounded responses and a five-second original observation interval. Controller writes, labels, annotations, command arguments, environment values and arbitrary spec/status messages are absent from the returned value.

The resolved value contains the exact immediate controller UID used by context collection, normalized workload UID, node UID/boot ID, pod/root resource versions and original timestamps. It is current observation, not an execution permit. Admission and the executing collector still recheck current authorization, local ceiling, privacy, budgets and runtime identity before effects. Browser/MCP handlers must not expose this internal resolver without their normal target authorization boundary. This component does not replace the later all-replica inventory/watch service or grant permission to enumerate a namespace.

An unscheduled pod returns `ErrUnscheduled`; the initial node-bound context profile must show that limitation rather than capture a different replica. A later node-independent Kubernetes context profile can support that case without inventing a node identity. This does not remove the first-release requirement to explain scheduling failures or support direct-pod investigation.

The context API adapter now accepts an explicitly unowned pin only while the actual pod remains unowned. It rejects a newly added controller rather than treating a missing pin as a wildcard. The same adapter now refuses HTTP redirects and applies one five-second deadline to the complete API capture. Both changes have regression tests that failed on the previous implementation.

TLS protocol tests cover Deployment, StatefulSet and unowned success; pod/root/ReplicaSet/owner substitution; node UID/boot/name changes; unscheduled targets; unexpected/duplicate/case-aliased controlling references; denied reads; late observations and clock rollback. The two-cluster context fixture separately uses a narrowly scoped target-reader service account and leaves the context collector's credential unable to read owners/nodes. The two-cluster integration and affected Go/SQL gates passed with exit 0, recorded in `test/results/context-target-check.log`; owned fixtures were removed. This is component evidence, not public capture authority.
