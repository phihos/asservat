# Peer identity

C-04/C-20/C-21/C-24 under I-01/I-02, TASK-03 and S-01. Supersedes the
per-process hub-replica enrollment, registration and relay design (ADR-330 D3).

## Hub replicas

One installation CA, issued by cert-manager (`Certificate` with a CA `Issuer`)
or generated by Helm, signs the serving and client certificates of the hub
Deployments. Each replica mounts its certificate Secret and reloads it when
the projected file changes. Replicas authenticate each other with plain mutual
TLS against that one CA; the identity is the certificate's URI SAN. There is
no hub-replica enrollment, registration table, certificate audit, signing
budget, activation step or readiness PKI loop. Where a request must reach a
specific replica (the replica holding a connector connection), a SQL row names
that replica and its Service/headless DNS address.

## Connectors

Each cluster has one connector identity. An administrator-issued, single-use
bootstrap token obtains the first client certificate; the connector then
rotates it with a certificate signing request before expiry (kubelet TLS
bootstrapping, OCM cluster registration). Certificates last at most one hour.

The URI SAN is `spiffe://asservat.<installation-uuid>/cluster/<cluster-uuid>/connector/<peer-uuid>`,
with exact canonical spelling and no query, fragment, port or additional
identity. The certificate uses digital-signature usage, the client-auth EKU,
non-CA basic constraints and no common name, DNS, IP or email identity. TLS 1.3
is required. There is no forwarded-certificate or proxy-header fallback.

`mtls.PeerVerifier` verifies the client chain against the installation roots
during the handshake. The hub checks the SQL peer registration (enabled,
expected cluster, certificate digest not revoked) at handshake and at
certificate renewal; a revocation closes the peer's open connection. There is
no per-request registry lookup on a reused connection. A reused connection
never outlives its certificate.

## In-cluster workloads

Node collectors and regional readers authenticate to their connector with an
audience-bound projected ServiceAccount token, checked once per connection by
TokenReview over server-authenticated TLS; the established connection then
carries the session. The token's Pod and Node claims identify the caller; no
node boot ID, collector epoch or live owner-chain read is part of the identity.

## Messages

Work and results travel unsigned over these mutually authenticated
connections. Signature validity was never permission: every operation is
still authorized against current state as described in
[download authority](download-authority.md) and the owning component.
