# Initial installation handover and cleanup

[ADR-129](../decisions/129-initial-activation-handover.md) connects the private `initial-prepare` loader to the already implemented `initial-install` Pod and original installation coordinator. C-21 owns this finite supervisor; C-20 owns the optional private contracts. It adds no SQL migration, public route, background controller or dependency.

## Protected inputs and current checks

The capability must be present before creation of the original root and guards. The fixed mounted input adds `sql-history.json`: the derived installation history role and a fourth independent, canonical 32-byte password. The existing maintenance credential creates the exact passive role while SQL is pristine and the original setup interval is current. The protected desired plan includes the original trusted setup manager's independently supplied name and OID before root/guard creation. The runtime verifies its actual maintenance caller against that pin, then checks the single unavoidable incoming bootstrap-superuser ADMIN grant. It never attempts the ineffective creator REVOKE. Only grantor OID10, the exact pinned manager, ADMIN true, INHERIT false and SET false are accepted. The reader has no outgoing memberships, additional incoming members, table/column writes, object ownership, DDL or callable application SECURITY DEFINER rights. Its passive current check uses only its own login. Later manager LOGIN/CREATEROLE retirement preserves this identity; manager replacement or missing original grants require explicit reconciliation. The original manager is trusted administration and can deliberately re-grant access; false INHERIT/SET options do not isolate data from that administrator.

The pinned bootstrap probe account gets a retained Role/RoleBinding permitting only UPDATE of the exact target configuration name. Persistent writes remain denied by the final namespace guard. A named, explicitly dry-run UPDATE must identify that exact guard as the denial source. The staging exception admits only that independent probe; continuity and overlapping policies are not accepted as substitute denial evidence. Current administrator, namespace/account UID, root UID/plan, original immutable configuration and both admission guards are rechecked under original five-second deadlines.

These are trusted cluster administrator and installation-bootstrap boundaries. Someone able to replace the policy can replace the protection. Fixtures must identify their synthetic roots; they cannot supply runtime authority.

## Fixed sequence

1. Join all local original preparation owners. Each recorded Pod CREATE needs its own positive completion. The three credential-bearing preparation objects additionally require their original successful CREATE response under the new capability; GET, 409, timeout and legacy receipts do not qualify them.
2. Verify the complete original projection and credential intervals, then retain the public handover identity. No credential or private-content hash enters the root.
3. Claim and perform the canonical same-UID staging retirement. Only exact pending observed-generation status is retried as unavailable. Unknown effect replies never mint another claim.
4. Claim one original Pod UID/resource-version gate removal, bounded by the original five-second interval and all original credential expiries. A persisted claim with an unknown outcome is lookup-only. The bounded definite-conflict exception below retains the original interval. The scheduling gate alone never proves activation.
5. Observe the exact Pod/spec first, then independently read the original SQL claim, immutable audit receipt and historical activation. Reading SQL first could pair a pre-commit SQL snapshot with a subsequently successful terminal Pod. Both the read context and returned history deadline retain the original Pod/caller bounds. Require successful terminal status with zero restarts. Whole-second Pod timestamps can overlap the original launch second; an earlier second or future terminal observation is rejected.
6. Retain the original SQL claim ID, target Secret references and finite cleanup sequence. Positively closed CREATE owners and successful terminal process are prerequisites, not inferred from a missing object.

Cleanup advances one fixed step per independently current invocation. Rights reduction and UID/resource-version deletion may be retried after a lost reply; no cleanup method issues a credential or new workload:

| Step | Positive acknowledgement |
| --- | --- |
| `sql` | Existing transactional role retirement excludes earlier effects and removes current table/column/schema privileges, password and login; existing-session rights also disappear |
| `wrap`, `unwrap` | The original issuer verifies accessor revocation and independent original-token authentication rejection |
| `probe` | Exact original token-bound Secret absence plus actual original-token TokenReview rejection, accounting for API authentication caches |
| `target-secrets` | Original projection and SQL state Secrets absent after scoped deletion; no uncertain original CREATE can qualify this step |
| `setup-rbac` | Original setup Role/Binding rules or subjects are empty in place; the two minimal history objects remain unchanged |
| `private-state` | Original bootstrap private Secret is the immutable canonical retired map; all required credential/termination acknowledgements already exist publicly |
| `pod` | Full original UID/spec and successful terminal state qualify the fixed retirement marker; exact UID/resource-version deletion is observed complete |

The new final guard binds marker updates and deletion to the actual original Pod UID, successful phase and unchanged spec/labels/other annotations. The marker cannot be removed. Continuity allows only the selected administrator or exact assigned kubelet terminal-deletion branch. Producer-side checks additionally require every preceding cleanup acknowledgement; a marker/name by itself never completes the root or resolves an unknown request. Legacy guards retain their bytes.

The root accounts for eleven declarative objects, nine final inputs, one original Pod with at most sixteen request records, and one fixed cleanup record. The probe, SQL-state and final-projection Secrets remain private tracked objects; no arbitrary additional effect inventory is introduced. These stay under the existing 64-entry / 48 KiB public journal and 16 KiB private-state ceilings.

The three-minute new-profile process budget is distinct from current five-second leases. An interrupted cleanup preserves acknowledgements and only continues remaining reductions. The retained private Secret contains no credential after clearing, and the root, inert RBAC/policies and minimal history pair are a finite installation-owned inventory. The bootstrap-supplied provider/material inputs are not represented as issued or revoked by this supervisor. In particular, externally supplied S3 credentials remain operator-managed.

## Passive replay and boundaries

A completed root is read before maintenance/provider preflight. Current bootstrap authority and `sql-history.json` suffice for an exact historical SQL read; deleted Pods, cleared private material and expired original tokens are not reopened. A missing SQL record is never proof of no prior effect. Historical Activated is neither current RecoveryReady nor permission for another activation.

Unknown original Secret or Pod CREATE, lost pre-effect claim, failed activation and expired provider retirement retain their original uncertainty and identifiers. No automatic reinstall/reset or authority widening is supplied here. A qualified restart/restore bridge and safe exceptional recovery remain required. The official chart still has no enabled runtime composition.

## Definite conditional-conflict recovery

Original Pod launch and in-place staging retirement each retain one original claim and deadline. If their actual conditional UPDATE returns HTTP 409 and a bounded exact Kubernetes v1 Status Failure/Conflict matching the original API group/resource/name, the response owner may persist its original completion inside that unchanged deadline. Arbitrary 409, AlreadyExists, transformed client errors, server failures, cancellation, late responses and later GETs cannot establish no-effect.

One additional resourceVersion CAS claim may then be acknowledged. It binds a fresh unique retry ID and the independently read new resourceVersion while rechecking the exact original UID/spec. Only that acknowledged owner may send the second UPDATE; a lost claim reply is lookup-only. No third request, new Pod, expanded claim interval or refreshed credential lifetime is available. A retained actual negative reply may finish persistence under the original deadline after its first acknowledgement fails, but cannot be reconstructed by another process from observation.

The optional fields are absent for original claims without a definite conflict, retaining historical bytes. Native Pod and VAP wire-shape qualification is recorded independently; a synthetic TLS fixture verifies parser discrimination, original-deadline/CAS behavior and conservative unknown results. This does not reconcile an original unknown activation.

The measured native Pod and unbound VAP status-only updates returned actual HTTP 409 with `kind: Status`, `apiVersion: v1`, empty `metadata`, `status: Failure`, `reason: Conflict`, matching `details.name` and plural `details.kind`, and `code: 409`; the core Pod omitted `details.group`, while the VAP supplied `admissionregistration.k8s.io`. Parsing rejects duplicate/unknown JSON fields, unrelated resources, embedded UID/causes/retry hints and an outcome inferred only from a client error. Kubernetes documents resource-version conditional updates in [API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions). Synthetic loopback TLS tests separately exercise lost negative-acknowledgement and retry-claim replies before/after storage, concurrent resumptions, changed original UID/spec, late responses, and a lost second effect response. A stored retry claim with no acknowledged owner remains observation-only even if the target is still gated.
