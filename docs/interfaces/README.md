# Outward-facing interfaces

One application service layer serves the browser, MCP and authenticated Kubernetes request bridge. Its authorization, planning, admission, privacy and projection decisions are shared. Transport adapters do not own a second policy engine. The [operation registry](operations.yaml), [browser OpenAPI](browser-openapi.yaml), [MCP workflows](mcp-workflows.md) and [error catalog](errors.yaml) make the boundaries reviewable. All are designs; no endpoints are running in this repository.

## Complete surface inventory

| Surface | Audience / protocol | Contract and behavior |
| --- | --- | --- |
| Shared console | Maintainers, recipients, reviewers, operators; HTTPS HTML | [Screen definitions](../ux/surfaces.yaml); one role-aware console, React/TypeScript, compiled assets served by Go; search pickers for clusters, namespaces, workloads, recipes, users and groups by name |
| Browser data/commands | Same-origin session-authenticated JSON and Server-Sent Events | OpenAPI 3.1.1: every catalog operation, the browser-only human-console operations and three streams (native content, page status events, live-watch events); strict request/response schemas |
| MCP | External agents; authenticated Streamable HTTP | [Tool catalog](../../specs/contracts/mcp-tools.json) and [MCP requirements](../../specs/mcp.md): few tools with typed discriminators, all enabled by default; bounded structured results, approved extracts first |
| Declarative configuration | Administrators / GitOps / maintainers; Kubernetes API | [All 15 CRD kinds](../../specs/apis.md); Kubernetes discovery/schema/CEL, resourceVersion conflicts, controller Conditions |
| Authenticated capture submission | Browser/MCP or DebugCapture | Existing immutable accepted-scope service; DebugCapture is an optional request/status envelope, not a second execution store |
| Human reviews | Independent approvers; browser JSON | Exact scope, revision/idempotency, optional step-up (off by default); the approval starts the approved work; no MCP approval tool |
| Enrollment / install | Cluster operators; Helm / kubectl | Chart values register each cluster by name and ServiceAccount issuer (ADR-334); readiness reports; nothing copied from the hub to a workload cluster; no browser-held admin kubeconfig |
| Identity | Organization IdP / clients | OIDC browser flow with the standard `groups` claim; one OAuth protected resource (the installation origin) for MCP and native downloads, issuer/audience checks and scope challenges |
| Incoming incidents | Configured Alertmanager; authenticated HTTPS | Standard v4 webhook, bounded body/batches, fingerprint + startsAt + per-alert status deduplication |
| Outgoing notifications | Configured scoped webhook destinations | CloudEvents 1.0 structured JSON, signed exact bytes, stable retry ID, allowlisted minimized fields |
| Observability | Operators / monitoring | Protected `/metrics`, `/healthz`, `/readyz`; content-free state/counters, no evidence or workload-label cardinality explosion |
| Deep links / agent handoff | Signed-in users and agents | Stable `asservat://case/<uuid>`, `/capture/`, `/grant/`, `/share/` reference kinds; authenticated HTTPS resolver; no bearer credentials |
| Error responses | All clients | Shared domain codes; bounded reasons/actions; nondisclosing before access is established |
| Internal connector / node protocol | Connector and in-cluster workload identities | [Federation](../../specs/federation.md): one outbound multiplexed HTTP/2 connection per cluster to the hub's HTTPS endpoint, authenticated by the connector's projected ServiceAccount token (ADR-334); commands, receipts, cluster-state pushes, live rows, uploads and download bytes are streams, idempotent by operation ID ([ADR-330](../decisions/330-event-driven-system-design.md) D2); not a public generic execution API |

No new general CLI is needed in the first release: kubectl and Helm cover configuration; MCP covers agent investigation; the console covers human interaction. Do not expose arbitrary SQL, object-store credentials, public raw-download URLs, a generic Kubernetes proxy or approval automation through a model tool.

## Browser routing, sessions and data

Prototype routes are `#/screen-id` for offline navigation. Production routes are normal URLs such as `/clusters/<cluster>/namespaces/<namespace>/<kind>/<workload>` (names, [ADR-335](../decisions/335-usable-by-default.md) D4), `/captures/<capture-id>`, `/cases/<case-id>/artifacts/<artifact-id>`, `/downloads/<download-id>`, `/shares/<share-id>` and `/admin/clusters/<cluster>`. Screen IDs are stable design references, not an API promise to use hashes. Every route loads an authorized projection; a copied link never authorizes its target. Keep reasons, expressions, pcap/display filters, user names, handles and tokens out of URLs/referrers/access logs. Locale/timezone display never changes UTC contract values.

Use an HttpOnly Secure SameSite session cookie, exact origin checks, session-bound CSRF tokens for POST and validated local return paths. `GET /api/v1/session` bootstraps identity and CSRF metadata without mutation. Logout is a CSRF-protected POST; login starts server-side state/nonce/PKCE, the IdP callback verifies state/issuer/token before establishing a session. Where an installation enables step-up, it is server-verified context bound to the review, never a client boolean. OIDC values and short enrollment secrets are not stored in browser localStorage.

Shared browser operations use fixed `POST /api/v1/operations/<literal-operation-name>` endpoints. POST bodies keep sensitive filters out of URLs; `x-effect=read` still means side-effect-free planning/querying. This is an explicit typed operation API, not arbitrary tool-name dispatch. Request and output schemas mirror the MCP catalog exactly. A read cannot arm a recorder, trial a protocol survey or pin a ring. Analysis queries can create bounded analysis work where the existing contract explicitly permits it.

Shared operations return HTTP 200 with the existing `status=ok|pending|error` domain envelope. A pending result is acceptance of bounded work, not evidence availability. Auth/session/malformed body failures use appropriate 4xx/5xx `application/problem+json`. Console-only operations use typed successful projections/receipts and non-2xx problem details for failures. Clients must inspect both HTTP status and, for shared operations, domain status; never infer success from 200 alone. This deliberate compatibility boundary avoids inventing a different MCP error vocabulary.

All commands carry Idempotency-Key; where the existing body already contains an idempotency field, the values must agree. Key scope is principal + client + command kind; same key/different canonical body is Conflict. Expected domain revision is a bounded integer; expected Kubernetes resourceVersion is an opaque string. They are not interchangeable. `get_operation` reads a command receipt under the operation's authorization and returns the same operation identity; receipts never leak a privileged credential.

Lists default to 20 items, maximum 100 per page (response memory and SQL work grow with page size), with opaque principal/client/query-bound cursors that do not expire; each page is authorized under REQ-INT-003. An MCP tool result is at most 96 KiB, derived from the common MCP client tool-output limit (Claude Code `MAX_MCP_OUTPUT_TOKENS`, 25,000 tokens, about 100 KB), and aims at 24 KiB by default to leave room in the model context; list-shaped results continue with cursors. The console has no response byte ceiling: server pages and SSE bound it. Configuration impact previews page through all affected targets with explicit completeness; the editor diff is bounded by its input object. `stage_editor_draft` accepts UTF-8 YAML up to 1.5 MiB (the Kubernetes API server request limit for the staged object), no aliases/custom tags/multiple documents, and a fixed supported CRD-kind list. The server applies one global request body cap of 2 MiB (a 1.5 MiB object plus envelope) against oversized requests; operations whose largest legitimate field is smaller reject earlier. No HTML from evidence is trusted. Use `Cache-Control: no-store`, a restrictive CSP and no third-party scripts/analytics.

## Configuration authoring without a second permission API

`stage_editor_draft` validates a bounded authored manifest against the supported kind’s server-pinned Kubernetes schema and semantic policy, then stores the draft as a principal/client-bound SQL row ([ADR-330](../decisions/330-event-driven-system-design.md) D8). Its handle carries no permission. Empty base resourceVersion means create; existing resources require their observed opaque version. Resolve namespace/resource UIDs server-side at submission; a recreated object of the same name is the same configuration target. Unknown kinds and controller-only runtime CRDs are rejected.

Own-access explanation defaults to the caller. An explicit other principal or hypothetical configuration evaluation requires the administrator delegation envelope; results are Allow, Deny or Indeterminate and never enumerate group members.

`preview_configuration` is a dry run: it returns the scoped diff, its `plan_digest`, source revision, impact reasons and submission mode, and stores nothing. `submit_maintainer_configuration` takes the draft and `expected_plan_digest`; a changed plan is ReviewChanged. It accepts only DebugPolicy, EvidenceRecipe and CaptureProfile. It uses authenticated submission provenance and current Kubernetes rights under REQ-PER-007, never an unbounded hub identity. For GitOps-owned fields, show/export the diff and let the existing field manager apply it; do not force conflicts. Execution acceptance remains separate from successful Kubernetes persistence.

AccessBinding, PermissionSource, CollectionCeiling, EvidenceRetentionPolicy and capacity/storage configuration are **Kubernetes-only writes**. Their browser editor is a local proposal/preview/export workflow; the OpenAPI has no endpoint that persists those resources. Authenticated diff rendering uses the originating draft handle through the protected editor view, within the output cap. It cannot render arbitrary object URLs. Raw evidence is not exported with configuration.

## Human commands unavailable to MCP

The console supports independent execution/raw-query/raw-sharing decisions, grant revocation, stopping future sharing, explicit owner-team replacement, privacy restriction/erasure, enrollment/revocation and cleanup retries. OpenAPI `x-required-role` labels describe authorization responsibilities, not additional AccessBinding role names; map them to the existing fixed roles, current resource scope and delegation rules. Every command has a narrowly authorized role, exact resource/revision and idempotency. Operator status alone does not automatically confer artifact-read or approval authority. The prototype's “Operator + maintainer” persona deliberately combines roles for review; real assignments are independent.

`decide_review` binds request ID, current revision, reviewed scope digest and, where enabled, the step-up reference; its reason is optional. The server checks separation of requester/reviewer, applicable role and current freshness. `stop_future_sharing` preserves existing concrete shares. `revoke_share` on an instruction denies child shares as specified; neither operation resets spent publication slots. `transfer_share` (ADR-238, shared browser/MCP operation; it replaces the earlier design-only `replace_share_managers`) validates the complete nonempty manager set against the current manager's own owner teams; it does not modify recipients, creator, grant or expiry.

`apply_privacy_action` binds an exact selection digest, propagates through authorized lineage, and returns work receipt. `retry_deletion` requests an attempt; it never marks absence verified. Cluster registration takes public data only (name, ServiceAccount issuer or JWKS); the fallback join token of ADR-334 is shown once and never logged. Readiness distinguishes configured, passively checked and actively qualified capabilities. No web button performs an undisclosed privileged qualification experiment.

## External transport behavior

Alertmanager input is `POST /integrations/alertmanager/<configured-receiver-id>`, authenticated before parsing, with a 10 MiB body cap against oversized requests (whole Alertmanager groups of large alerts fit) and no alert-count cap: per-policy trigger rate limits bound the resulting captures. Reject oversized bodies with 413 rather than silently dropping alerts; report the sender’s `truncatedAlerts`. Alertmanager's per-receiver `max_alerts` setting limits batch size on the sender side. Per-alert schema/target mapping failures are counted with safe reasons, never interpreted as a privileged arbitrary capture request. Receiver identity, fingerprint and startsAt identify the episode; resolved is terminal even when deliveries reorder. [Trigger semantics](../../specs/triggers.md) remain authoritative.

Outgoing event schema and signing are already specified in [federation](../../specs/federation.md) and the [event contract](../../specs/contracts/event.schema.json). A 2xx response acknowledges delivery; bounded retries/backoff preserve the event ID, respect deadline and destination scope, and surface exhausted work. No evidence content, reasons, usernames or arbitrary labels in default payloads. Recipients authenticate separately when resolving dataref. Webhooks cannot add destinations from capture parameters.

Health probes disclose only process readiness. `/readyz` distinguishes service acceptance from optional regional mechanisms; loss of one analysis capability must not falsely make every stored-evidence read fail readiness. `/metrics` is operator-only, with bounded labels such as region/capability/reason enum; never artifact IDs, raw labels, identities or URLs. Detailed diagnosis remains an authorized UI/API projection.

Transport/version policy: browser `/api/v1`, explicit MCP negotiated versions, Kubernetes `v1alpha1`, versioned manifests/events and immutable profile versions evolve independently. Breaking DTO changes need a new version or negotiated capability and migration fixtures. No silent default widens acquisition, retention or permission. The `asservat.io` API group and illustrative host remain subject to the existing domain-registration gate.

## Status events

Each console page opens one Server-Sent Events stream, `GET /api/v1/events`, naming the captures, grants and downloads it shows (bounded by the page size and the URL length); the caller's own pending queries are included. The hub pushes each committed change (PostgreSQL `LISTEN/NOTIFY`) as one `StatusEvent` carrying the unchanged result envelope of the matching status operation, and sends current state once on connect and reconnect. The console sends no status polls. Authorization is the decision reused for at most 30 seconds (ADR-311); a reader who loses access receives `accessLost` and the stream closes. MCP clients get the same changes from the status tools' `after_revision`, which waits server-side for at most 30 seconds. Status reads and events are never charged.

## Live observation boundary

The shared `list_recordings` and `watch_live` operations implement [live watching](../../specs/live-watch.md) as fixed `/api/v1/operations/` routes. The browser receives rows, gaps and state changes over one SSE stream per watch, `GET /api/v1/live/watches/{watch_id}/events`, with the [live-watch event](../../specs/contracts/live-watch.schema.json) schema; reconnect sends `Last-Event-ID`. MCP uses `watch_live(action=read)`, which waits server-side up to `wait_ms` (at most 30 seconds) and returns on the first new row or state change. An empty active batch can carry next_cursor as a continuation position; ordinary list pagination semantics remain unchanged. They reuse existing sessions/OAuth and bounded envelopes; no websocket, new permission API or mandatory message service.

Watch IDs and cursors are principal/client-bound and not share links. Filters remain in bounded POST bodies and protected session scope, never URLs/logs. A watch stays open while its stream is connected or reads arrive at most 10 minutes apart, and ends at Close, source end or access loss; its delivery rate is bounded. Pause/resume/filter edits are revision-checked and idempotent; they do not mutate recording. Read responses include source/view generations, gaps, timestamps/uncertainty and explicit untrusted/transient handling. Saving is the existing recording-save preview and `request_capture`. Opening views needs evidence-read rights on the source, not collection rights; no implied acquisition scope escalation.

A paused view keeps its stream and receives access and source-end changes; no new rows. Closing the tab closes the stream; the watch closes after the 10-minute idle window. Reconnect restores neither a closed view nor rows beyond the replay buffer. For 2026-07-28 and 2025-11-25 MCP, typed bounded reads are the interoperable baseline; resource subscription hints are not advertised.

Live failures reuse stable codes: NotAuthorized for unavailable source/view rights, TargetGone for a stale source incarnation, CapabilityUnavailable for an unsupported approved projection, BudgetExceeded for view admission/spend, Conflict for revision/idempotency mismatch, InvalidCursor for an invalid authorized-view cursor, RetryLater for overlapping reads/rate pressure, and ClusterOffline when no live dispatch is possible. Valid but lagging continuation is represented by a gap plus a new cursor, not by inventing complete history. Closed watches return their permitted terminal control state with no rows and no continuation; source-specific losses can leave other originally selected sources active. Filters unsupported by the chosen projection fail before reading it; they are never broadened or ignored.

## Download for local tools

All gathered evidence and saved derivatives support native download, and a core downloads as one debugger-ready bundle with meaningful file names ([ADR-335](../decisions/335-usable-by-default.md) D17). The shared `download_artifact(action=prepare|status|cancel)` operation uses the existing application authorization boundary; `GET /api/v1/downloads/{download_id}/content` streams the exact file to a browser session or a bearer token for the installation's single OAuth protected resource. Public here means documented, not anonymous: the path grants no rights and redirects to storage are forbidden. Raw files need the equivalent Kubernetes right or a covering grant. MCP returns `content_path` and the console page `browser_url` (`/downloads/{download_id}`) instead of bytes. A started response runs to the session's `AccessUntil`, retention cut-off, Stop or end of range, whatever the caller's token lifetime; resumes are unlimited until `AccessUntil`. Every status, including terminal ones, carries the artifact's verified size and SHA-256 while its metadata is readable, and proves no local file save. The console receives status changes over the page's event stream. See [canonical contract](../../specs/artifact-downloads.md).

One bounded capture and its requesting human's selected result access can share a single independent review under [investigation approval](../../specs/investigation-approval.md). Shared preview/request/status schemas carry result_access; ordinary decide_review binds both collection and result-access digests, without another endpoint. Authentication and current underlying entitlements remain required; step-up only where enabled. Native transfers use the existing authenticated content endpoint.

The initial [fleet-administration projection](../architecture/fleet-administration.md) maps enrollment operators through protected Kubernetes installation settings. It is separate from workload AccessBinding roles and grants no evidence access. The browser command still needs audited issuance and configured secret-channel delivery; the reader alone does not implement enrollment ingress.

The separate [browser authentication protocol](browser-auth-openapi.yaml) defines login/callback, read-only CSRF bootstrap, explicit refresh, local sign-out and signed provider logout. It does not add business operations or MCP tools. The [session architecture](../architecture/browser-sessions.md) records current runtime qualification and remaining deployment prerequisites.
