# Small deployments without separately operated infrastructure

Researched: 2026-10-10. Scope: upstream documentation, release/maintenance checks and inspection of Asservat's current adapters. **No new deployment or integration experiment was run for this report.** Existing SeaweedFS, PostgreSQL, Keycloak and OpenBao fixture results do not qualify the proposed bundled installation.

The maintainer requires local users/login, a static-key alternative to external key management, and PostgreSQL deployable through the official Helm installation. The maintainer subsequently accepted implementation of the engineering recommendations below. Exact-version qualification and runtime delivery remain separate from that acceptance. [ADR-063](../decisions/063-small-deployment-alternatives.md) records that distinction; [deployment requirements](../../specs/deployment-profiles.md) define the invariant contract.

Subsequent implementation starts with [local wrapping/signing and credential-provider ports](../architecture/local-keys.md), under ADR-064. That component work does not change this report's research-only scope or qualify a deployable small profile. Actual commands/results are tracked in [implementation progress](../implementation-progress.md).

## Recommendation and full dependency inventory

Offer an explicit **small** deployment profile alongside the existing external-service profile. Select identity, keys, database and evidence storage independently. Small describes operational size and availability, not weaker evidence access or privacy. It can manage multiple clusters in the same organization; topology (`hub`, `cluster`, `combined`) remains a separate choice. Bundled data services belong only to the hub/regional storage installation, not every workload-cluster chart.

| Dependency or capability | Small deployment recommendation | Existing-service / larger deployment | Residual obligation |
| --- | --- | --- | --- |
| Browser identity and groups | Built-in accounts, local groups and login; state in the existing PostgreSQL database | Qualified OIDC provider; Keycloak remains the first tested external provider | Secure authentication, recovery, revocation and independently authorized reviewers |
| MCP / CLI authentication | Internal OAuth authorization endpoint over the local accounts; reuse a maintained protocol library | Qualified external OAuth provider | Code + S256 PKCE, discovery, client/resource binding and bounded revocable sessions; browser passwords never given to agents |
| Evidence and application key services | Internal purpose-scoped key service with versioned static keys referenced from Kubernetes Secrets | Existing OpenBao integration; future qualified cloud KMS | Separate wrapping, unwrapping, session encryption, signing and CA authority; key recovery |
| Evidence object storage | Bundled single-instance SeaweedFS, authenticated TLS S3, persistent local filer metadata and volumes | Qualified existing S3 or Ceph RGW | Capacity, deletion, storage durability and independent backups if evidence backups are enabled |
| Hub database | Bundled single-instance PostgreSQL 18 with a dedicated PVC; maintained upstream image base and pgBackRest tooling | Managed/existing PostgreSQL; optional existing CloudNativePG installation | Tested backup/restore, explicit major upgrades; single instance has planned/unplanned downtime |
| Database backup repository | pgBackRest encrypted POSIX repository on a separately supplied durable volume, or configured S3/SFTP repository | Operator backup service with equivalent contract | A second PVC on the same disk/node is not independent disaster recovery |

There is no Redis, broker, search server, dedicated profiling backend, Node server, SaaS account, licence service or embedded agent to replace. Inspektor Gadget and analysis tools are packaged mechanism dependencies, not extra infrastructure services an administrator must procure. Optional mechanisms stay off or unavailable until qualified.

## Local identity: build the account workflow, reuse security protocols

Recommend local accounts in Asservat, rather than bundling another full identity product merely to provide its login screen. Provide account/group administration, invite, disable, recovery, active-session revocation and a clear local-login/SSO choice. Use immutable issuer-scoped user/group IDs; usernames and emails are display/login identifiers. Local groups can be referenced by the same AccessBindings, namespace ownership mappings and evidence shares as external groups. Account administration must not silently grant workload/evidence access. Managing group membership is itself security-sensitive because existing bindings/shares can target that group; separate that privilege and show its effect.

Keep permission configuration in the Kubernetes API. Account credentials, local membership and sessions are identity state in PostgreSQL, not a second permission-binding API. No self-registration by default. First administrator setup uses a short-lived, single-use bootstrap secret retrievable only by the installing Kubernetes administrator. No default password. Existing source-trust protection and independent reviewer requirements still apply; one person creating two local accounts is not a legitimate substitute for a distinct reviewer.

Use Argon2id via Go's maintained `golang.org/x/crypto/argon2`; tune bounded password hashing concurrency as well as cost, so authentication cannot exhaust a small hub. Add secure cookies, CSRF, rate limiting and non-enumerating responses. Offer passkeys/security keys, with server-verified user verification and recent step-up for protected operations, plus bounded recovery codes. An authenticator library handles WebAuthn validation; Asservat still owns challenge persistence, one-use handling, RP/origin checks, credential lifecycle and account recovery. No mandatory email or SMS service. [OWASP password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Go Argon2](https://pkg.go.dev/golang.org/x/crypto/argon2), [go-webauthn](https://github.com/go-webauthn/webauthn).

Local login must include a standards-based MCP login flow. The MCP authorization server may be hosted with the resource server; external SSO is not a protocol prerequisite. Prefer a narrowly configured `zitadel/oidc` provider library candidate over writing OAuth exchanges. Restrict supported flows to the reviewed code/PKCE and refresh profile; implement current membership/session checks, refresh reuse handling, exact redirect registration, resource audience and scope limits. Library support does not establish MCP conformance, nor does an OIDC client certification certify our server. Verify metadata, resource indicators, supported client registration and actual target MCP clients. Pre-registered clients must work without runtime public URL fetching. Never silently weaken SSRF protection to support client metadata discovery. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [ZITADEL library](https://github.com/zitadel/oidc).

Local disable, membership removal, password/credential recovery and session revocation advance authoritative identity state and invalidate dependent access within the existing freshness/effect bounds. An old token or restored SQL session cannot override that state. Team automation retains its independent Kubernetes workload authority under ADR-059; it does not need to impersonate an offline local user. Recovery of a human account never creates a policy approval.

## Static keys: remove the external service, preserve the role boundary

OpenBao currently supplies more than evidence wrapping: credential protection, purpose-specific signatures and peer certificate issuance also need local alternatives. Inventory all provider calls before claiming that local mode no longer needs OpenBao.

Retain the Tink framed artifact format and random per-artifact data/index/manifest keysets. Wrap those small keysets under a versioned static key-encryption key using established AEAD, including the existing canonical binding. The static key is a random cryptographic key, not a password used directly on evidence. It is never distributed to collectors or the hub API as an all-purpose decryption credential. [Tink primitives](https://developers.google.com/tink/choose-primitive), [current artifact binding](../architecture/artifact-format.md).

Proposed placement: an isolated internal key-service role, optionally per region, mounts Secret-referenced keys and exposes narrowly authenticated wrap/unwrap/sign/issue operations through consumer-owned ports. Use separate key material and authorization per purpose. Collectors/publishers receive wrap-only access; acquisition gets only current exact-artifact unwrap authority; hub roles get their required session/signing operations without raw-evidence unwrap. The role has no general evidence-store reader, database superuser or unrestricted certificate-signing interface. Asservat must qualify its authorization, failure and audit behavior before enabling it. This is additional product code, not a feature of the existing OpenBao adapter.

Key IDs and versions are immutable. Generate once, retain across upgrades and allow administrator-supplied Secrets. New writes use the active version; old versions remain readable for the required retained data and recovery window. Separate session/backup/signing/CA keys from evidence keys. Rotation is a controlled operation, never a Helm render side effect. Do not claim selective artifact erasure from deleting a shared root key. Keep historical readers during migration; a rewrap that changes an immutable receipt requires the normal verified copy/commit protocol.

Static keys simplify operations but put keys in the cluster's trust boundary. Kubernetes Secrets are base64-encoded, not inherently encrypted at rest. Require restricted access and an encrypted control-plane/backup configuration for production, with no requirement for an external KMS merely to achieve that protection. Back up the necessary key versions separately and test recovery; losing them can make evidence and sessions unrecoverable. Compromise of a cluster administrator can expose local keys. [Kubernetes Secret guidance](https://kubernetes.io/docs/concepts/security/secrets-good-practices/), [local and KMS encryption providers](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/).

"Transit" here names OpenBao's cryptographic service. Static keys replace that provider; they do **not** replace TLS for data in transit. Use the Go TLS/X.509 implementations with a narrowly constrained local issuer for service certificates; retain existing peer identity, expiry and revocation checks. Browser certificate trust is configured separately.

## Evidence storage: keep S3 and bundle SeaweedFS

Recommend one S3 data path with a bundled small backend. SeaweedFS is Apache-2.0, actively released and already used in our synthetic integration fixtures. Upstream documents versioning, checksums, conditional writes and multipart operations. Its conditional-operations documentation explicitly describes atomic compare-and-create. Those are useful selection signals, not proof of our exact custody contract. [Project](https://github.com/seaweedfs/seaweedfs), [conditional operations](https://github.com/seaweedfs/seaweedfs/wiki/S3-Conditional-Operations).

For the compact profile, package the released combined server mode behind our first-party chart: one persistent instance, local persistent filer database, bounded volume layout and explicit S3 authentication/TLS. Disable unused services and keep internal administration endpoints private. The upstream 4.48 chart defaults include authentication off; copying upstream defaults would be unsuitable. The release's chart documents a minimal separate master/filer/volume layout, while the released server supports combining them. Therefore the one-instance packaging needs our own tested templates; do not assume newer `master` chart all-in-one examples exist in a pinned release. [4.48 chart](https://github.com/seaweedfs/seaweedfs/blob/4.48/k8s/charts/seaweedfs/README.md), [4.48 values](https://github.com/seaweedfs/seaweedfs/blob/4.48/k8s/charts/seaweedfs/values.yaml), [combined server source](https://github.com/seaweedfs/seaweedfs/blob/4.48/weed/command/server.go).

Evidence arrives encrypted by Asservat. Separate credentials for upload, acquisition, verification, deletion and administration still matter. Backend-specific bucket/prefix action enforcement must pass negative tests; a service-wide superuser token is not an acceptable shortcut. Bound local disk compaction, temporary files and metadata as physical capacity, not just uploaded ciphertext. Retain workload protected allocations and dedicated system/deletion headroom. Separate database and evidence PVCs help, but shared underlying storage needs enforceable capacity backing before promising failure isolation.

The exact image/configuration must pass conditional create races, immutable pinned reads/ranges, checksums, version/null-version enumeration/deletion, delete markers, multipart cleanup, crash/power-loss behavior, disk-full handling, verified expiry and restore tests. Keep all object versions/copies charged until cleanup is proved. Do not enable object-lock policies that prevent the required early erasure or absolute deletion deadline. Volume/metadata persistence must be recovered together; a live filesystem copy is not automatically a consistent object-store backup.

| Alternative | Assessment |
| --- | --- |
| Garage | Attractive small self-hosted store, but its own compatibility table marks bucket versioning and `ListObjectVersions` unsupported. Our custody adapter always enumerates versions, including for unversioned profiles. It therefore requires a new qualified adapter contract; it is not a drop-in substitute. [Compatibility](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/) |
| MinIO community | Repository is archived and explicitly says it is no longer maintained. Do not adopt it as a new maintained default or replace it with a licence-key-dependent default. [Repository](https://github.com/minio/minio) |
| Existing Ceph RGW | Retain as the external reference. Installing an entire Ceph cluster solely for a small Asservat instance creates disproportionate operator work. |
| Direct filesystem/PVC adapter | Possible, but adds immutable publish, crash durability, path safety, ranges, inventory/cleanup, writer fencing and migration behavior that the S3 path already centralizes. The storage service disappears while its correctness responsibilities move into Asservat. Defer unless measurements show bundled S3 is too costly. |
| PostgreSQL large objects | Adds evidence bandwidth/retention to the authority database and its WAL/backups, worsening workload isolation and deletion policy. Do not select as the first small-store alternative. |

## PostgreSQL: a deliberately limited bundle

Recommend a first-party Helm single-instance StatefulSet with persistent storage, TLS, separate runtime/migration/backup credentials, and a pinned PostgreSQL 18 image derived from the maintained Docker Official Image. Include pgBackRest in a reproducible build; never download packages at pod startup. pgBackRest supplies encrypted repositories, physical backup/WAL archiving and restore, with filesystem and remote repository choices. Asservat owns the templates, backup scheduling/status, credential/certificate integration, restore entry point and upgrade tests. This is a real maintenance commitment, not a claim that an upstream image is a complete managed database. [Image documentation](https://github.com/docker-library/docs/blob/master/postgres/README.md), [pgBackRest guide](https://pgbackrest.org/user-guide.html), [repository configuration](https://pgbackrest.org/configuration.html).

Limit this bundle to one PostgreSQL instance. Do not implement our own automatic failover/operator, imply that adding hub replicas provides database HA, or support a SQLite fork of the transaction model. Explicit PostgreSQL major-version migration must be tested; notably PostgreSQL 18's official image changed its data/volume paths, so do not reuse a PostgreSQL 17 mount recipe unchanged. Preserve PVCs and Secrets on uninstall, and never force-delete a database pod during uncertain node fencing.

CloudNativePG is the stronger choice when the installation already operates it or needs database HA. It has maintained upstream operator/cluster charts and automatic certificate management. It also brings CRDs/controller lifecycle; its current standard Barman Cloud backup chart requires a separate plugin and cert-manager. Requiring all of that for the smallest profile would defeat much of the simplification. Keep it an optional operator-managed integration and reuse an existing operator without competing ownership. [CNPG Helm chart](https://github.com/cloudnative-pg/charts/blob/main/charts/cloudnative-pg/README.md), [backup architecture](https://cloudnative-pg.io/docs/current/backup/), [Barman plugin chart prerequisites](https://github.com/cloudnative-pg/charts/blob/main/charts/plugin-barman-cloud/README.md).

Do not base the new bundle on unmaintained Bitnami Legacy images. The upstream catalog notice distinguishes available chart source from the discontinued updates to legacy images. Prefer a pinned, maintainable build that needs no commercial registry credential. [Upstream notice](https://github.com/bitnami/charts/issues/35164).

Backup storage is not magically removed by bundling PostgreSQL. Offer an encrypted repository on operator-supplied durable storage or S3/SFTP. A local repository is usable, but report its shared failure domain when applicable. Never claim disaster recovery from a backup on the same failed disk. Database backup capacity must not consume protected evidence allocations, and raw evidence must not enter SQL backups. When archiving fails, report the threatened RPO and storage pressure; never silently discard required WAL to keep a green status. Finite backup retention and post-restore revocation/tombstone fencing remain mandatory.

## Installation ergonomics, migration and remaining gates

The intended small installation asks for the installation hostname/TLS choice, storage class and capacity, and backup destination or explicit evaluation status. It generates stable secrets once through a scoped bootstrap operation, references them from Helm, and offers one-time administrator setup. An upgrade must not regenerate encryption keys, passwords, issuer identity or CA roots. Loss of a Secret with existing state is a recovery condition, not a reason to initialize a new unrelated installation. Do not store secret values in Helm values, rendered Secret templates, logs or release metadata.

Show a single capability/health view with separate identity, database, evidence, key, certificate, backup and optional-analysis status and precise remedies. Small mode does not add per-developer database/S3 accounts. Local tools and MCP retain the same capture, approval, sharing, download and deletion workflows. No new mandatory privacy consent dialog.

Migration can be gradual: local accounts to explicitly linked SSO identities; local key versions to external wrapping while preserving old readers; PostgreSQL bundle to managed PostgreSQL; SeaweedFS to another qualified S3. None is a blind endpoint switch. Preserve actor IDs, ownership/audience history, artifact identity, native hashes, copy ledgers, deletion deadlines and recovery epochs. Never merge users by matching email, regenerate grants or extend retention during migration. Capacity covers both storage copies until old copies are verified deleted.

Implementation gates, still pending:

1. Freeze local identity/provider and key-service contracts, minimal role authority and typed installation configuration; add them to canonical schemas/catalogs with actual consumers.
2. Qualify local browser/MCP authentication, passkey step-up, recovery, membership removal and restore/replay denial against the existing authorization tests.
3. Qualify local keys for every existing OpenBao purpose, wrap-only isolation, rotation, lost-Secret handling, TLS/CA renewal and native evidence readback after restart/restore.
4. Qualify exact SeaweedFS/PG/pgBackRest images and first-party templates under Restricted control/data pods, restart, disk pressure, upload interruption, backup loss, upgrade and uninstall.
5. Exercise fresh install, repeat upgrade, recovery and migration with synthetic evidence and real browser/MCP/native downloads. Measure footprint and overhead before promising minimum CPU/RAM figures.

The current Helm chart remains configuration-only and still rejects runtime enablement. Proposed choices in this document are not accepted chart values or a working small-deployment feature.
