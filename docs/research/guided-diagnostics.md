# Guided diagnostic planning: feasibility and choices

Research checked 2026-10-09. This is documentary evidence, not a running Asservat integration. The normative proposal is [guided evidence selection](../../specs/guidance.md). Existing Gadget/packet choices remain; no new vendor service, embedded LLM or privileged workstation experiment is introduced.

| Question | Primary evidence | Design consequence |
| --- | --- | --- |
| Can we enumerate live processes? | Inspektor Gadget documents a [process snapshot](https://inspektor-gadget.io/docs/latest/gadgets/snapshot_process/) with PID and parent identity. Linux exposes an [executable link](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html), including access/deletion caveats. | Feasible input for assistance. Gadget output alone is not a stable process selector: Asservat must qualify executable/runtime enrichment, namespace and start identity, races and permissions. No argv/environment harvesting for convenience. |
| Can traffic be associated with a process? | Gadget's [TCP event tracer](https://inspektor-gadget.io/docs/latest/gadgets/trace_tcp/) reports connect/accept/close activity with process fields; [socket snapshots](https://inspektor-gadget.io/docs/main/gadgets/snapshot_socket/) cover existing sockets. | Combine qualified socket/event identity with capture time. A packet alone cannot prove its owning process, and a connection actor does not prove all subsequent writers. Shared sockets, old connections, UDP and proxies require ambiguous/unknown outcomes. |
| Can a short pcap inform protocol/peer choices? | Wireshark documents [protocol hierarchy and conversation statistics](https://www.wireshark.org/docs/wsug_html/) and [capture snaplen](https://www.wireshark.org/docs/wsug_html_chunked/ChCapCaptureOptions.html). | Offline packet analysis is an established mechanism. Asservat still needs bounded, sandboxed, versioned classifiers and projections. This does not establish that a ten-second sample sees every dependency or that snaplen removes secrets. No new Wireshark runtime dependency is selected by this research. |
| Can Kubernetes tell us the application protocol or Service? | Kubernetes calls [`appProtocol` a hint](https://kubernetes.io/docs/concepts/services-networking/service/#application-protocol); [EndpointSlice](https://kubernetes.io/docs/reference/kubernetes-api/discovery/endpoint-slice-v1/) represents Service backends. | Use declarations to suggest inspection, then distinguish confirmed observations. Several Services can select the same backend; NAT and observation location can prevent a unique mapping. Current permitted metadata can provide candidates, not guaranteed original-Service attribution. |
| Can encrypted traffic reveal HTTP semantics? | [TLS 1.3, RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) encrypts application traffic and EncryptedExtensions. [ALPN, RFC 7301](https://www.rfc-editor.org/rfc/rfc7301.html) distinguishes the client protocol list from the server selection. | Offer transport/TLS context and application-side alternatives. An offered protocol is not a negotiated result; absence of a visible handshake leaves gaps. No automatic decrypt/secret extraction feature follows from the request. |
| Can runtime profiles be recommended automatically? | Go's [pprof endpoint documentation](https://pkg.go.dev/net/http/pprof) distinguishes profile types and sampling prerequisites. | Capability-aware catalog rules can suggest useful profiles without enabling samplers or guessing endpoint URLs. Acquisition and approval still use the normal plan. Other runtimes require qualified packs. |

These are current upstream documentation pages, some tracking `latest`/`main`; they are not production version pins. Attempts to open matching v0.57.0 documentation routes did not succeed. Implementation must verify each adapter against the selected source/image digest and qualified kernel/CNI matrix, not infer compatibility from these pages.

## Selected mechanism

Use deterministic local playbooks and existing capture/action primitives. Ship three small discovery diagnostics, two read-only MCP planning/projection tools, and one browser journey. Generic process/network snapshots supply metadata; bounded packet recipes supply samples. Offline analyzers produce field-allowlisted protocol/flow projections. The existing diagnostic-handle preview/submission flow accepts generated recommendations, avoiding a separate survey execution API or resource type.

First classifiers cover transport, DNS, plain HTTP/1, visible TLS handshakes and HTTP/2 cleartext preface recognition. This scope is a proposed implementation requirement, not a claim that the current Gadget adapter already performs all classification. Further protocols need qualified classifier packs; unsupported traffic remains visible as transport/unknown. Live connect events are an optional enrichment until their adapter is qualified, not a prerequisite for basic discovery.

Ring sizing uses retained bytes, segmentation slack and a stated burst assumption. These are planning estimates; measured kernel/user-space buffering, loss, per-node cost and burst response remain EXP-20 work. A short sample cannot promise peak-rate coverage, reliable deadlock diagnosis, exact future core size or complete protocol discovery. Assistance remains useful by explaining these limits and suggesting a next measurement.

## Required evaluation

EXP-20 must exercise process reload/reuse and interpreter ambiguity; missing profiles; wrong protocol ports; cleartext/TLS/unknown traffic; long-lived/shared sockets; multiple Services/NAT/loopback; idle and bursty traffic; different raw/retained rates; saturated survey budgets; stale/revoked evidence; same-user multiple agents; malicious evidence strings and expiring copies. Measure task completion and active user effort under EXP-17. All runtime experiments remain **NOT RUN**.
