# Live-watch feasibility and interaction research

Checked 2026-10-09; documentation research, not an Asservat benchmark.

Kubeshark documents a live API stream and distinguishes per-view display filters from capture filters that affect recording. Its click-to-add filtering is a useful interaction pattern. Asservat adopts that distinction and narrowing interaction, with typed approved fields and without copying its filter language, URL persistence or feature/edition claims. [Kubeshark display filters](https://docs.kubeshark.com/en/display_filters), [live walkthrough](https://kubeshark.com/post/kubeshark-live-demo-walkthrough).

MCP has resource-update notifications, but the mechanisms differ between the existing supported protocol profiles: 2026-07-28 uses subscriptions/listen, whereas 2025-11-25 documents resources/subscribe. A notification indicates change, not a replay guarantee or a bounded evidence-consumption workflow. This design therefore uses explicit finite watch tools with bounded reads on both profiles; no resource subscription is required for correctness. Optional future wake-up hints would need separate capability, authorization and client conformance testing. [Current resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [older profile](https://modelcontextprotocol.io/specification/2025-11-25/server/resources).

Streamable HTTP can carry JSON results or request-scoped streaming responses; transport streaming alone does not define application flow control, evidence permissions or lifetime. The existing transport can deliver bounded long-poll reads without introducing a proprietary websocket or mandatory broker. This is a design inference, not a measured throughput claim. [MCP transport definition](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports).

The proposed Asservat adapter attaches a nonblocking bounded projection reader to already authorized source processing. Qualified parser reuse could reduce duplicate work, but compatible source representations, incremental HTTP parsing, PID/peer attribution and syscall pairing must be demonstrated. Existing offline analyzers are not automatically qualified live parsers. Unavailable live projections stay unavailable while original recording may continue. The [packet](../../specs/packets.md) and [syscall](../../specs/syscalls.md) integration evidence remains applicable; no Kubeshark dependency is introduced.

Required qualification: workload overhead under fanout and event storms, parser/scan bounds, independent viewer filters, zero blocking of recorder/snapshot paths, accurate drop/lag reporting, cursor replay and failover gaps, mid-batch revocation, short row retention in paused views, and real clients on both MCP profiles. Compare no-viewer, one-viewer and maximum-viewer runs while a protected incident snapshot uploads. Record limits and environment, not a universal overhead percentage.
