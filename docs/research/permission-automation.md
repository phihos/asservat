# Permission automation research

Inspected 2026-10-09. These are documentation findings and proposed integration choices, not tested Kubernetes behavior. The product remains one organization per installation. The corresponding contract is [permission management](../../specs/permissions.md).

## Findings and choices

| Mechanism | Verified facts | Asservat decision |
| --- | --- | --- |
| Kubernetes resources as the administration API | Custom resources expose Kubernetes APIs and can be managed declaratively. [Kubernetes custom resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) | Keep permission configuration in protected hub CRDs. Use the native Kubernetes API for provisioning tools; no duplicate HTTP CRUD service, additional database, identity directory or required custom Terraform provider (ADR-018). |
| Namespace labels/annotations | Metadata has no built-in ownership meaning. The default namespace `admin` role does not itself allow changing the Namespace object, but additional grants can. An annotation's prefix does not protect it. [Annotations](https://kubernetes.io/docs/concepts/overview/working-with-objects/annotations/), [RBAC roles](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#user-facing-roles) | A configured source may interpret administrator-controlled namespace metadata. Reuse existing keys; bind group IDs to a configured issuer and fixed role. Namespace creators/writers become permission administrators for that scope. |
| Admission guards for ownership metadata | ValidatingAdmissionPolicy can inspect the incoming object, old object and authenticated request, with enforcement through `Deny`. [Validating admission policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/) | Where developers may edit other namespace metadata, protect ownership keys and every selector used for permission derivation. Check creation, update, removal and replacement, including server-side apply. An existing qualified Kyverno/Gatekeeper policy may provide the guard; neither is a required dependency. |
| Existing exec permissions | SubjectAccessReview accepts the exact user/groups and named resource/subresource/verb. The resource attributes do not encode a container or command. Kubernetes 1.35 introduced a default-enabled additional `create` check for WebSocket exec; old `get`-only advice is insufficient for the proposed support window. [SAR schema](https://kubernetes.io/docs/reference/kubernetes-api/definitions/subject-access-review-v1-authorization/), [v1.35 release notes](https://github.com/kubernetes/kubernetes/blob/v1.35.0/CHANGELOG/CHANGELOG-1.35.md) | Provide opt-in `kubernetesExec` inheritance. Require `create` on `pods/exec` for each actual target, evaluated by that cluster. This is an application authorization input, not proof that an exec command will run successfully. |
| Admission restrictions on exec | Authorization precedes admission; admission can reject connection requests. A SAR does not execute the requested operation or run its admission path. [Authorization](https://kubernetes.io/docs/reference/access-authn-authz/authorization/), [admission](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/) | Before enabling exec inheritance, operators must declare whether exec has additional container/command/JIT restrictions. Reproduce those restrictions through a qualified adapter or leave this source disabled. Never run a test command to discover eligibility. |
| Reading RoleBindings or rules summaries | RBAC supports aggregation, wildcards and named resources. Kubernetes explicitly warns against using SelfSubjectRulesReview as an external authorization decision engine; results can be incomplete. [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/), [rules review](https://kubernetes.io/docs/reference/kubernetes-api/definitions/self-subject-rules-review-v1-authorization/) | Ask for the exact decision with SAR. Do not infer authority from a role named `edit`, scrape a permissions list, or implement a partial RBAC evaluator. |
| Workload metadata | Labels describe objects but do not impose ownership semantics. Kubernetes does not provide a formal application model. [Labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/), [recommended labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/) | Support protected Deployment/StatefulSet ownership metadata for shared namespaces. Do not trust pod labels or owner references alone as proof of who maintains an application. |
| GitOps/provisioning integrations | Flux can reconcile using a scoped service account. Argo CD projects can restrict sources and destinations; the default project starts permissively. [Flux authorization](https://fluxcd.io/flux/installation/configuration/multitenancy/), [Argo CD projects](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/) | Let existing provisioning workflows manage namespaces and AccessBindings. Review the actual writer identity, repository controls and destination permissions. A GitOps label or field-manager name is not authenticated provenance. |
| Service catalog ownership | Backstage describes `spec.owner` primarily as display information and explicitly cautions against using it to assign runtime authorization. [Backstage descriptor](https://backstage.io/docs/features/software-catalog/descriptor-format/) | An optional trusted integration may publish bindings after validating authoritative ownership. Never turn arbitrary `catalog-info.yaml`, CODEOWNERS or Git labels into permission automatically. |
| Identity provider groups | Authenticated group membership answers who belongs to a team; it does not inherently say which applications that team owns. Kubernetes and Asservat may use different identity mappings. [Kubernetes authentication](https://kubernetes.io/docs/reference/access-authn-authz/authentication/) | Reuse qualified IdP group membership, including configured nested-group semantics, with explicit issuer-scoped workload mapping. Avoid a second membership database or mandatory SCIM service. |

## Recommendation

Ship explicit AccessBindings, namespace metadata sources, protected workload metadata sources, exec inheritance and exact Kubernetes permission checks in the first production authorization slice. All inferred sources are enabled deliberately per cluster; enabling one rule can cover newly provisioned namespaces without individual Asservat setup. Identity eligibility and local collection ceilings remain prerequisites.

Use namespace metadata as the default onboarding recipe when administrators already own namespace provisioning. Use exec inheritance when teams' Kubernetes access is the maintained source of truth. Permit multiple independent sources, with explicit denies taking precedence. Keep an explanation endpoint that shows the contributing source, resource UID, revision and freshness.

Generic SAR inheritance can map a deliberately chosen existing permission, such as patching a named Deployment, to a limited Asservat role. It is optional, not an automatic interpretation of all `edit`/`admin` role bindings. Dedicated RBAC grants on `debugcaptures` can serve as a namespace-wide opt-in; creating a CRD object still does not skip runtime authorization.

Keep service-catalog and cloud-IAM-specific adapters outside the initial hard dependency set. Integrators can already use the Kubernetes API and GitOps CRDs. No source grants platform administration, node-wide access, or automatic approval of intrusive actions merely because someone can maintain an application.

## Qualification still required

EXP-16 must exercise real API-server authorizers, admission guards, namespace recreation, role changes, expired identity claims, connector outages, exec restrictions, forged request identity, GitOps updates and cross-team selectors. A successful schema check proves none of those integrations. Test each supported Kubernetes minor and identity mapper, including custom authorizers; do not claim universal parity with a cluster's entire exec policy from a SAR alone.

## Accepted API simplification (ADR-018)

The user accepted Kubernetes-only permission configuration. CRDs provide declarative CRUD/list/watch through the API server; server-side apply records field ownership and detects conflicting changes. Admission still needs to constrain custom binding content, because the native role-escalation safeguards do not automatically apply to application CRDs. Dry-run exercises validation/admission without persisting or running the controller; readiness must reflect reconciliation and propagation. Effective-access explanation remains a read-only query in the existing browser service. This removes duplicate permissions-specific OAuth scopes, CRUD routes, ETag/idempotency machinery and their separate OpenAPI lifecycle.

Primary references: [Kubernetes custom resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/), [API concepts and dry-run](https://kubernetes.io/docs/reference/using-api/api-concepts/), [server-side apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/), [native RBAC escalation protection](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping). Production structural schemas, admission, status and real-cluster tests remain deliverables; none is implemented by changing this document.

The subsequent accepted pod-scope decision removes container-granular configuration and permissions. An exec source must establish whole-pod eligibility; container-restricted access cannot be widened by a SAR mapping. Use a separate explicit whole-pod assignment when that source is insufficient. This narrows the earlier admission-adapter proposal; see REQ-TGT-006 and REQ-PER-004.
