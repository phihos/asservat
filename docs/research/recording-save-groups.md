# Grouped manual Save: implementation proposal

This proposal began at `850684b3`. The grouped implementation now has local
application, transport and console component checks, plus qualified two-source
PostgreSQL/S3/OpenBao ordinary, grant-backed and mixed-cancellation cases.
Installed workflow and sixteen-source SQL qualification remain pending. The existing single-source Save, cancellation and grant-backed
SQL/storage component results are recorded in [implementation progress](../implementation-progress.md).
Installed collector, syscall, optional reason and full end-to-end qualification
remain separate unfinished work.

## Required behavior and accounting

One request selects 1–16 distinct source sessions from one accepted policy execution scope/workload/cluster/namespace. Sort by sourceSessionID; reject duplicate source IDs and duplicate (PodUID, actionID). Incident maxPods counts DISTINCT PodUIDs, not source count, and is separate from all-replica observation ceilings. A group with multiple action sources on one Pod does not consume extra incident Pods. The currently implemented single packet action means the first usable group slice normally has one selected source per Pod; multi-action/syscall support remains unfinished rather than removed from the accepted contract.

First successful admission samples ONE SQL acceptance time after exact replay lookup under the existing root lock. Every child uses that t0 and its own before window ending exactly at t0, after=0. No child dispatch, delayed acceptance, retry or cancellation may move it. A denied/unavailable selected member rejects the entire new admission before any child dispatch. AFTER acceptance, independently frozen snapshots can succeed/fail/cancel/publish; do not roll back useful sibling evidence or stop the live sources.

Budget units are distinct:

* Shared workload/policy occurrence GCRA/cooldown: ONCE per Save, never once per child. Manual does not tick/reset detector state.
* Policy authority maxExecutions: **once per Save**, regardless of selected source count. The maintainer explicitly selected this rule on 2026-10-30 to preserve incident accounting. Applicable grant starts remain per source. This supersedes the earlier open design question; retries cannot spend another policy execution.
* Applicable grant maxExecutions: N individual sensitive snapshot starts, regardless of parent capture count. Collected/output bytes: sum of each child's worst-case output reservation. No single-start grant can fund N children. Ordinary children without a grant still consume policy/output/resource capacity.
* Existing source observation credit is not debited again. Each child reserves actual incremental frozen/output/encryption/upload/storage/control/audit resources; a parent ID cannot fund 16 artifacts through one artifact/control slot. No uncertain/cancelled spend refund.
* Each child independently intersects retained original source audience with its current full audience and original/current retention. Never union siblings' audiences or inherit recurring sharing. Explicit per-capture sharing uses the existing ordinary sharing rules and must be validated for the complete group; if a target cannot apply to a member, fail before admission rather than silently omit it.

Authoritative references: recording-saves REQ-SAV-002/003; authorization REQ-AUT-004; targets REQ-TGT-005/006; execution source-window canonicalization and aggregate action phases; capacity occurrence-vs-individual-start and recording-save reservations. The maintainer resolved the policy counter unit as one per Save; grant counters remain per source.

## Why current rows cannot be a parent

ContextPreview.Valid requires one artifact/attempt/pin and singular snapshot context. context_capture has NOT NULL one unique custody attempt and one expectation/Pod pin. context_execution, audit, completion, processing and native custody are one capture/attempt/artifact. ContextProgress is also singular although the public response already exposes actions[]. A case ID routes artifacts; it is not an atomic acceptance/idempotency record. Neither a fake parent artifact nor 16 calls to Request/AdmitContext is valid.

## Smallest persisted group

Keep N existing, independently funded context_capture children and their custody/execution/publication protocols. Introduce ONE bounded parent header table and nullable immutable group_id/group_ordinal columns on context_capture (no separate N-row link table). Header owns public captureID, original requester/client request-key + submission digest, canonical full selection digest/scope, policy acceptance, immutable ordered child IDs/count, acceptedAt and original group deadline. Children bind parent/ordinal to their own artifact/attempt/source. Constrain membership/root/order/1–16 cardinality and prohibit replacement; verify complete membership at transaction commit with a bounded deferred check. The header has no artifact, execution permit, encryption key or custody attempt. Group identity is an admission/control entity, not evidence.

Reuse existing root serialization. Replay checks both singleton and group request-key namespaces before reading an expiring preview; no cross-table duplicate request permitted. Exact accepted replay returns the same parent/children/t0, changed content conflicts. Existing single-source records remain readable/replayable unchanged. New group path can initially serve N>=2 while singleton stays its existing path; both expose the same public capture API and scope semantics.

Use a purpose-specific aggregate passive preview containing shared workload/policy/requester/canonical scope plus 1–16 existing child blueprints. Do not overload one child blueprint's artifact/attempt as the group parent or recursively persist 16 public previews. Reuse the existing preview journal/caps/expiry with a typed variant. Its current 128 KiB row cap is a real gate: measure a compact group encoding with shared target/authority/assessment data once and per-child pins/windows/provenance. Do not multiply 16 complete worst-case child blueprints or silently raise the cap. If the compact bounded form cannot fit, present the measured cost before changing the limit. No plaintext reason belongs here.

## One admission transaction, existing child effects

1. Resolve identity/current human eligibility and original policy executor; read exact selected protected source records in one bounded query (ReadRecordingSources already accepts an array). Prepare current per-source facts outside the transaction without refreshing original deadlines. Sort lock order by source ID. Admission must not require all source windows to be Full; existing truthful Unknown/Partial semantics remain.
2. Under existing recovery/root/accepted-policy/storage locks, resolve exact group/singleton replay FIRST. Check every member current identity/entitlement, source/session binding, audience/retention, approved window/output bounds and distinct-Pod cap. No HTTP/KMS/evidence transfer while SQL locks are held.
3. Sample acceptedAt once at the same point as existing manual acceptance. Reanchor ALL children using the same value and their original processing/retention horizons. Freeze child IDs before writes. Check all aggregate budgets with overflow-safe sums and one policy execution; reserve shared GCRA once, grant starts N, output sum, and each child's incremental custody/control/audit/output reservations atomically. Early execution debit must still precede existing SpendPolicyCollectedBytes' executions_spent>0 guard; any later failure rolls the transaction back.
4. Insert parent and N genuine child rows within this transaction, then final current/deadline checks and complete-membership validation. Do not invoke the current independently committing AdmitContext N times. Extract a private transaction-local child admission helper from the current adapter; its existing constraints and purpose-specific SQL role checks remain. Parent acceptance becomes visible only with the full accepted set.
5. Existing per-child encrypted capture-intent audit remains required before that child's dispatch. Extend its typed intent with immutable parent ID/selection digest/ordinal/count so the audited child cannot be substituted into another group. No new cipher/key purpose or parent evidence-writer is needed: parent mapping is SQL control state; each real effect retains its own audited capture. Preserve a child whose audit is temporarily unavailable and report that child explicitly; do not dispatch unaudited siblings on its behalf or invent a global evidence transaction.
6. Dispatch the existing typed snapshot work per child with its original capture/attempt/source/request and COMMON t0. Node frozen/global resource limits remain unchanged. Validate the existing configured node/ceiling pins at central admission. Local reservations still occur per child before copy/encryption through the existing node protocol; a later local capacity race is an explicit child failure. Do not add distributed pre-acceptance freeze leases or assume a group size of 16 overrides node capacity. A lost source is not replaced and t0 is never resampled.

Each child keeps its own manifest, effective retention, artifact, full processing lineage and native read. Up to 16 outputs, each currently at most 8 MiB: at most 128 MiB reserved native output for this existing packet slice, subject to stricter parent/workload/node/storage/grant bounds. This is a sum of configured maxima, not measured payload or overhead.

## Public progress, cancellation and history

request_capture returns ONE parent captureID. get_capture authorizes the parent requester/current scope then projects all accepted members into actions[] with stable per-source child identity (action ID alone repeats across Pods). Derive aggregate phase using execution.md: active child means Running, all required successes means Succeeded, useful successes plus failures means Partial, no useful required result means Failed, uncertainty remains explicit. Preserve individual phases/reasons and separate sharing result. Do not materialize a second background aggregate-state machine; compute from <=16 current child rows.

Cancel parent means persist cancellation for all unfinished child captures in one root-locked operation; reuse the existing joined per-child cancellation work/proofs and stored-wins rule. Keep successfully stored/published children. Replaying cancellation is idempotent; no live-source stop and no budget refund. Existing per-child internal cancellation identity remains intact; no new public child-cancel UI is required by this slice. Group revision can be derived from the ordered vector of child revisions plus parent's cancellation revision; do not sum revisions if the public equality token would lose identity/order changes.

History must show ONE manual recordingSave entry, not N unrelated manual requests. Group rows are roots; suppress linked children from the top-level history listing while keeping child artifacts visible in the authorized case. recordingSaveSettings already has action_windows[] and must represent all selected preferences and the original accepted t0; repeated selections are fresh inventory, not old IDs. Reuse authorized child encrypted history-parameter envelopes for detailed provenance/settings where available; the parent binds their exact IDs/digests and must not receive a fake artifact/history key slot. A group with unavailable/expired child history must report its honest history availability; do not manufacture source data or select a sibling without current rights. During implementation, audit the existing singular history authorizer/storage/key resolver before committing a concrete parent read projection. No new reason storage is smuggled into group history.

## Required compatibility and guard audit

One new migration (coordinate the next unused number), no runtime role additions. Extend only existing capture-admit, preview, execution/history/progress/cancel/read facets with exact necessary group columns/table privileges; none to source observer or browser. API execution, SQL audit matcher/history origin, publication processing, key authority, cancellation and history have all exposed singular assumptions in previous fixtures: enumerate each now and add narrow group routing while keeping child cryptographic/custody protocols unchanged. Do not change generic raw/native limits or rely on Go's case-insensitive JSON decoding where SQL uses exact canonical paths.

Public actions[] avoids a new endpoint, but it does NOT prove current Go progress/TS response mappings already support repeated action IDs and multiple artifacts. Add typed aggregate projection and render each child distinctly; parent caseID links all authorized outputs. Current React controller already selects several handles but server cap=1; expose the actual accepted incident cap after compiled policy support exists, not a client-invented 16. Lift maxPods=1 in the ongoing private policy compiler only with equivalent approved cap/digest enforcement; existing cap1 acceptances remain cap1. Do not change automatic detector grouping or broaden accepted policy scope silently.

## Complexity gate: eleven answers

1. Frequency/harm: actual accepted feature currently always rejects >1 selected source. Production frequency unmeasured, not a speculative fault; effect is inability to save replica context with one t0.
2. Accepted risk: retain current conservative spend, 5s freshness/request bounds, node/resource caps and independent post-acceptance failure. No demand for atomic all-artifact success or instantaneous cancellation.
3. Typical benefit: multi-replica workloads; N=1 behavior remains compatible. Multi-action same-Pod/syscall follows the same membership model but is not claimed implemented by packet work.
4. Precedent: internal execution.md already defines parent action aggregation; capacity.md freezes/reserves complete episodes; existing child custody/work is proven component behavior. No external novelty claim or new scheduler is needed for this control composition.
5. Privileges/network: 0 new external privileges, credentials, collector APIs or browser tokens. One group table and exact existing role grant extensions; N existing real output authorities remain required.
6. States: 0 new evidence lifecycle states; parent accepted membership plus cancellation intent, aggregate read projection. Existing child pending/failed/partial/cancel/uncertain states reused. No retry/fallback queue.
7. Configuration: 0 new knobs. Existing incident cap, 1–16 schema bound and existing node/storage/output limits apply.
8. Dependencies: 0 new components/libraries/providers. Existing SQL/KMS/object store/transport requirements unchanged; <=N existing effect calls after admission.
9. Cost: N<=16; one parent row plus N existing child rows (+2 nullable child columns), no N extra link rows. The parent consumes one additional existing full/replay metadata unit, alongside N child and N pre-existing source charges (2N+1 total); those charges remain monotonic. One transaction/root lock rather than N root-lock transactions; per-source checks/reservations O(N), output/control/encrypted audit/registration work N, source observation 0 extra. Full preview stays <=128 KiB unless measured evidence justifies otherwise; native maximum 16*8 MiB=128 MiB aggregate. Current group SQL latency, lock hold time, serialized bytes and KMS count are NOT measured. Measure 1/2/16 success and last-child rollback; protect original5s deadlines rather than extend them to make tests pass.
10. Upgrade/rollback: additive nullable child links preserve legacy records. Down refuses retained populated groups/provenance instead of dropping identity. Test empty Down/Up and populated refusal. Disable new group acceptance while retaining existing group read/cancel/completion; no refund or deletion of accepted work.
11. Smaller alternatives: 16 public requests change t0, share no atomic admission/cooldown and can silently leave a partial selection accepted; they violate the requirement. One merged artifact requires new cross-node writer/audience/custody composition and is larger. Header + existing real children is the smallest coherent path; leave reason and source-metadata retirement explicit gaps rather than add machinery here.

## Practical implementation/qualification slice

Implement parent + 2–16 existing packet-source children under one opted-in accepted policy/workload, first with ordinary permission and then the already-supported covering-grant branch. No new recorder acquisition, container choice or syscall substitute. Preserve single-source path and all existing component evidence; do not rerun unchanged expensive suites without source delta.

Start meaningful REDs: two sources with clock advancing between child preparation still get identical SQL t0; duplicate source and duplicate Pod/action reject; maxPods uses distinct Pods; later member permission/capacity/grant failure leaves zero parent/child/spend/GCRA/reservations; exact/unknown replay after preview expiry does not spend/shift t0; grant N starts and sum bytes; exactly one parent policy execution. Then existing child owner tests plus mixed success/failure/cancel stored-wins aggregate, one history row/fresh repeat, audiences separated, recurring sharing excluded, native bytes per successful artifact. Max16 bounded serialization and measured lock/call budget before external qualification.

Implementation ownership should separate application/aggregate admission,
SQL migrations and query generation, transport projections and React behavior.
Serialize shared `capture.go` and SQL generation changes, and freeze exact source
before external qualification. The preview encoding, parent metadata charge and
cleanup, history projection and repeated-action sharing identities remain
engineering follow-ups; the proposal does not establish their implementation.
