# S-06 plan: sharing, reuse and administration (2026-10-26)

Phase A of [S-06](../architecture/implementation-slices.md): an audit of what exists, the
[AGENTS.md complexity gate](../../AGENTS.md#complexity-must-pay-for-itself) for each feature, and an
ordered list of increments. This plan contains no product code. It does not amend the specifications.
Where it proposes a narrower first implementation than the specification describes, each increment
updates the affected spec text in the same PR, as AGENTS.md requires.

Baseline: `origin/main` at `a5d9dafd` (S-03 complete, ADR-228–231). Traceability: C-01/03/06/09/15/16/17/20,
TASK-07/08/11. Relevant specifications: [authorization](../../specs/authorization.md) REQ-SHR-001–008,
[capture history](../../specs/capture-history.md) REQ-HIS-001–004,
[capture profiles](../../specs/capture-profiles.md) REQ-CPR-001–005,
[permissions](../../specs/permissions.md) (explanation/impact preview), [privacy](../../specs/privacy.md)
(retention impact preview), [user experience](../../specs/user-experience.md) REQ-UI-004 and the
[MCP tool catalogue](../../specs/mcp.md#tool-catalogue).

### 2.3 Simplifications against the current spec text

Each simplification keeps the accepted outcome and invariants: concrete snapshots, immutable creator,
team management, expiry ≤ artifact retention, current eligibility and deny at every read, audit,
and no widening on group/namespace churn. Each is recorded in the spec by the increment that
implements it.

| Spec mechanism | Proposal | Why |
|---|---|---|
| Separate `SharingIntent` record with Pending/Active/Draining/Completed/Suspended/Denied/Revoked/Expired, registrations, child shares per selection, publication slots | One `evidence_share` row per (share, artifact). A capture-time or policy instruction is a nullable column on the accepted capture or policy acceptance. Shares are materialized in the existing catalog publication transaction. Read-time state is derived: `active`, `expired`, `revoked`, `suspended` (no valid manager). | ADR-022 simplify action. With one output per capture, selections, slots and children have nothing to select (q1 hypothetical, q6 ≥8 states). |
| Re-validate manager authority at publication | Materialize without a publication-time check. The share pins the creator's contributing owner assignment IDs and revisions; every read requires at least one pinned assignment to still be the same current assignment, plus deny, recipient and expiry checks. | A re-grant creates a new assignment, so a share whose managers lost rights stays suspended and is never silently restored (REQ-SHR-007); resuming needs a new share. This replaces the publication-time check of REQ-SHR-004 and removes a permission read from the regional publication path (q9). |
| Administrator-enabled sharing policy toggle and adjustable 7-day maximum | No toggle. Sharing is enabled by assigning `evidence-owner` and granting the `evidence:share` client scope, both already administrator-controlled. The 7-day maximum and 24-hour default are constants. | q7: a toggle tunes only Asservat's own machinery and duplicates existing controls. |
| Explicit `management: {mode: teams}` selection requiring delegation; audited transfer/replacement | Default management only: the creator's current `evidence-owner` Group assignments covering the target (≤8), else creator-only when individually assigned. Transfer: an owner revokes and creates a new share. | Default covers the accepted case (creator leaves, team keeps control). Transfer machinery is unobserved (q1). **Superseded by §2.4** (increment 9). |
| Administrator revoke API | Use an explicit Deny AccessBinding (stops recipient reads now) or remove `evidence-owner` (suspends the shares). | The existing mechanism is installed-qualified. A new admin role/API adds privilege surface (q5). **Superseded by §2.4** (increment 9). |
| Directory check that a group ID exists | Accept issuer-scoped stable IDs from the configured issuer only. Display names are rejected. | A directory reader needs credentials ADR-059 forbids by default (q5). |
| History: encrypted parameter snapshots, keyed selector/settings digests, 128 KiB cap, 1,000/100,000 eviction, `repeatedFromCaptureID` lineage | SQL query over `context_capture` (+ one index), visibility = own requests plus current retained-audience match, page ≤100. Repeat prefills the normal preview. | The only settings today are target/preset/retention, which contain no user-supplied personal values. Add snapshots when a parameterized recipe (packet filter, paths) lands (S-04). **Superseded by §2.4** (increment 6 base, 12 full). |
| Recurring sharing via SharingIntent registration before dispatch | The policy acceptance carries `sharing` (recipients, `maxCaptures` 1–100, absolute `notAfter`). Each occurrence capture atomically increments a counter and copies the instruction while under both limits. Stop = policy edit, Revoke-all = revoke by acceptance ID. | Same outcome and bounds; no draining state machine. The automation binding must hold `evidence-owner` (reuses roles, no schema field). |

## 3. Increments

Each increment is one PR. Each must pass `make pre-push`, unit tests, the affected custody/SQL
component tests on real PostgreSQL, and at most one installed focus (`ASSERVAT_JOURNEY_FOCUS=share`
on the fast feature fixture, ≤20 minutes). Component tests prove the path before any installed run.
The installed focus reuses the journey's existing unrelated principal as the recipient.
