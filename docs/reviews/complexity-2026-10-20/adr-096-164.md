## ADR-096

**Database incarnation fence before recovery activation**

**Recommendation:** keep. **Confidence:** medium.

**Source:** [docs/decisions/096-database-incarnation-fence.md](../../decisions/096-database-incarnation-fence.md)

**Provenance:** Engineering refinement of requested restore safety; exact incarnation mechanism not a documented maintainer choice.

**Qualification:** ADR records reproduced SQL recovery bypass; independent restore/ordinary-restart protocol remained incomplete.

| Complexity question | Assessment |
| --- | --- |
| 1. Observed frequency and impact | Reproduced stale recovery flag became usable after ordinary observation; deployment frequency unmeasured. |
| 2. Already accepted risk | No accepted risk of restoring old authority is documented; relaxed download permission timing does not waive restore fencing. |
| 3. Common deployment coverage | Protects rare restores but also fences every database restart, a normal operational path. |
| 4. Comparable projects | ADR supplies no comparable-project recovery design; do not infer necessity of every downstream witness. |
| 5. Added privileges or exposure | Runtime loses activation-write privilege; trusted recovery administration remains required. |
| 6. Failure states | At least three states: unactivated, current incarnation, recovery-blocked; failed restart activation adds operational outage. |
| 7. Knobs for the machinery | Activation/incarnation fields are internal, not useful end-user configuration. |
| 8. External coupling | Depends on PostgreSQL process start/database identity and an independent recovery protocol. |
| 9. Aggregate runtime cost | Adds predicates/locks to trust reads; aggregate contention and restart downtime unmeasured. |
| 10. Upgrade, rollback and disable | Migration preserves old state as blocked; rolling upgrade and automatic restart recovery were not qualified. |
| 11. Smaller solution | A single explicit recovery epoch/fence can retain the essential protection; compare operational restart cost before expanding it. |

**Reasoning:** A concrete authority bypass justifies a fence, not unlimited machinery around it.

**Action:** Retain the core guard; qualify normal restart and compare a simpler operator-controlled restore epoch.

**Evidence:** [docs/decisions/096-database-incarnation-fence.md](../../decisions/096-database-incarnation-fence.md); [docs/architecture/initial-installation.md](../../architecture/initial-installation.md).

## ADR-097

**One-use installation witness**

**Recommendation:** simplify. **Confidence:** medium.

**Source:** [docs/decisions/097-one-use-installation-witness.md](../../decisions/097-one-use-installation-witness.md)

**Provenance:** Engineering anti-reinitialization mechanism; no explicit demand for a one-use Kubernetes witness found.

**Qualification:** Native component consumption/race/denial checks documented; database facts were synthetic.

| Complexity question | Assessment |
| --- | --- |
| 1. Observed frequency and impact | Prevents accidental new-install activation over missing/restored SQL; production occurrence unknown. |
| 2. Already accepted risk | No explicit acceptance of that loss is documented; cluster administrators already remain trusted. |
| 3. Common deployment coverage | Initial installation and disaster recovery, not routine investigation. |
| 4. Comparable projects | No comparative implementation evidence in ADR; a trusted installer/state marker is an alternative to evaluate. |
| 5. Added privileges or exposure | Adds protected ConfigMap, independent probe account and update-only consumer rights. |
| 6. Failure states | Unconsumed, claimed, uncertain, missing/replaced and recovery-required states exceed two. |
| 7. Knobs for the machinery | Requires exact UID/guard/source pins and finite proof settings for this mechanism. |
| 8. External coupling | Relies on Kubernetes CAS, admission enforcement and a separately preserved control plane. |
| 9. Aggregate runtime cost | Fixed objects per installation, repeated guard/API reads per consume; measured cumulative installation cost absent. |
| 10. Upgrade, rollback and disable | Preserved on upgrade/uninstall; control-plane rollback remains outside its guarantee. |
| 11. Smaller solution | Consolidate the witness into one retained installer state and explicit restore procedure, retaining missing-state refusal. |

**Reasoning:** The cross-store signal has value, but is not independent of a Kubernetes restore and duplicates retained installation journals.

**Action:** Compare a single retained root plus explicit recovery gate; preserve old witness identities during migration.
