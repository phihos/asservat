Phase A of [S-04](../architecture/implementation-slices.md): an audit of what exists, the
[AGENTS.md complexity gate](../../AGENTS.md#complexity-must-pay-for-itself) for each feature, the
test environment for privileged collectors and an ordered list of increments. This plan contains no
product code and does not amend the specifications. Where an increment implements a narrower or
different mechanism than the specification text, it updates that text, the contracts and
traceability in the same PR, as AGENTS.md requires.

this plan, not yet implemented or measured.

## Published-gadget decision and implementation checkpoint

The maintainer's later 2026-10-27 decision supersedes the original custom-gadget
proposals: use Inspektor Gadget's published gadgets, pinned by digest. Do not add
custom kernel/eBPF programs or hand-written packet parsers. The baseline audit
and feasibility results below remain historical evidence, not permission to
revive those mechanisms.

[ADR-248](../decisions/248-manual-packet-capture.md) implements the finite-capture
part of increment 4 with the published tcpdump gadget, its tc attachment, the hub-compiled libpcap program
evaluated in user space, and gopacket header decoding. It provides finite manual
captures capped at 8 MiB, encrypted publication and native PCAPNG downloads.
Continuous rings, policy arming, trigger saves, summaries and the streaming lift
remain work in the increments below. The user-visible feature scope remains;
the implementing ADR and [progress record](../implementation-progress.md) state
what has actually passed. Future peer and syscall work must qualify the published
engine path and report capability gaps without substituting custom programs.

## 4. Increments

Each increment is one PR with its ADR (where a contract changes) and the spec/contract edits of
§3. Each passes `make pre-push`, unit tests and the affected component suites on real PostgreSQL /
S3 before any installed run. Native collector suites (§5) and at most one installed focus run on

confirms it. Sizes are rough code estimates, not effort forecasts.

| # | Increment | Changes | Proof | Est. size |
|---|---|---|---|---|
| 1 | **Packet/syscall plans in preview (no recorder yet)** | Typed `packetCapture`/`syscallTrace` actions in the compiler; `executionMode` normalization and the `action-lifecycle/v1` plan (On trigger vs Records while armed; saves on trigger); `onTrigger` requires `before: 0s`. Embedded builtin `network-connections/v1` and `syscall-activity/v1` profiles, selectable as a one-component `profile_composition` with typed edits (filter, window, ring, mode) so no throwaway preset path is created (S6). ### 4.1 Authorization in increments 4–11 (before the grant system of increment 12)

The specification requires **no grant for metadata-only sources or their saves**:

- [actions.md](../../specs/actions.md) (action table): `packetCapture` defaults to sanitized network
  headers, and "HTTP inspection and raw payload need sensitive grants". `syscallTrace` metadata
  needs no user-memory reads, and "argument/buffer mode requires sensitive-observation approval".
- [action-lifecycle.md](../../specs/action-lifecycle.md) REQ-LIF-004: "Metadata packet/syscall
  observation still requires collection rights, current scope, finite local leases and impact
  limits. HTTP/raw packet and syscall argument sources additionally need their reviewed acquisition
  grants".
- [syscalls.md](../../specs/syscalls.md) REQ-SYS-002: "Metadata observation uses ordinary scoped
  collection permission and impact budgets unless an administrator requires more."
- [recording-saves.md](../../specs/recording-saves.md) REQ-SAV-001 requires "normal acceptance and
  any applicable fresh approval". REQ-SAV-003 reserves grant budgets only "where the grant requires
  them". [authorization.md](../../specs/authorization.md) ("Manual saves under reviewed policy
  authority") says "Applicable grants must cover the sensitive source". For a metadata source no
  grant is applicable.
- [execution.md](../../specs/execution.md) ("Recording-save execution identity") binds a save to
  its own recording-save/v1 scope: "Only this typed operation may consume a reviewed policy save
  permit". That limits who may consume such a permit. It does not create a permit requirement
  for sources that need no grant. [investigation-approval.md](../../specs/investigation-approval.md)
  SC-INV-001: "A context-only request adds no approval step". Its single review applies to
  captures that need one (sensitive or intrusive actions, or raw `resultAccess`).

Increments 4–11 therefore authorize exactly as S-02/S-03 do today. Manual captures use the
requester's current whole-pod collection rights, the `evidence:capture` client scope and current
deny checks. Policy sources (6–7) use the accepted policy's ADR-059 automation identity, whose
AccessBinding `automation.allowedActions` ceiling already lists `packetCapture`/`syscallTrace`
(`domain/authorization/automation.go:24`), plus capacity and impact limits. Saves (8) use the
caller's current collection rights plus that unchanged policy executor. Until increment 12:

- The compiler accepts only metadata profiles (`networkHeaders`, syscall `metadata`). A plan that
  selects `httpHeaders`, `rawPackets`, syscall `arguments` or a raw-byte filter predicate is
  refused at preview with `ApprovalRequired` (manual) or at policy compile time with the field path.
  Nothing is armed and nothing is charged.
- If an administrator configures approval for metadata recordings (the REQ-SYS-002 "unless an
  administrator requires more" case), affected plans get the same refusal. A recording is never
  armed without the approval that is required.

No path in increments 6–8 needs a grant, so they do not depend on increment 12. Increments 13–15
(and the administrator-required metadata approval) do.

## 6. Open verification items (facts to measure, not decisions)

1. ADR-248 records actual runner kernel/BTF/cgroup facts and the published gadget's tc
   attachment. Broader kernel/CNI qualification remains open; TCX detection alone does not
   establish that this gadget uses TCX.
2. Qualify finite peer-generation changes in the bounded matcher while the published gadget
   stays attached. Measure matcher work and stale-generation suppression; do not assume custom
   map access or modify the upstream kernel program.
3. Detection-to-pin latency for S-03 triggers (restart, probe, alert) under the 15 s poll; sets the
   S3 margin.
4. Static libpcap linking in the hub build (licence notices, image size, reproducibility).
5. Collector idle and loaded CPU/RSS per node with N armed sources; Go allocator overhead above the
   16 MiB ring (the lab did not measure RSS).
6. Packet loss and overhead at the qualification rates. 1/10 Gbit/s (EXP-02) cannot be measured on
   a 4-vCPU runner; record what the runner sustains and leave the 10 Gbit/s figure pending for S-09.
7. API server cost of the S5 polling: one paged consistent LIST per followed query per second at
   4,096 endpoints, and at the 64-query cap; and whether the target Kubernetes versions serve
   consistent LISTs from the watch cache.
8. Pod-loopback observation: which hook sees pod `lo` traffic in kindnet and Cilium; duplicate
   counting.
9. Syscall metadata: raw tracepoint `sys_enter`/`sys_exit` overhead at 10,000 events/s per target
   and the no-user-memory-read property verified by program inspection (no `bpf_probe_read_user`
   in the metadata object).
10. Keycloak step-up (`acr`) claim delivery in the identity fixture for P14 approvals.
11. ADR-248 resolves the initial header-only path with the published gadget's fixed snaplen
    and maintained user-space decoders, dropping unsupported formats. Future format coverage
    must qualify the existing published-engine path; no custom truncation program is authorized.
12. ADR-166 streaming custody at 256 MiB (32 parts) for the largest frozen ceiling (increment 2).
13. Packet byte rate per target at which the 16 MiB ring holds less than `before` + margin (S3):
    above that rate the age margin adds nothing and achieved history is byte-bound.

### 6.1 Points for the maintainer

No mechanism this plan adds beyond the specification combines weak benefit with questionable
cost, so nothing is paused. Three points change scope or ordering and are stated so the
maintainer can object before the affected increment starts:

1. **The approval/grant foundation moves from S-08 into S-04 (increment 12).** HTTP headers,
   raw packets and syscall arguments are specified as sensitive acquisitions that need a grant
   before the first read, and no grant system exists. Building it here is required by the spec,
   not added. It does mean S-04 carries work the slice table assigns to S-08.
2. **Peer freshness by LIST polling instead of watches (S5).** Benefit is clear (simple,
   fail-closed); the cost is up to 64 consistent LISTs per second per cluster at the cap.
   Open item 7 measures it. If the API load is unacceptable, the fallback is a watch plus the
   spec's progress check, which is the more complex mechanism.
3. **Detection-latency ring margin (S3).** Without it, a 15 s detector poll silently loses up to
   half of the requested 30 s history. The margin raises only the age limit; the 16 MiB byte cap
   and memory reservation are unchanged. It helps only below the cap fill rate (about 328 KiB/s
   for the preset). The window stays anchored at the event time t0, not at detection time. The
   20 s value is a starting point, to be set from open item 3.

Nothing in this plan marks a TASK checkbox or EXP gate complete. Increments that narrow or
restate spec mechanisms (§3) update `specs/packets.md`, `specs/syscalls.md`,
`specs/action-lifecycle.md`, `specs/capture-profiles.md`, `specs/capture-history.md` and
`specs/traceability.yaml` in the same PR.
