# Final correctness and feature review

Reviewed 2026-10-09. This follows the [earlier review](design-review.md), including the later profile/history/lifecycle/impact-assessment additions. The architecture remains appropriate: Kubernetes configuration, PostgreSQL transactional hub state, encrypted regional objects and bounded node execution. The remaining risks are mostly interactions between those components. No runtime code, cluster qualification or privacy certification is claimed.

“Corrected” below means the written contract and, where applicable, offline examples/checks have changed. Implementation and failure testing remain mandatory. P0 identifies a possible authorization/privacy breach; P1 a broken incident path or prerequisite; P2 misleading capability or unnecessary friction.

Before editing, four issues were reproduced against the existing schemas and semantic checker: missing manual pod bindings, a core without process identity, a log after-window exceeding its action deadline, and an acquisition without lifecycle provenance. All were accepted. The revised gate contains explicit rejection cases. Other findings are design/source analysis, not reproduced runtime vulnerabilities.

## Features to add, extend or remove

| Recommendation | Priority and rationale | Boundary |
| --- | --- | --- |
| **Add Save existing recordings now — accepted** | First-release addition, now specified: an engineer sees a suspicious event and wants the existing prehistory before it rolls out of the ring. Recreating a manual capture cannot recover it. | New explicit snapshot-only request bound to current policy revision, concrete authorized pods/sources, t0/window and existing incident quotas. Current collection/sensitive-read rights required. Never run policy cores/commands implicitly or borrow a policy's grant for arbitrary ad hoc work. The dedicated recording-save contract, examples and regression checks are now integrated; runtime support remains unimplemented. |
| **Extend policy health explanations** | First-release extension applied under FR-09. It answers “why no evidence?” without requiring log access or repeated collection. | Project existing state, bounded suppression counters and remediation links; no new service or sampling. |
| **Extend stopped-source handling** | First-release correction applied under FR-03. Crash/exit diagnosis is a core use case. | Finite old-source retention, no new observation or renewed rights, capacity and expiry enforcement. |
| **Extend the installation report** | First-release qualification must show analysis storage, worker logging/core/swap controls and concrete capability gaps. | Distinguish configured, inspected and tested. Read-only installation checks do not prove backend deletion or workload overhead. |
| **Defer interactive trigger replay/simulation** | Useful after the real evaluator exists: run sanitized typed test events through the same engine and explain states. | No alternate mock evaluator presented as proof, no automatic production capture and no arbitrary CEL/runtime code. |
| **Remove the inert manual policy detector** | Applied; an accepted configuration with no implementation path is worse than a clear capability boundary. | Keep ordinary manual captures. The snapshot-only proposal replaces the misleading promise. |
| **Keep optional extensions out of baseline guarantees** | Legal-exception holds, durable text-index cohorts, GPU dumps and TLS-aware capture each need separate qualification. | Preserve their existing optional/future status. Do not silently reduce requested first-release profiles, MCP, multicluster management, permissions, fairness or privacy controls. |

Do not add another database, broker, permission CRUD API, embedded agent, arbitrary plugin/template language or automatic trial profiling to solve these gaps. Current services and typed contracts are sufficient. No additional breadth is more urgent than demonstrating identity, isolation, resource accounting and deletion under failure.

## Follow-up decisions accepted

The maintainer accepted the qualified encrypted scratch StorageClass prerequisite (ADR-036) and Save existing recordings now (ADR-038). Collection can run while offline analysis reports missing scratch qualification. The [recording-save specification](../../specs/recording-saves.md) defines the narrow operation and its policy/authorization, API/MCP, quota, history and privacy boundaries. Runtime implementation and qualification remain pending.

## Source checks and limits

- Kubernetes describes [emptyDir lifecycle and memory accounting](https://kubernetes.io/docs/concepts/storage/volumes/#emptydir) and [RWO/RWOP access modes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes). These establish the handoff error; they do not qualify a CSI encryption/reclaim implementation.
- [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) is pod-scoped, and application of changes/existing-connection behavior does not supply a secure credential-removal phase boundary. Separate Jobs remain the design.
- Linux documents [CPU/cgroup counters](https://docs.kernel.org/admin-guide/cgroup-v2.html), [PSI totals versus averages](https://docs.kernel.org/accounting/psi.html) and [piped core handling](https://man7.org/linux/man-pages/man5/core.5.html). Metric formulas and crash-path constraints are design choices based on those interfaces, not measurements of supported kernels.
- [Alertmanager's webhook](https://prometheus.io/docs/alerting/latest/configuration/#webhook_config) carries per-alert status, startsAt, endsAt and fingerprint. The proposed bounded episode/replay policy is Asservat behavior, not an Alertmanager exactly-once guarantee.

The review cross-checked target/permission/approval boundaries, trigger-to-source-to-incident lifecycles, storm/storage accounting, packet/syscall/profile semantics, regional encryption/analysis, SQL versus Kubernetes authority, sharing/audiences, privacy/copy retention, history/composition/guidance and browser/MCP parity. No recommendation reintroduces tenants or container-level configuration. Original-source provenance and the previous implementation gates remain intact.

The [new tabletop cases](use-case-walkthroughs.md#uc-36--a-crash-event-arrives-after-the-source-stops) and [validation additions](../validation.md#final-review-regressions) define required failure tests. The actual offline gate result is recorded in [spec-validation.txt](../research/spec-validation.txt). It validates documents/contracts, not deployability. Implement accepted ADR-036 and run the existing feasibility gates before product implementation claims.

The later [review from user outcomes](user-task-review.md) identifies gaps this correctness review did not catch. Its open findings, including bounded trigger testing, are not resolved by the previous document-coverage checks.
