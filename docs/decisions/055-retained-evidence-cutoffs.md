# ADR-055 — Monotonic retained-evidence cutoffs and signed lifecycle journal

Status: implementation refinement under the maintainer's sustained continuation. Implements the already accepted REQ-PRV-002/004 behavior; it does not enable collection or disclosure.

The deletion-budget correction subtracts a newly required cleanup budget from the already-bound hard deadline, even if the new maximum is longer. Migration 00016 permits the restrictive overlay's read cutoff to equal the original anchor when no positive readable interval remains. Original registration/new collection still require positive time. This closes access and makes deletion claimable; it does not manufacture an already-missing cleanup window or extend the hard deadline.

An administrator's shorter maximum must apply to existing evidence, including evidence whose revised deletion deadline is already past. Reusing collection admission for that calculation incorrectly loses overdue cleanup because admission rejects expired evidence. Changing original manifest dates would invalidate cryptographic provenance and later verification.

Keep original registration/manifest dates immutable. Migration 00014 adds a separate, monotonically decreasing read/deletion overlay and an ordered lifecycle decision per actual shortening. Serialize the update with transfer/publication admission, retain the acquisition anchor, request and classification, and recheck policy freshness after blocking locks. A longer policy, removed override or retry cannot increase an old deadline. Read, finalization, download and cleanup facets consume the effective dates; transfer notices and socket deadlines use current, shorter authority.

Restrict access immediately in the same SQL transaction that records pending journal work. Do not keep evidence readable while a signer, KMS or object store is unavailable. Independently publish an immutable, encrypted, signed lifecycle record and acknowledge its exact object receipt. Pending journal work remains visible as unfinished work; it is not proof of durable audit or completed deletion. Restore must remain closed until authoritative lifecycle reconciliation is complete. Storage reservations remain charged until the existing writer barrier and verified purge succeed.

Reuse the pinned jwx implementation and its Ed25519 algorithm profile with an explicit `asservat-retention-lifecycle+jws` type, dedicated protected installation keys and no incoming key URLs. Use standard detached compact JWS over the canonical versioned decision, with the payload stored in the existing Tink-encrypted control record. The signature exposes neither the payload nor a bearer capability. Historical verification retains explicitly configured public keys; rotation must not require rewriting old objects. This follows [JWS detached content](https://www.rfc-editor.org/rfc/rfc7515.html#appendix-F) and the [fully specified Ed25519 identifier](https://www.rfc-editor.org/rfc/rfc9864.html#section-2.2).

The first adapter handles the accepted pod-status producer. Protected policy-source acceptance, selector/topology qualification, signing-key provisioning/rotation, propagation to remote workers, restore promotion, finite journal/SQL/backup cleanup and a production writer barrier remain required. The key constructor is a frozen adapter configuration, not a policy authority. Tests use synthetic policy and signing inputs. No legal hold, erasure workflow or preservation exception is introduced by this monotonic path.
