# ADR-078 — Durable owner configuration acceptance

Date: 2026-10-10. Status: implementation refinement under the maintainer's continuation; Go/race/import/SQL/design gates and owned SQL/S3/Kubernetes suites pass. Exact qualification and remaining fixture inputs are tracked in [implementation progress](../implementation-progress.md).

ADR-077 proves current Kubernetes protection and content, but a process-local observation cannot detect rollback after restart or prove that a trust change was durably audited. Extend the existing PostgreSQL and encrypted audit adapters with one owner-configuration head per installation/hub cluster and immutable source revisions. Keep the Kubernetes source, SQL observer, audit acknowledger and current reader as separate authority facets. No new service, dependency, public endpoint or developer approval is introduced.

Migration 29 pins the immutable source UID for that head, stores at most 1024 bounded revisions and permits only monotonic revision/observation progress. Replacing the source UID requires separately qualified recovery/re-enrollment; ordinary reconciliation cannot establish a second current source. Observe only within the original five-second source deadline and the current installation issuer/recovery state. Take the recovery row lock before the configuration lock, and check time after blocking operations. Never perform object/key-service I/O inside these transactions.

A changed revision immediately displaces the old head but remains unusable until its exact encrypted audit receipt is acknowledged independently. Acknowledging historical audit does not select that revision or refresh its observation. Repeat observation of an already acknowledged revision reuses its receipt without another key operation. The current reader retains the original source deadline and clips it to current recovery validity. Suspension, recovery blocks, issuer mismatch, missing audit and expiry deny use.

Persist failure watermarks even before the first successful observation. Reject delayed observations at or before a known failure; a later valid observation can restore availability without changing the immutable revision content. A known rollback or same-generation mutation commits a fence before returning a conflict: rolling back that transaction would otherwise leave the previous fresh trust usable. Old cleanup cannot fence a newer observation. Equal timestamps cannot renew freshness; comparisons use PostgreSQL microsecond precision. If negative cleanup itself cannot reach SQL, consumers remain bounded by the already-issued original deadline; do not claim the failure was durably recorded.

The acceptance record contains only public routing/trust configuration, not signing keys or evidence credentials. Public CA validity is still qualified by the Kubernetes/X.509 source. Audited acceptance does not activate a certificate, clear recovery, authorize a request or provide a protected issuer bootstrap. Those remain required before private forwarding or public downloads are enabled. See [the architecture contract](../architecture/owner-configuration.md).
