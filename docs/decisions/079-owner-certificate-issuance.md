# ADR-079 — Purpose-separated hub owner certificate issuance

Date: 2026-10-10. Status: implementation refinement under the maintainer's continuation; full Go/race/import/design and owned fleet/Kubernetes provider regressions pass. Measured results and remaining fixture inputs are tracked in [implementation progress](../implementation-progress.md).

ADR-076 defines exact client/server owner identities and ADR-078 supplies accepted routing/root configuration. Implement provider issuance against those contracts using the existing maintained OpenBao client and Go X.509 primitives. Each issuer instance has one fixed HTTPS provider, mount, role, installation, hub cluster, issuer epoch and leaf purpose. Separate provider credentials/roles issue client and server leaves; neither instance can manage roles, generate/export private keys, activate a registration or grant forwarding authority.

Owners are long-lived hub processes. Reusing the download worker's eight-hour lifetime would force unnecessary hub restarts. Use twenty-minute periods anchored to UTC, with preparation of the following period permitted one minute early. Retrying an attempt preserves its exact requested expiry. This supplies renewal arithmetic, not permission to renew: every period still requires fresh ownership/configuration/recovery, durable signing spend and independently audited activation. Retained active slots, history cleanup and aggregate issuance limits belong to that lifecycle, not the provider adapter. Per-period attempts have ordinals one or two; the SQL coordinator must spend them before I/O and retain uncertainty.

The private permit binds attempt ID, exact Pod/process, one leaf purpose, CSR public-key digest, enrollment-audit digest, the original configuration/recovery observations, period/ordinal and at most five seconds to sign. The provider receives only an identity-free CSR, server-assigned URI, the exact server DNS SAN when applicable, and the fixed expiry. OpenBao requires `alt_names` as a string; the first actual provider test rejected the initial array form. Preserve that failure and the corrected qualification; synthetic local verification alone did not establish the API contract.

Share the strict certificate/chain verifier with actual TLS verification without manufacturing a completed handshake. Check proof of possession, exact CSR key, identity, single EKU, validity and configured trust. Additionally verify the issued chain against the roots in the current accepted configuration, so an old constructor cannot preserve a removed anchor. Deep-copy accepted certificate bytes. Reject provider-returned private keys, malformed/oversized chains, expired proof, altered deadlines and foreign identities. Requests retain their original deadline, have bounded response size, and never automatically retry or redirect.

This adds a C-04 issuer port, C-24 pure permit/certificate values and C-21 adapters. It adds no SQL migration, public endpoint or new developer approval. Current ownership proof, protected workload/issuer bootstrap, durable signing/audit/activation/renewal and request forwarding remain required. The [issuance contract](../architecture/owner-issuance.md) distinguishes these components from a usable enrolled hub process.
