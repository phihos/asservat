# ADR-069 — Durable dispatch and retirement of download workers

Date: 2026-10-10. Status: implementation refinement of ADR-054/066/068. Components and explicit fixture qualifications precede runtime installation.

Create the acquisition Job through a durable, separately audited dispatch intent attached to the existing download session. Job scheduling can exceed a five-second disclosure lease, so dispatch has its own finite lifetime and does not pretend to be a content-read batch. Current download authority, retention and recovery are still required at reservation, launch claim and worker binding. Evidence credentials and bytes require their existing additional checks after the worker starts.

Kubernetes documents that a Job can sometimes start its program more than once even with one completion, one parallel pod and `restartPolicy: Never`. `podReplacementPolicy: Failed` delays replacement until termination but is not an exactly-once guarantee. [Kubernetes Job documentation](https://kubernetes.io/docs/concepts/workloads/controllers/job/). Therefore pin the actual first accepted Pod UID and complete spec. A replacement cannot inherit its identity or keys.

Migration 25 stores immutable intent/audit/launch/Job/Pod transitions and worker capacity separately from byte-transfer batches. Commit a single-use launch claim before the API call; a lost create reply permits exact reconciliation only. Never replay the create or adopt a different spec/UID. A new worker generation is possible only after confirmed retirement, within the original session and finite attempt budget. Initial limits are sixteen unresolved workers per installation, two per workload allocation and two per human across clients; they are bounds, not a qualified scheduler or a promise of backed CPU/memory capacity.

Use a fixed restricted download-only template with digest-pinned image, one process container, finite resources, read-only root, no automatic API token, a dedicated audience token projection and an immutable public control ConfigMap. Registry pull Secret references are optional, explicit and bounded; neither static root keys nor evidence credentials enter the template. Use a private UUID label with a manual Job selector so approved selectors do not depend on server-generated controller labels. Validate actual Job/Pod specs including admission changes; only qualified scheduler/default fields may differ.

Qualification exposed an admission conflict when `preemptionPolicy: Never` was set without a matching PriorityClass. Pin and check a dedicated class with value zero, `globalDefault: false` and `Never`, and name it in the template. Installation must provide it; runtime receives only exact named read permission. This preserves non-preempting behavior instead of inheriting a cluster's default. See [Kubernetes priority admission](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/#non-preempting-priorityclass).

Retries reuse the independently acknowledged immutable audit receipt; they do not repeat key wrapping/object writes while waiting for scheduling. Missing acknowledgement still goes through authenticated encrypted audit, and current authority is always rechecked. Reject a new reservation if intersected deadlines leave less than one second, rather than consuming capacity for an invalid zero-second Job deadline.

Retirement is a two-step journal. First observe the terminal Job and known terminated containers, then persist that proof. Delete with the exact Job UID and foreground propagation; confirm Job and selected-pod absence before releasing capacity. Persisting termination first lets a restarted reconciler recover a lost delete reply without inferring process death from a later 404. Unbound, missing or uncertain workers remain charged until a separate qualified reconciliation/fencing procedure can prove cleanup. No force-deletion shortcut.

The dispatcher introduces no developer approval or public permission surface. Protected profile acceptance/rollout fencing, capacity backing/priority scheduling, complete orphan handling, peer certificate issuance, authenticated control mediation, the actual acquisition executable and Helm/runtime composition remain separate required work. See [component contract and test boundaries](../architecture/download-worker-dispatch.md).
