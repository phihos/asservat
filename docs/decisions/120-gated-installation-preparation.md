# ADR-120: Explicit gated installation preparation and original credential binding

Status: accepted; integrated component and selected native qualification pass.
Full installation and runtime enablement remain pending.

ADR-117's continuously occupied declarative names remove the ambiguous first-POST
recovery gap for nine specific setup objects. The executable installer Pod was
explicitly excluded. Repeating a one-use launch or provider issuance remains
unsafe, but a single inert scheduling-gated Pod can have a narrower protocol.

New installations may declare the immutable
`asservat-initial-preparation-activation/v1` continuation capability. Its compiled
continuity guard protects the exact Pod key against deletion before any create.
The current namespace staging guard separately restricts creation/mutation to the
trusted installation administrator. The producer admits only the existing closed
Restricted Pod template: no assigned node, executing container/init/sidecar,
extra volume/token or caller-supplied body. Known qualified Kubernetes defaults
are normalized for comparison; the actual full returned specification is then
pinned. The recorded UID changes all retries to lookup only. Earlier identical
in-flight creates cannot replace the occupied winner.

Each actual Pod CREATE also claims one of sixteen fixed request records before
network I/O. The live owner can acknowledge only its own fully received positive
response and must join local work before reporting drain. Another observation,
cancellation or timeout never proves server-side completion. Unknown records
remain charged against this finite setup budget and keep the name occupied.
This ledger is specific to the single gated Pod; retained inert ADR-117 names do
not become a generic request-retirement engine.

This does not amend old ADR-117 roots silently. The capability changes the desired
plan digest and expected guard specification. Changing existing protection needs
an explicit requalification preserving prior root/guard identities; the new
producer does not supply that migration path.

The complete startup digest must include that actual Pod UID. Before SQL role or
private target-Secret effects, one root UID/resource-version CAS retains the exact
original private material Secret UID, complete startup digest and original
whole-second fifteen-minute credential interval. Concurrent or uncertain callers
recover the winning values; no later clock replaces them. Private material is not
a derivation seed, and public state contains no password or secret-payload hash.

The capability does not authorize launch, witness consumption, token/provider
reissuance or activation. Those remain separate one-use effects with exact
uncertain-result reconciliation. Original and final guard observations retain
all original deadlines after blocking work.

A terminal occupied Pod is an interim safety state, not a completed retirement
protocol. Supported cleanup must positively drain/fence the original request and
credential writers before deleting/reusing an identity. Missing objects, a failed
Pod, old activation success or elapsed time alone cannot prove that. This remains
required installer work; runtime and official Helm enablement stay blocked.
