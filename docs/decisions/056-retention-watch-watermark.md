# ADR-056 — Complete retention history before source availability

Status: implementation refinement under the maintainer's sustained continuation, preserving REQ-PRV-002/004. Verification results are recorded separately. No new product approval or public collection authority is introduced.

Matching final policy values and per-object resource versions does not prove that every intervening restriction was processed. A policy can be created and deleted between complete lists, leaving the same objects and values behind. Such a transient restriction must still pass through retained-evidence reconciliation.

Before accepting a fresh complete observation, require the durable watch cursor to have reached that LIST's resource version. Compare only versions of this same CRD resource, using the pinned `k8s.io/apimachinery/pkg/util/resourceversion` helper. The existing Kubernetes 1.35–1.37 qualification profile permits arbitrary-precision positive decimal ordering for the same resource; preserve original strings and never compare different resource types. Invalid versions fail closed. Older-cluster or alternate API-server profiles require separate qualification.

Kubernetes documents this guarantee in [1.35 resource versions](https://v1-35.docs.kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions); [KEP-5504](https://www.kubernetes.dev/resources/keps/5504/) explains the same-resource scope. [Watch bookmarks](https://kubernetes.io/docs/reference/using-api/api-concepts/#watch-bookmarks) prove delivery through their version, but are optional and have no guaranteed cadence. The [pinned server](https://raw.githubusercontent.com/kubernetes/apiserver/v0.37.0/pkg/storage/cacher/cache_watcher.go) attempts a bookmark two seconds before watch timeout. The qualified client uses a three-second server watch within a five-second client bound to leave time for observation renewal. This is implementation behavior, not a portable availability guarantee. A slow or missing watermark leaves the source unavailable; it cannot justify using matching final values as a fallback.

Keep at most five original LIST/guard observations, obtaining at most one per second. A bookmark confirms the freshest pending LIST whose watermark it covers; older pending input is discarded. Keeping only the first waiter can leave almost no validity at confirmation, causing avoidable availability gaps. Continuously replacing it with the newest list can instead starve catch-up. The bounded window avoids both behaviors without adding time to any observation. Expired entries and their references are discarded.

Schedule each refresh from the last actual observation's start time, retaining the minimum one-second spacing. A fixed periodic tick combined with that spacing check can miss an entire cycle when guard-call latency changes: a 120 ms initial shift reproduced a 1.88-second renewal interval. Recompute the remaining delay after maintenance and watch reconnection; elapsed work consumes the delay. Reject observed clock rollback and never restart the age of a queued LIST, guard proof or accepted observation. This scheduling correction improves timeliness but supplies no guarantee that Kubernetes will deliver a bookmark before expiry.

Neither a bookmark, retry nor lock wait refreshes an observation's original five-second lifetime. Persist bookmark cursors independently, with no new policy checkpoint, audit item or artifact scan. Data events invalidate the previous complete observation. A fresh trusted LIST with different policy state commits immediate invalidation while returning a retryable catch-up result. If final objects are unchanged but watch progress is behind, preserve only the preceding observation's original deadline. Record a nondecreasing floor from accepted or known-changing LISTs; an older delayed response cannot restore availability after a known change. An unconfirmed same-state list does not move this floor and starve earlier still-valid pending observations.


Migration 00018 stores observation sequence, finite times and the nondecreasing LIST watermark. There is no writable Ready bit. The read facet derives source readiness from current epoch/guard proof, complete history, every prior catch-up job, all checkpoint audit receipts and all linked lifecycle audit receipts. It checks time after blocking locks and before returning. Restart, suspension, recovery blocking or a new policy checkpoint invalidates availability. Full acquisition/disclosure still requires accepted source topology, selector facts and the corresponding transaction fences; a ready source alone is not an execution or read permit.
