# ADR-095 — Protected hub workload garbage collection

Date: 2026-10-11. Status: selected under continuing implementation authorization. Requirements: REQ-DEP-003/005, REQ-FED-001; part of TASK-02/11 and S-01/S-02.

## Evidence and problem

The native ADR-094 worker completes protected observation and Lease-loss shutdown, but foreground deletion leaves controller-owned objects pending. An actual request impersonating the built-in garbage-collector account is RBAC-permitted and receives the private namespace policy's exact denial on a metadata update. The existing policy permits that controller only to DELETE. Kubernetes [garbage-collector implementation](https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/controller/garbagecollector/operations.go) patches metadata to remove finalizers and manage owner references. DELETE alone cannot complete that lifecycle. After the metadata correction, the actual kubelet journal independently records denied final Pod DELETE requests. The native API also reproduces that denial for the assigned node identity. Actual failed runs and corrected qualification belong in [implementation progress](../implementation-progress.md).

## Decision

Permit UPDATE of the main resource for core Pods and apps Deployments/ReplicaSets by the exact built-in `system:serviceaccount:kube-system:generic-garbage-collector` identity, or the existing qualified shared controller-manager identity. Require both old/new workload specs to exist and remain equal; labels and annotations must also remain equal, including presence. The native API preserves immutable object identity. Finalizer and owner-reference maintenance is allowed; image, command, environment, volume, service-account, replicas and other spec changes are not. No new runtime RBAC is granted. Shared controller-manager credentials still have the existing union of qualified controller operations; dedicated garbage-collector negative tests do not prove isolation between controllers sharing one identity.

The [kubelet status manager](https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/kubelet/status/status_manager.go) removes already-deleting terminal Pods using a UID precondition. Permit only core Pod main-resource DELETE by a `system:nodes` identity whose exact username matches the stored assigned node, with an existing deletion timestamp and phase Succeeded or Failed. It cannot initiate deletion of a running Pod. Preserve native [NodeRestriction](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/#noderestriction), Node authorization and the API's immutable identity rules. The fixture must observe normal actual kubelet removal, not force-remove the API record.

This is separate from the controller's existing DELETE permission. It does not admit CREATE, subresource/exec/ephemeral-container updates, configuration, Secrets, token minting, arbitrary ServiceAccounts or other resource kinds. The hub worker itself remains unable to modify workloads. Compromised Kubernetes administrators/controllers remain outside the existing namespace-admission trust boundary; the exception is not an attestation of historical controller integrity.

The common policy remains namespaced and pinned. These narrowly gated branches additionally read `object` and `oldObject`, superseding ADR-080's request-fields-only implementation for these operations. Wildcard resource matching does not provide schema type-check coverage; do not claim empty type-check status proves those field accesses. Guard optional metadata fields with `has`, restrict kinds before accessing workload specs, and qualify the actual native requests for each supported kind plus foreign-resource and changed-spec denials. Preserve exact policy-spec/generation/UID verification and independently denied non-controller probes. Installer upgrades must synchronize the changed expected policy and pins; accepting an old mismatched policy is not a compatibility strategy.

## Qualification and boundaries

Require real foreground deletion of a running Restricted worker and its Deployment/ReplicaSet/Pod chain. Observe original object identities and normal termination; no force deletion, finalizer stripping by the fixture administrator, disabling admission or background-deletion substitution. Test the controller's metadata-only dry-run for all three supported kinds, reject changed specs and labels/annotations, and reject credential/configuration writes even when underlying RBAC permits the attempt. Require the exact admission cause rather than guessing the API reason enum from its human-readable Forbidden wording. The original scheduling and source-protection checks remain mandatory.

The final full native suite and this reference Deployment-chain case pass; source hashes, image identity and terminal cleanup are recorded in implementation progress. This qualifies only the reference Deployment chain. StatefulSet/PVC finalizers, other controllers and managed-provider variants remain separate qualifications. Production installer/restore activation and public investigation flows remain unfinished.
