# ADR-129: Original installation handover and healthy retirement

Status: implementation checkpoint. Native command/image qualification is recorded separately; this decision does not enable the Helm runtime or public evidence collection.

## Decision

A newly created preparation plan may explicitly select `asservat-initial-preparation-handover/v1`. Keep absent-field encodings and guard templates unchanged for previous plans. The new capability retains a bootstrap probe with two permanent, named RBAC objects for independent historical-read protection, bringing the declarative inventory from nine to eleven. The final activation-input inventory remains nine.

After preparation has joined its original requests, verify the original credential projection and acknowledge handover. Retire the staging policy in place by adding exactly one false match condition; its UID, name and binding remain occupied. The independently pinned final workload guard must pass before and after. Persist one original, at-most-five-second conditional gate-removal claim. A definite, independently decoded HTTP 409 resourceVersion Conflict can permit one second conditional UPDATE, only after its actual response owner durably acknowledges that negative completion. The retry receives a unique CAS claim ID and newly read resourceVersion; its exact original UID, specification, operation ID and deadline do not change. At most two conditional requests are possible. Unknown transport/server/cancellation outcomes, malformed or unrelated 409 responses and responses after the original deadline permit exact original lookup only. No replacement Pod, fresh claim, credential renewal or restart follows a missing or failed launch.

A separate installation-owned SQL login has only schema USAGE and SELECT on `goose_db_version` and `fleet_initial_activation`. The protected plan independently pins `historyManager.name` and `historyManager.oid` before any preparation effects. PostgreSQL grants a non-superuser role creator administrative membership through the bootstrap superuser; that creator cannot remove this grant. The original no-membership design was infeasible and is superseded by an exact check of this single incoming grant: the pinned original manager, bootstrap grantor OID10, ADMIN true, INHERIT false and SET false. Reject every outgoing history membership and every other incoming grant, option or privilege. A renamed/recreated manager cannot be adopted.

The manager remains trusted SQL administration: ADMIN permits deliberate re-granting of access, so false SET/INHERIT flags prevent accidental access rather than malicious administration. The passive reader receives only its separate credential, verifies the original manager identity and narrow role on current reads, and never opens maintenance credentials. Disabling the manager's LOGIN/CREATEROLE does not change that identity or prevent passive reads. Rotation or retirement of this retained history login belongs to trusted SQL administration. Its fixed `sql-history.json` never enters the activation Pod. Older non-handover encodings remain unchanged; unresolved handover roots lacking the independently pinned manager require explicit reconciliation, never automatic pin adoption.

The supervisor observes both the exact original, successfully terminated Pod and the independently verified original SQL activation/audit record. It then performs eight fixed cleanup steps: revoke temporary SQL rights, revoke wrap and unwrap children, delete the token-bound probe Secret and observe original-token rejection, remove the two target credential Secrets, retire setup RBAC, clear private progress irreversibly in place, and remove the original Pod. Preserve the minimal history RBAC pair. Acknowledgements retain only original public identities and times. Supplied external S3 credentials remain externally managed.

Only newly selected handover plans can retain original Secret CREATE completion. A positive response from the actual CREATE is distinct from an exact GET or another invocation's collision. Original uncertain requests cannot gain completion by observation. The same joined local owner may persist its retained positive result; legacy state cannot acquire that proof retroactively.

## Consequences

The new supervisor has a finite three-minute process budget; legacy preparation retains its one-minute budget. Every current guard/effect lease remains at most five seconds, and every SQL/provider/probe credential keeps its original lifetime. Kubernetes terminal timestamps are observed at their documented whole-second serialization precision; this does not round or extend authority deadlines.

An already completed invocation can reopen history using current protected bootstrap credentials and the retained SELECT-only login, without reopening expired setup credentials or depending on the deleted Pod. Historical activation never establishes current recovery readiness.

Uncertain original writes and launches remain explicit unresolved states. A known terminal failed activation cannot become a replacement attempt. Existing-record adoption, reconciliation after a database restart/restore, expired issuer retirement and deployment packaging remain required follow-up work; this healthy completion path is not a generic recovery protocol.

See [the implementation contract](../architecture/initial-activation-handover.md), [ADR-120](120-gated-installation-preparation.md), and [ADR-128](128-initial-provider-provisioning.md). Kubernetes [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) and [object names/UIDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) provide platform semantics; production qualification remains necessary. The pinned `metav1.Time` serializer uses RFC3339 without subseconds; time comparisons preserve this observation precision explicitly.

The selected real PostgreSQL diagnostic confirmed one exact bootstrap-superuser creator grant before and after the creator's REVOKE, which completed without removing it. The unchanged production verifier then rejected that retained grant. This measured failure and [PostgreSQL18 role attributes](https://www.postgresql.org/docs/18/role-attributes.html), [membership catalogue](https://www.postgresql.org/docs/18/catalog-pg-auth-members.html) and [bootstrap identity definition](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/include/catalog/pg_authid.dat) establish the correction's basis. Passing corrected native qualification is recorded separately.
