# ADR-131: Produce original installation pins from trusted static inputs

Status: accepted implementation direction; native qualification and packaging remain pending.

The official installation flow must not ask administrators to hand-author Kubernetes UIDs, SQL role OIDs or private random passwords. The existing preparation and schema commands correctly require those independent pins, but their native fixtures have supplied them manually.

Use a bounded trusted producer before those commands. Its initial trust entry is an explicitly selected administrator-controlled bootstrap namespace and separately supplied Kubernetes/SQL/provider credentials. This does not establish historical namespace cleanliness. The producer creates the finite public observation account/RBAC/markers and token anchor, then installs and independently tests its exact native admission guard before private state or SQL/provider effects. That guard does not authorize its own prerequisite creation.

A create-only private seed chooses the original installation/request/cluster/issuer IDs and distinct random SQL passwords. Fixed ordered create intents retain original object UIDs/resourceVersions. Only the positively acknowledged first intent may issue its one CREATE; uncertain replies and reopen perform exact lookup only. The producer generates the existing protected `InitialPreparer` projection, including ADR-130's explicit schema capability. Native admission readiness is checked before claiming the final projection CREATE.

A distinct trusted SQL-administrator facet creates the finite nonsuperuser setup manager, with original 30-minute LOGIN/CREATEROLE interval, client-derived SCRAM verifier and a content-minimized provenance comment. A current matching name alone is not creation provenance. Unknown SQL outcomes recover the original role/password/attributes/comment/OID; no reset, adoption, new attempt or extended interval follows. The manager later receives only the existing compiled three-facet grant union from the separate schema command.

After independently checked complete original handover, joined preparation and a fresh exact SQL activation/history observation, trusted cleanup disables manager login/role creation, revokes its exact grant union and terminates its original authenticated sessions. Flags alone cannot close existing connections. The original 30-second cleanup claim cannot renew. Final acknowledgement requires measured zero sessions and rejection of the original login; unknown completion uses exact-state lookup.

Preserve passive history access while removing its manager-origin grant dependency: within the same transaction, verify its exact three non-grantable privileges and actual object owners, grant the same rights from those owners, remove only the original manager-origin copies using the pinned role, and use RESTRICT for manager revocation. No CASCADE or blanket privilege removal. The original manager identity and exact creator ADMIN provenance remain for history verification. PostgreSQL's [REVOKE semantics](https://www.postgresql.org/docs/18/sql-revoke.html) explain the dependent-grant requirement; real-service qualification remains separate from this design.

Completed whole-install replay selects protected passive history before opening any DDL, manager or provider credentials. Interrupted schema-complete preparation uses the original embedded bundle/history/database-incarnation verifier, also enforced at the direct initial-prepare/activation boundaries. A journal completion is not new recovery or restore authority.

The current component does not enable Helm runtime, mount a public interface, or claim final managed credential-copy deletion. Asservat-created SQL/provider source Secrets need a separately qualified exact final-delete transition with positive reader/writer/credential closure and permanently occupied names. Operator-owned originals and upstream credential ownership remain untouched. See the [implementation contract](../architecture/initial-bootstrap.md).
