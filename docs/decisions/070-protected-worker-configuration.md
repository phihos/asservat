# ADR-070 — Protected worker configuration and rollout fencing

Date: 2026-10-10. Status: implemented component refinement of ADR-069; scoped Kubernetes/SQL/S3 qualification passed, production runtime remains pending.

A constructor-supplied worker profile is insufficient authority to schedule or attest an acquisition worker. Resolve it from an independently pinned administrator ConfigMap in the protected worker namespace, with a closed `worker-profile.json` payload. Pin installation, cluster, namespace and ConfigMap UID; qualify the exact native admission policy and binding before accepting its content. Administrator usernames/groups are bootstrap trust, never fields inside the profile itself.

The guard checks exact policy/binding identities, specifications and successful type checking, then uses a separate non-administrator probe identity. That identity must have Kubernetes RBAC for the exact ConfigMap UPDATE; a dry-run resubmission must be denied by the exact expected admission policy. Ordinary RBAC denial cannot stand in for this evidence. No probe writes a real configuration. Read the profile twice inside the original five-second window and recheck protection. Deletion, same-name replacement, changed protection or unavailable APIs deny observation.

Migration 26 persists monotonically accepted revisions and original observation deadlines. An independently credentialed audit role must acknowledge a matching encrypted immutable snapshot before use. A new staged revision immediately supersedes the previous head, even while its audit is pending; no fallback to an older audited revision. Refreshing the identical revision does not create another audit record or invoke encryption. Suspended settings deny work. Recovery blocking and source expiry remain independent fences.

Dispatch, binding and identity lookup check the current audited revision. The Kubernetes Job driver also requires the current configuration before creating or observing a worker. Historical accounting and proven cleanup remain possible after suspension or rollout: revoking authority must not prevent retirement. Existing immutable dispatch records cannot be rewritten to inherit a new image/configuration. An already issued worker proof keeps only its original deadline, capped by the configuration observation, so configuration changes have a bounded five-second exposure window rather than an instantaneous distributed revocation promise.

The initial rollout policy interrupts old-profile downloads: a changed revision requires a newly admitted worker after confirmed retirement. It cannot refill counters or extend the download/evidence deadline. Graceful concurrent profile draining is not implied. This conservative first implementation needs a visible interrupted/retry status in the eventual runtime, not manual developer configuration. The chart/installer will resolve object UIDs and hashes; hand-written developer profile JSON is not a product workflow.

Configuration history is capped at 1024 immutable revisions per enrolled source; observations reuse the existing revision. Safe history cleanup and its backup obligations remain required. Protected bootstrap of the administrator/policy pins, actual acquisition executable/issuer, continuous runtime supervision and Helm composition remain unfinished. The native guard and transactional projection establish these particular boundaries without claiming a deployed investigation platform.
