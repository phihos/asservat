# ADR-094 — Native hub-worker credentials and workload

Date: 2026-10-11. Status: selected under continuing implementation authorization. Requirements: REQ-DEP-003/005, REQ-FED-001, REQ-DB-005; part of TASK-02/07/11 and S-01/S-02.

## Problem

ADR-091 provides a runnable configuration worker but its native-service fixture runs outside Kubernetes, using three manually issued Kubernetes tokens. Projecting different ServiceAccount identities into one Pod is not supported by the native token volume. All three credentials were already accessible to the same process, so their separate files did not isolate effective process privilege. Requiring operators to manage those tokens would add rotation work and an unnecessary credential broker.

## Decision

Use one narrowly scoped Kubernetes ServiceAccount per private process role and kubelet-managed Pod-bound API token projections. Retain independent client facets and their existing fixed token paths. For the configuration worker, the account receives the union of its existing namespace/source-policy reads, named source ConfigMap get/update probes, and named scheduling Lease get/update. It receives no administrator membership, Secret reads, token minting, workload writes, wildcard access or Lease creation/deletion. SQL roles and audit key credentials remain separate. The source probe must still be a non-administrator, pass the real RBAC check and receive the exact source-policy dry-run denial. Namespace protection admits only the explicitly listed nonpersistent probes and named scheduling updates under ADR-092/093.

[Kubernetes ServiceAccount projections](https://kubernetes.io/docs/concepts/storage/projected-volumes/#serviceaccounttoken) use the Pod's ServiceAccount and permit an audience and expiration request. API tokens use the server's default API audience; future owner enrollment retains its separate dedicated audience and never uses that token for API calls. Request 600-second token lifetimes and reopen the projected files for actual HTTP requests. Do not use subPath mounts or copy tokens into Secrets. [ServiceAccount documentation](https://kubernetes.io/docs/concepts/security/service-accounts/) describes the kubelet-managed short-lived credential mechanism. Scheduled native renewal is a separate measured qualification, not implied by short fixture runs or synthetic file replacement tests.

`BuildHubWorkerWorkload` is an installation-owned C-21 native-object builder. It returns a zero-replica Deployment, ServiceAccount and named RBAC objects. Cluster-scoped role names encode namespace and workload with unambiguous separators. The source ConfigMaps must differ from each other and from the immutable deployment-input ConfigMap. This prevents a source-probe permission from becoming write scope over process configuration. The image is digest-pinned. A non-root Restricted Pod runs only `/asservat hub-worker`, with a read-only root, all capabilities dropped, seccomp RuntimeDefault, finite CPU/memory and a read-only 0440 projected input directory. The process has no public listener or extra credential volume. Source observation remains independent of Kubernetes Pod readiness.

Only `deployment.json` is selected from the configuration projection. Exactly the six existing SQL/audit credential files are selected from the provider Secret. The three API token files are kubelet projections, not stored credentials. The caller must provision protected immutable startup inputs and separate current source documents; generating these objects neither proves clean installation nor activates recovery. Explicit installation sequencing protects the namespace before credentials and launches the Deployment only after prerequisites. An application deployment or developer capture never controls this plan.

## Verification and remaining work

Unit tests cover rejected aliases/mutable images/invalid names, inert startup, token and secret projections, Restricted settings, exact privilege sets, binding scope and object independence. The context harness builds a local scratch image from the current source and records binary SHA-256, Docker image identity and the loaded containerd manifest reference. It never publishes the image. Hash collection begins before compilation and must match after tests. Only its owned Kind node and a synthetic TLS bridge container join its owned internal fixture network. The bridge has no published host ports; native test Pods use verified TLS to that container, while fixture backend hops remain private HTTP/PostgreSQL. A separate recorded probe showed container-to-host-gateway TCP timeout on this workstation; the fixture does not modify its firewall. The local test image also contains the standalone fixture bridge executable; this is not a release image or a production bridge component. This is not production provider topology qualification.

The final in-Pod case passes within the full context suite recorded in implementation progress. It uses the actual role executable and generated resources, preserves initial blocked recovery, permits only one explicit fixture recovery transition, and checks automatic encrypted configuration acceptance, source-protection removal and original Lease loss. The outside-Pod case remains independently covered. Actual results and failures are recorded in [implementation progress](../implementation-progress.md); a compiled or generated template alone is not native execution evidence.

The official chart remains configuration-only. Production installer orchestration, independent initial/recovery/restore acceptance, owner in-Pod enrollment/routing, whole-hub health, timed native token renewal and public investigation/download flows remain unfinished. No database migration, new dependency, public API, developer approval or complete task/slice exit follows from this change.
