# ADR-335 — Usable by default

Date: 2026-11-14. Status: accepted (maintainer: operator and user friction must
be found and removed without being asked; resolves
[the friction audit](../reviews/friction-audit-2026-11-14.md)). Supersedes every
earlier ADR, specification or chart default that contradicts the decisions
below. ADR-334 (connector workload identity) and ADR-332 (standing connector
identity) cover the multi-cluster items.

The product capabilities and maintainer decisions in AGENTS.md "Authority and
invariants" stay; four are honoured with less friction (D5–D8).

## Decisions

### D1 A default install works

`helm install` with no values beyond the hostname and an identity provider
yields a working single-cluster installation: capture enabled, node collector
enabled where its namespace is allowed, approvals possible, sign-in working on
the first pass. No manual SQL calls (`initialize_processing` runs in setup), no
undocumented ConfigMaps, no second install pass.

### D2 Capacity without arithmetic

Capacity is described by a few operator-facing values with defaults derived
from the cluster: evidence storage size, retention, per-workload share and
concurrency. Byte, WAL, row and footprint figures are internal estimates, not
values. Changes apply on `helm upgrade`.

### D3 Nothing is fixed at first install

Every value can change on `helm upgrade` and takes effect without reinstall:
Keycloak hostname/realm/redirects (the realm is reconciled), capacity, retention,
connector counts (none exist, ADR-332), namespace keys. Write-once storage of
configuration is removed; generated secrets stay stable but are never compared
against values.

### D4 Names, not UUIDs

Operators and users refer to clusters, namespaces, workloads, recipes, groups
and people by name. Cluster IDs are generated by the hub from the cluster name;
recipes are referenced by name (the hub records the digest); the standard OIDC
`groups` claim is used by name; a binding narrowed to a workload names it, so a
recreated Deployment keeps its access. UIDs and digests remain provenance.
The console and MCP offer search/pickers for users, groups, workloads and
recipes.

### D5 One independent approval, only where the maintainer asked for it

Manual intrusive collection needs one independent approval (maintainer
decision). No second person is needed for:
evidence collected by an already reviewed policy; reads and downloads by a user
who holds the equivalent Kubernetes right on that workload (for example
`pods/exec` for raw packets or cores, `pods/portforward`/`proxy` for profiles);
read-only diagnostics such as a pprof GET. Step-up re-authentication is
optional and off by default. An approval covers its stated window, not a
5-minute submit deadline: the approved request is submitted by the approval
itself.

### D6 Expiring grants only for automatic intrusive actions

Automatic intrusive actions keep expiring grants (maintainer decision), with
administrator-configured periods (default 90 days), renewal in place, and
idempotent re-apply of unchanged YAML. Non-intrusive policies do not expire and
have no run count. Always-on recorders are bounded by rates and ring sizes, not
lifetime byte budgets.

### D7 Retention the administrator controls, with usable defaults

The administrator-enforced maximum stays (maintainer decision). Defaults:
evidence 14 days, cores 14 days, shares until the evidence's retention ends
(no separate 7-day cap), recurring sharing without weekly renewal.

### D8 Storm protection with usable limits

Rate and concurrency limits stay (maintainer decision), defaulting from cluster
size: concurrent captures per cluster at least 8, policies unlimited (bounded by
Kubernetes object limits), sessions unlimited (bounded by rate limits),
post-trigger windows up to the capture's configured duration (minutes).

### D9 Human timescales

Human-facing waits are minutes to days, never seconds: downloads run to their
original bounds regardless of access-token expiry (session-bound, ADR-312) and
have no request-count cap; previews and approvals stay valid while unchanged
(stateless previews, ADR-330 D9); live watches stay open while the client is
connected or within a 10-minute idle window; result handles last as long as the
evidence.

### D10 Backups and restore are documented and complete

Backups go off-cluster (pgBackRest S3/repo targets, object-store replication or
Velero for SeaweedFS, OpenBao snapshots, Keycloak realm export); a `restore`
procedure with a Helm value and runbook exists and is tested.

### D11 External services with standard setup

OpenBao is optional (static keys from a Kubernetes Secret per ADR-063 cover
every purpose); an external OpenBao needs one policy and one role created by the
setup Job when given an admin token once, or documented in a single snippet. An
external object store needs one credential with one bucket/prefix. External
PostgreSQL needs one login per process with a pool size the chart sets (default
total ≤ 30).

### D12 Standard TLS trust

Connections to public endpoints use the system trust store; CA bundles are
optional.

### D13 No downtime on upgrade

hub-api uses RollingUpdate with at least two replicas available; hub-worker
uses leader election with a standby replica.

### D14 One access model

Administrators are one Helm-listed group (or subjects); everyone else gets
access through AccessBindings or PermissionSources. `processingOperators`,
`fleet.groups`, eligibility lists and similar parallel lists collapse into that
model. A cluster-wide AccessBinding (`ClusterAccessBinding`) exists like a
ClusterRoleBinding. Team policies live in the team's namespace.

### D15 Everything a capture needs can be triggered

Every recipe kind (packets, syscalls, profiles, dumps, logs, pod status) can be
triggered by a policy, within its lifecycle (ADR-action-lifecycle).

### D16 Examples and CRDs are shipped and valid

Every example validates against the spec and the shipped CRDs; the chart ships
every CRD an example uses. The values schema refuses settings that would crash
a component.

### D17 Debugger-ready downloads

A core download offers one bundle (core, executable, available debug files, a
gdb/dlv script) with meaningful file names (`<workload>-<pod>-<time>.core`).

## Consequences

The specification and chart are revised to these decisions first; the code
follows in slices tracked in docs/implementation-progress.md, starting with D1
(the defaults that block everything).
