# ADR-168 — Rotating cluster enrollment credential with outbound-only connectivity

Date: 2026-10-14. Status: accepted by the maintainer; design recorded here,
implementation pending. Requirements: REQ-FED-001 and REQ-FED-002; existing
SC-FED-001 and TASK-03 / TASK-11 retain traceability ownership.

## Context

[ADR-126](126-connector-process-identity-and-renewal.md) requires ordinary Pod and
container restarts to obtain a fresh connector process identity without
administrator reenrollment. Process-owned P-256 keys are deliberately in memory and
disappear on restart. The legacy one-use bootstrap credential expires after five
minutes and yields a client-only leaf; it cannot provide indefinite restart
identity. REQ-FED-001 keeps connectivity outbound-only: the hub stores no workload
cluster kubeconfig and does not call that cluster's API.

ADR-126 and [ADR-153](153-operation-owned-connector-enrollment.md) prove the Pod,
token and controller chain through reads that run in the workload cluster. In
the outbound topology, the hub receives that only as a **delegated regional proof**.
Without a cluster-held credential, it has no way to tell that proof came from that
cluster's protected connector rather than from any client that learned its UUIDs.

The maintainer chose between (a) a narrowly scoped, automatically rotated
enrollment credential in a protected Secret in each workload cluster, and
(b) hub access to each cluster's Kubernetes API for online TokenReview. They
selected (a). Offline hub validation of a Pod token was rejected: it cannot
establish live Pod/deletion protection. This also supersedes an earlier staged
proposal, never implemented, to tunnel hub-side Kubernetes API requests through
the connector's outbound stream; that would have been option (b) in another form.
SPIRE's agent key manager and Kubernetes kubelet certificate rotation separate a
long-lived node/bootstrap identity from short-lived process credentials. They are
cited only for that distinction ([SPIRE memory key manager](https://github.com/spiffe/spire/blob/main/doc/plugin_agent_keymanager_memory.md),
[SPIRE agent](https://github.com/spiffe/spire/blob/main/doc/spire_agent.md),
[kubelet rotation](https://kubernetes.io/docs/tasks/tls/certificate-rotation/)).
They do not establish a lifetime.

## Decision

### Credential and scope

Each enrolled connector profile (installation, cluster UUID, connector peer
account) has one **cluster enrollment key**: an Ed25519 key pair generated by the
connector. The private key exists only in one protected Kubernetes Secret in the
connector's own namespace, and in the connector process's memory while it is used.
The hub's SQL retains the public key, its SHA-256 digest, a monotonic generation
and original validity dates. A public key is not a reusable bearer, and the hub
never receives the private key.

The key authorizes exactly one thing: requesting connector **process admission and
leaf renewal** for that exact profile under ADR-126/153. It is not evidence access,
workload authority, key-service or raw-unwrap authority, or administrator,
enrollment or fleet authority. It never authorizes another cluster or profile. It
is distinct from process-owned keys, from issued leaves and from the legacy
bootstrap credential.

### Possession proof

A connector process presents the proof over the existing server-authenticated
TLS 1.3 channel to its pinned hub roots. It signs one canonical request with
purpose `asservat-cluster-enrollment/v1`. The signed request binds:

- installation, cluster and peer IDs, and the key generation;
- process epoch and Pod UID;
- both CSR public-key digests and the operation purpose;
- the request time;
- a 32-byte TLS exporter value for this connection (RFC 5705/8446 exporter, label
  `EXPORTER-Asservat-Cluster-Enrollment-v1`, matching the existing
  `EXPORTER-Asservat-…-vN` convention).

The exporter binding prevents replay on another connection or relay through
another server. The hub rejects request times more than 30 seconds from its own
clock, unknown or superseded generations, revoked or expired keys, profile
mismatches and any signature failure. The proof is checked first. Then the
existing delegated regional proof, recovery, source, slot, signing-spend, audit
and original-deadline rules of ADR-126/153 apply unchanged. Possession alone
admits nothing.

### Lifetime and rotation

Two separately configurable bounds apply, installation-wide with per-profile
overrides only shorter:

- **Validity**: default 7 days, allowed 1 hour to 30 days. This is the longest
  continuous period during which a connector can be down, or cut off from the hub,
  and still recover without an administrator. Seven days covers an extended
  weekend or holiday outage of either side. A longer value only widens the window
  in which an unrotated copy stays usable.
- **Rotation interval**: default 24 hours; it must be at most one third of
  validity. This bounds passive theft. Once the legitimate connector rotates, a
  copied old key stops working after the overlap below. A copy therefore survives
  for at most about one rotation interval, not the whole validity. The one-third
  rule leaves two missed rotation attempts before expiry.

These defaults are a justified design choice, not a measured qualification.
Operators can shorten them; lengthening beyond 30 days is rejected.

Rotation is an idempotent two-phase protocol:

1. The connector generates the next key pair. It first persists it into the
   Secret as `pending` with a resourceVersion compare-and-swap. A pending key
   already present is always reused; there is never a second pending key.
2. It sends `rotate(current generation → pending public key)`, signed by the
   *current* key and exporter-bound. The hub atomically inserts generation N+1,
   marks N superseded and records the transition. Repeating the exact same
   request returns the original result.
3. After an acknowledged reply, the connector compare-and-swaps the Secret so
   that pending becomes current. An uncertain reply leaves `pending` in place;
   the exact same rotation is repeated. Generation N remains acceptable only for
   that exact replay, until N+1 is first used or expires. An earlier draft also
   capped replay at 10 minutes. That was removed during implementation: it would
   fence a connector that crashed after an unacknowledged rotation and stayed
   down longer, while adding no protection. Exact replay requires the pending
   key, which sits in the same Secret as the current one.

If the hub sees generation N used to rotate to a *different* key, or a superseded
generation used outside exact replay, it records a **fork**. It fences the
profile's credential: no admission, renewal or rotation until an administrator
reenrolls the cluster. Two lineages from one key mean the key was copied.
Existing leaves are not extended and expire within their original ≤30-minute
periods.

### Revocation, expiry and restart

An administrator can revoke a profile's credential through the protected fleet
administration path; the revocation is audited. Revocation denies every later
admission, renewal and rotation for that profile. Rotation cannot undo it.
Already issued leaves are not extended.

An expired credential stops automatic recovery. The cluster keeps its logical
identity. An administrator reenrolls it through the existing audited bootstrap
issuance, which installs a new generation-1 lineage. Old generations never
revive.

A restarted connector container or new Pod reads the Secret through the API: get
and update on exactly one named Secret, granted to the connector account by
resource name. It completes any pending rotation first, then proves possession
for a new process epoch. Pod Security Restricted is unchanged.

### Persistence and audit

Credential issuance, rotation, fork and revocation records use the existing
encrypted private audit protocol (conditional create, verified read, independent
acknowledgement), with no private key material in SQL, audit or logs. The SQL
change is **migration 00060**. Embedded migrations must be contiguous from 1 to
the pinned head, so the planning reservation of 00060 for the still unimplemented
streaming custody moves to 00061.
It uses separate roles for proof verification (read), rotation (append/supersede)
and revocation (administrator); none can issue leaves directly.

## Consequences

A stolen Secret lets its holder impersonate that one cluster's connector for
admission until the next legitimate rotation. Active misuse is detected as a fork
and fences the profile. It never grants evidence access, because ADR-126/153
proof, recovery and authorization checks still apply. Clusters remain
outbound-only. The hub's API surface grows by one rotation operation on the
existing private enrollment listener.

## Implementation status

Implemented components:

- **Domain** (`internal/domain/fleet/cluster_credential.go`): profile, policy
  bounds, request validity and a pure decision (accept, rotate, exact replay,
  fork) from a verified-signature flag, the successor digest and the database
  clock.
- **Application** (`internal/application/fleet`): canonical exporter-bound
  message, Ed25519 sign/verify, `ClusterCredentialVerifier`, and the
  connector-side `ClusterCredentialRotator`. The rotator persists the pending key
  before any request, repeats only the exact rotation after an uncertain reply or
  crash, and refuses admission signing while a rotation is pending.
- **SQL** (migration 00060, `postgres.ClusterCredentials`): lineage and credential
  tables with append-only guard triggers, one current lineage per profile, a
  fork fence committed before the denial, revocation, and reenrollment.
- **Transport** (`transport/clustercredential`, `mtls.ClusterCredentialClient`):
  one exporter-bound POST per TLS 1.3 connection, with no reuse, redirect or
  retry. Status 409 is the permanent fence.
- **Secret store** (`kubernetes.ClusterCredentialSecret`): a single installer-pinned
  Secret with resourceVersion compare-and-swap.

Verification: domain/application/transport/Secret component tests, plus the
real-PostgreSQL qualification inside `connector-identity-fast`
(`test/results/adr168-cluster-credential-sql-1`, `-2`): enroll, admission,
rotation, replay, fork fence, append-only guard, reenrollment and revocation.

## Remaining work

- Encrypted audit records for issuance, rotation, fork and revocation.
- Hub private-listener composition, and consumption of a presentation by the
  ADR-126/153 admission path.
- The installer step that creates the Secret and enrolls generation 1 under
  audited bootstrap.
- Helm/RBAC resources (get/update on one Secret name).
- Installed two-cluster native qualification, including restart and exporter
  relay attempts.
- Remaining hub-to-regional API dependencies: download-worker peer proofs
  (`WorkerAPIs`) are fenced to the hub cluster and migrate to delegated
  regional proofs under [ADR-178](178-delegated-connector-source-on-context-start.md).

No runtime path selects these components yet.
