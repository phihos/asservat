# ADR-067 — Protected local key source and bounded lifecycle observations

Date: 2026-10-10. Status: implementation refinement of accepted ADR-063/064/065. Components implemented; integration qualification and runtime/installer remain separate.

An immutable crypto backend alone does not establish current permission to use its root keys. Require its service backend to implement `KeyConfigurationGuard`, checked after operation authority resolution and again after cryptography. Intersect the original operation deadline with the original configuration deadline; a second check cannot renew either. The handler refuses a backend without this guard. Raw crypto constructors remain internal implementation/fixture building blocks, not eligible service backends.

Read a separately pinned, administrator-protected ConfigMap with closed `asservat-local-key-configuration/v1` data. It names one immutable Opaque Secret by name, UID and SHA-256. Namespace/ConfigMap identities, scope, recovery epoch, exact Secret identity/digest and a second configuration read must match. Service credentials get only named reads, never Secret list or writes. Neither a successful GET nor this adapter proves the source's administrator protection; deployment admission/RBAC and initial source enrollment still require qualification.

A bounded public observation may be reused inside one service instance for at most five seconds, measured from the start of its original read. Cache hits never renew it. Coalesce concurrent refreshes; retain no separately cached plaintext Secret. Every crypto operation still checks durable SQL history before and after the effect. An accepted newer snapshot fences old instances across replicas; unobserved source deletion/suspension is detected within the remaining observation lifetime. Source failures after expiry deny access. No disconnected grace period or regenerated keys.

Migration 23 records public configuration snapshots and immutable version fingerprints. The private lifecycle facet checks current installation recovery under the existing fleet lock, then serializes scope transitions and checks freshness again after blocking locks. It rejects source substitution, accepted revision rollback, different content at the same revision, active-version rollback, version material changes and material reuse across purposes/key IDs. First acceptance requires separately pinned source identity and live recovery; it is not public registration. The current transition supports additive rotation only. Removal is refused until a retirement operation can prove all retained-data and recovery obligations permit it; maximum sixteen versions is a recovery/rotation planning ceiling, not automatic pruning.

A fresh immutable backend loads the accepted active version; its historical keys read retained evidence. The old backend never mutates or silently reloads. Reconfiguration/peer issuance, encrypted key-administration audit, source bootstrap/backup/recovery, retirement and runnable service/Helm composition remain unfinished. No collector, hub or acquisition process receives a static root. [Lifecycle contract](../architecture/local-key-lifecycle.md) gives implemented scope and test boundaries.
