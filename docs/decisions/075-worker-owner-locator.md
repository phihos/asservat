# ADR-075 — Shared worker request locator

Date: 2026-10-10. Status: implemented component refinement; focused SQL/race tests, full SQL/S3 regression and Kubernetes/OpenBao regression pass. Authenticated process discovery and network forwarding remain pending.

ADR-074 provides local request ownership but another hub replica cannot locate that process. Keep credentials in the authenticated owner and store only a short-lived locator in the existing primary PostgreSQL database. Do not add a broker, sticky client sessions, durable personal credentials or caller-selected endpoint addresses.

Migration 28 adds one current locator row per admitted worker: request UUID, hub Pod UID, process-start epoch, monotonically increasing fence, start/expiry and optional release time. Installation, session and scope remain in the existing parent records. A claim requires current human/download/recovery/configuration checks and the exact admitted worker; it lasts at most thirty seconds within the original request, worker, session and access deadlines. Reconciliation returns the same fence and deadline. A fresh request can replace only a released or expired owner; process restart never silently resumes another process's authenticated operation.

Serialize claims in the existing recovery/permission/session lock order, then worker and locator. Recheck current time and authority after blocking locks. PostgreSQL [row locking](https://www.postgresql.org/docs/current/explicit-locking.html) supplies mutual exclusion; Asservat supplies scope, deadline and transition validation. A [row trigger](https://www.postgresql.org/docs/current/plpgsql-trigger.html) additionally refuses lease mutation, revival and takeover of an active fence. Direct SQL tests must establish these behaviors for the chosen runtime roles.

Register the local owner before publishing its locator. Close it if publication fails. A lost SQL reply leaves an uncertain locator bounded by its original expiry, never a guessed release or deadline extension. Explicit owner cleanup closes local work first and releases only its exact SQL fence through a bounded cancellation-independent cleanup call. No background retry queue is introduced. Lookup is metadata only and grants no certificate, evidence, worker-capacity refund or automatic takeover.

The exact-owner receiver facet checks the shared locator and exact local handle before enrollment, then rechecks the locator before returning a delivery. The operation's existing current human, Pod, audit and activation checks remain mandatory. No artifact bytes, credentials, tokens or endpoint URLs are stored here. One row follows each worker's existing minimized lifecycle record; its eventual metadata cleanup remains tied to that parent, not to evidence-copy deletion or a new indefinite retention policy.

Authenticated process discovery, hub-to-hub mTLS forwarding and connector proof mediation remain required before this becomes a network rendezvous. The locator alone does not attest a Pod/process, qualify HA failover or enable public downloads. See [the implementation contract](../architecture/worker-owner-locator.md) and [actual results](../implementation-progress.md).
