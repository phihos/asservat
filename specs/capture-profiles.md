# Reusable capture profiles

A capture profile is a versioned, parameterized building block containing ordinary evidence actions. It is distinct from a runtime CPU/heap **profile artifact** and from an operator's engine/security profile. Users select several capture profiles, adapt exposed settings, preview the combined plan, and collect or enable a policy. This is a first-release requirement; implementation and qualification remain pending.

The fixed `pod-status/v1` preset described in [ergonomics](ergonomics.md) is selected through `preset_ref`, not `{catalog: builtin, name: pod-status, version: v1}`. It creates no `CaptureProfile` resource or profile source UID and has no typed-edit/composition contract. Do not synthesize a profile reference or composition provenance for it. A future composable profile containing that action requires an independently published, immutable definition under these existing catalog rules.

## REQ-CPR-001 — Shipped, organization and namespace catalogs

Introduce the namespaced `CaptureProfile` configuration CRD. Its definition contains a name/version, display name, description, a complete bounded expanded recipe and an explicit list of editable fields. Definitions are data, never scripts, arbitrary BPF, shell templates, plugins or remote include URLs. Existing typed actions and endpoint/engine qualification remain authoritative. Shipped definitions are installed from the release's offline bundle in a protected builtin-catalog namespace; organization definitions live in a protected hub catalog namespace; namespace definitions live in the target workload namespace. These locations are installation configuration, not caller-controlled search paths.

The reference `(catalog: builtin|organization|namespace, name, version)` has no implicit precedence or shadowing. Namespace lookup is confined to the selected workload cluster/namespace. The resolver binds source cluster, namespace/profile UIDs, immutable definition digest and dependencies. A resource claiming a builtin name in a workload namespace cannot impersonate the shipped profile. Publication/read permissions are enforced through Kubernetes RBAC, authenticated submission and existing source trust, with current target eligibility. Catalog visibility does not grant collection authority, node privileges, action approval or secret access.

The definition digest is SHA-256 of the canonical JSON object `{name, version, definition}` using the execution canonicalization rules; it excludes mutable availability and Kubernetes metadata. The identity and definition are immutable after publication; editing creates a new version. Separate availability fields allow administrators/authorized publishers to disable or deprecate a version without changing its definition digest. Deprecated versions remain pinned and visibly discouraged; disabled/deleted versions cannot authorize new starts through stale caches or history. Never switch to `latest` automatically. Existing work follows current emergency deny and short-permit rules. Publisher status must distinguish accepted, catalog-visible and propagated to relevant clusters. No per-workload installation step is needed for shipped/organization profiles.

Administrators publish through Kubernetes/GitOps and the browser's authenticated Kubernetes authoring path. Authorized maintainers can save a derived namespace profile through the same path, without a hub kubeconfig or a global publisher role. Derived profiles materialize the fully expanded reviewed recipe and an explicit set of editable fields into their own version. Retain up to eight non-executable `definition.origins` source identity/digest records for attribution (included in definition immutability, never treated as authority), but do not nest executable profile references inside definitions. This avoids recursive resolution and cycles. Original publisher grants/identity are never inherited. Disabling a source catalog entry does not ban an independently authored equivalent action; use collection ceilings or engine/pack disablement for that prohibition.

Catalog definitions cannot contain resolved credentials or captured evidence. Endpoint credential references remain confined to current target scope. Discovery-derived personal values retain their provenance/deadline in drafts; saving a reusable definition must pass the existing configuration/privacy admission rules, rather than turning samples into indefinitely retained Kubernetes data. Publication does not fetch URLs, install binaries, enable profilers or run a sample capture.

### SC-CPR-001

Given a builtin and namespace profile share a display name, when a maintainer selects the builtin reference, then the namespace object cannot replace it. A namespace maintainer can save a derived local version but cannot publish organization-wide or mutate a published definition. Disabling a pinned version blocks new captures instead of selecting a newer version.

## REQ-CPR-002 — Typed adaptation without a template language

Each editable field names an existing action ID and a field from the finite registry in [the composition contract](contracts/capture-composition.schema.json). The registry maps fields to typed action locations: packet peers/filter/window/ring and supported execution mode, process selector/batch, profile duration, syscall filter/mode/window/limits, file path, command argv, and action timeout/output cap. Values are literal typed data. No JSONPath evaluation, arbitrary JSON patches, interpolation, environment expansion or user-defined expression/schema execution is permitted.

The profile's complete recipe supplies defaults; users need enter only changes. Component recipe totals are default planning values, not additional authority or immutable administrator ceilings. After edits, recompute effective component cost and validate the final aggregate recipe against the composition bounds and all administrator ceilings; never silently raise the submitted aggregate bounds. Show useful labels, effective defaults, units, valid value shapes and current administrator ceilings. A field may be changed only if that profile version exposes it and it applies to the named action. Duplicate edits or unknown fields/actions fail with a field-level remedy. Apply all edits, then validate the resulting action, DAG, timeout/budget relationships and capabilities as a whole; a type-correct edit can still make a plan infeasible. For example, changing packet duration may need a longer action timeout and changing ring size may need compatible segment settings. The UI offers the related adjustment explicitly, never increases it silently.

Editable fields are convenience controls, not a substitute for authorization. Any adapted recipe receives normal current validation, impact/privacy classification and review; a user cannot downgrade an action's impact or replace its engine/projection through an override. A user authorized to author expanded recipes can choose **Customize as a new profile/recipe** to edit other supported fields. That creates independently validated configuration, without reusing an existing intrusive approval. Profile publication is not approval of its executions.

### SC-CPR-002

Given a profile exposes packet peers, after-duration and action timeout, when a user narrows peers and extends duration, then all values are type-checked and preview reports the resulting cost and approval. An unexposed field, duplicate override, `$(...)` interpolation attempt or an attempted impact change cannot execute code or evade validation; command argv remains literal under the existing command rules.

## REQ-CPR-003 — Compose into one bounded recipe

`profileComposition` contains one to eight uniquely named components, each with an explicit versioned reference and zero to 32 typed overrides, plus aggregate `maxTotalBytes` and `maxDuration`. It is a third authoring form for `DebugCapture`/`DebugPolicy`, mutually exclusive with `recipeRef` and presets. Target, triggers, observation, sharing and execution identity keep their existing semantics. The browser computes initial aggregate bounds from the selected defaults; users may lower them, and administrators retain all ceilings. Composition does not introduce another collector or execution service.

Resolve and validate all components before accepting the plan. Namespace every action and endpoint-binding identity deterministically; use `a` plus the first 24 hexadecimal SHA-256 characters of UTF-8 `componentID + NUL + localActionID`, with analogous `e`-prefixed endpoint IDs. Reject collisions. Rewrite internal dependencies and endpoint references through this map. Keep a human-readable `component/action` alias and a complete source-to-expanded-action map for preview, sharing and provenance. Maintainers choose friendly names in the UI; clients receive the resolved IDs and never compute hashes themselves. Cross-component ordering is handled by the execution scheduler or an explicit expanded recipe, not unvalidated dependency injection.

Resolve and display each action's executionMode under [action lifecycles](action-lifecycle.md). Compile ongoing source activation separately from incident snapshots/onTrigger dispatch; the recipe is not one graph launched from scratch for every trigger.

The final plan has at most 16 actions and 16 endpoint bindings under existing contracts, irrespective of component count. Sum action output maxima after allowed deduplication; multiply incident output by selected pod/fanout bounds and separately reserve ongoing rings across the larger observation pod set, frozen snapshots, parser/scratch, observed-byte/event budgets, CPU/concurrency and uploads. Profiles cannot reserve the same protected capacity independently and then exceed the combined limit. Enforce cumulative process-start/stop and observation budgets across the whole capture and workload, including other active policies/captures.

Only identical, independent `kubernetesSnapshot`, `processSnapshot` and `networkSnapshot` actions may be deduplicated in the initial compiler: same kind, parameters, limits and impact, no dependencies. The shared action is required if any alias is required. Preserve all aliases and resolve references/sharing to the one actual acquisition; never count or publish the same artifact twice merely because it has two aliases. Choose the first component/action in authored order as the canonical ID. Do not silently merge packet filters, logs/time windows, file reads, commands, profilers, dumps or argument traces. Duplicate expensive-acquisition comparison ignores ordering dependencies and resolves endpoint bindings to their underlying definitions, so different generated endpoint names cannot hide the same acquisition. Identical expensive actions produce an actionable duplicate conflict; overlapping non-identical sensors show aggregate cost and either run under a qualified coexistence profile or fail with a remedy.

Serialize operations that stop the same process. For exclusive profilers/sensors, validate a compatible serial schedule within the total deadline or report a conflict; do not pause an application to resolve one. No nested profile can hide an expensive action or a second process stop because definitions are expanded-only. Required/optional action outcomes stay separate; optional work awaiting review cannot prevent independent context from progressing. One combined review shows all actions and exact aggregate budgets, while acquisition, sharing and raw-analysis grants retain their separate purposes.

Run [combined impact and data assessment](capture-assessment.md) after expansion/deduplication and scheduling. Friendly names, publisher descriptions and individually permitted components cannot assert that the combination is low impact or nonpersonal. The effective panel reflects overrides, all observation pods, incident fanout, incompatible operations and mixed retention rules; alternatives are explicit edits with stated coverage loss.

### SC-CPR-003

Given HTTP headers, syscall metadata and process context are selected, when compiled, then one recipe and one current execution scope contain every action and budget. Duplicate independent process snapshots are acquired once with both aliases retained. Duplicate core dumps, too many actions, incompatible profilers or a combined ring/parser budget over the node limit are rejected before collection.

## REQ-CPR-004 — Useful initial profiles and precise capability labels

Ship the following versioned definitions; qualification/capability checks can make individual entries unavailable without disabling the catalog:

| Reference | User-facing purpose | Execution mode | Defaults and explicit limits |
| --- | --- | --- | --- |
| `builtin/process-context/v1` | Process and socket context | On trigger | Identity/status/cgroups plus bounded socket context; no argv/environment or attach |
| `builtin/network-connections/v1` | Incoming and outgoing transport traffic | Ongoing; save on trigger | Requested 30-second history plus ten seconds after trigger; verified networkHeaders, both directions, all approved peers of selected pods; bounded ring/window, no application payload |
| `builtin/http-headers/v1` | HTTP/1 headers, both directions | Ongoing; save on trigger | Approved plain HTTP/1 projection, all TCP ports by default, both requests/responses; bounded flows/reassembly/ring; sensitive-observation approval |
| `builtin/go-cpu/v1` | Short Go CPU profile | On trigger | Qualified named endpoint template, ten seconds, ordinary live-profiling approval; no guessed endpoint or enabled sampler |
| `builtin/syscall-activity/v1` | System calls of all pod processes | Ongoing; save on trigger | Metadata mode, all syscall names, existing/new pod processes, requested 30-second history plus ten seconds after trigger, bounded event rate/ring; no user buffers |

“All” means all eligible sources within the selected pods and declared interval, under visible loss/capability limits; it never promises unbounded or lossless capture. HTTP/1 headers are not full HTTP conversations. The initial approved projection retains method/status and validated Content-Type/Content-Length, omitting URL/query/Host and credential headers; broader reviewed projections are explicit administrator variants. Both directions describes observed traffic, not permission to retain every header. HTTPS plaintext, HTTP/2 headers and HTTP/3 are not acquired by this shipped profile. Protocol classification, Service filters and narrower windows can be suggested by [guidance](guidance.md), with confidence and exclusions shown. A pod/loopback/CNI path that is not qualified stays a visible gap.

The [syscall contract](syscalls.md) provides an explicit sensitive argument/buffer mode for qualified adapters and reviewed variants. It is not enabled by the shipped metadata profile. Additional administrator profiles can expose it alongside other supported actions. Users may combine any permitted action kinds, not only the five initial bundles.

### SC-CPR-004

Given a maintainer asks for all HTTP traffic, when offered the shipped profile, then the UI explains the plain HTTP/1 header projection and encrypted/unsupported traffic gaps. Choosing syscall activity follows new workers without a PID picker, but shows loss/overflow instead of pretending every event was retained. Unavailable pprof does not fall back to a custom command.

## REQ-CPR-005 — Shared browser/MCP planning, guidance and history

The browser presents a searchable, capability-aware catalog with publisher/catalog, version, purpose, defaults, editable controls, impact, evidence classes and approval requirements. Add/remove profile cards, adapt settings, and preview the combined plan without writing an action DAG. Group actions by On trigger and Ongoing; save on trigger, and show added/deduplicated/conflicting actions, ongoing versus per-incident costs and a before/after diff when changing an existing plan. **Save as profile** uses current Kubernetes publication rights and creates a new immutable version, not a server-side script.

Add read-only `list_capture_profiles(target_handle, catalog?, cursor?, limit?)` and `get_capture_profile(target_handle, profile_ref)`. Results are target-authorized and bounded by ordinary MCP limits; no profile reveals secrets or otherwise hidden namespace configuration. The detail projection contains the versioned definition and exposed editable-field names; typed values are specified by the shared preview/composition contract. Definition details and previews containing full composition settings are protected extracts, not catalog metadata. Large definitions return a bounded error with authenticated browser navigation; the client can still select/preview a known profile reference without fetching all of it.

Extend normal `preview_capture` selection to exactly one of diagnostic handle, preset or `profile_composition`. Target selection is unchanged; the history restore branch remains exclusive. Compilation happens here without sampling, acquiring evidence or reserving execution authority. The preview includes a bounded component/action map, deduplication/conflict explanations and effective aggregate cost. Submission still uses request_capture(preview_id, idempotency_key). Agents need no special composition execution or approval API.

Guidance recommends profile references/edits and can produce the same composition handles; every recommendation is recompiled under current versions/ceilings. Policy acceptance and history snapshots retain authored references/overrides, resolved source cluster/namespace/object UIDs and definition digests, expanded recipe and alias map. Add `captureProfile` to execution dependency roles. Collection digests bind profile versions and effective actions; changing recipients alone still does not change collection scope. A publisher's availability revision is current authority checked at start, not a perpetual grant.

History repeats restore the original resolved versions/overrides rather than today's catalog defaults. Missing or disabled dependencies block new starts; edits and intentional version upgrades are explicit new plans. Expired evidence-derived settings retain their old deadline even when wrapped in a composition. Profile history and saved definitions never inherit execution grants, owner assignments, recipients or raw-query approval.

### SC-CPR-005

Given identical target and profile choices in browser and MCP, when previewed, then both produce the same expanded recipe, aliases and budgets. The agent can submit the returned preview without hashes. A later profile version does not change a saved policy or history repeat; disablement, revoked namespace publication/access and expired inferred values cannot be bypassed through old handles.

Shipped network/syscall building blocks use ongoing recording with 30 seconds of requested history; HTTP headers retain their existing 30-second before/after windows. Each exposes the supported actionExecutionMode control. Selecting onTrigger also requires explicitly setting the before window to 0s; the UI proposes that coupled change and explains loss of history before acceptance. Direct inspection/survey diagnostics remain finite, and may use explicit post-trigger-only variants. Existing published versions cannot be edited; these checked-in v1 examples refine the unreleased design.
