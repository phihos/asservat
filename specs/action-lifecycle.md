# When evidence actions run

Actions have two execution modes, separate from impact and data sensitivity. The resolved mode is visible in profiles, previews, accepted plans, history and acquisition provenance. Selecting an ongoing action authorizes a bounded observation session; it does not mean continuously uploading evidence.

The [capture assessment](capture-assessment.md) displays cost while sources are armed separately from cost when evidence is saved or acquired. A low incident pod limit does not cap ongoing observation overhead. Both phases disclose transient inspection, retained data and earliest-source retention.

## REQ-LIF-001 — Explicit execution categories

| Mode | User label | Behavior | Initial actions |
| --- | --- | --- | --- |
| `onTrigger` | On trigger | Start one bounded action for an admitted incident or manual capture | Live core/heap dumps, commands, file reads, context snapshots, diagnostic endpoint calls, runtime diagnostics, pprof/profile acquisition, log retrieval and collection of already produced artifacts |
| `ongoing` | Ongoing; save on trigger | Arm a bounded recorder before incidents; each admitted trigger preserves its own before/after window while recording continues | Packet captures and syscall traces by default |

`action.executionMode` may be omitted in authored configuration. The [action contract](contracts/action.schema.json) fixes the default and allowed modes for every kind; normalization MUST resolve and record the value in the accepted execution plan. Ordinary users do not need to classify each action manually. Changing mode changes collection scope and requires fresh acceptance and applicable approval. No mode downgrade can reduce an action's sensitivity or waive approval. Contract-version changes cannot silently reinterpret a saved plan.

Only packetCapture and syscallTrace initially support both modes. An explicit onTrigger variant captures the next bounded interval and MUST have before: 0s; it cannot promise pre-trigger history. Their default remains ongoing even when before is zero: a zero history window does not silently change when the source runs. Commands, dumps and snapshot actions cannot be configured as an ongoing polling loop. New ongoing adapters require a defined lifecycle, accounting model and qualification before extending the allowed-kind registry.

`kernelCore` is an event-driven onTrigger acquisition with a **natural crash** origin: interception infrastructure and finite local permits must already be prepared, but no core bytes exist before the crash. Consume the crash stream only after immediate matching local admission at that event, without waiting for a remote decision or a later composite expression. If the configured condition/authority cannot admit it at that point, reject promptly and report a missed core rather than speculatively collecting one. A crashArtifact notification can refer to an already saved core; it does not start that core acquisition again. An unrelated probe/log trigger cannot manufacture a natural core; use a separately approved liveCore if desired. An OOM kill does not imply a core is available. Reconcile the crash acquisition with its occurrence without capturing or charging it twice.

Log retrieval can read history already retained by the runtime, without Asservat starting a new log recorder at policy activation. Continuous log/resource/probe **detectors** are distinct from evidence actions. Likewise pprof cumulative mode reads counters maintained by the application; it is still an onTrigger acquisition. Existing application flight recordings may be collected explicitly as artifacts; Asservat does not assume ownership or silently start continuous profiling.

### SC-LIF-001

Given a mixed recipe with a live core, packets, syscalls and logs, when previewed, then the core/log reads appear under On trigger and packet/syscall sources under Ongoing; save on trigger. A future-only packet variant needs explicit onTrigger and before: 0s. A natural crash uses a ready local interception permit, while an ordinary health trigger cannot claim it generated a kernel core.

## REQ-LIF-002 — Arm sources before incidents

Policy activation resolves all ongoing actions and reserves their observation resources **before** attaching hooks or reading evidence. Arm them across the authorized observation pod set, independently of the smaller target.maxPods incident collection cap. Include new replicas under the same reviewed scope and ceilings. Per-action coverage can be limited while cheaper detectors continue; show eligible, armed, warming, blocked and lost counts separately. Never claim complete history merely because the trigger detectors are Ready.

An ongoing source has a service-owned session identity bound to cluster/node boot/pod UID, action/recipe/engine/filter digests, mode, execution authority and reservations. Proposed source states are Pending → AwaitingApproval/Capacity → Arming → Warming → Ready, with Degraded, Stopping and Stopped transitions. Readiness is scoped to that source and requested lookback: a newly armed 30-second ring is Warming until it has sufficient continuously observed coverage, even if quiet. Capacity eviction, loss, target restart and authorization gaps shorten or invalidate coverage. before: 0s can be Ready once the source is active.

Ongoing sources run without incident artifacts until a trigger is admitted. Rotate bounded ring segments and erase expired/evicted contents; do not create a capture, upload an artifact or spend a dump execution on every rotation. Source arming may consume its own session/start budgets. Detectors can activate and permitted onTrigger work can run even when an independent optional recorder is unavailable. Required missing history makes that incident partial/failed according to actual useful output; it must not delay unrelated evidence until a failing process disappears.

The source identity is distinct from a capture/action-attempt identity. A trigger references the already armed matching session; it must not attach another recorder per incident. Initial semantics do not implicitly share sessions between policies or principals. Future reuse requires equal scope/retention/representation and independently accounted leases, never access to a broader source just because it is running.

### SC-LIF-002

Given 20 replicas, a one-pod incident cap and an approved ongoing packet action, when the policy activates, then source reservations cover all eligible observation replicas within admin ceilings. A trigger from replica 17 snapshots its existing ring; it does not create a new recorder or infer history from the other replicas. A new replica and an exhausted source are visibly Warming and Degraded respectively while unrelated detectors remain usable.

## REQ-LIF-003 — Incident windows and dependency ordering

Anchor each admitted incident to a recorded trigger time t0 and its clock/observation uncertainty. The requested window is [t0-before, t0+after], restricted to bytes/events actually observed under valid authority and before retention cutoffs. Delayed event delivery, queues and late approvals do not move t0 forward or synthesize missing history. Pin the available pre-trigger segments immediately after snapshot admission; collect only the remaining original post-trigger interval. Source loss during that interval produces partial evidence. Slow upload must not extend recording or pinning beyond approved bounds.

An ongoing source has two separate limits: its finite observation/session permits, and each snapshot's action timeout/output cap. Action limits.timeout and recipe.maxDuration apply to incident work from admission (including post-window completion/finalization), not to how long a policy may remain armed. Setup/session leases have separate finite administrator bounds. Watchdog/expiry failures stop the affected source; no action timeout accidentally restarts it on every trigger.

Save operations and onTrigger actions start independently at incident admission under their own capacity/approval checks. Do not wait for a core dump or a human before pinning an independently authorized ring window. Ongoing actions cannot have dependsOn edges: source startup must not depend on an action that runs only after a trigger. An onTrigger action may depend on an ongoing action; that edge waits for this incident's saved output, not for the source to stop. Prefer independent acquisitions and offline analysis dependencies; preview warns about delays that can lose transient evidence.

Concurrent incidents use separately bounded snapshot identities and references while the live source continues. Deduplicated trigger delivery reuses the original snapshot operation. At snapshot limits, coalesce only under the existing occurrence rules without extending the accepted window/deadline, or refuse with a gap. A sustained trigger cannot extend one post-trigger window forever. Stop/suspension/revocation can shorten windows, never extend them.

### SC-LIF-003

Given an armed ring and a live dump waiting for approval, when an incident at t0 is admitted, then ring preservation proceeds under existing authority without waiting for the dump. A second trigger at capacity is deduplicated/coalesced or refused; it neither attaches a second recorder nor grows pinned memory indefinitely. Delayed upload and a crash during the post-window preserve truthful partial timing.

## REQ-LIF-004 — Continuous cost, permission and cleanup

Before arming, reserve per-pod ring/parser/thread state, collector CPU/rate and applicable sensitive-observation session/event/byte budgets. These costs scale with the **observation** pod set, not selected incident pods. At snapshot time reserve additional frozen/copy-on-write replacement buffers, output/object slots, encryption/spool and upload capacity for only the admitted incident set. OnTrigger dumps/commands reserve their impact and output immediately before dispatch. No trigger is needed for ongoing sources to consume resources or sensitive-observation authority.

Metadata packet/syscall observation still requires collection rights, current scope, finite local leases and impact limits. HTTP/raw packet and syscall argument sources additionally need their reviewed acquisition grants **before the first sensitive read**, even if no trigger ever fires. Arming and trigger cooldowns are independent: cooldown suppresses new saves/actions while the admitted recorder continues within its budgets. No-trigger traffic, ring eviction, permit refresh, snapshot refusal and process/pod/controller restart cannot reset cumulative observation spend. The bounded sessions in REQ-AUT-006 remain finite; a long policy approval is not an unlimited recording session.

Ordinary sanitized ongoing packet sources use the distinct source-purpose contract in [ADR-263](../docs/decisions/263-ordinary-ongoing-source-leases.md), not a fake finite capture or execution. Their fixed active leaf is at most 30 seconds, while source/ring hard lifetime and each segment's acquisition-based content expiry remain separate. Expiring an old segment does not stop the whole continuing source; snapshots inherit the earliest expiry of included segments. Same-source renewal preserves identity, fence, original hard end, input counters and rate tokens. It reserves no second ring/count/burst allocation. Unchanged positive cumulative credit permits additionalCredit=0 with fresh proofs, locked current source/authority reads and absolute issuance ordering, without a source-state UPDATE; only a positive increase uses durable expected-credit CAS and prepays its positive delta. Charge original wire length before filtering.

On policy pause/delete, source disablement, authority expiry/revocation, exhausted observation budgets, lost target or an applicable circuit breaker, detach/stop acquisition within the existing lease/cancellation bounds. No new observations or snapshots may use expired authority. Healthy unaffected detectors/sources may continue. Already captured and validly admitted evidence can finalize under its own still-valid processing/storage authorization and deadline; erase unsaved rings and release resources only after workers detach and outstanding references settle. Natural target exit alone may use the narrowly bounded stopped-source grace in REQ-LIF-006; explicit pause, revocation, expiry and emergency denial take precedence. Stopping a single incident's save does not cancel a separately authorized policy source. Source restarts create new epochs, report gaps and never resume old “full history” status without rebuilding coverage.

### SC-LIF-004

Given a sensitive recorder with no incident triggers, when it exhausts its observation grant, then it stops despite having produced no artifact. A burst of later triggers cannot replenish that grant. Pausing the policy stops its sources, while cancelling one saved incident leaves an otherwise authorized policy recorder running. Other workloads retain their reserved capacity.

## REQ-LIF-005 — Manual captures, profiles and visible provenance

A manual DebugCapture is finite. OnTrigger actions begin after the ordinary request/approval/admission steps. An ongoing action requested manually opens a bounded **manual session**, uses the same ring/snapshot adapter, and stops after that capture's window/finalization or cancellation. It does not install a persistent policy. Default Collect now does not wait to fabricate requested history: a newly created session has no pre-request coverage and reports it. Use an explicit future-only variant (onTrigger, before: 0s) for short surveys. A manual DebugCapture does not fire another policy or borrow its source/grant. The separate [Save existing recordings now](recording-saves.md) operation uses explicit reviewed policy permission and never compiles an ordinary manual recipe; the first-release detector schema has no inert manual-policy leaf. Ordinary history repeat or shared evidence does not confer such authority.

The UI separates **Runs on trigger** from **Records while armed; saves on trigger**, showing ongoing scope/cost/approval and incident scope/cost independently. Mixed reusable profiles list both modes, preserve them during composition and retain typed mode overrides only when explicitly exposed. Show current source readiness and achieved history, not merely the configured ring age. Make the post-only tradeoff explicit before switching modes. Profile version pins and history snapshots retain the resolved execution modes and dependencies; repeat creates fresh sessions and approvals rather than reusing old rings or source IDs.

MCP catalog rows expose execution_modes; preview_capture includes the protected action-lifecycle/v1 plan with per-action mode, activation phase, requested window and observation scope. No new arming/approval tool is needed. Browser and MCP compile the same plan. Capture progress reports the incident save/action state separately from policy source readiness. Every new artifact's actionLifecycle provenance identifies mode, invocation origin/time (policy, manual or direct natural-crash acquisition), and, for ongoing saves, source epoch/session, snapshot identity, source start, requested window and history coverage/gaps. Ongoing acquisition provenance also requires windowCoverage for the entire requested before/after interval; sourceStoppedAt records a known source end. Full prehistory does not imply full post-trigger coverage. A known stop before the window ends prevents full window coverage; full window coverage requires no gaps and complete requested history. The manifest records the source epoch as its `sourceSessionID`: a restarted source starts a new session ([ADR-244](../docs/decisions/244-native-artifact-types.md) verifies these rules and the whole provenance against the accepted expectation). Existing artifact startedAt/completedAt describe actual acquisition, never a fabricated trigger timestamp. A fully covered quiet interval can contain zero records; absence of events alone proves neither loss nor complete coverage. For an existing-source snapshot, a known observation closure is recorded separately as sourceClosedAt; unlike a natural sourceStoppedAt it does not imply targetGone. Artifact acquisition bounds end at the earliest requested end or known stop/closure, while snapshot processing completion remains separate. Observed stop/close and processing event times preserve their nanoseconds; accepted source/admission/t0/deadline precision is unchanged.

### SC-LIF-005

Given a user repeats a packet/syscall profile manually, when no authorized source was already recording, then preview explains the finite session and unavailable prehistory. Completion/cancellation stops that session. A source started after t0 cannot report full prehistory, and a history snapshot or catalog entry cannot revive a previous recording or grant. Browser/MCP display the same two action groups.

## REQ-LIF-006 — Preserve stopped sources for delayed exit events

Loss of a source's pinned pod/runtime identity stops that source's new reads immediately but may leave already collected ring contents available to a delayed matching exit/crash occurrence. Exit of one process or sidecar must not stop a still-valid whole-pod packet/syscall recorder; it is only a trigger/provenance event for that recorder. The node holds a **stopped** source under its original pod UID, source epoch/session and node boot; a new pod or runtime gets a new source. The grace is an operator-level bounded retention of existing bytes, default 30 seconds, ceiling 60 seconds, further limited by the original source/processing authority, earliest content expiry and local capacity. Grace starts at the locally observed stop, never at later trigger arrival. It cannot renew a grant or resume observation.

Reserve and account stopped buffers inside the existing workload/node ring budget, with a finite retired-session count and byte ceiling. Proposed local defaults are two retired sessions per workload per node and 32 per node, across actions; administrators may lower them. A retired session uses its existing ring byte ceiling and never allocates a second uncharged ring. Expose these as local collector configuration limits under the existing operator-managed deployment, not per-container or end-user settings. New sources must fit alongside them or report unavailable history; rapid churn cannot allocate an unbounded queue. At pressure, erase unreferenced stopped buffers first and report historyEvicted. Snapshot only for an incident admitted while the stopped source and its processing authority remain valid; ordinary incident storage/output reservations still apply. A late event does not extend its original requested window. Ordinary manual capture/repeat cannot discover or borrow retired sources. An explicitly approved recording save under REQ-SAV-001–004 may select a stopped policy source within this same grace and remaining authority; it cannot extend either.

Explicit suspension/deletion, revocation, an emergency deny, deadline (including ordinary source active-leaf expiry) or exhausted authority overrides the grace and disallows new snapshots. Finalize already admitted snapshots only under their remaining processing/storage authority. No-match expiry erases unsaved contents and releases charges after references settle. Node loss loses volatile history; do not promise recovery from local RAM. Record sourceStoppedAt, prehistory coverage, whole-window coverage and gap reasons independently. If a source stops after t0 but before t0+after, prehistory may be full while the whole window is partial.

### SC-LIF-006

Given recording before a probe incident at t0 and pod exit at t0+2 seconds, when the matching exit arrives within a valid grace, then the old source can yield admitted prehistory and two seconds of the requested ten-second post-window. It reports full history but partial window and targetGone. A replacement pod, a late event after grace, or policy revocation cannot reuse that source. A rapid series of exits stays within the reserved bytes/session count; node loss reports unavailable history.

## Live readers of ongoing sources

[Live watching](live-watch.md) attaches separately budgeted, finite readers to eligible existing ongoing packet/syscall sources, including finite manual sources. It is not a third action executionMode, a detector or an implicit source-arming operation. Display filtering/pause/close affect only the viewer, never source lifetime, acquisition filters or incident windows. Source-sensitive acquisition authority is still required before any observation, independently of viewers. Manual-session completion and source revocation terminate corresponding delivery. Save current recordings uses the existing policy-only snapshot capability with fresh handles; watching does not broaden it.
