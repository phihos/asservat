# Capture history and repeating requests

Users MUST be able to revisit captures for a workload or pod selector and repeat their settings without re-entering them. This first-release behavior uses the existing [execution service](execution.md), [hub persistence](persistence.md) and [MCP workflow](mcp.md). It adds no history CRD, collector or execution API. Specifications and fixtures describe proposed behavior; no product implementation is claimed.

## REQ-HIS-001 — Find previous requests for the same selector

Provide **Recent captures** on the target/selector page and **Repeat capture** on each authorized request and case-linked capture. Show request time, manual/policy/discovery origin, permitted requester identity, action kinds, outcome, evidence availability, saved-settings availability and an authenticated request link. Include pending, failed, cancelled and partial accepted requests, not only successful cases. A rejected request that never reached acceptance is a local form/error state, not durable shared history. History is populated on acceptance, before evidence exists, and updated from the same capture execution records.

Default to manual requests, newest first. Offer explicit policy and discovery filters so automatic trigger storms and short surveys do not bury manually chosen diagnostics. Grouping identical settings is presentation over authorized bounded records; show the covered interval and avoid unaudited global counts. Each policy occurrence has an existing capture identity; history does not create another occurrence or rearm the policy. Suppressed triggers are available through existing suppression summaries, not manufactured capture-history entries.

The **selector key** binds cluster identity and namespace UID, plus either the authored workload kind/UID or canonical authored pod-label expression. Ordinary Deployment/StatefulSet pod rollouts do not change it. Ignore resolved pod members, resourceVersion, map ordering, recipe, maxPods and per-capture pod choice when grouping requests for that selector; preserve those settings in each request. A namespace or workload recreated with the same name has a different identity and MUST NOT silently join the previous history. Different label expressions remain different selectors even if they happen to match the same pods today; do not attempt general logical equivalence. Canonical equality for the current matchLabels form sorts keys and preserves exact key/value strings. An empty/unauthorized live selector cannot disclose neighboring history.

The request also retains a separate **settings key**, covering the full normalized collection configuration: pod selection/count, recipe version and overrides, process selectors, packet peers/filter/ring settings, endpoints and requested limits/retention. Exclude request IDs, timestamps, grant references, free-text reasons and sharing. This allows several useful past configurations under one target without overwriting them with the newest one. SQL lookup keys for potentially identifying labels/settings MUST be keyed digests; plaintext label values, arguments and packet filters belong in protected parameter records.

### SC-HIS-001

Given two captures using different packet filters for the same Deployment, when its pods roll, then both settings remain discoverable under that Deployment. Reordered matchLabels keys return the same selector history; a different selector that currently matches the same pods does not. Recreating the namespace or Deployment under its old name cannot inherit the old grouping or permissions.

## REQ-HIS-002 — Restore settings into a fresh, reviewable request

**Repeat capture** restores a new draft from the immutable accepted request's parameter snapshot, not the current mutable recipe of the same name. Keep the original authored target, requested collection settings, fully expanded action recipe, immutable dependency versions/digests and requested retention. Preserve both requested and original effective values where administrative clamping occurred, so preview can explain changes. The stored snapshot is data, never delegated authority. No manual hash, UID or old grant entry is required.

The normal path is select history entry → review restored settings and current differences → **Collect again**. Editing uses the existing capture editor and creates a new preview. Show original versus current effective pod count, capabilities, privacy/retention, budgets and approval needs. Preserve action DAG order/dependencies; unavailable or denied pinned versions are explicit blockers. Never silently switch to the latest recipe, image, runtime pack or projection. An intentional upgrade is an edited plan with a visible difference. Saving/previewing a repeated draft does not collect anything.

The new request has a new capture identity, acceptance deadline, requester/executor, execution digest and idempotency key. Record `repeatedFromCaptureID` as independently expiring opaque lineage. It never grants access to the source record. Revalidate current ownership, collection rights, ceilings, capacity, artifact-purpose rules and dependencies. Automatic policy grants cannot authorize a new ad hoc capture; any intrusive/sensitive repeat needs its own applicable ad hoc approval. It consumes normal workload-wide rate/storage/impact budgets, with no counter reset. A repeat of a policy occurrence creates one manual capture, not a policy or another scheduled series.

Resolve current eligible pods under the same pinned workload/namespace identity. Preserve logical process selectors and dynamic peer queries; resolve their current members under the usual rules. Do not copy old resolved pod/PID/IP lists as if they were current. An explicit Pod or exact `selectedPID` remains identity-pinned and cannot be replaced silently; if gone, show **Choose a current target/process** while retaining the other settings. An automatic occurrence using `triggeringPod` needs an explicit manual pod-selection choice because the new request has no trigger. A recreated workload or peer identity requires explicit re-adoption through an edited plan.

Old grants, execution permits, deadlines, credentials, resolved secrets, idempotency keys, creator/owner assignments and sharing instructions are not restored as authority. Secret references may be restored and must be resolved under current scope. Default repeat creates no sharing instruction; the ordinary sharing section lets the user select recipients for the new request. Do not copy the previous free-text reason; use the current diagnostic purpose and a generated repeat reference or a newly entered reason. Clearly show these resets without asking users to rebuild the collection parameters.

Retries of the **same newly submitted repeat** use its same idempotency key and return that operation even after preview expiry, as normal. Another deliberate Collect again creates another operation. Disable duplicate submission in the UI while accepting, and show already-running captures before another intentional start; server admission remains authoritative. Repeating a Failed/Indeterminate request is an explicit new collection, never an automatic retry of an uncertain process-affecting action. The existing analysis-only retry remains available when fresh acquisition is unnecessary.

Repeat recomputes [impact and data-handling assessment](capture-assessment.md) against current rules, metrics, workload size and retention. Previous success or an old low-impact label is not a transferable safety verdict; old assessments are not restored as authorization.

### SC-HIS-002

Given a previous capture of two matching workers plus packet context, when a maintainer selects Repeat capture, then the settings are restored, fresh matching pods/processes are resolved and present-day limits/approval differences are shown. A double click or lost response creates only one new capture. A new intentional repeat cannot reuse the old ad hoc grant. An expired exact process asks for selection; repeating a policy occurrence cannot silently enable monitoring.

## REQ-HIS-003 — History is bounded private control data

Authorize each record with retained request/audience provenance and current entitlement. Default visibility is the requester who still has current scoped rights, or maintainers with the retained and current request-view assignment. Newly acquiring a workload does not automatically expose historical parameters from a former owner. Explicit administrative historical transfer follows the existing ownership rules. A shared evidence snapshot grants neither capture history nor the recipe/command/settings behind it. Listing, counts, source lineage, cursors, detail reads and replay previews use the same evaluator; repeat additionally requires current collection authority. Unauthorized records use the existing uniform unavailable response.

Keep content-minimized history summaries under the configured case-metadata policy (initial requested default seven days). Store parameter snapshots and inline expanded recipes in encrypted, scope-bound regional object records, with original provenance, classification and independent access/deletion deadlines. SQL retains opaque references, keyed selector/settings digests, origin/state/timestamps and minimal lineage. No arguments, arbitrary selectors, reasons, credentials or sampled process/traffic lists enter SQL/audit backups for convenience.

A history summary can outlive its evidence, and repeatable configuration can outlive evidence **only when its content policy permits this**. Pure approved configuration may use the finite case-metadata lifetime; arbitrary user-supplied paths/arguments/filter literals remain potentially personal and receive applicable stricter limits. Configuration inferred from discovery/evidence inherits the earliest source deadline; history cannot extend it. Retain no captured output in the parameter snapshot. Expired/redacted/incomplete settings produce **Parameters expired/unavailable**, with current catalog choices as a recovery path; do not silently reconstruct them from audit logs, backups, expired objects or an unreviewed current recipe. Saved reusable configuration is a separate explicit authoring action, not a hidden retention exception.

Initial extra history bounds: at most 1,000 summaries per selector and 100,000 per installation, with at most a 128 KiB serialized parameter snapshot per request. These are administrator-lowerable view/cache ceilings in addition to normal capture/object/account limits. Older history projections may be evicted within the originating workload/namespace allocation without deleting live evidence, execution accounting, grants or mandatory audit/revocation state. New history must not evict another workload's retained settings to gain room; if no eligible capacity remains, decline the new history projection while retaining ordinary capture admission. Parameter objects remain charged to their originating account until verified deletion. History capacity must not reject an otherwise admissible incident capture: report HistoryUnavailable/SettingsUnavailable with normal collection still functioning. Recording the snapshot before acceptance publication must be bounded; an unknown write remains charged and is reconciled like other protected objects.

At least one snapshot is bound immutably by digest to the accepted request before marking its settings available. A mutable referenced recipe disappearing later does not destroy a retained snapshot, but execution still requires its pinned dependencies to be installed and permitted. Snapshot deletion, version/replica cleanup, backup deadlines and restore suppression obey REQ-PRV-008. Viewing, repeating or pinning a history item never extends the source snapshot/evidence lifetime. Fresh evidence gets its own acquisition clock; existing parameter content keeps its provenance/deadline unless explicitly authored independently under an approved configuration policy.

### SC-HIS-003

Given evidence has expired but an authorized configuration snapshot remains within its own permitted lifetime, when the owner opens history, then they can preview a repeat without recovering the old evidence. Once parameters expire, the summary explains that repeat is unavailable. A new owner or share-only recipient cannot read the old settings. A repeated discovery-derived filter cannot retain personal data beyond the source deadline; history eviction cannot release live capture charges.

## REQ-HIS-004 — Browser and agent use the same history

Add `list_capture_history` with exactly one of a current `target_handle`, a named `target_ref` (as in `preview_capture`) or explicit `cluster_id` plus `target` selector, optional origin filter, cursor and page limit (default 20, maximum 100). An explicit selector resolves namespace/workload identity under current authority before lookup. Default origin is manual. Stable ordering is descending accepted time then capture ID; cursors bind caller/client, selector/origin, authorization revision and query snapshot under the existing 15-minute maximum. Bound scan work and never leak hidden totals; provide a narrowing hint for incomplete scans.

`get_capture_settings(capture_id)` returns the authorized immutable settings projection: original target, expanded recipe, dependency pins, requested retention if present, settings digest, original effective digest and expiry. It does not return historical reason, recipients, credentials or grants. Arbitrary strings remain untrusted data. The full projection still obeys the standard MCP byte limit; an oversized snapshot returns SettingsTooLarge with authenticated browser navigation rather than malformed/truncated executable settings. Repeating by reference remains available without downloading the settings; the browser presents bounded sections under identical authorization. This limit does not permit larger raw tool responses.

Extend `preview_capture` with a separate `history_capture_id` branch, optionally a new reason and explicit new sharing instruction. It is mutually exclusive with target/diagnostic/preset inputs and requested_retention_seconds, avoiding hidden retargeting or a silent change to the retained requested lifetime. To shorten or otherwise edit retention, use the normal preview editor with optional repeated_from_capture_id provenance. Return the normal preview plus `repeated_from_capture_id`, bound to the new draft. The same field is returned by `request_capture` and `get_capture` when applicable. `request_capture(preview_id, idempotency_key)` remains the only submission step; listing, reading and repeat preview never start acquisition. Advanced edits use a fresh normal preview with optional repeated_from_capture_id provenance, supported equally in browser and MCP. This normal branch explicitly supplies target and diagnostic/preset and restores no parameters implicitly; supplying provenance still requires current access to its source. It cannot be combined with history_capture_id. Editors retain this reference when copying settings, so current checks and original content deadlines remain attached. Recipe snapshot availability never bypasses administrator disablement.

Both new read tools use evidence:read and current scoped history authorization; preview/submission additionally require collection eligibility and the existing evidence:capture submission gate. Handles/caches use existing limits and cannot outlive the parameter source deadline. Revocation or expiry between listing and preview/submission blocks reuse. Passing a source history ID is not proof of ownership. Existing get_capture remains available for accepted execution status independently of whether its history projection has expired.

### SC-HIS-004

Given an eligible external agent sees a successful capture in selector history, when it calls preview_capture with history_capture_id and then submits the returned preview, then one new capture uses the retained settings under current authorization. Combining history_capture_id with a different target is rejected. Share-only access, revoked history access, expired settings and unavailable dependencies cannot be bypassed through handles or get_capture_settings. A large snapshot can still be repeated by reference within normal MCP output limits.

## First implementation (ADR-236)

[ADR-236](../docs/decisions/236-capture-history-collect-again.md) implements the base of REQ-HIS-001–004 for the pod-status preset; the remaining mechanisms ship with the first parameterized recipe (S-06 increment 12) and stay required:

- History begins at migration 00089. Each accepted capture records its cluster, namespace UID, workload UID and origin (`manual` or `policy`) at acceptance; there is no backfill and no discovery origin yet. The selector key is the current workload identity: `list_capture_history` resolves the named workload object first (without requiring any Pod, so a workload scaled to zero keeps its history readable), so a recreated namespace or workload starts a new history.
- `list_capture_history` also accepts `target_ref` (the selector `preview_capture` takes); the runtime implements only that selector. Visibility: current ordinary read rights on the workload, then the original requester or a current member of the capture's retained audience. Summaries and settings are available for seven days after acceptance (the initial case-metadata default). Pages are bounded to 100 entries and 200 examined rows; the cursor is a keyset position bound to the selector and origin, and every page re-authorizes every row.
- For pod-status the repeatable settings are the accepted authored target, the built-in recipe and its dependency pins and the requested retention. These contain no user-supplied content beyond the workload name, so the immutable accepted scope serves as the parameter snapshot; encrypted parameter records, keyed selector/settings digests, the 1,000/100,000 ceilings and eviction, `SettingsTooLarge` and `HistoryUnavailable` are deferred.
- `preview_capture(history_capture_id)` returns `repeated_from_capture_id` and runs every check of a new preview. A name that now resolves to another workload UID fails with `TargetReplaced` after current collection eligibility. `request_capture` and `get_capture` do not yet return `repeated_from_capture_id`; persisted lineage is deferred.

## Repeating compositions

For [capture-profile](capture-profiles.md) requests, the immutable settings snapshot also stores authored components/typed edits, resolved definition UIDs/digests and alias map alongside recipe_spec. All dependency pins and source privacy deadlines remain bound. Restore the original versions; do not consult today's defaults as if they were historical settings. A disabled or deleted profile is a named blocker with an explicit replace/customize path and fresh review. Snapshot sharing still provides no catalog publication, workload history or collection right.

Store resolved execution modes with the accepted recipe/plan. Repeat preserves the chosen modes and requested windows, but recompiles activation for its new request context: a manual repeat of a policy occurrence is finite and does not reactivate policy sources or retain their session/snapshot IDs. Show absent prehistory explicitly; enabling continuous monitoring is a separate explicit policy action. See [action lifecycles](action-lifecycle.md).

## Recording-save entries

REQ-SAV-004 adds operation=recordingSave to manual-origin history. Store only the selected snapshot action IDs/lookbacks and target/policy identity in recordingSaveSettings, never the policy's unselected dumps/commands or old handles/grants/sharing. The existing protected history retention/audience rules apply. Repeat uses requiresSelection and fresh recording inventory; it does not become an ordinary new-recorder capture. The settings digest covers this distinct typed settings object, while original_execution_digest refers to recording-save/v1. get_capture_settings remains read-only and ordinary preview_capture(history_capture_id) returns RecordingSelectionRequired for this kind.
