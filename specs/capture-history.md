# Capture history and repeating requests

Users MUST be able to revisit captures for a workload or pod selector and repeat their settings without re-entering them. This first-release behavior uses the existing [execution service](execution.md), [hub persistence](persistence.md) and [MCP workflow](mcp.md). It adds no history CRD, collector or execution API.

## REQ-HIS-001 — Find previous requests for the same selector

Provide **Recent captures** on the target/selector page and **Repeat capture** on each authorized request and case-linked capture. Show request time, manual/policy/discovery origin, permitted requester identity, action kinds, outcome, evidence availability, saved-settings availability and an authenticated request link. Include pending, failed, cancelled and partial accepted requests, not only successful cases. A rejected request that never reached acceptance is a local form/error state, not durable shared history. History is populated on acceptance, before evidence exists, and updated from the same capture execution records.

Default to manual requests, newest first. Offer explicit policy and discovery filters so automatic trigger storms and short surveys do not bury manually chosen diagnostics. Grouping identical settings is presentation over authorized bounded records; show the covered interval and avoid unaudited global counts. Each policy occurrence has an existing capture identity; history does not create another occurrence or rearm the policy. Suppressed triggers are available through existing suppression summaries, not manufactured capture-history entries.

The **selector key** binds the cluster, the namespace name and either the authored workload kind/name or the canonical authored pod-label expression, matching how targets follow names ([REQ-TGT-001](targets.md)). Ordinary rollouts and a workload recreated under the same name keep the key; UIDs are recorded per request as provenance. Ignore resolved pod members, resourceVersion, map ordering, recipe, maxPods and per-capture pod choice when grouping requests for that selector; preserve those settings in each request. Grouping is not authorization: each record stays visible only under REQ-HIS-003, so a new owner of a recreated workload does not see a former owner's records. Different label expressions remain different selectors even if they happen to match the same pods today; do not attempt general logical equivalence. Canonical equality for the current matchLabels form sorts keys and preserves exact key/value strings. An empty/unauthorized live selector cannot disclose neighboring history.

The request also retains a separate **settings key**, covering the full normalized collection configuration: pod selection/count, recipe version and overrides, process selectors, packet peers/filter/ring settings, endpoints and requested limits/retention. Exclude request IDs, timestamps, grant references, free-text reasons and sharing. This allows several useful past configurations under one target without overwriting them with the newest one. Both keys are SHA-256 digests of the canonical JSON (RFC 8785) of their inputs and are indexed columns of the history row.

### SC-HIS-001

Given two captures using different packet filters for the same Deployment, when its pods roll or the Deployment is recreated under its name, then both settings remain discoverable under that Deployment. Reordered matchLabels keys return the same selector history; a different selector that currently matches the same pods does not. A user without rights to a record's retained audience does not see it, whatever the grouping.

## REQ-HIS-002 — Restore settings into a fresh, reviewable request

A `preview_capture` that restores saved settings runs the settings lookup and the
fresh preview under the request's single deadline (REQ-EXE-002), in browser and MCP
alike. Acquisition bounds of a later submission are separate.

**Repeat capture** restores a new draft from the immutable accepted request's parameter snapshot, not the current mutable recipe of the same name. Keep the original authored target, requested collection settings, fully expanded action recipe, immutable dependency versions/digests and requested retention. Preserve both requested and original effective values where administrative clamping occurred, so preview can explain changes. The stored snapshot is data, never delegated authority. No manual hash, UID or old grant entry is required.

The normal path is select history entry → review restored settings and current differences → **Collect again**. Editing uses the existing capture editor and creates a new preview. Show original versus current effective pod count, capabilities, privacy/retention, budgets and approval needs. Preserve action DAG order/dependencies; unavailable or denied pinned versions are explicit blockers. Never silently switch to the latest recipe, image, runtime pack or projection. An intentional upgrade is an edited plan with a visible difference. Saving/previewing a repeated draft does not collect anything.

The new request has a new capture identity, acceptance deadline, requester/executor, execution digest and idempotency key. Record `repeatedFromCaptureID` as independently expiring opaque lineage. It never grants access to the source record. Revalidate current ownership, collection rights, ceilings, capacity, artifact-purpose rules and dependencies. Automatic policy grants cannot authorize a new ad hoc capture; any intrusive/sensitive repeat needs its own applicable ad hoc approval. It consumes normal workload-wide rate/storage/impact budgets, with no counter reset. A repeat of a policy occurrence creates one manual capture, not a policy or another scheduled series.

Resolve current eligible pods of the same named workload in the same namespace. Preserve logical process selectors and dynamic peer queries; resolve their current members under the usual rules. Do not copy old resolved pod/PID/IP lists as if they were current. An explicit Pod or exact `selectedPID` remains identity-pinned and cannot be replaced silently; if gone, show **Choose a current target/process** while retaining the other settings. An automatic occurrence using `triggeringPod` needs an explicit manual pod-selection choice because the new request has no trigger. A recreated workload or peer under the same name is followed unless the original request pinned its UID.

Old grants, execution permits, deadlines, credentials, resolved secrets, idempotency keys, creator/owner management and sharing instructions are not restored as authority. Secret references may be restored and must be resolved under current scope. Default repeat creates no sharing instruction; the ordinary sharing section lets the user select recipients for the new request. Do not copy the previous free-text reason; a reason is optional, and a repeat carries a generated repeat reference. Clearly show these resets without asking users to rebuild the collection parameters.

Retries of the **same newly submitted repeat** use its same idempotency key and return that operation. Another deliberate Collect again creates another operation. Disable duplicate submission in the UI while accepting, and show already-running captures before another intentional start; server admission remains authoritative. Repeating a Failed/Indeterminate request is an explicit new collection, never an automatic retry of an uncertain process-affecting action. The existing analysis-only retry remains available when fresh acquisition is unnecessary.

Repeat recomputes [impact and data-handling assessment](capture-assessment.md) against current rules, metrics, workload size and retention. Previous success or an old low-impact label is not a transferable safety verdict; old assessments are not restored as authorization.

### SC-HIS-002

Given a previous capture of two matching workers plus packet context, when a maintainer selects Repeat capture, then the settings are restored, fresh matching pods/processes are resolved and present-day limits/approval differences are shown. A double click or lost response creates only one new capture. A new intentional repeat cannot reuse the old ad hoc grant. An expired exact process asks for selection; repeating a policy occurrence cannot silently enable monitoring.

## REQ-HIS-003 — History is bounded private control data

Authorize each record with retained request/audience provenance and current entitlement. Default visibility is the requester who still has current scoped rights, or maintainers whose current rights cover the record's retained audience. Newly acquiring a workload does not automatically expose historical parameters from a former owner. Explicit administrative historical transfer follows the existing ownership rules. A shared evidence snapshot grants neither capture history nor the recipe/command/settings behind it. Listing, counts, source lineage, detail reads and replay previews use the same rules; repeat additionally requires current collection authority. Unauthorized records use the existing uniform unavailable response.

Keep content-minimized history summaries under the configured case-metadata policy (default 90 days, bounded by the administrator maximum). Store each parameter snapshot, including its inline expanded recipe, as a PostgreSQL row next to the accepted capture row ([ADR-330](../docs/decisions/330-event-driven-system-design.md) D8; supersedes ADR-255's object-store records), with original provenance, classification and its own `expires_at`. Rows are protected by volume and backup encryption and the ordinary history authorization; no credentials, reasons or sampled process/traffic lists are stored in them.

A history summary can outlive its evidence, and repeatable configuration can outlive evidence **only when its content policy permits this**. Pure approved configuration keeps the case-metadata lifetime (default 90 days), so last month's capture can be repeated; arbitrary user-supplied paths/arguments/filter literals remain potentially personal and receive applicable stricter limits. Configuration inferred from discovery/evidence inherits the earliest source deadline; history cannot extend it. Retain no captured output in the parameter snapshot. A snapshot row is deleted when its `expires_at` passes. Expired/redacted/incomplete settings produce **Parameters expired/unavailable**, with current catalog choices as a recovery path; do not silently reconstruct them from audit logs, backups or an unreviewed current recipe. Saved reusable configuration is a separate explicit authoring action, not a hidden retention exception.

History bounds: at most 1,000 summaries per selector and 100,000 per installation, with at most a 128 KiB serialized parameter snapshot per request; administrators may lower the counts in Helm values. The snapshot is written in the capture's acceptance transaction. When the bound is reached, the oldest summaries of the same workload/namespace are evicted, never another workload's and never live evidence, execution accounting, grants or audit rows. History capacity must not reject an otherwise admissible capture: without room the capture is accepted without a snapshot and reports SettingsUnavailable.

At least one snapshot is bound immutably by digest to the accepted request before marking its settings available. A mutable referenced recipe disappearing later does not destroy a retained snapshot, but execution still requires its pinned dependencies to be installed and permitted. Backup deadlines obey REQ-PRV-008. Viewing, repeating or pinning a history item never extends the source snapshot/evidence lifetime. Fresh evidence gets its own acquisition clock; existing parameter content keeps its provenance/deadline unless explicitly authored independently under an approved configuration policy.

### SC-HIS-003

Given evidence has expired but an authorized configuration snapshot remains within its own permitted lifetime, when the owner opens history, then they can preview a repeat without recovering the old evidence. Once parameters expire, the summary explains that repeat is unavailable. A new owner or share-only recipient cannot read the old settings. A repeated discovery-derived filter cannot retain personal data beyond the source deadline; history eviction cannot release live capture charges.

## REQ-HIS-004 — Browser and agent use the same history

Add `list_capture_history` with exactly one of a current `target_handle`, a named `target_ref` (as in `preview_capture`) or an explicit cluster name plus `target` selector, optional origin filter, cursor and page limit (default 20, maximum 100). An explicit selector resolves namespace/workload identity under current authority before lookup. Default origin is manual. The caller's authorized namespaces and history audiences are resolved once per request (ADR-311) and applied as a SQL filter; rows are not reauthorized one by one. Pagination is keyset on descending accepted time then capture ID; the cursor binds only the caller and the query. Never return hidden totals.

`get_capture_settings(capture_id)` returns the authorized immutable settings projection: original target, expanded recipe, dependency pins, requested retention if present, settings digest, original effective digest and expiry. It does not return historical reason, recipients, credentials or grants. Arbitrary strings remain untrusted data. The full projection still obeys the standard MCP byte limit; an oversized snapshot returns SettingsTooLarge with authenticated browser navigation rather than malformed/truncated executable settings. Repeating by reference remains available without downloading the settings. The authenticated browser uses a fixed server-owned 160 KiB response budget for this operation only, covering the bounded 128 KiB snapshot and its envelope in one read under the same authorization and source deadline. Canonical JSON avoids HTML-sensitive string expansion; the browser presents bounded sections. No caller-selected budget or larger raw tool response is introduced.

Extend `preview_capture` with a separate `history_capture_id` branch, optionally a new reason and explicit new sharing instruction. It is mutually exclusive with target/diagnostic/preset inputs and requested_retention_seconds, avoiding hidden retargeting or a silent change to the retained requested lifetime. To shorten or otherwise edit retention, use the normal preview editor with optional repeated_from_capture_id provenance. Return the normal preview (plan and `plan_digest`) plus `repeated_from_capture_id`. The same field is returned by `request_capture` and `get_capture` when applicable. `request_capture` with the previewed request, its `expected_plan_digest` and an idempotency key remains the only submission step; listing, reading and repeat preview never start acquisition. Advanced edits use a fresh normal preview with optional repeated_from_capture_id provenance, supported equally in browser and MCP. This normal branch explicitly supplies target and diagnostic/preset and restores no parameters implicitly; supplying provenance still requires current access to its source. It cannot be combined with history_capture_id. Editors retain this reference when copying settings, so current checks and original content deadlines remain attached. Recipe snapshot availability never bypasses administrator disablement.

Both new read tools use evidence:read and current scoped history authorization; preview/submission additionally require collection eligibility and the existing evidence:capture submission gate. Revocation or expiry before submission blocks reuse. Passing a source history ID is not proof of ownership. Existing get_capture remains available for accepted execution status independently of whether its history projection has expired.

### SC-HIS-004

Given an eligible external agent sees a successful capture in selector history, when it calls preview_capture with history_capture_id and then submits the returned preview, then one new capture uses the retained settings under current authorization. Combining history_capture_id with a different target is rejected. Share-only access, revoked history access, expired settings and unavailable dependencies cannot be bypassed through earlier previews or get_capture_settings. A large snapshot can still be repeated by reference within normal MCP output limits.

## Runtime contract

- Every newly accepted capture writes its parameter snapshot row in the acceptance transaction; settings and repeat never fall back to execution scope JSON. The write is charged against the history quota, not workload capture capacity, and needs no live workload observation. A new repeat acquisition still requires the normal workload and capacity checks.
- Runtime selectors are named Deployment, StatefulSet and explicit Pod targets through `target_ref`. Listing resolves the named workload, including at zero replicas, before the keyed lookup; a recreated workload of the same name keeps its grouping. Authored label selectors in history follow once the preview/policy compiler supports them; discovery-origin history follows its own workflow.
- Manual/policy origin filters, original requester, action kinds, outcomes, evidence state and saved-settings state come from execution/history rows filtered by the caller's authorized scope. Pages return at most 100 rows.
- Snapshots retain authored target/selection, recipe, typed composition and dependency pins, requested and original effective retention, and the accepted policy generation. Metadata expiry is independent of evidence expiry and cannot renew source-derived content.
- `get_capture_settings` and by-reference `preview_capture` use current history rights and retained audience. Recorder repeats restore original filters/windows, version pins and composition through the normal current preview, refuse implicit dependency/compiler upgrades and require explicit current Pod selection for policy triggering-Pod occurrences. Browser editing of restored compositions uses finite typed overrides and the same normal MCP preview branch. No old approval, reason, sharing or execution identity is restored.
- Repeat lineage is stored at acceptance and exposed by request/progress only under current source-history rights and its independent source deadline. Edited repeats retain that source binding.

## Repeating compositions

For [capture-profile](capture-profiles.md) requests, the immutable settings snapshot also stores authored components/typed edits, resolved definition references/digests and alias map alongside recipe_spec. All dependency pins and source privacy deadlines remain bound. Restore the original versions; do not consult today's defaults as if they were historical settings. A disabled or deleted profile is a named blocker with an explicit replace/customize path and fresh review. Snapshot sharing still provides no catalog publication, workload history or collection right.

Store resolved execution modes with the accepted recipe/plan. Repeat preserves the chosen modes and requested windows, but recompiles activation for its new request context: a manual repeat of a policy occurrence is finite and does not reactivate policy sources or retain their session/snapshot IDs. Show absent prehistory explicitly; enabling continuous monitoring is a separate explicit policy action. See [action lifecycles](action-lifecycle.md).

## Recording-save entries

REQ-SAV-004 adds operation=recordingSave to manual-origin history. Store only the selected snapshot action IDs/lookbacks and target/policy identity in recordingSaveSettings, never the policy's unselected dumps/commands or old handles/grants/sharing. The existing protected history retention/audience rules apply. Repeat preselects the same policy and save actions on the workload's current pods, with the reason prefilled, and previews them as a recording save over fresh recording inventory ([ADR-335](../docs/decisions/335-usable-by-default.md) D4); it does not become an ordinary new-recorder capture. When no current source matches, the preview reports `NoCurrentSource`. The settings digest covers this distinct typed settings object, while original_execution_digest refers to recording-save/v1. get_capture_settings remains read-only; `preview_capture(history_capture_id)` returns the preselected recording-save preview for this kind.
