# Save existing recordings now

This is a first-release, snapshot-only invocation of a policy's already authorized ongoing packet/syscall sources. It does not evaluate a fake detector, rerun the recipe, start a source, change filters or collect a dump. It uses the existing capture service, SQL execution/capacity/audit state and regional publication pipeline; no new CRD or service is needed. The [recording-save contract](contracts/recording-save.schema.json) distinguishes it from ordinary collection. Mechanisms follow [ADR-330](../docs/decisions/330-event-driven-system-design.md).

## REQ-SAV-001 — Discover eligible recordings and explicit policy scope

`DebugPolicy.spec.recordingSaves.enabled` authorizes eligible workload maintainers to request bounded saves from that policy. It defaults to true for a policy with ongoing actions and is invalid without one. The policy grant review displays it: the reviewer sees that maintainers may save existing recordings without a detector firing. It is not part of the collection execution digest, because a save only freezes bytes the reviewed policy already observes: changing it neither restarts the recorder nor invalidates the grant. A change is an ordinary audited policy edit by its owners and appears on the grant's review page and at its next renewal. Setting it to false stops new saves at once.

The caller needs current whole-pod collection entitlement for every selected pod and the configured client scope. The policy execution identity must independently retain all original acquisition/save authority and applicable sensitive observation grants. Under ADR-059 this is the recorded team policy identity and its automation envelope, not continued membership of its creator. The save initiator still requires current personal authority. A policy's authorization is never transferred to the caller: the save runs as that policy's narrowly approved snapshot operation and records the initiating actor separately. A share, evidence-reader role, grant or recording handle alone confers no collection ability. Disablement, local deny, suspension, source authority expiry/revocation or a policy execution-digest change invalidates new saves, including accepted but unstarted work. While its connector is disconnected, a source runs to its admitted hard end. Entitlement follows the workload name (ADR-335 D4); a handle pins its exact source session, so a replacement pod's recorder is never reached through an old handle.

Expose **Save existing recordings now** in the authorized policy/workload view. Passive inventory shows only permitted policy/pod/action rows, source state, observed history duration/gaps, configured maximum lookback and eligibility/blocker. No packet contents, syscall arguments, process inventory or hidden-source counts. A recording handle is an opaque, principal/client-bound reference to an exact source session, action/filter and policy execution digest; it has no wall-clock lifetime and is checked against current state when used. It is not bearer authority. Reading inventory or preview does not read payload, pin buffers, reserve capacity, extend a source's hard end or arm collectors. Pages default to 20 rows and also end at the MCP result bound; cursors are opaque positions authorized on use.

### SC-SAV-001

Given a maintainer and an extract-only share recipient, when they inspect one workload, then only the maintainer can discover/request eligible saves. Setting recordingSaves to false stops new saves without restarting the recorder; setting it to true leaves the grant valid and shows the change on the grant. A disabled policy or a replaced pod's source cannot be saved through an old handle.

## REQ-SAV-002 — Snapshot identity, window and narrow execution

One save selects one or more distinct source handles from one policy execution scope, cluster, namespace and workload; their number is bounded by the policy's incident pod cap (maintainer decision: per-incident collection is capped independently) × its ongoing actions. Apply that cap and local ceilings; this selection may choose any authorized observed pod within that cap instead of needing a triggeringPod. UI defaults to the currently selected pod and its eligible sources, and displays any cap before submission. Do not silently drop unauthorized selections or combine sources from different policies. Only ongoing packetCapture/syscallTrace actions are eligible. A source with zero configured history cannot supply a historical save; show NoHistoryConfigured and an explicit separate future-capture choice.

Default lookback is each selected source's policy-configured before. An optional common before can only shorten those bounds and must be positive. This operation has **after: 0s**: it saves already observed bytes, without extending recording into a new post-window. Future capture remains an explicit ordinary capture choice. Preserve representation, filters, endpoint/action identity, source audience, limits and privacy ceiling exactly. No new dependencies, context actions, runtime profiles, cores, commands, process selection or acquisition parameters are accepted.

The preview is a stateless dry run (ADR-330 D9). It returns the resolved recording-save/v1 plan and its digest: requester, policy executor/reference/execution digest, exact source/pod/node/action/definition identities, per-source lookback/output caps, pod cap, effective ceiling/retention and the capture assessment. It stores nothing and promises no capacity or history. Submitting the plan digest with an idempotency key either accepts that plan or reports what changed. Metadata-only policy generation changes are provenance; execution identity and save enablement remain authoritative.

Acceptance persists one immutable t0=acceptedAt with its clock uncertainty, finalize deadline, plan digest and idempotency key. t0 is the end of every selected source's requested [t0-before,t0] interval. The caller cannot supply t0 or a future window, and retry or dispatch never changes it. Node receipt later than t0 may lose history; it never captures newer bytes to compensate. Clock uncertainty, retained-source grace, local coverage and earliest content expiry bound usable evidence. Use a qualified wall-to-monotonic mapping and exclude records that cannot be placed before t0 within its bound; unknown mapping produces ClockUncertain/partial or refusal, not a claim of exact coverage. Warming/degraded/stopped-but-still-valid sources may yield explicit partial output; a different source session never fills the gap.

Acceptance authorizes the save once (ADR-311) and commits the parent capture, one child per selected source, their audit rows and their dispatch work in one SQL transaction. The hub then pushes each child to its node over the connector connection immediately; the node pins the selected ring segments on receipt. No child waits for a separate audit acknowledgement or for its siblings. A child starts when its node receives it and saves whatever history is still retained before t0; it is bounded by the source's hard end, its processing authority and ring eviction, and reports its actual coverage. A child whose source has ended or whose history was evicted yields Partial/Failed with its reservation released. Accepted dates never change.

After acceptance, each source save is independent. Race with rotation, pod/source loss or revocation produces Partial/Failed/Denied under normal capture state rules. At least some meaningful retained coverage must exist to save; a fully observed quiet interval can be a valid empty-record artifact with coverage metadata. A wholly absent source yields no fabricated successful evidence. Already frozen snapshots can finalize under their remaining processing/storage authority. Cancellation releases only this capture's snapshot references/reservations and never stops its separately authorized recorder. No source restart or unapproved fallback occurs.

### SC-SAV-002

Given a policy containing packets, syscalls and a live core, when the user saves two sources with 20 seconds of lookback, then only packet/syscall snapshots are admitted. No core or new recorder starts. A source that became stale after preview is rejected at submission or reported lost after acceptance; retry with the same idempotency key returns the original capture and t0. A retired source can provide only the still-authorized portion ending at its recorded stop.

## REQ-SAV-003 — Budgets, privacy, audience and sharing

Manual saves use the same policy/workload occurrence cooldown/rate, concurrent snapshot/output, per-node, storage and fair upload limits as automatic incidents. A save charges no run count: recorders and policies have none ([ADR-335](../docs/decisions/335-usable-by-default.md) D6), and those rate, cooldown and concurrency limits (D8) bound saves. The false/true detector hold/rearm condition is not needed for this separately authorized operation, and is not reset by it. No reserved emergency bypass. Bursts of clicks or multiple users/policies remain subject to shared workload accounts. Offer an already admitted capture only when the caller may read it, as a clearly labeled alternative rather than a new save. Refuse with a precise blocker/retry time when immediate bounded admission is unavailable; do not silently queue a fresh future save after cooldown. A repeated submission with the same idempotency key returns that capture; a different request with the same key conflicts.

A save draws on no cumulative grant budget: the sensitive bytes were authorized when observed, and the grant's expiry bounds its lifetime (ADR-335 D6). Saving existing bytes does not count a second wire observation or spend a live-core execution. Snapshots consume workload storage quota and capacity/occurrence budgets, reserved at acceptance. Each child's reservation is released or settled to actual usage when its outcome is known; an unknown child outcome is resolved by looking up its operation ID (ADR-330 D7). Cancellation does not reset rate or occurrence counters. Pin/copy/encrypt only after acceptance has committed. No per-click human approval is needed when this exact manual-save capability was already approved; missing approval blocks the save and links to policy review rather than retaining unapproved buffers while waiting.

The assessment describes the **incremental** freeze/copy/encryption/upload cost and continuing recorder baseline separately. Saving creates no new probe/ptrace pause, but collector CPU/memory, storage and transfer may still contend with the workload. Preserve unknown overhead, possible sensitive contents, source-age retention and external-agent handling warnings. The UI may preview and submit in one interaction; a changed plan digest at submission refreshes the review. A preview never guarantees how much history survives until acceptance.

Retention starts at original source acquisition, not the save click or upload. Inherit the earliest applicable deadlines, processing restrictions and retained audiences of included segments, intersected with current rules. Split outputs at incompatible audience boundaries or use the intersection; never union old and new ownership into wider access. New creator/initiator status, policy operation and current exec rights do not grant raw read permission or retroactive audience membership. Default evidence access uses these source audiences and current evidence entitlements. Raw queries retain their per-principal/client grants.

Recurring policy sharing instructions do not automatically apply to these manual saves. An owner may attach a new per-capture `sharing` instruction to the preview using the existing capture-time declaration/approval/count/expiry rules. Validate the instruction before acceptance; bind it to this recording-save plan digest and captured action IDs. Materialize only authorized actual outputs and approved derivatives. Pending raw-sharing approval does not freeze a live ring indefinitely or authorize a raw read. Report collection/sharing progress independently.

### SC-SAV-003

Given two maintainers repeatedly save a sensitive ring during an automatic incident, when shared quota/cooldown is exhausted, then later saves are refused without another ring, dump or capacity slice. An admitted save retains the earliest source deadlines/audience. A new team member does not gain old evidence through the click, and a policy's unrelated future-sharing instruction publishes nothing from this save. Explicit authorized capture-time sharing follows its normal checks.

## REQ-SAV-004 — Browser, MCP, history and provenance

MCP uses `list_recordings(target_ref, policy?, cursor?, limit?)`, then `preview_capture(recording_handles, before?, reason?, sharing?, repeated_from_capture_id?)` (the recording-save branch of the ordinary preview), and `request_capture` with the returned plan digest and an idempotency key. `request_capture` is enabled by default for authorized users and needs evidence:capture; preview/inventory require current collection eligibility as well. Preview returns operation=recordingSave, the plan digest, selected rows/window, incremental capture assessment and blockers. Handles are service-owned; users do not enter hashes/session IDs. The browser uses the same services and evaluator. get_capture/cancel_capture keep the existing capture/progress contract with an explicit recordingSave operation discriminator; the browser receives progress over its page's event stream and MCP `get_capture` waits server-side for the next change (ADR-330 D1). The recording-save branch compiles only recording-save/v1 plans and the recipe branches never accept recording handles. These are runtime capture operations; Kubernetes remains the only policy/permission configuration API.

Grouped progress retains one public parent `capture_id` and one action row per selected source. Each grouped row has an immutable `action_instance_id` (the actual child identity), retained `pod_uid`/`pod_name`, and the configured `action_id`; the configured action may repeat across Pods. Child identities distinguish results without creating child navigation or submission targets. A parent cancellation requests all unfinished snapshots; stored results win and remain available. `cancellation_requested` is not proof that remote work has stopped. Per-source capture-assessment rows use `recording_handle` to bind the selected row, retain its original source acquisition retention anchor, and describe only the incremental save cost; they do not relabel a packet snapshot as pod status or claim measured ongoing-recorder overhead.

Accepted saves appear in the same selector-scoped history with origin=manual and operation=recordingSave. A recordingSaveSettings SQL row retains only the target, policy name, action IDs, lookback, reason and original plan provenance, under the normal audience and history retention. Do not include the policy's other recipe actions, source handles, grants or sharing instructions in repeat parameters. Repeat preselects the same policy, actions and lookback on the workload's current running sources and opens the ordinary save preview with the old reason prefilled and editable, retaining optional repeated_from lineage; it never replays the old source session or silently turns this into a new recording/core capture. get_capture_settings returns the distinct typed record. preview_capture(history_capture_id) for this kind returns that preselected save preview, or NoCurrentSource with the inventory link when no matching source runs; it never interprets the record as a recipe.

Artifacts carry ongoing acquisition provenance with triggerKind=recordingSave, t0, original source session, snapshot ID and truthful prehistory/whole-window coverage. recordingSaveOrigin binds the policy UID/execution digest; collectionProvenance.planDigest is this save's recording-save/v1 digest, not the policy's collection-scope digest. Store requester/actor separately from the unchanged policy executor; neither is editable by a client. The encrypted artifact manifest retains the exact accepted source window and source binding (node and source session), so it remains inspectable after source metadata retirement. Selections, settings and status are ordinary SQL rows (ADR-330 D8).

The optional reason is nonempty free text, bounded only by the HTTP request body limit, preserved verbatim in the capture's SQL row as descriptive metadata. It is not justification, consent, collection/grant authority or a scope change. Grouped saves retain one parent reason across all children. `get_capture` displays it to callers authorized to read the capture's metadata. The reason is deleted with the capture history row and never extends retention.

### SC-SAV-004

Given an enabled MCP client, when it saves an eligible ring and retries the same submit after an ambiguous response, then it gets one capture and can follow/cancel it with existing tools. History labels it as a recording save; repeat preselects the same policy actions on current recordings and cannot invoke the policy's liveCore action. The evidence manifest identifies both the saved source and the manual-save origin. A request with a dump parameter, mixed-policy handles, after>0, forged executor or a handle whose source session has ended fails before new acquisition.

## Saving from a live view

The [live watcher](live-watch.md) offers the same save action for a policy source, using current eligible recording handles and the unchanged save preview/acceptance checks. The selected display predicate is not a capture filter; it cannot narrow/widen source acquisition parameters or define the saved artifact representation. A paused view does not pin a row. Explain that t0 is the new save acceptance time and earlier displayed rows may already have rotated out. Do not attach a live-only source/session to this policy-save API or silently substitute the ongoing policy's recipe. Finite manual-session sources lead to their own capture outcomes. Ordinary owner sharing/retention checks apply only to committed results.

## Immediate save interaction (REQ-SAV-001/002)

One action, “Save last N seconds” (N = the approved lookback, i.e. the policy's own `before`, bounded by its ring; default 30), appears wherever an eligible source is shown: recording inventory, live view and capture history. It is the only way users save existing recordings. Display source, available history, output/access/expiry and bounds before the click. An explicit click performs a dry-run preview and submission without another human review page when the plan digest and material disclosures are unchanged. “Customize” opens the existing selector/review. If scope or impact changes, block/refresh with a precise explanation; never silently broaden or pin before acceptance. Browser/MCP callers use the same preview/request contracts and idempotency. t0 remains the acceptance time, so network latency/eviction can still produce explicit missing coverage. The receipt identifies the actual saved source/window; never advertise recovery of evicted history.
