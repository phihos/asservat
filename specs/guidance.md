# Guided evidence selection

Asservat helps maintainers and external agents decide **what to capture for a diagnostic goal**, then produces an editable, executable plan. This is a first-release requirement. It builds on [actions](actions.md), [packet capture](packets.md), [execution](execution.md) and [ergonomics](ergonomics.md). The [research](../docs/research/guided-diagnostics.md) separates upstream capabilities from work Asservat must implement. All examples and defaults here are design proposals, not measured results.

## REQ-GDE-001 — Start with the question

The normal browser journey MUST support workload → diagnostic goal → ranked evidence suggestions → effective preview → collect or create a policy. Keep direct diagnostic selection available to experienced users. Do not require knowledge of debugger commands, process IDs, BPF, snaplen, profile formats or ring arithmetic. Offer `unknown`, `crash`, `memoryGrowth`, `highCPU`, `latency`, `hang`, `network`, `dns` and `probeFailure` goals with plain-language labels. A goal is not a diagnosis.

Use a local, deterministic, versioned rule catalog over current capabilities, authorized observations and explicit preferences. No embedded LLM, external model call or uploaded evidence is required. Each suggestion has a reason, supporting observations with times and confidence, what it can answer, what it cannot answer, prerequisite gaps, impact, maximum bytes/process starts, retention and approval requirements. Give useful alternatives when a recommendation is unavailable; do not replace an unavailable action with a more intrusive one silently. The user can skip discovery, edit the proposed plan, or choose another supported diagnostic.

Initial goal coverage:

| Goal | Start with | Escalation when useful | Explain the limit |
| --- | --- | --- | --- |
| Unknown failure / failed probes | Events, recent logs, restart/probe timeline, resource and process/socket context | Runtime stacks, short profile or narrowly scoped traffic | Current discovery cannot recover events that were never recorded |
| Crash or repeated restart | Existing kernel core if present, previous logs, termination reason, exact build/symbol availability | Arm bounded next-crash collection; live dump of a surviving matching process | SIGKILL/OOM may leave no core; a replacement process cannot reconstruct the dead one's memory |
| Memory growth / OOM | cgroup limit/pressure, RSS and mappings; existing runtime heap summaries | Supported heap/allocs profiles and comparable baselines; core for native state | RSS alone is neither a leak diagnosis nor an upper bound on core size; no forced GC by default |
| High CPU | cgroup throttling, resource timeline, process identity; supported short CPU profile | Qualified runtime/thread stacks or native sampling pack | Profiles need a qualified adapter; a core is not the default CPU measurement |
| Latency / hang / deadlock | Probe timeline, process/thread state, socket counters; supported runtime stack/block evidence | CPU/block/mutex profiles if prerequisites hold; bounded sequential process dumps | Sequential dumps are not a simultaneous distributed snapshot; disabled sampling is not zero contention |
| Network / DNS | Endpoint readiness, routes/socket/counter context and L3/L4 sample | Approved protocol reconnaissance; narrow DNS/HTTP projection or raw prefixes | Ports and Service declarations suggest protocols; TLS, missed handshakes and partial traffic limit inference |

Identify missing capability or ownership prerequisites before asking for expensive evidence. Do not run a profiler, force GC, stop a process, probe an arbitrary port, read arbitrary files, or generate network traffic merely to decide which suggestion to show. Configured endpoint templates and runtime metadata can establish candidates; their existence does not prove that an endpoint responds.

Rank suggestions using the [current capture assessment](capture-assessment.md): explain combined impact/uncertainty and likely sensitive contents alongside goal relevance. Prefer a less disruptive useful alternative when available, but explain lost diagnostic coverage and let the user select it. Recommendations never run a trial capture merely to produce an impact estimate; optional surveys retain ordinary capture/approval semantics.

### SC-GDE-001

Given a Go workload with a qualified CPU endpoint and high CPU, when a maintainer chooses that goal, then the first useful plan explains throttling/context and short CPU profiling, including the profile's approval. A JVM workload without a qualified pack receives a capability-specific alternative, not a fabricated pprof URL or command.

## REQ-GDE-002 — Discover processes and propose durable selectors

Offer an explicit **Inspect processes** action, using the same bounded capture service as any other diagnostic. Reuse sufficiently fresh authorized evidence when available; show its age and coverage, and offer refresh without silently acquiring new data. Discovery covers selected whole pods, with the existing 64 runtime-instance / 256 process ceilings per pod, pagination and explicit incompleteness. Default one pod; show the pod selection and offer other authorized replicas. A one-pod sample says nothing conclusive about every replica.

The qualified `processSnapshot` identity projection supplies process reference, display PID in its recorded namespace, executable path/name, start identity, parent relation, qualified runtime/build identity and available memory/counter metadata. `process_ref` pins the complete internal identity; equal display PIDs in separate PID namespaces are distinct rows. Whole-pod permission and configuration remain unchanged. Exclude Asservat's own diagnostic workers and the sandbox process. Missing executable/build/runtime identity remains unknown. Do not collect argv, environment, arbitrary file contents or memory to improve a suggestion. Executable paths, socket addresses and process names remain potentially sensitive evidence; escape display text and enforce projection policy.

Suggest stable `matchedProcesses` selectors using the existing exact executable/runtime/build fields. Explain that a build ID is intentionally narrower across an upgrade and that a generic `python`, `node` or `java` executable can match several unrelated workers. Never invent an application identity from a truncated process name. Where no safe distinction exists, show the ambiguity and offer an exact current process or an explicitly broader bounded batch. Do not introduce container selection as a workaround.

For a proposed selector, show matching processes, excluded processes and reasons, descendant inclusion, current count, incomplete discovery and the worst permitted batch. A complete inventory is required to assert a complete match count; overflow cannot be presented as a successful partial match. A fresh process-reference selection resolves to `selectedPID` internally without asking users to type boot IDs or start ticks. Logical selectors resolve again at dispatch and pin identities under [the existing dump rules](actions.md); stale exact references fail. No dump, attach or stop occurs during discovery or preview. Multi-process plans expose serial stop time, per-process bytes, total bytes and all individual rate-budget charges.

### SC-GDE-002

Given two `/app/worker` processes and a reloader, when inspection suggests an exact executable selector with descendants, then the user sees the matching set and bounded batch. Reloading before dispatch selects the new matching identities; reuse of an old exact PID cannot target a different process. Two indistinguishable interpreter applications remain ambiguous rather than receiving a guessed selector.

## REQ-GDE-003 — Short reconnaissance is an ordinary bounded capture

Provide three immutable discovery diagnostics through the existing diagnostic catalog, without a new CRD, permission API or execution service:

| Diagnostic | Acquisition | Initial packaged bounds per selected pod |
| --- | --- | --- |
| `inspect-processes/v1` | Identity/status/cgroup process snapshot and qualified socket-owner metadata | 2 MiB total output, 5 s action deadlines, 10 s overall |
| `inspect-network/v1` | Network/process context and a verified network-header sample | 10 s sample, 4 MiB packet output plus 2 MiB context, 20 s overall; no application bytes retained |
| `inspect-protocols/v1` | Same context and explicitly sensitive raw packet prefixes, then a fixed approved protocol projection | 10 s sample, 2,048-byte snaplen, 8 MiB packet output plus 2 MiB context, 20 s acquisition overall |

Initial packet recipes have `before: 0s`, one capture snapshot, memory rings, finite peer scope and no persistent monitoring. Header survey ring: four 1 MiB segments. Protocol survey ring: four 2 MiB segments. Discovery never claims prehistory. No implicit survey retention exception applies: access expiry is earlier than the cleanup deadline where the configured deletion budget requires it. A broader peer scope must be displayed as all traffic of the selected pod within the administrator ceiling; it does not authorize collection inside peer pods. Users may narrow peers before sampling. Stop at the earliest duration/output/impact/observation limit, and report why it stopped. Do not loop, auto-retry partial surveys, or run another sample while recommending a plan.

Header sampling uses administrator impact/rate ceilings. Protocol sampling additionally requires an individually approved ad hoc sensitive-observation grant, with default proposed reservation of 64 MiB observed wire bytes, 8 MiB/s and 10 s, all clamped to administrator limits. Raw prefixes can contain credentials and user data even at small snaplen. Existing policy grants do not authorize an unrelated ad hoc survey. The browser provides one reviewable request and an approval link; agents use the same flow. Do not charge only retained prefixes: all bytes entering the sensitive path count against the observation grant. Increasing snaplen or widening scope produces a new reviewable plan.

Surveys share workload/node concurrency, rate, bandwidth, storage and impact accounts with regular captures. Initial additional discovery ceilings are one in-flight survey per workload, one start per 30 s and ten starts per hour across principals/clients; administrators may lower them. Reserve before starting, and give ongoing incident collection priority over reconnaissance. Shared reuse requires current read and collection authority and matching scope/projection; an idempotent retry or reuse incurs no new acquisition. Defaults are finite and exposed in installation configuration, not per-maintainer YAML.

Survey captures are private to their ordinary evidence audience unless explicitly shared. Initial requested acquisition lifetime is 15 minutes, including raw input, projections and evidence-bearing recommendation drafts, clamped to hard retention maxima. Cleanup starts inside this lifetime under the existing deletion budget. If analysis/deletion cannot fit, refuse the sensitive survey with a remedy. A five-minute recommendation handle does not reset the acquisition clock. Plans that persist observed paths/peers carry privacy provenance and a finite expiry; a new diagnostic plan is not a way to store observations indefinitely in SQL or audit. An independently authored recurring selector is configuration, still access-controlled; make this transition explicit when saving a policy and retain no sampled process list/traffic in its spec.

### SC-GDE-003

Given a maintainer who may collect context but has no sensitive grant, when they inspect processes or choose the header survey, then no extra second-person approval is invented. Choosing protocol reconnaissance creates a single bounded approval request. A rapid repeated click, another agent or exhausted workload quota cannot start a second sensor; waiting for approval starts no raw sampler.

## REQ-GDE-004 — Show observed traffic, qualified attribution and uncertainty

The discovery report MUST include capture interval, selected/covered pods, observed versus retained bytes, drops/truncation/early-stop reasons, classifier/projection versions, and actual coverage. Flow views show transport, peer address/port, direction, visible Kubernetes peer candidates, protocol evidence and process association where qualified. Report `observed`, `inferred`, `ambiguous` or `unknown` with the basis for **each attribution**, not one confidence score for the whole flow.

- L3/L4 headers establish transport and addresses, not arbitrary application protocols. Port numbers and `appProtocol` are hints. A qualified decoder may confirm DNS, plain HTTP/1, a visible HTTP/2 cleartext preface or a TLS handshake from approved raw input. First release requires these bounded classifiers; unsupported protocols remain unknown. Recognizing an HTTP/2 preface does not enable HTTP/2 header capture. Do not persist DNS names, URLs, header values, TLS names or payload excerpts in this planning projection.
- TLS hides application data. A client's offered ALPN values do not prove the negotiated application protocol; missed/encrypted handshakes can prevent classification. Label outer TLS separately from a hinted inner protocol. No automatic decryption, TLS-key acquisition or socket uprobes are introduced.
- A pcap has no PID field. Combine qualified socket-owner snapshots and, where qualified, bounded connection events with packet observation time, socket identity, network namespace and process start identity. A connect event identifies its actor at that time, not every subsequent sender. Shared/inherited sockets, proxies, UDP and vanished processes may yield several candidates or unknown. Do not require full PID attribution for a useful capture.
- Resolve Service/backend/workload candidates from fresh authorized Kubernetes metadata. One backend can belong to several Services; packet data after NAT may not identify the original Service. Preserve candidate sets and the observation point. DNS names and reverse DNS are not authoritative Service identity; do not send external DNS queries to decorate results. Hidden peer inventory remains hidden; a visible traffic address does not grant peer workload permissions.

Recommend capture observation points automatically only within the qualified pod-attributed hooks, for example the workload network interface or supported pod loopback. Explain which path each covers, duplicate handling and whether proxy/NAT effects obstruct interpretation. Do not claim that an arbitrary node/host/TLS attach site is selectable. Lack of a qualified site yields a capability gap with available context alternatives.

### SC-GDE-004

Given TLS on port 8080 to a backend selected by two Services and a socket shared by two workers, when a survey completes, then the report distinguishes TLS observation, application-protocol hints, both permitted Service candidates and ambiguous process attribution. An empty sample reports no traffic observed in that interval, not that the workload has no dependency.

## REQ-GDE-005 — Generate useful filters, capture modes and sizes

Recommendations MUST produce an editable diagnostic handle accepted by the existing preview flow, plus an understandable settings view. Prefer a current UID-resolved Service/Deployment/StatefulSet peer with `resolution: follow` when the evidence supports that choice. Explain backend versus VIP coverage. Keep several plausible choices visible when Service identity is ambiguous. Generated pcap expressions are checked capture-filter syntax, not Wireshark display syntax; intersect them with whole-pod and peer scope. Use bounded literals/AST construction, never concatenate untrusted process/hostnames into commands. Display filter scope and estimated excluded traffic before execution; a zero-match sample does not prove a future filter is useless.

Suggest `networkHeaders` for transport failures, `httpHeaders` for supported plain HTTP/1 application context, and `rawPackets` only when the goal requires approved payload/prefix analysis. An HTTP-header goal selects the parser/projection and reassembly budgets, not a magic snaplen. TLS/HTTP2 limitation messages include useful alternatives such as existing application logs and profiles. Raw snaplen is a byte/diagnostic tradeoff; show measured truncation and protocol uncertainty. Do not automatically increase it or claim any finite prefix always includes a complete request.

Offer **desired history** and **ring storage limit** as the primary ring controls, with separate output/frozen/parser costs visible. Advanced segment count/size remain available. Estimate from the serialized retained representation for the proposed filter/profile, including record overhead, not from link throughput or the entire unfiltered sample. Prefer replaying an already approved sample through the proposed qualified projection; if unavailable, show the basis as estimated or unknown. Observed wire-byte rate is a separate input for sensitive-observation grants. Sparse, saturated, truncated or single-replica samples cannot establish a reliable workload peak.

Initial sizing rule: with retained bytes/s `r`, desired history seconds `H`, explicit burst factor `f` (default 2) and segment bytes `S`, recommend `N = max(2, ceil(r * H * f / S) + 1)` segments and `M = N * S` bytes. The extra segment accounts conservatively for writable/eviction slack. Apply packet schema bounds, `maxAge >= H`, node aggregate, frozen snapshots, parser/scratch, upload, workload protected capacity and retention constraints. Treat estimates and hard limits separately. If `N > 64` or a ceiling cannot fit, offer less history, narrower peers, smaller evidence representation or a reviewed capacity request; do not silently clamp while claiming the original history.

For example, projected retained traffic of 512 KiB/s, 30 s history, factor 2 and 4 MiB segments suggests nine segments / 36 MiB per pod. At a 16 MiB ceiling the same formula supports at most 12 s with four segments; disclose the tradeoff. Show total selected-pod and same-node costs separately. Reserve the actual maximum ring, output, frozen and parser space under existing accounting; a recommendation is not a reservation or an upload-completion guarantee. Zero traffic produces an unknown estimate and bounded packaged default, not a zero-byte ring. A newly armed ring starts empty: display warm-up and actual available history; discovery samples do not manufacture pre-trigger history for a later capture. Runtime coverage/loss can recommend a new plan but must not silently resize an active approved capture.

### SC-GDE-005

Given the 512 KiB/s sample and a 16 MiB ceiling, when the user requests 30 s history, then the UI and MCP explain the 36 MiB estimate and offer an explicit 12 s alternative or narrower filter. A large payload-bearing HTTP packet is never advertised as headers-only because snaplen is small. A burst after the survey yields a visible history gap without budget escalation.

## REQ-GDE-006 — Equal assistance for people and agents

Browser and MCP MUST use the same catalog, projections, evaluator and plan compiler. The service extends the existing capture workflow rather than creating another execution API:

1. `list_targets` / `list_diagnostics` discover eligible scope and diagnostics, including the three inspection entries. `recommend_diagnostics(target_handle, goal, discovery_capture_ids?, preferences?)` can start with existing capability metadata and explicitly state missing observations. It is passive: no new live reads from the application, packet acquisition or analysis of unapproved raw content.
2. A discovery diagnostic runs via `preview_capture` → `request_capture` → `get_capture`. In the UI, a clearly labeled **Inspect processes** or **Sample traffic for 10 seconds** button composes this ordinary sequence; display pod count, limits, privacy and approval before the explicit acquisition click. Avoid separate forms asking for hashes/UIDs. `cancel_capture` stops remaining survey work.
3. `get_target_discovery(capture_id, section, cursor?, limit?)` returns bounded approved process/flow/summary projections, never raw packet bytes. Fixed offline projections run under the accepted capture/analysis plan, not as arbitrary raw queries. Report pending projection using the existing bounded asynchronous query envelope; polling never starts or repeats acquisition.
4. `recommend_diagnostics` consumes at most four authorized discovery captures and returns up to eight ranked choices. Each contains a `diagnostic_handle`, rationale, confidence/gaps, cost/impact/privacy, and applicable selector/packet/ring settings. The user can inspect the expanded plan in the browser and edit supported fields before a fresh preview. The external agent can focus a recommendation on process/flow references from the supplied discoveries, use the resulting handle directly with `preview_capture`, or use the existing expanded recipe authoring path for advanced changes.
5. Preview and accepted execution recheck current target UIDs, policy, budgets, permissions and capabilities. Recommendation handles bind principal/client, target, catalog/dependency digests and input provenance; they expire within five minutes or earlier source expiry. They share the existing 10-per-principal / 1,000-per-installation planning allocation (each result group counts once), use bounded encrypted content storage, and never become bearer authority. Captures, query jobs and evidence retain their existing quotas/deletion rules.

Tools accept and return the strict [guidance contract](contracts/guidance.schema.json). All normal MCP output/cursor/audit/client-disclosure limits apply; process/flow projections are evidence extracts, not harmless control metadata. Current artifact-read and live-target collection eligibility are both required for discovery planning; shared-evidence recipients use ordinary case/extract tools and gain no live inventory. Recheck every source artifact, including on pagination. Untrusted executable names, labels and packets never become tool instructions, links to fetch, parser plugins, or executable code. Recommendation rank is not authorization, diagnosis certainty or automatic approval.

### SC-GDE-006

Given a browser user and an authorized external agent with identical target, preferences and observations, when each asks for latency guidance, then both receive equivalent ranked plans and limits. An expired survey, hidden peer, revoked source permission, foreign handle or malicious process name cannot leak data or cause acquisition. Two retries of the same discovery capture return the original operation. Saving a future policy shows its distinct target/trigger/approval and retained configuration before submission.

## Recommendations built from capture profiles

Prefer compatible [capture-profile](capture-profiles.md) components for reusable recommendations. A diagnostic handle can bind the same typed composition; preview returns its effective versions, edits, aliases and aggregate cost. Suggestions for HTTP/1 headers expose encryption/framing gaps. Suggestions for syscall activity begin with bounded metadata and explain that syscall names/results cannot reveal paths or message bodies; argument collection is an explicit separately approved change. New workers are included at pod scope without a PID picker. Recommendations must not acquire trial syscall traces or publish derived profiles merely to populate the catalog.

Recommendations distinguish evidence that can be acquired after a symptom from evidence that must already be recording. Packet/syscall history requires an ongoing armed source; future-only surveys are finite and cannot recover prior traffic. Suggest enabling an ongoing profile for a future recurrence when history is missing, with its continuing cost/approval visible. Do not label a pprof interval started after a failure as historical evidence. The common [lifecycle preview](action-lifecycle.md) makes those boundaries visible to users and agents.
