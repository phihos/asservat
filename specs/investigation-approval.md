# One review for a bounded investigation

The maintainer selected one independent human approval for a one-off capture and the same developer's subsequent inspection and download. This refines [authorization](authorization.md) and [downloads](artifact-downloads.md) under [ADR-335](../docs/decisions/335-usable-by-default.md) D5/D9. It does not remove review, confer workload eligibility or create a general future-artifact grant.

## REQ-INV-001 — Review the intended outcome once

A manual `operation=collect` capture may request `resultAccess` with its collection plan. The UI offers **Collect and investigate** when raw follow-up access is needed, and a collection-only choice. The one review shows acquisition effects, the exact capture/Pod scope, selected output actions, allowed follow-up operations, the requesting human, artifact/count/byte/query ceilings and the access end. Result access belongs to the requesting human and covers every client that authenticates as that human (the console and the user's MCP clients, ADR-335): an agent acting for the user gets the same evidence access, including raw evidence and downloads. There is no client allow list or per-client data-class ceiling. Another person needs their own approval. Ordinary approved extracts and downloads still use existing rights without review, and a requester holding the equivalent Kubernetes right needs no result access at all ([REQ-AUT-002](authorization.md#req-aut-002--authorization-composition)).

The request names action IDs, finite operations, `maxArtifacts`, `maxBytes`, `maxOperations` and optional `notAfter`. The UI fills these from the selected mechanisms and a practical query/transfer allowance and never asks for hashes or IDs. The output selection is validated against the compiled actions. The review shows whether the byte budget covers the maximum requested full downloads; a full-file workflow is never offered with an insufficient cap. Each count is installation-bounded. A download is full-file disclosure; local tools cannot be restricted after delivery.

The service binds a canonical result-access digest to the accepted capture UID and collection execution digest and includes it in the single review. The adHocCapture grant carries the resolved scope; input cannot set requester, approver or a pre-approved scope. Same human means same issuer and subject. Result access lasts until its `notAfter`, which defaults to the access end of the collected evidence; no deadline restarts when an artifact arrives. Acquisition and disclosure have separate budgets, both shown in the review.

### SC-INV-001

Given a developer requesting a core and local inspection, when an independent reviewer approves the combined plan, then capture and the subsequent core download and queries from the console, and from the developer's MCP agent need no second review. Another human, a changed output selection or another capture cannot use the approval. A context-only request adds no approval step. Approval hours after the preview, approval against the exact original target, revocation racing admission and a replay without new timing are covered; a missing or replaced Pod or a material scope change needs a new preview and review.

## REQ-INV-002 — Materialize exact grants after verified commit

When C-14 publishes an artifact of an approved capture, the same publication transaction creates one child rawQuery grant per artifact if the parent is Approved and unexpired, the requester is still eligible, and the artifact's recorded capture UID, execution digest and action ID match the approved result access. The child names the existing artifact digest, the requesting human, the matching operations, the parent's reviewer provenance, the parent's expiry and the parent's shared disclosure pool. No unknown artifact is ever named in an executable grant. The unique key (parent, artifact) makes repeated publication idempotent. Team automation has its own executor and cannot use a human's result access. Automatic policies, unrelated captures, recording-save sources, other people's artifacts and later derivatives are not covered. Approved ordinary extracts need no raw child. A separately selected companion collected by the same capture can qualify.

All children of a parent spend one pool: `maxArtifacts` counts distinct published outputs across clients; every operation and delivered byte is charged against the parent across all clients. Each use reserves under an idempotency key and settles to the bytes and operations actually used when the outcome is known; a reservation whose outcome is never reported is charged in full at the parent's hard end ([ADR-330](../docs/decisions/330-event-driven-system-design.md) D7). Local transfer and query limits apply as well. A started child transfer runs to its original bounds ([ADR-312](../docs/decisions/312-started-downloads-run-to-original-bounds.md)), never beyond the access end. Children expose `resultOrigin` (parentGrantID, captureUID, executionDigest, resultAccessDigest, actionID).

Child creation and every child use include the parent's state and expiry as predicates in the effect statement, so a wait for another transaction cannot let an expired or revoked parent through. Revoking, denying or expiring the parent refuses new children and every later child use. Exhausting the capture-start counter is not revocation of the separately budgeted result access; the two states are shown separately. Cancelling remaining capture work does not revoke results already collected. Artifact expiry, restriction and current entitlement still win. An artifact that arrives after the access end needs a new existing-artifact review, never a recollection.

### SC-INV-002

Given duplicate publications, a console and an MCP client of the same human and a bounded parent pool, when children are created and used from both clients, then each output is registered once and every use spends the same pool. A forged action, capture or parent digest, broadened operations, another principal, an expired or revoked parent or an exceeded count or byte limit refuses creation or delivery. Capture-budget exhaustion does not consume the result budget. A transfer interrupted after 10 MiB of a 100 MiB reservation leaves 10 MiB charged once its outcome is reported.

## REQ-INV-003 — One browser/MCP journey with truthful progress

`request_capture` accepts optional `result_access` for a reviewed plan and binds it before the review is created ([ADR-249](../docs/decisions/249-sensitive-acquisition-grants.md)). `preview_capture` is a dry run that returns the plan, its digest and the eligible output actions (`result_access_actions`, exact compiled action IDs with supported follow-up operations; metadata-only actions omitted); it binds and stores nothing and does not expire. The result-access digest covers `{captureUID, executionDigest, resultAccess}`, never only the execution digest; changing it needs a fresh preview and review. Supported operations are `download_artifact`, `query_artifact(operation=packets)` and `query_artifact(operation=syscalls)` ([ADR-305](../docs/decisions/305-bounded-saved-packet-queries.md), [ADR-306](../docs/decisions/306-bounded-saved-syscall-queries.md)), with at most 16 actions and a 256 GiB pool. Result access is refused on a plan that needs no review. Direct manual requests and DebugCapture carry the equivalent `resultAccess`. Capture status shows the result-access state and the current principal's child handles; automatic resolution uses those children for queries and downloads.

The reviewer sees collection and follow-up access together and approves or denies once; step-up applies only when configured ([REQ-AUT-003](authorization.md#req-aut-003--individual-and-policy-grants)). Result states are NotRequested, AwaitingReview, WaitingForArtifacts, Ready, Partial, Expired and Revoked. A saved artifact is never labelled a collection failure. Repeating a capture may offer the previous access preferences but never copies approval, issue time, children or spent counters.

The review request stores the exact submitted plan and its `plan_digest` in SQL until the grant ends ([ADR-252](../docs/decisions/252-approved-capture-acceptance.md)). The review stays decidable while the plan is unchanged, until the request's `notAfter` (default 24 hours). Approval submits the stored request: the approval transaction admits it against its exact Pod under the requester's current entitlement, retention and the approved grant, keeping the original IDs, composition, filter, audience, storage, relative retention and approved digest, and the capture starts within its plan window. If the Pod no longer exists or the plan no longer fits, the request ends `TargetChanged` and the requester is notified in the console and capture status. A retry with the same idempotency key returns the original acceptance and never recollects. A change of the recording-approval setting in either direction requires a new preview and review. The approval view shows when the plan was previewed and the plan's capture window. Presentation hints confer no authority.

### SC-INV-003

Given a combined request approved at 02:00 while the developer is away, when the capture completes and the developer opens the download at 09:00 or the developer's agent queries it, then the capture started at 02:00 and the review resolves automatically into exact artifact rights. Refresh and retry need no duplicate form and never recollect. The UI shows both capture readiness and evidence access.
