# Download evidence for local investigation

The maintainer requires local-tool access to **all gathered evidence**, including packet captures and cores. This supersedes the original brief's blanket prohibition on raw file export. Managed evidence remains encrypted; authorized delivery returns ordinary native files over authenticated HTTPS. Download is a common artifact operation, not a packet-only exception. See the [review correction](../docs/reviews/local-investigation.md).

## REQ-DLD-001 — Native files for every artifact

Every retained collected artifact and saved derivative MUST support authorized download in its recorded native representation. This includes sanitized or raw PCAPNG, native cores/runtime dumps, pprof and other runtime profiles, logs, files/pseudo-file snapshots, syscall recordings, command output, approved extracts and available executable/symbol companion artifacts. Unknown/new artifact kinds inherit download support: no per-kind allowlist may make bounded query support a prerequisite. A structured HTTP projection downloads as structured data, not an invented packet capture. Download cannot recover bytes excluded, truncated or lost during collection, nor expose unsaved live buffers.

Serve exact verified artifact bytes after removing Asservat's storage encryption/compression wrapper; do not require a proprietary decryptor or access to object storage/KMS. Preserve intrinsic format compression (such as a native compressed profile). Show size, format, full-file SHA-256, acquisition coverage, truncation and actual managed retention. Use safe server-generated filenames `artifact-<uuid><extension>` from the artifact-type registry ([ADR-244](../docs/decisions/244-native-artifact-types.md): PCAPNG `.pcapng`, syscall records JSON Lines `.jsonl`, HTTP header projection `.json`). Content-Type stays `application/octet-stream`; the native media type is part of the verified manifest. Collected archives stay archives; do not silently execute or expand them. Optional adjacent provenance JSON is separately authorized and excludes hidden artifacts, credential material and unselected configuration.

For native cores, offer recorded architecture, runtime, executable/build identity and separately selectable existing authorized companion files. State missing/mismatched symbols and libraries before download; allow the core download anyway. Never substitute a current deployment image for the captured build, implicitly acquire new files, disclose private registry credentials or imply every runtime dump opens in GDB. Local debugger/tool choice is the user's; download is tool-neutral and requires no debugger selection. The UI describes compatible tools as optional examples, never as a supported-tool whitelist or a mandatory GDB workflow. Any named suggestion must match the recorded format, architecture and runtime; otherwise say ‘Your preferred compatible debugger’. Asservat never launches it on their workstation. Sensitive bytes in local tools remain untrusted input.

### SC-DLD-001

Given an authorized developer and saved packet, ELF core, pprof, log, syscall, file and command-output artifacts, when downloaded, then each is available in its native representation with verifiable checksum and coverage. The PCAPNG opens in Wireshark; the ELF core plus exact available executable/libraries opens in a compatible local debugger, with GDB as one representative test rather than the only supported choice. Missing symbols are explicit and do not block download. An HTTP-header JSON artifact is never mislabeled PCAP. These are required runtime tests, not results of this specification pass.

## REQ-DLD-002 — Reuse authority; review only missing raw permission

Each content GET authenticates its caller as the download session's principal/client and completes one full authorization before its response starts: identity, ordinary entitlement or share, retained audience, raw result access, processing restriction, retention and delivery policy ([ADR-311](../docs/decisions/311-operation-authority-recheck.md), [ADR-330](../docs/decisions/330-event-driven-system-design.md) D5). The start fixes `AccessUntil` (the effective retention end, narrowed to an admitting share's or raw grant's end) and the response's byte allowance. Per [ADR-312](../docs/decisions/312-started-downloads-run-to-original-bounds.md) the started response then reads no identity, permission, share or policy again and runs until its original bounds end it: the caller's session/token expiry, the download session deadline, `AccessUntil`, an effective retention cut-off or managed deletion, explicit Stop, or its byte allowance. Retention cut-offs, deletion and Stop reach the stream as events (PostgreSQL `LISTEN/NOTIFY` cancels its context); they are not read per chunk. Permission, share and processing changes take effect at the next response start (a resume or new download).

The installation download policy comes from a watched ConfigMap. The cached policy stays valid until the watch replaces it; a watch failure makes it unavailable until the relist completes (ADR-330 D1). Prepare and status requests reuse their operation's authorization for at most `identity.AuthorityRecheckInterval` (30 s), never past the original request deadline; each new public request authorizes again.

Download needs current retained-artifact entitlement or explicit share coverage, no deny/restriction, current authenticated principal/client, `evidence:download`, transfer capacity and an audit row. Ordinary artifact readers may download the actual approved artifact they can read without independent human review. An extract view does not confer access to its hidden raw parent. Existing ordinary shares that authorize reading an explicit approved artifact also authorize its native download; raw shares require explicit download coverage.

Reading already stored evidence (download preparation/transfer and approved inspection) MUST NOT depend on live capacity observations of the source workload; workload capacity gates collection only. Evidence of a deleted workload remains readable within retention, bounded by regional evidence reader concurrency, per-principal limits and authorization (maintainer decision 2026-10-23).

A processing restriction (privacy restriction of an artifact or workload) is a flag on the artifact/workload rows and is checked in the same SQL query as the rest of the authorization; it covers ordinary metadata reads as well as native bytes. Publication or a new artifact ID cannot clear an existing restriction. Release requires current privacy-operator authority, not an ordinary read or capture approval. Storage, reader and connector placement is static Helm configuration and is not re-verified per request. A restrictive decision applies from the next content response start.

For raw artifacts, the existing per-principal/client artifact grant must explicitly cover `download_artifact`, exact existing artifact digests and sufficient cumulative plaintext output bytes. Reuse a valid covering grant without another approval. Otherwise the Download action opens the existing independent review flow with the selected artifacts and exact sizes prefilled; no manual hashes or byte arithmetic. `rawQuery` remains the stored grant-type name for artifact raw operations, now including download. The review explicitly grants disclosure of the whole file: local inspection cannot be limited to particular debugger commands after delivery. A bounded `pcap_query`, `read_memory` or collection grant alone does not authorize full-file export. The raw-request API supports the existing 1 TiB grant ceiling when download is included; other raw-query-only requests retain their prior 1 GiB request ceiling and tool-specific output caps. Multiple selected existing files can share one bounded review, while each response start authorizes each file independently.

A one-off request may include its intended inspection and download in the same independent human review under [investigation approval](investigation-approval.md). Only verified resulting artifacts materialize exact child rawQuery grants. Collection-only grants still confer no raw access; later or uncovered needs use existing-artifact review. A regular developer with workload/raw eligibility can request download; being a team lead, evidence owner or administrator is not a prerequisite. Shares cannot authorize unrelated companion files.

### SC-DLD-002

Given an ordinary reader of a sanitized capture, a raw reader with a covering download grant, and an extract-only recipient, when Download is selected, then the first two proceed without new human review and the recipient can download only the shared extract. A query-only grant returns a prefilled missing-permission request. Repeated preparation with the same idempotency key returns the same session. A different principal/client cannot use the prepared transfer.

## REQ-DLD-003 — Bounded authenticated transfer and resume

An `ArtifactDownload` session is a SQL row referencing the exact immutable artifact/version, actor/client, idempotency key, absolute deadline, emitted-byte counter and outcome. It is neither a CRD nor a plaintext evidence copy. States: `Preparing`, `Ready`, `Completed`, `Failed` (with reason such as `Expired`, `Denied`, `Integrity`) and `Cancelled`. `Preparing` lasts only until the regional evidence reader has opened the artifact and returned its verified native metadata (filename, format, size, checksum, ETag, coverage); before that the response omits the whole metadata group and never invents a size or checksum. An interrupted connection leaves the session `Ready`; the client resumes with HTTP Range within the session deadline. `Completed`, `Failed` and `Cancelled` are terminal and cannot restart. Opaque paths are not bearer capabilities.

Preparation is idempotent under its key ([ADR-330](../docs/decisions/330-event-driven-system-design.md) D7): a retry with the same key returns the existing session. Prepare normally returns `Ready` in the same request. When it returns `Preparing`, the browser follows the session on the page's Server-Sent Events stream and MCP `get_artifact_download` waits server-side (at most 30 s) for the next state change; both are woken by `NOTIFY` on the session row. Status reads never dispatch, unwrap, decrypt or re-prepare evidence and are never charged. Terminal status remains readable after the transfer deadline while current identity, evidence metadata access, retained audience and retention permit metadata disclosure; it does not renew any deadline. `Completed` records the server transfer outcome and is not proof that a client saved or verified the local file.

Stop (`cancel_artifact_download`) requires the original actor/client to be authenticated but remains available after loss of evidence-read/download scopes. It is an idempotent SQL update of the session to `Cancelled`, one audit row and a `NOTIFY` that closes any active response. Already-terminal sessions keep their state and return `AlreadyTerminal`; the receipt reveals no hidden artifact metadata.

Browser/MCP share `prepare_artifact_download`, `get_artifact_download`, `cancel_artifact_download`. MCP returns bounded status/metadata and an authenticated application path, never file bytes/base64 or a presigned storage URL. An OAuth-capable local client streams the same HTTP resource outside the model transcript; a client without file-transfer support uses the authenticated browser handoff and prepares under its own client identity. Never put credentials in a command line, query string or copied link. UI uses its authenticated session. MCP cannot approve itself or select an arbitrary local path/remote destination.

`GET /api/v1/downloads/{download_id}/content` serves attachment bytes over TLS; same-origin browser checks, explicit OAuth audience/client validation, no public CORS or redirects to storage. Return safe Content-Disposition, `application/octet-stream`, `nosniff`, `Cache-Control: no-store, private`, opaque version ETag and a known native Content-Length. No HTTP content compression or proxy response buffering. Support a single byte range; reject multipart ranges. Clients resume with `Range` plus the strong opaque `If-Match` ETag, returning 412 without file bytes on mismatch. Optional `If-Range` follows standard HTTP semantics ([ADR-054](../docs/decisions/054-native-download-protocol.md)): mismatch yields a full 200 response, which needs authorization and a byte allowance for the entire response. Clients must never append a 200 response to a partial file. Unknown range units follow the same 200 fallback. If-None-Match uses weak comparison after authorization and If-Match, with a matching GET returning 304 without file bytes; no-store still applies. Date validators are unavailable and ignored. Sessions always pin the same immutable artifact. Size, offset and exact version are checked before output. The server can report bytes handed to the transport, not prove client disk persistence. Local clients verify the complete SHA-256; interruption leaves a clearly incomplete local file.

A content GET that returns bytes writes one audit row in its authorization transaction and records its emitted bytes and outcome on the session row when it ends; 304 and 412 responses disclose no bytes and write no audit row (ADR-330 D6). Failure after response headers aborts the stream rather than appending an error body.

The regional evidence reader ([REQ-EVD-005](evidence.md#req-evd-005--analysis-isolation-and-output-classes)) streams the exact object range: verified streaming decrypt/decompress with bounded memory, no target code/parser/debugger execution and no plaintext scratch. It does not require the offline analyzer's PVC path. Bytes flow from the reader over its hub connection to the HTTP response with ordinary flow control (`io.Copy` under the response context); no file content enters SQL, logs or retry caches, and the hub has no unwrap key. All configured reader/hub locations must be permitted for that artifact; an unapproved location is an explicit blocker. Authenticate encryption segments before emitting plaintext and validate final digest/length. For a full-file transfer, withhold the final bounded delivery batch until those final checks pass; after all Content-Length bytes have been emitted, a server-side error alone cannot reliably signal an incomplete download. A partial range verifies its authenticated indexed frames and exact range length; the client verifies the full checksum when assembling a resumed file. A Range request starts at the frame containing its offset; resume never rereads earlier frames.

Raw grant maxDuration also bounds the transfer; the planner/review resolves a practical transfer allowance (30-minute default, narrowed by original access expiry and administrator limits) rather than reusing a short debugger-query or collection-action timeout. Per-query tool limits remain unchanged. Each response start reserves its requested byte range against the raw grant's cumulative output and the per-workload read counters; the emitted-byte counter is updated asynchronously in batches and at the end, and the unused part of the reservation is released when the response ends. Bytes emitted, including retransmission after a resume, count against the raw grant. Defaults: two concurrent streams per principal; installation concurrency is the reader replicas times the configured per-replica stream limit, further narrowed by workload/region budgets; downloads yield to incident saving/uploads. Sessions default to thirty minutes, configurable up to eight hours, always clamped to artifact/grant limits.

Browser content GETs read the current browser session and never refresh it ([ADR-224](../docs/decisions/224-remove-download-refresh-owners.md)); the Download/prepare POST is the ordinary audited operation, as for MCP. A started content GET runs to the session's fixed expiry, or for OAuth to the presented token's expiry, and may resume under a new authenticated request within the original transfer and grant budget. Bounded TLS/socket buffers mean bytes already emitted cannot be recalled. Cancellation disconnects the active stream and denies further ranges without deleting the source artifact. Browser tab closure is distinct from cancellation of the download.

### SC-DLD-003

Given a multi-GiB core transfer interrupted mid-file, when resumed, then current rights, immutable version and cumulative bytes are checked at the new response start, exact range bytes are returned, and the completed file matches its full checksum. Revocation before a response starts, source expiry, the effective retention cut-off, Stop, the session/token expiry, exhausted quota, changed object identity, invalid ranges and corrupt ciphertext stop delivery; a permission change after a response started does not (ADR-312). Duplicate requests, parallel readers and slow clients stay within their byte allowances; concurrent downloads do not starve incident uploads. Logs/caches/SQL contain no artifact body.

## REQ-DLD-004 — Visible download UX and external-copy limits

Every artifact viewer and artifact list offers Download or an actionable reason it is unavailable. A missing raw grant opens the prefilled review; a covering grant starts without redundant review or a generic confirmation modal. Show native type/size, optional companion files, integrity/coverage and a concise persistent notice: “Downloaded copies are outside Asservat's automatic deletion. Follow your organization's handling and deletion policy.” Do not force a checkbox or claim DRM, remote erasure, local encryption or expiry after bytes leave the service. Local tools need ordinary readable bytes; managed storage encryption remains mandatory.

Audit rows record preparation, each byte-returning response start, emitted bytes, cancellation and outcome. Successful HTTP delivery is not proof of local analysis or deletion; Asservat makes no verified-deletion claim for a developer's laptop. Source expiry still blocks new/resumed delivery and cleans managed copies on schedule. This is an ordinary investigation workflow, separate from privacy-rights responses.

### SC-DLD-004

Given an unfamiliar non-lead developer, when asked to investigate a saved packet capture or core using a local tool, then they can find Download, obtain only missing authorization, get native files plus any selected exact companions, and explain both coverage and the local-copy deletion responsibility. Repeat for every collected kind and an otherwise ineligible share recipient. Validate with actual files/tools and users, not only an internally consistent screen walkthrough.
