# Permission management and automatic inheritance

This specification defines application permissions inside one organization. It introduces no tenant model. Read with [authorization](authorization.md), [targets](targets.md) and [research](../docs/research/permission-automation.md). The [initial ordinary evaluator](../docs/architecture/identity-eligibility.md) implements current-deny and retained-audience rules against protected projection ports; explicit-binding admission, continuous reconciliation and SQL acceptance now have component and combined-fixture tests. Automatic source adapters and production authority wiring remain incomplete.

The [permission observation component](../docs/architecture/permission-observation.md) now reads Kubernetes bindings/source definitions and selected namespace metadata, and expands unaccepted binding/value-map candidates. The [acceptance component](../docs/architecture/permission-acceptance.md) adds persistent SQL assignment reconciliation and encrypted audit-gated projections. Actual source trust, continuous observation and production authority composition remain pending; a successful read or candidate is not permission activation.

## REQ-PER-001 — Canonical permission configuration

These resources configure ongoing application eligibility; they do not replace expiring `AccessGrant` execution approvals. Store `AccessBinding` and `PermissionSource` resources in the protected hub control namespace. `AccessBinding` assigns an issuer-scoped user, group or qualified workload identity a fixed role over one cluster and a namespace UID, optionally narrowed to explicit workload UIDs. `effect: Deny` subtracts the named role's operations. Wildcard subjects and cluster-wide workload scope are not supported in the first contract. Multiple namespaces use multiple bindings or a configured automatic source.

`PermissionSource` describes one administrator-enabled derivation rule for one cluster: `namespaceMetadata`, `workloadMetadata`, `kubernetesExec` or `kubernetesAccessReview`. It binds selectors, role, trusted identity mapping, protection assumptions, limits and freshness. Metadata sources resolve groups; SAR sources evaluate the current authenticated principal. Effective decisions and provenance are computed, not user-writable grants or one CRD per pod/member. Source and binding status is service-owned.

Kubernetes writes MUST enforce authenticated permission-administrator authority, the writer's configured cluster/namespace delegation envelope, and its allowed roles. No role below gives permission to edit this configuration. Delegated automation cannot widen its envelope, create another permission administrator or change source trust settings. Those bootstrap settings belong to protected installation/cluster configuration. Admission MUST enforce these content/scope checks for every writer; native RBAC protects the resource but does not apply RoleBinding bind/escalate protections to custom resources. GitOps does not bypass admission. Denies override explicit and derived allows, including shares. Local `CollectionCeiling` rules further restrict every collection decision.

| Role | Operations granted within scope |
| --- | --- |
| `evidence-reader` | Discover permitted cases and read metadata/extracts; no collection, sharing or raw access |
| `workload-maintainer` | Reader operations; manage collection policies; observe triggers/rings and collect approved ordinary evidence; request intrusive capture and raw-query grants |
| `evidence-owner` | Reader operations; personally or jointly through pinned owner-team assignments manage shares/instructions under REQ-SHR-008; share explicit existing evidence or authorize bounded capture/policy result-sharing instructions under configured sharing policy; raw sharing still requires review |
| `action-approver` | Review intrusive capture/raw-query/raw-sharing requests in scope; no automatic evidence reading and no self-approval |

A role never constitutes an active intrusive or raw-query grant. `workload-maintainer` provides baseline raw-query eligibility for permitted evidence, but actual raw operations still require the per-principal/client grant and OAuth scope. Other readers can request such a grant; approval cannot invent missing raw eligibility. Raw shares can supply that eligibility under the existing composition rules. The role's permitted ordinary collection is intersected with recipe classification and local ceilings; users cannot relabel a sensitive action as ordinary.

### SC-PER-001

Given a payments-scoped provisioning identity, when it creates a payments binding, then the binding can be accepted. A payroll binding, changed source trust settings, self-assigned permission administration or a forged status field is rejected for kubectl, GitOps and other Kubernetes API clients. A deny removes the matching operation even if another source permits it.

## REQ-PER-002 — Kubernetes administration and effective access explanation

The Kubernetes API is the only public permission-configuration CRUD interface. Administrators and provisioning identities manage `accessbindings.asservat.io` and `permissionsources.asservat.io` in the hub control namespace using kubectl, GitOps, Terraform's Kubernetes integration or ordinary Kubernetes clients. Use Kubernetes authentication, resource RBAC, admission, list/watch, server-side apply and resourceVersion concurrency; do not add a second permission HTTP API or permission-specific OAuth CRUD scopes. Management-cluster API connectivity is needed by administrators/provisioners, not application maintainers or evidence recipients.

Use stable object names and field managers for declarative configuration. Non-apply replacements MUST carry the last resourceVersion; a stale replacement returns Kubernetes Conflict (409). Server-side apply detects conflicting field ownership; never force ownership automatically. Deletions use UID/resourceVersion preconditions. After an ambiguous response, read/reconcile the same named resource rather than minting a new operation. `kubectl diff` and `apply --server-side --dry-run=server` validate schema/admission, but do not reconcile, propagate permissions or simulate cross-cluster effects. Publish structural schemas, `kubectl explain` descriptions, status printer columns, RBAC examples and admission compatibility fixtures in TASK-07.

Status uses a protected `/status` subresource. Report `Pending`, `Ready`, `Disabled`, `Stale`, `UnsafeSource` or `Rejected`, Conditions, observed generation, last verification time and bounded reasons. A successful API write is not permission activation. `Ready=True` is meaningful only for the current generation and reports which enrolled clusters acknowledged that revision; connected invalidation and disconnected expiry retain REQ-PER-006 bounds. GitOps health examples MUST check generation as well as condition.

The existing authenticated browser/query service provides read-only effective-access explanation and a bounded configuration impact preview using the real evaluator. These are queries, not another configuration store or permission-management CRUD API. Return `Allow`, `Deny` or `Indeterminate`, contributing revisions, target UIDs, freshness expiry and unmet conditions such as `GrantRequired`. Users can explain their own selected workload/operation; evaluating another principal or a proposed configuration requires the administrator's delegation envelope. Preview is side-effect-free, bounded to 1,000 target objects and a 256 KiB result, marks incomplete or unavailable-cluster results, and never enumerates group members or evidence. Check authorization before revealing candidate targets. These query contracts are part of the existing browser OpenAPI deliverable; evidence MCP errors carry actionable self-explanation without adding admin tools.

Configure Kubernetes audit for these resources, keep payload/secret values out of audit, and retain service reconciliation/activation audit. Report whether API audit coverage is configured rather than claiming that CRDs enable it automatically. Source trust qualification is reusable per cluster/protection profile, not a review ticket for every namespace. Initial bulk validation and subsequent trusted writes establish the provenance described below.

### Implementation refinement (ADR-234)

The first implemented part of this query is the caller-only `explain_access` operation (MCP and the shared browser operation route, [ADR-234](../docs/decisions/234-access-explanation.md)). Input is a named workload (as for `preview_capture`) and one operation: `capture`, `read` or `download`. The service resolves the workload to the same whole-pod target as the preview, reads the current permission projection and runs the ordinary evaluator unchanged; the answer is `Allow`, `Deny` or `Indeterminate`, the unmet condition (`NoMatchingAllow`, `ExplicitDeny`, `ClientScopeMissing` with the scope, `PermissionObservationStale`, `IdentityUnavailable`, `AudienceOverflow`, `ServiceUnavailable`), the roles that permit the operation, the target UIDs, the caller's own contributing allow assignments or matching deny (assignment ID, role, subject kind, basis kind/UID, basis digest as revision) and, on Allow, the decision's validity. Details are returned only when the projection lists at least one assignment that matches the caller; otherwise, and for a workload that does not resolve, the reply is uniformly `Deny`/`NoMatchingAllow` with no target or assignments. It evaluates the target scope only: retained artifact audiences, shares and approval grants are not explained. Explaining another principal remains a separate, unimplemented part of this requirement; the configuration impact preview follows.

### Implementation refinement (ADR-237)

The configuration impact preview is the browser-only `preview_access_change` operation ([ADR-237](../docs/decisions/237-permission-impact-preview.md)); evidence MCP gets no admin tool. The administrator's delegation envelope decides who may call it, checked before any proposal is decoded or permission data read: a current fleet operator (the installation-wide administrator of the protected fleet administration) previews any change on the enrolled clusters; a browser principal named as `previewer` of an installed permission delegation previews only objects that fit that envelope (cluster, namespace, workloads, roles, issuers, no automation; PermissionSource changes are administrator-only), and sees only targets inside it; an updated or deleted object is evaluated only when every affected cell was read and all its assignments lie inside the envelope; otherwise it is reported exactly like a nonexistent one, so existence beyond the envelope cannot be probed. Input is 1–16 AccessBinding or PermissionSource create (spec), update (UID and spec) or delete (UID) changes; specs pass the same schema and checks as observed objects. For every namespace that a proposal names or that holds an updated/deleted object, the service reads, in one consistent snapshot, the current accepted projection of each workload UID named by a current or proposed binding and of one cell standing for all other workloads (at most 1,000 cells). It removes the changed objects' assignments, adds the candidates the observation derives from the proposed specs, and runs the ordinary evaluator before and after for every subject whose assignments change, each subject evaluated alone (a group as one member with no other groups) with every client scope. Each change row names target UIDs, subject, operation, both decisions and unmet conditions and the deciding assignments with their revisions (basis digests, proposed rows marked); the reply carries the earliest freshness expiry. The listed result is bounded to 256 KiB and delivered in pages that continue the same request through `next_cursor`, bound to the permission revision so a changed projection restarts the preview. Cells with stale or unreadable permission data, or outside the enrolled clusters, are `Indeterminate` and never evaluated. PermissionSource creations and edits are `Indeterminate` (`InheritanceNotAccepted`) while the installation accepts explicit bindings only; once inheritance is accepted, they must be evaluated against its accepted namespace-metadata observation. Group members, evidence and retained audiences are never read; admission beyond the delegation envelope is not simulated (`kubectl --dry-run=server` remains that check).

### SC-PER-002

Given two clients replacing one resourceVersion, when both write, then one succeeds and the other receives Conflict. An apply field conflict requires explicit resolution. Dry-run starts nothing; a persisted source remains Pending until the current generation is verified. A developer without hub Kubernetes access can use the browser's own-access explanation without discovering another team's inventory.

### SC-PER-009

Given a maintainer whose group holds `evidence-reader` on a workload, when they call `explain_access` for `read`, then the result is `Allow` with that group assignment; for `capture` it is `Deny` with `ClientScopeMissing` or `NoMatchingAllow` and the required role `workload-maintainer`. When a deny naming their group is added, `read` is `Deny`/`ExplicitDeny` naming that deny. A user with no assignment on the workload receives the same `Deny`/`NoMatchingAllow` reply as for a workload that does not exist, without target UIDs or any other principal's assignment.


### SC-PER-010

Given a fleet operator and a namespace where group team-a holds `workload-maintainer` through a namespace-wide binding, when they preview deleting that binding, then every workload cell without another binding for team-a shows `Allow` → `Deny` for capture, read and download with the deleted binding's revision as the before basis, and a workload that a narrowed binding still covers shows no change. A proposed deny naming team-a shows `Allow` → `Deny`/`ExplicitDeny` with the proposed revision. A cell whose permission data is stale or whose cluster is not enrolled, and a proposed PermissionSource, are `Indeterminate` and never `Allow`. A delegation previewer of a workload-narrowed envelope sees only that workload and is refused (`DelegationExceeded`) for a proposed namespace-wide binding, another namespace, another role or issuer, an automation envelope or a PermissionSource; deleting a binding in another namespace or wider than the envelope gives the same reply as deleting a nonexistent UID. More than 16 changes or 1,000 target cells are refused; a larger result is paged within 256 KiB; a caller who is neither a current fleet operator nor a previewer receives `AdministratorRequired` before any permission data is read; MCP does not offer the operation.

## REQ-PER-003 — Namespace metadata inheritance

An enabled `namespaceMetadata` source MUST support a configured annotation or label key; do not require renaming existing organization metadata. Match a bounded namespace selector and exclusions, then resolve the field into issuer-scoped group IDs using either an explicit value-to-subject map or `groupID` mode with a fixed issuer and configured directory validation. Values never select roles, issuers, actions, URLs, KMS profiles or administrator authority. The source fixes those choices. Missing, unknown, malformed, ambiguous or oversized values grant nothing. One field represents one stable group ID; multiple owner groups use the explicit mapping mode, not ad hoc comma parsing.

Namespaces created by the trusted provisioning workflow inherit permissions after observation and validation; no separate per-namespace click is needed. A namespace-wide source deliberately includes eligible future workloads in that namespace. Shared namespaces should use narrower workload metadata or explicit bindings. Namespace collection opt-in/deny remains separately controlled by `CollectionCeiling`; ownership metadata alone cannot enable collection where the local administrator forbids it.

Each source selects a protection mode:

- `administratorManaged`: the cluster administrator explicitly attests that namespace creation, deletion and relevant metadata/selector writes are controlled by trusted administrators/provisioners. This fits clusters already enforcing that boundary; it does not require an additional admission product. Record the attestation owner/revision and expose it in diagnostics. Asservat cannot discover every indirect privilege path from RBAC alone.
- `admissionEnforced`: reference a qualified enforcing policy and binding, with protected keys and allowed writer identities. Its rules must cover CREATE, UPDATE/PATCH/apply, removal, object replacement and every selector/exclusion key that can expand authority. Guard configuration and parameters must themselves be protected. `Warn`/`Audit` alone is insufficient. Namespace DELETE/recreation authority must also be restricted.

A guarded key is authoritative only after its existing values have been reviewed or reasserted by a trusted writer. Installing a guard does not authenticate historical content. Guard profiles and identity-mapping references resolve only to administrator-configured local records, never arbitrary URLs or user-supplied executable plugins. When guard readiness is lost or the configured source is stale, stop granting from it. Do not treat namespace annotations as secure solely because their name begins with `asservat.io/`.

### SC-PER-003

Given an enabled source reading an administrator-managed ownership annotation, when the provisioner creates a new namespace for the payments group, then members gain only the configured role there. A developer changing unrelated workload labels gains nothing. In guarded mode, an unauthorized ownership-key edit or removal is rejected; missing or non-enforcing guard state disables inheritance.

## REQ-PER-004 — Exec-based and generic Kubernetes inheritance

`kubernetesExec` is an explicit per-cluster option that maps verified exec authorization to `workload-maintainer` eligibility for the whole selected pod. The local connector MUST submit `authorization.k8s.io/v1` SubjectAccessReview using the caller's trusted per-cluster identity mapping and these attributes:

```yaml
resourceAttributes:
  group: ""
  version: v1
  resource: pods
  subresource: exec
  verb: create
  namespace: payments
  name: payments-api-7d9f-example
```

The connector identity submits the review; the review's subject MUST be the actual user or approved automation identity, never the connector. Mappings must account for issuer, username/group prefixes, UID/extra claims and cluster authentication configuration. Clients cannot submit arbitrary Kubernetes usernames/groups. Unsupported or ambiguous mapping denies this source; it does not map by email/display name as a fallback. Do not require general API impersonation or execute a command to check access.

Require `allowed: true`, `denied != true`, no evaluation error and a fresh result. Timeouts, no opinion and missing review authority do not permit collection. Use `create pods/exec` for the supported Kubernetes window; do not treat old `get`-only exec grants, `nodes/proxy`, port-forward or generic pod-read rights as equivalent. Kubernetes does not express container/argv in this SAR. Before enabling the source, the cluster administrator MUST attest whole-pod eligibility and either no additional exec admission/JIT restrictions or a qualified adapter for those restrictions. A permission confined to particular containers cannot become whole-pod access; mark that source UnsafeSource and use an explicit whole-pod assignment instead. Asservat has no container permissions. Never claim SAR proves the actual container can run a shell, has ptrace permissions or exposes a pprof endpoint. Exec inheritance is an explicit operator decision to authorize Asservat's bounded diagnostics for that workload, not a claim that the collector has exactly the same Linux privileges as an exec session. Stronger diagnostics remain subject to action grants and local ceilings.

Evaluate every resolved pod separately; permission on one replica is not permission on another. Keep pod/container UID checks through dispatch and execution. An automatic policy is bound to its recorded executor identity and re-evaluated for each replacement pod. Permission source eligibility does not waive live-dump, profiling, custom-command, sensitive-file or payload-capture grants; it does not grant node access, peer workload memory or permissions administration.

`kubernetesAccessReview` optionally maps a configured permission to `evidence-reader` or `workload-maintainer`. Supported first-contract checks are `create debugcaptures` in the selected namespace, or `get`/`patch`/`update` on the exact Deployment/StatefulSet. An operator may thereby reuse workload-edit rights, but must deliberately accept that semantic mapping. Never infer eligibility from a role name or SelfSubjectRulesReview. A SAR authorizer allow may be broader than admission; the same qualification requirement applies.

### SC-PER-004

Given a user who can `create pods/exec` only for pod A, when a selector resolves A and B, then B is never observed or collected. A false/error SAR, a spoofed group, a legacy get-only grant or an unqualified whole-pod exec admission restriction cannot authorize A. A permitted live dump still waits for its action grant. An approved automatic policy rechecks each replacement replica under its recorded identity.

## REQ-PER-005 — Workload ownership and integration adapters

`workloadMetadata` provides the same fixed-role, issuer and value-mapping semantics for Deployment/StatefulSet metadata in shared namespaces. It requires `admissionEnforced` protection for ownership keys and scope selector keys, covering object creation as well as mutation. Users who deploy applications often control these objects, so ordinary application metadata is not automatically trusted. Resolve namespace/workload UIDs; derive pods through a validated controller chain without allowing forged owner references or pod labels to substitute an unrelated workload. A local adapter that cannot validate that binding reports the source unavailable for that pod.

GitOps, Terraform, namespace provisioners and approved service-catalog integrations MAY manage AccessBindings through the Kubernetes API within their delegated envelope. A catalog adapter must supply authenticated, bounded, revocable updates from an organization-approved authority. Catalog display ownership, CODEOWNERS, field-manager names, creator annotations and arbitrary GitOps labels are not standalone permission evidence. No catalog, policy engine, cloud IAM or SCIM service is a hard dependency. Provider-specific adapters can be qualified later without changing the binding API.

### SC-PER-005

Given two applications owned by different teams in one namespace, when protected workload ownership is resolved, then permissions apply only to the matching workload UID and validated child pods. Editing a pod label, copying an ownerReference or supplying a Backstage owner string cannot expand scope. A scoped integration cannot publish bindings for another team's workload.

## REQ-PER-006 — Freshness, composition and explainability

An effective operation requires organization identity eligibility, current source/binding authority, no explicit deny, local target/action ceilings, and all additional grant/share conditions. Union independently valid allow sources; an unavailable unrelated allow source need not block a known explicit binding. However, if authoritative deny configuration is unknown/stale, fail closed. No source failure falls back to a broader role. Restrict sources to the configured cluster and namespace envelope.

Default positive source-decision freshness is 30 seconds, maximum 60 seconds; deny cache at most 5 seconds. Source configuration/revocation changes invalidate connected caches. Identity group freshness retains the separate maximum five-minute bound from the authorization specification; the UI reports both limits. Collection permits expire no later than the earliest identity assertion, source decision, grant or local ceiling lease. Do not add cache lifetimes serially. For intrusive work, resolve current source authorization when issuing a permit; recheck before query output. An offline connector cannot renew a stale source decision. Disconnected acquisition follows only an already valid bounded permit.

Reconcile CRD authority into SQL with accepted digest/freshness under REQ-DB-001; a stale projection never authorizes work. Watch metadata and source revisions; SAR-based sources use short live decision lifetimes rather than assuming a RoleBinding watch covers every authorizer. Namespace recreation, target UID replacement or source digest change invalidates the old authorization context. A derived assignment overflow (more than 32 audiences for an artifact) is rejected at planning with a narrowing diagnostic; never silently omit an owner or create an unbounded manifest. Audit the source UID/revision, principal mapping, target UIDs, decision time/expiry and reason; do not audit bearer tokens. The API/UI can explain exactly why access exists and what would be lost if a source were removed.

The complete deny set has an independent observation deadline even when empty. Refreshing positive source/configuration state or completing a later evidence lookup MUST NOT renew it. A missing, future, expired or overlong deny interval fails closed. Incomplete paginated binding lists cannot prove absence of a deny. Allow-only automatic-source failures are reported separately and do not discard independently complete explicit bindings while their original deadlines remain valid.

### SC-PER-006

Given a cached positive decision, when ownership or a binding is revoked, then connected invalidation prevents new work and disconnected use ends by the original freshness/permit deadline. A connector restart cannot refresh the old decision's timestamp. A SAR outage denies that source; an independent valid explicit binding still works unless current deny state cannot be established.

## REQ-PER-007 — Authenticated submission and policy execution identity

Accepted executions and submission references live in SQL; CRD status is only a projection. A controller MUST NOT execute a user-editable CRD merely using its own privileges. Record the authenticated submitter and an authorized execution identity for each accepted policy/capture generation. HTTP submissions derive identity from validated credentials and receive a protected submission record. Direct Kubernetes submissions require the qualified admission adapter: authenticate the API server connection and derive the actor from AdmissionReview `userInfo`, then use the configured Kubernetes-to-Asservat mapping. A GitOps controller is recorded as its actual service identity; commit authorship does not automatically become the actor.

The adapter signs a canonical submission envelope bound to cluster, namespace UID, resource kind/name, canonical spec digest, actor/executor, issuance/expiry and operation nonce. On acceptance the controller binds it to the persisted object UID/generation and writes service-owned execution status. Replaced objects, spec changes or copied envelopes cannot reuse that status; resubmission requires current actor authorization. Atomically consume the acceptance nonce and retain its replay record at least through envelope expiry, even if the object is deleted. Validate the final post-mutation spec digest before acceptance; another admission mutation cannot silently widen a signed submission. Protect envelope/status writes and reject unstamped or unknown-origin changes. Admission dry-run produces no execution permit or durable side effect. Admission alone is not acceptance; controller validation after persistence closes the authorization decision.

The post-persistence human-policy profile in [ADR-062](../docs/decisions/062-policy-submission-signatures.md) additionally binds permission root, installation/recovery epoch, exact stored UID/generation and independently resolved collection scope. Its dedicated OpenBao key signs a purpose-specific canonical JWS with a maximum sixty-second submission lifetime. Current public-key trust has an original observation lifetime of at most five seconds. Verification produces a matching, bounded proof that acceptance MUST recheck after blocking work; verification cannot renew the envelope or create collection authority. AdmissionReview request UID is never used as the persisted object UID. The admission-origin attestation and this final submission profile are distinct, and direct Kubernetes/GitOps origin mapping remains required.

After acceptance, execution rechecks the immutable, authenticated acceptance/audit record and current source, delegation, grants, budgets and short execution permit. It does not reuse a human submission token as a long-lived execution credential or require its original sixty-second deadline to cover the whole policy lifetime. Exact acceptance retries return the historical receipt without reactivation, changed expiry or budget reset; public retry/status paths still require current caller authorization. Key retirement prevents new submission verification; execution-key revocation and policy/delegation revocation use their own current authority boundaries.

Recurring team policies use the installation-local policy execution identity and protected, finite `AccessBinding.spec.automation` delegation under [team policy automation](policy-automation.md). The authenticated creator remains immutable audit provenance; logout, expired personal assertions or departure alone do not revoke independently authorized team execution. Current human authority is checked at creation, edit, management, live viewing and evidence disclosure. Execution rechecks the recorded team delegation, sponsoring assignments and current denies; never store or replay human tokens/groups to execute a policy. Human-only exec inheritance supplies no automation delegation. GitOps records its actual submitting service identity. Changing executor or delegation requires protected acceptance and applicable review; no automatic migration of human-bound policies. Ordinary approvers cannot approve applications outside their own scope, and policy acceptance cannot exceed the current submitting actor's authorized scope.

### SC-PER-007

Given a developer who can create DebugPolicy objects, when they set a forged requester, copy another policy's signed metadata or name a powerful service account, then no collection starts. A valid admission dry-run starts nothing. A GitOps edit records its authenticated scoped service identity and invalidates approval when execution scope changes; it cannot execute as the privileged reconciler. After an authorized team policy creator leaves, that person cannot manage or read through former membership, while valid team automation remains eligible. A revoked delegation, replaced sponsoring assignment, stale deny set or forged workload executor blocks execution. Ordinary delegated binding writers cannot add, edit or delete an automation-bearing binding.

## REQ-PER-008 — Ownership changes and retained evidence

Default for automatic sources: changing an ownership assignment grants access to future evidence; it does not silently expose existing dumps to a different team. Future evidence remains the default; an explicit authorized historical transfer/share is required to disclose existing evidence to a new team. Record immutable `accessProvenance` inside the encrypted artifact manifest: namespace UID, bounded original audience assignments, their role, assignment ID and authorizing source/binding UID and digest. Each assignment has an immutable assignment ID that changes on removal/reassignment, including an A → B → A ownership cycle. Persist current assignment identity/revisions in SQL and immutable transitions in encrypted object storage; do not create a CRD per group member or pod. Store stable issuer-scoped users/groups, not group membership lists. Derived extracts inherit the originating assignments; combining artifacts requires authorization to all parents.

Ordinary reads require both a recorded audience assignment and its currently valid assignment ID and authorization basis, or an explicit EvidenceShare. Group membership may change within the same stable team group under the existing freshness rules; a changed owner group is a different assignment. Source configuration changes require reconciliation that preserves equivalent assignments explicitly and invalidates widened/replaced ones; a new assignment cannot be backdated. An admin-created binding also does not retroactively add an audience to old artifacts merely by matching their namespace. Explicit denies and expiry always apply.

For a SAR source, record the authenticated capturing principal as the audience; do not enumerate or assume all users who might pass SAR. Evidence may be read by that principal while the original source remains enabled and a fresh review allows the original recorded resource attributes. A deleted pod can be evaluated by its recorded name only when the qualified authorizer/adapter supports that semantics, the namespace UID is unchanged, and no same-name replacement conflicts with the recorded pod UID. Otherwise use an explicit binding/share through the evidence-owner workflow. SAR never authorizes unrelated historical artifacts for a user who only gained exec rights later.

An authorized evidence administrator can explicitly take ownership of selected retained evidence and issue a share to the new team under the existing sharing/approval rules. This is audited and does not manufacture a raw-query grant. The UI must show which older artifacts need that decision. A namespace rename/recreation or changed workload UID does not inherit prior evidence implicitly. Do not make evidence deletion depend on namespace deletion.

A fresh relist after an observation gap establishes current values, not continuous assignment history. Matching old/new annotations, object UIDs or spec digests cannot by themselves rule out A → B → A reassignment. Recover verified continuous history or invalidate uncertain assignments before reuse; do not derive assignment IDs solely from current field values. Equivalent unrelated/status-only changes may preserve assignments only through explicit reconciliation. A routine controller restart must preserve assignments whose exact unchanged source observations are proven within the same qualified cluster incarnation. Changed opaque resource versions require verified transition continuity; generation or final-value equality alone is insufficient. A changed trust root retires assignments before accepting replacements.

### SC-PER-008

Given a namespace reassigned from payments to payroll, when payroll collects new evidence, then its current team assignment is recorded. Older payments cores remain inaccessible to payroll until an explicit authorized share/ownership decision. Removing payments' current authority also prevents ordinary access through its old cached assignment. A newly created namespace with the same name inherits no old audiences.

Artifact readers may download the approved artifacts they are entitled to inspect; there is no team-lead-only download role. Raw downloads still need raw eligibility, explicit download operation coverage and per-principal/client review under [REQ-DLD-002](artifact-downloads.md). A download path or extract share cannot reveal a hidden raw parent or companion.
