# Deployment profiles and internal dependency alternatives

The maintainer requires a small-deployment path that does not require separately operated SSO, KMS, S3 or PostgreSQL and has accepted the recommendations in [ADR-063](../docs/decisions/063-small-deployment-alternatives.md). The [research report](../docs/research/small-deployments.md) distinguishes selected choices from measured qualification. Installation is Helm-native ([ADR-328](../docs/decisions/328-administrator-only-namespaces.md), [ADR-330](../docs/decisions/330-event-driven-system-design.md) D13) and usable by default ([ADR-335](../docs/decisions/335-usable-by-default.md)); the [Helm guide](../docs/installation/helm.md) describes the chart.

## REQ-DEP-001 — Independently selectable infrastructure

Official Helm installation MUST offer explicit bundled and external choices for identity, key services, PostgreSQL and evidence storage (`services.identity`, `services.keyService`, `services.postgres`, `services.objectStore`). The defaults are bundled PostgreSQL, the bundled object store and local static keys; the administrator chooses bundled Keycloak or an external OpenID Connect provider. Each provider is overridable independently, and selecting an external provider omits the bundled workload. Deployment size is separate from hub/cluster topology and never introduces tenants. Workload-cluster enrollment MUST NOT install duplicate hub databases or identity services. Reuse existing configured infrastructure without taking ownership of it.

`helm install` with a hostname and an identity provider and no further values yields a working single-cluster installation (`mode: combined`): capture enabled, the node collector enabled where its namespace is allowed, approvals possible and sign-in working on the first pass (ADR-335 D1). No second install pass, manual SQL call, console initialization step or undocumented ConfigMap is required.

Helm renders every Kubernetes object, including the CRDs as templates annotated `helm.sh/resource-policy: keep` (`crds.install`, default true), so `helm upgrade` upgrades them. A `secrets` pre-install/pre-upgrade hook Job creates each missing generated Secret and never changes an existing value; generated Secrets carry no Helm ownership, so uninstall keeps them. A `setup` Job applies the schema, creates or updates the runtime SQL roles, reconciles the selected bundled providers (including the bundled Keycloak realm) and initializes processing from the values, all idempotently. `helm upgrade --install --wait --wait-for-jobs` returns when setup has completed and the workloads are ready. Operators may supply `existingSecret` references instead of generated Secrets. Hub workloads start once the schema is current. Components read configuration and credentials from mounted ConfigMaps and Secrets and do not re-verify installation objects at runtime. Precedent: cert-manager, Argo CD, GitLab and Keycloak charts.

Every value can change on `helm upgrade` and takes effect without reinstall (ADR-335 D3). Configuration is never stored write-once; generated Secrets stay stable and are never compared against values. The values schema refuses settings that a component would reject at startup; its bounds are generated from the same constants the components enforce.

Bundled Keycloak is an explicit identity choice, independent of the PostgreSQL, object-store and key-service selections; an existing external Keycloak or other OpenID Connect provider remains selectable. The setup Job reconciles the bundled realm's clients, redirect URIs, scopes and groups through the Keycloak admin API on every run, so hostname, realm and redirect changes apply on upgrade. Bundled Keycloak keeps its user, group and client identities and its selected database across restart and upgrade; changing the database requires an explicit supported migration ([ADR-326](../docs/decisions/326-individually-selectable-small-services.md)). It is served through the console's Ingress or HTTPRoute under the console origin, and hub-api reaches it through its in-cluster Service.

The bundled object store uses one bucket with disjoint prefixes for evidence and audit export. An external object store needs one credential limited to one bucket and prefix, or the platform's ambient workload identity (IRSA, GKE/Azure Workload Identity) with no Secret; per-purpose principals are not required. Asservat does not administer external IAM. Connections to public endpoints use the system trust store; a CA bundle per service is optional (ADR-335 D12).

Preserve the same authorization, audit, retention, fair capacity and native-download contracts in both profiles. Do not require a broker, email service, external monitoring backend, paid service, licence key or runtime internet access. Existing Kubernetes and durable persistent storage remain explicit prerequisites. Offline analysis may be unavailable without qualified encrypted scratch under ADR-036; that MUST NOT disable independently usable collection, live projections or native downloads.

### SC-DEP-001

Given a fresh cluster with suitable persistent storage and an HTTPS hostname but no IdP, KMS, S3 or database service, when the administrator installs the chart with the hostname and bundled Keycloak, then one `helm install` brings up the bundled services, the console sign-in works and an authorized user can capture and download pod status without further values, console steps or infrastructure credentials. Changing the Keycloak hostname or a redirect URI with `helm upgrade` takes effect. Adding another workload cluster reuses that hub. Unqualified or absent analysis scratch reports only the affected capability unavailable.

## REQ-DEP-002 — Local identity without a second permission system

Support local users, groups, login, invite/recovery, disable and session revocation using stable installation-issuer/subject identifiers and group names. Password credentials MUST use a reviewed memory-hard hash, never reversible encryption. Local authentication supplies verified recent assurance for approval or administration where step-up is configured (optional, off by default; ADR-335 D5). Authentication resource usage is bounded by per-client and per-subject rate limits, not by an installation-wide session ceiling: each attempt runs the memory-hard hash, so the default rate derives from the hash cost parameters and the hub-api CPU request. No default password, anonymous enrollment or mandatory email delivery. The chart's NOTES print the command that reads the generated bootstrap administrator password; `services.identity.keycloak.initialUsers` optionally creates users with group memberships and generated one-time passwords that must be changed at first login. Account/group administration is separately authorized/audited; a group membership change may change existing rights and MUST show that consequence. Evidence ownership and immutable creators remain separate from account administration.

Use the existing Kubernetes permission resources for local and external identities. Administrators are one Helm-listed group or subject list (`administrators`); everyone else gets access through AccessBindings, ClusterAccessBindings or PermissionSources (ADR-335 D14). Sign-in eligibility is any authenticated user of the configured issuer and client. Do not infer Kubernetes exec rights by matching a local username; inheritance still needs a qualified explicit identity mapping. MCP and CLI login MUST use the reviewed OAuth discovery/code/PKCE/resource/client-bound flow without receiving the user's password. Local disable and membership/session changes take effect at the next authorization check, at most `identity.AuthorityRecheckInterval` later; cached tokens cannot extend them. Local identity outages fail closed for dependent interactive access. Team policy execution retains independently delegated workload authority, not a local user's perpetual refresh token.

### SC-DEP-002

Given a local developer authorized through a group AccessBinding and a separate authorized reviewer, when the developer connects an MCP client, then authentication uses browser login and scoped tokens, and the same evidence rules apply as with SSO. Removing group membership or disabling the account blocks dependent access within the authority recheck interval. Recreating the same username does not inherit the deleted subject's grants, ownership or shares.

## REQ-DEP-003 — Local key services with unchanged evidence isolation

The default key service is the local static-key service ([ADR-064](../docs/decisions/064-local-key-material.md)); it covers every required purpose: artifact key wrapping/unwrapping and protected browser credentials. OpenBao is optional and used only for artifact key wrapping. Hub certificates come from the installation CA (cert-manager or Helm-generated, [ADR-330](../docs/decisions/330-event-driven-system-design.md) D3), not from the key service; connectors authenticate with their cluster's ServiceAccount tokens (ADR-334) and need no certificate. Reuse established cryptographic implementations and the existing artifact format/bindings. Separate keys and authorization by purpose; collectors and publication are wrap-only, unwrap serves only currently authorized evidence reads, and the hub has no raw-evidence unwrap authority. Static root keys MUST NOT be mounted into application, collector or reader Pods to avoid implementing this boundary.

Keys are random, versioned, created once by the `secrets` hook (or supplied through `existingSecret`) and read from mounted Secrets following [local-key-secret.schema.json](contracts/local-key-secret.schema.json): one active version plus retained older versions per purpose. Stable key and CA identities survive Helm upgrades, rollback and uninstall. Missing keys with existing installation state are a recovery failure, never a reason to regenerate. Rotation (`secrets.rotate`) adds a version; an old version is removed only by an explicit operation after all its ciphertexts are deleted, and its removal is no selective erasure.

The key service exposes wrap and unwrap over mutual TLS ([local-key-service.schema.json](contracts/local-key-service.schema.json)) with a five-second I/O timeout (ADR-330 D5); its concurrency is bounded by its callers (capture concurrency and reader replicas). The caller's installation-CA certificate role selects the allowed operations: only the regional reader (role `download-reader`) may unwrap, and the hub never does. Nodes obtain wrapped data keys through a reader over their connector stream; with OpenBao, the reader's ServiceAccount is the only OpenBao client and needs one policy and one role. The AEAD binding limits an unwrap to the artifact attempt it was wrapped for, so the key service performs no SQL lookup and issues no tickets. Wrap and unwrap are idempotent and simply retried. Load is three wraps per artifact attempt (REQ-EVD-001).

### SC-DEP-003

Given retained evidence encrypted under local key version one, when the chart upgrades and version two becomes active, then old evidence remains readable only through authorized reads and new evidence uses the new version. A collector's wrap credential cannot unwrap either version. Losing the old Secret produces a specific recovery failure; reinstalling cannot make the old ciphertext appear successfully restored.

## REQ-DEP-004 — Bundled durable services, backups and upgrades

The bundled PostgreSQL and evidence-store modes MUST use persistent storage, authenticated encrypted transport, separate service roles, pinned maintained images and resource requests/limits and PVC sizes (real memory and disk cost; Kubernetes scheduling needs requests) whose defaults derive from the configured cluster and storage size (ADR-335 D2). Evidence remains encrypted before upload. Evidence capacity is accounted per workload under [capacity isolation](capacity.md); database, backup and system volumes are sized by PVC values and monitored for headroom, not prepaid per row or WAL byte. Do not silently discard required WAL or evidence to keep service healthy.

Backups leave the cluster (ADR-335 D10). Bundled PostgreSQL uses pgBackRest with finite encrypted base/WAL recovery; its repository may be a local volume and SHOULD be an off-cluster S3 or repository target (`services.postgres.bundled.backup.repository`) with a configurable schedule and a retention that defaults to the configured maximum evidence retention (ADR-335 D7), because backups retain deleted rows. The evidence store is protected by object-store replication or, for bundled SeaweedFS, Velero volume backups. OpenBao, when used, is protected by its snapshots; the bundled Keycloak realm is in its database backup, or exported when Keycloak uses its own database. The generated Secrets (keys, CA, credentials) form one labelled backup set that must be kept with the data it opens. Same-disk backup copies are not independent disaster recovery. Each component exposes the age of its last successful backup as a metric (`/metrics`, optional ServiceMonitor) and in installation status; a stale or failed backup is reported, not hidden in a readiness probe.

The support contract includes tested restart, backup and restore (`recovery` value and runbook, REQ-DB-005), capacity exhaustion, credential/certificate rotation, minor upgrades without downtime and explicit major migration. hub-api uses a RollingUpdate with at least two replicas available, and hub-worker runs a standby replica under leader election (ADR-335 D13). Schema migrations are expand/contract so the previous minor release runs on the current schema; that is the supported `helm rollback` window, because each further supported schema generation adds migration and test cost (the same N/N-1 rule as connectors, [federation](federation.md)). Single-instance bundled services state their downtime and failure-domain limitations. Retain persistent state on Helm uninstall; explicit removal workflows remain responsible for evidence deletion.

### SC-DEP-004

Given a small deployment with two workload allocations, when one workload reaches its evidence quota or the object disk becomes pressured, then expensive acquisition is suppressed before consuming another workload's protected allocation or the system reserve. Restart preserves committed artifacts and accounting. After a same-volume PostgreSQL restart, fresh console and MCP logins retain the original user, group and client identities; a new capture and a fresh authorized download of an earlier artifact succeed within the original evidence bounds. Restart does not renew retention, permissions or reservations. `helm upgrade` serves console requests throughout. A restore from the off-cluster backup with the `recovery` value serves nothing until setup has re-applied revocations, expiries and deletions (REQ-DB-005). Chart uninstall does not erase retained data or recovery keys.

## REQ-DEP-005 — Low-effort bootstrap, rotation and safe provider migration

Use the `secrets` hook and `setup` Job to create stable credentials, with idempotent create-if-absent behavior and diagnostics that name the failing stage. setup retries unreachable providers with backoff until the Job's `activeDeadlineSeconds`, which defaults to the Helm `--timeout` (default five minutes) minus a margin, because `--wait-for-jobs` enforces that timeout anyway. Secret bytes MUST NOT be supplied through Helm values, rendered Secret templates, release metadata or ordinary logs. Support existing Secret references. Do not rotate or recreate credentials merely because a template renders. Rotation is explicit: listing a generated credential in `secrets.rotate` makes the next setup run issue a new version (altering the SQL role, adding a key or MAC version), and Pods pick it up through a checksum. A changed `dnsNames` value reissues the generated serving certificate under the unchanged CA. No second privacy consent or per-maintainer infrastructure setup is introduced. setup initializes processing from the `processors` values and the retention purpose under the installer identity and writes its audit row; the console's processing route remains for later restrictions and releases.

With external OpenBao, setup creates its transit key, policy and Kubernetes-auth role from an admin token Secret supplied once, or the administrator applies the single documented snippet (ADR-335 D11). Runtime workloads log in with their projected ServiceAccount token and renew; they do not read back their own policies, hold provider-administration or token-creation privileges, or require application maintainers to manage provider tokens. This workload authentication is independent of human SSO. Local-key deployments remain independent.

Installation status shows each dependency as available or unavailable with the exact remedy. Provider migration is documented: explicit identity mapping (never automatic linking by email or name), preserved audit actors and artifact hashes, copies counted against capacity and unchanged deletion deadlines. The old installation's workloads are stopped before the new one writes, and old key/store readers stay available until retained evidence is migrated or expires.

### SC-DEP-005

Given a working local installation, when SSO and external storage are adopted separately, then explicitly mapped users retain only reviewed access, audit actor history is unchanged, ongoing copies count against capacity and their deletion deadlines do not move. An interrupted migration can resume from recorded state without duplicating grants, silently replacing objects or erasing the old keys. Rotating the hub's SQL credential through `secrets.rotate` keeps the console available and leaves no Pod on the old password after rollout.
