# Deployment profiles and internal dependency alternatives

The maintainer requires a small-deployment path that does not require separately operated SSO, KMS, S3 or PostgreSQL and has accepted the recommendations in [ADR-063](../docs/decisions/063-small-deployment-alternatives.md). The [research report](../docs/research/small-deployments.md) distinguishes selected choices from measured qualification. Installation is Helm-native ([ADR-328](../docs/decisions/328-administrator-only-namespaces.md), [ADR-330](../docs/decisions/330-event-driven-system-design.md) D13); the [Helm guide](../docs/installation/helm.md) describes the chart.

## REQ-DEP-001 — Independently selectable infrastructure

Official Helm installation MUST offer explicit bundled and external choices for identity, key services, PostgreSQL and evidence storage (`services.identity`, `services.keyService`, `services.postgres`, `services.objectStore`). A small profile selects compatible bundled defaults; administrators can override each provider independently. Selecting an external provider omits the bundled workload. Deployment size is separate from hub/cluster topology and never introduces tenants. Workload-cluster enrollment MUST NOT install duplicate hub databases or identity services. Reuse existing configured infrastructure without taking ownership of it.

Helm renders every Kubernetes object. A `secrets` pre-install/pre-upgrade hook Job creates each missing generated Secret and never changes an existing value; generated Secrets carry no Helm ownership, so uninstall keeps them. A `setup` Job applies the schema, creates or updates the runtime SQL roles and configures the selected bundled providers, all idempotently with create-if-absent semantics. Operators may supply `existingSecret` references instead of generated Secrets. Hub workloads start once the schema is current. Components read configuration and credentials from mounted ConfigMaps and Secrets and do not re-verify installation objects at runtime. Precedent: cert-manager, Argo CD, GitLab and Keycloak charts.

Bundled Keycloak is an explicit identity choice, independent of the PostgreSQL, object-store and key-service selections; an existing external Keycloak remains selectable. Bundled Keycloak keeps its realm, client and group identities and its selected database across restart and upgrade; changing the database requires an explicit supported migration ([ADR-326](../docs/decisions/326-individually-selectable-small-services.md)). The bundled object store uses one bucket with disjoint purpose prefixes for evidence and audit export. An external object store uses an operator-managed scoped credential Secret; Asservat does not administer external IAM.

Preserve the same authorization, audit, retention, fair capacity and native-download contracts in both profiles. Do not require a broker, email service, external monitoring backend, paid service, licence key or runtime internet access. Existing Kubernetes and durable persistent storage remain explicit prerequisites. Offline analysis may be unavailable without qualified encrypted scratch under ADR-036; that MUST NOT disable independently usable collection, live projections or native downloads.

### SC-DEP-001

Given a fresh cluster with suitable persistent storage and trusted HTTPS configuration but no IdP, KMS, S3 or database service, when the administrator selects the qualified small profile, then the chart installs the chosen bundled services without asking application maintainers for infrastructure credentials. Adding another workload cluster reuses that hub. Unqualified or absent analysis scratch reports only the affected capability unavailable.

## REQ-DEP-002 — Local identity without a second permission system

Support local users, groups, login, invite/recovery, disable and session revocation using stable installation-issuer/subject/group identifiers. Password credentials MUST use a reviewed memory-hard hash, never reversible encryption. Local authentication MUST supply verified recent assurance for approval/administration where required, with bounded authentication resource usage. No default password, anonymous enrollment or mandatory email delivery. Account/group administration is separately authorized/audited; a group membership change may change existing rights and MUST show that consequence. Evidence ownership and immutable creators remain separate from account administration.

Use the existing Kubernetes permission resources for local and external identities. Do not infer Kubernetes exec rights by matching a local username; inheritance still needs a qualified explicit identity mapping. MCP and CLI login MUST use the reviewed OAuth discovery/code/PKCE/resource/client-bound flow without receiving the user's password. Local disable and membership/session changes take effect at the next authorization check, at most `identity.AuthorityRecheckInterval` later; cached tokens cannot extend them. Local identity outages fail closed for dependent interactive access. Team policy execution retains independently delegated workload authority, not a local user's perpetual refresh token.

### SC-DEP-002

Given a local developer authorized through a group AccessBinding and a separate authorized reviewer, when the developer connects an MCP client, then authentication uses browser login and scoped tokens, and the same evidence rules apply as with SSO. Removing group membership or disabling the account blocks dependent access within the authority recheck interval. Recreating the same username does not inherit the deleted subject's grants, ownership or shares.

## REQ-DEP-003 — Local key services with unchanged evidence isolation

Provide a local static-key alternative for every required external key-service purpose: artifact key wrapping/unwrapping and protected browser credentials. Hub and connector certificates come from the installation CA (cert-manager or Helm-generated, [ADR-330](../docs/decisions/330-event-driven-system-design.md) D3), not from the key service. Reuse established cryptographic implementations and the existing artifact format/bindings. Separate keys and authorization by purpose; collectors and publication are wrap-only, unwrap serves only currently authorized evidence reads, and the hub has no raw-evidence unwrap authority. Static root keys MUST NOT be mounted into application, collector or reader Pods to avoid implementing this boundary.

Keys MUST be random, versioned, created once by the `secrets` hook (or supplied through `existingSecret`) and read from mounted Secrets following [local-key-secret.schema.json](contracts/local-key-secret.schema.json) and [ADR-064](../docs/decisions/064-local-key-material.md): exact installation/purpose/key scope, bounded closed JSON, one active version and finite retained versions. Protect the Secrets and their backups at rest. Stable key and CA identities survive Helm upgrades, rollback and uninstall. Missing keys with existing installation state require recovery, never silent regeneration. Rotation adds a version and keeps old versions for retained readers; removing a version is a separate retirement operation that checks retained-data obligations, never automatic pruning, and claims no selective erasure from shared-key deletion. Local keys do not remove TLS, peer identity or browser trust requirements.

The key service exposes closed operation-specific requests over mutual TLS ([local-key-service.schema.json](contracts/local-key-service.schema.json)) with finite payload, concurrency and deadline limits. Callers authenticate with an installation-CA client certificate whose role decides the allowed operations; only the regional reader (A-READ, role `download-reader`) may unwrap artifact keys, and the hub process never does. The hub authorizes the user operation once before it assigns the read to a reader over the reader's connection. The wrapped keyset's AEAD binding means an unwrap returns only the keyset of the artifact attempt it was wrapped for; the key service performs no per-call SQL lookup and issues no tickets or key slots. Wrap and unwrap are idempotent, so a transient error is simply retried. Artifact encryption uses a bounded number of key wraps per attempt, independent of payload size; payload bytes never transit the key service.

### SC-DEP-003

Given retained evidence encrypted under local key version one, when the chart upgrades and version two becomes active, then old evidence remains readable only through authorized reads and new evidence uses the new version. A collector's wrap credential cannot unwrap either version. Losing the old Secret produces a specific recovery failure; reinstalling cannot make the old ciphertext appear successfully restored.

## REQ-DEP-004 — Bundled durable services and bounded operations

The bundled PostgreSQL and evidence-store modes MUST use persistent storage, authenticated encrypted transport, separate service roles, pinned maintained images and bounded resource/storage settings. Evidence remains encrypted before upload. Database, evidence, backup, system and cleanup capacity MUST be accounted separately; shared underlying storage requires backed limits before promising isolation. Preserve per-workload protected evidence allocations and physical headroom for compaction, temporary files, deletion and database/WAL operation.

Single-instance deployments MUST state downtime and failure-domain limitations. The support contract includes tested restart, backup/restore, capacity exhaustion, credential/certificate rotation, minor upgrades and explicit major migration. Database backups use finite encrypted base/WAL recovery; copying an active database directory or keeping a dump without a defined recovery objective is insufficient. Report stale/failed backups and threatened recovery objectives. Do not silently discard required WAL or evidence to keep service healthy. Same-disk backup copies are not independent disaster recovery. Retain persistent state on Helm uninstall; explicit removal workflows remain responsible for evidence deletion.

### SC-DEP-004

Given a small deployment with two workload allocations, when one workload reaches its evidence quota or the object disk becomes pressured, then expensive acquisition is suppressed before consuming another workload's protected allocation or database/system reserve. Restart preserves committed artifacts and accounting. After a same-volume PostgreSQL restart, fresh console and MCP logins retain the original user, group and client identities; a new capture and a fresh authorized download of an earlier artifact succeed within the original evidence bounds. Restart does not renew retention, permissions or reservations. A restore stays `recovery_blocked` until the recovery Job has re-applied revocations, expiries and deletions (REQ-DB-005). Chart uninstall does not erase retained data or recovery keys.

## REQ-DEP-005 — Low-effort bootstrap and safe provider migration

Use the `secrets` hook and `setup` Job to create stable credentials and an administrator invitation, with idempotent create-if-absent behavior and recovery diagnostics that name the failing stage. Secret bytes MUST NOT be supplied through Helm values, rendered Secret templates, release metadata or ordinary logs. Support existing Secret references. Do not rotate or recreate credentials merely because a template renders. No second privacy consent or per-maintainer infrastructure setup is introduced.

With OpenBao, the `setup` Job writes the Kubernetes-auth roles and policies for each purpose idempotently. Runtime workloads log in with their projected ServiceAccount token and renew; they do not read back their own policies, hold provider-administration or token-creation privileges, or require application maintainers to manage provider tokens. This workload authentication is independent of human SSO. Local-key deployments remain independent.

Expose independent dependency/capability status and exact remedies, distinguishing configured, qualified, unavailable and recovery-required states. Support documented provider migration with current authority, explicit stable identity mapping, preserved audit actors and native artifact hashes, copy accounting and unchanged absolute deletion deadlines. Do not link accounts automatically by email/name. Database/provider migration MUST fence old writers and authority; endpoint edits alone cannot authorize a second active installation or reset grants. Old key/store readers remain available until retained obligations are safely migrated or expire.

Bundled Keycloak may opt into an initially empty dedicated processing-operator group. The generated group's stable ID determines the resulting Kubernetes processing-operator declaration. This grants ordinary users no privacy authority and does not replace ordinary evidence permission checks. With opt-in disabled, behavior is unchanged.

### SC-DEP-005

Given a working local installation, when SSO and external storage are adopted separately, then explicitly mapped users retain only reviewed access, audit actor history is unchanged, ongoing copies count against capacity and their deletion deadlines do not move. An interrupted migration can resume from recorded state without duplicating grants, silently replacing objects or erasing the old keys.
