# Hub persistence and recovery

PostgreSQL is the single production hub state backend (ADR-023). Kubernetes remains the configuration API; regional object storage holds encrypted evidence and exported audit batches. Mechanisms follow [ADR-330](../docs/decisions/330-event-driven-system-design.md). Isolated [transaction experiments](../docs/research/feasibility-control-crash.md) support selected invariants.

## REQ-DB-001 — One authority for each field

Configuration authority stays in Kubernetes: recipes, policies, presets, permission bindings/sources, retention policies, storage pools, budget policies and collection ceilings. SQL stores accepted projections with source cluster/namespace/resource UIDs, opaque resourceVersion, generation, canonical digest and deletion marker. Projections are maintained from informer events (hub cluster) or connector pushes (workload clusters). A projection stays valid until a later event replaces it; a source becomes available once its informer has synced, and a watch failure marks it unavailable until the relist completes. Never compare resourceVersions numerically or across resources. SQL projections are not writable configuration APIs.

A DebugCapture CRD is a request envelope. Its accepted execution lives in SQL, uniquely keyed by source cluster/request UID/generation. Browser/MCP submissions use the existing authenticated request service and a principal/client-scoped idempotency key. CRD status projects acceptance and progress through `status.observedGeneration` and conditions; deleting the request or namespace does not delete evidence, outstanding charges or revocations. Disconnected work uses the connector's budget lease and unexpired permits, never a second hub database.

AccessGrant, EvidenceShare, policy acceptances, capacity accounts and reservations, cluster enrollment and work items are SQL runtime records, not CRDs. Their portable DTOs use `schemaVersion`, `kind`, `id`, `spec` and `status`; `spec` describes accepted scope and does not make them kubectl resources. No CRD exists per attempt, reservation or delivery; each connector keeps one bounded local checkpoint (REQ-FED-002, REQ-CAP-005). Secrets are references, not database content.

Audiences and share managers are recorded as group names and subjects of the installation's issuer (ADR-335 D4). AccessBindings are keyed by object UID and generation and recomputed on relist ([ADR-329](../docs/decisions/329-accessbindings-in-application-namespaces.md)); bindings that exist before the hub's first start take effect from its first list like any later relist, with no separate initial review.

### SC-DB-001

Given a namespace is recreated or the hub restores an old configuration projection, when authorization resumes, then informers have relisted and current source UIDs and deletions are applied first. An old accepted request is not executed again and namespace deletion does not release charges.

## REQ-DB-002 — Relational state and invariants

Use PostgreSQL 18 as the initial qualification baseline, supported patch releases pinned in release metadata. No mandatory extensions, broker, SQLite production mode or interchangeable Kubernetes state backend. Use ordinary typed columns and foreign keys for authority/accounting; bounded JSONB is only for versioned, validated plan/configuration shapes. Plans, settings, bounded reasons, filters and previews are ordinary SQL rows under the existing authorization, protected at rest by volume and backup encryption, with explicit control-data deadlines after which they are deleted. Evidence, full manifests and extracted text stay in the encrypted object store; full plaintext evidence hashes remain in protected manifests. Runtime DTOs are not literal table dumps.

The following logical schema is normative. TASK-02 must produce migrations and query contracts implementing it before any feature writes runtime state. UUID primary keys, bigint monotonic revisions, timestamptz deadlines and nonnegative bigint byte/object/count fields are standard. System IDs and durable uniqueness keys never depend on display names.

| Table family | Keys and relationships | Invariant / query index |
| --- | --- | --- |
| `config_projection`, `cluster` | Unique source cluster/resource UID; cluster UUID generated from the unique cluster name | Accepted digest/generation, deletion marker; cluster `revoked` flag, connection-holding replica, connection times |
| `operation`, `capture`, `action_attempt` | Unique caller/client/idempotency-key digest; unique source request UID/generation; unique capture/action/target/attempt | Request digest mismatch returns Conflict; immutable execution; never retry an ambiguous intrusive start as a fresh attempt |
| `capture_history` | Unique accepted capture ID; selector/settings digests; optional repeated-from ID | Bounded settings snapshot in the row; bounded selector/time/capture-ID listing with current and retained audience checks; independent summary/settings expiry; never cascade-delete execution state |
| `case_record`, `occurrence` | Case UUID; unique cluster/occurrence UUID | Content-minimized signature and time/scope indexes; occurrence association does not authorize every artifact in a case |
| `artifact`, `artifact_parent`, `artifact_copy` | Artifact UUID+digest; unique parent/child; copy ID+store/version | Commit state, class, capture/action/plan, region, access cutoff, stored effective deletion deadline; no raw paths/log text; bounded lineage traversal |
| `artifact_audience` | Artifact ID; issuer-qualified group name or subject | Retained access provenance; requires current entitlement, not a static SQL ACL alone |
| `access_grant`, `grant_reservation` | Grant UUID; unique grant/operation/action | Approved scope digest/revision, reserved/spent counters, expiry; <=64 active reservations |
| `capacity_account`, `capacity_reservation`, `budget_lease` | Account UUID hierarchy; unique operation/attempt/dimension; unique connector lease | Protected/burst separation, reserved+committed <= allocation; leased amounts charged until reported |
| `policy_acceptance` | Unique policy UID/generation | Immutable creator, sponsoring group names, sharing instruction, claimed-capture counter and end; the capture row carries its own sharing instruction |
| `evidence_share`, `share_artifact`, `share_recipient` | Share UUID; unique origin (acceptance or capture)/artifact; unique share/artifact/recipient | Snapshot only, parent denial checked, no reshare; explicit artifact/class/operation coverage |
| `revocation`, `lifecycle_work`, `deletion_tombstone` | Subject UUID+revision; unique artifact/copy/action | Deny before deletion; retention never extended by replay; finite tombstone retention covers the restore horizon |
| `audit_event` | Event ID; operation ID | Append-only, time-partitioned; written in the effect's transaction; export position |
| `outbox` (webhooks, CloudEvents), `work` | Unique event ID; work ID | Immutable payload digest; state, sent connection epoch, due_at, retry fields; no raw evidence |

Foreign keys must not cascade away grants, revocations, charges or historical evidence when a config/capture row is removed. Referential teardown is a lifecycle operation after dependent deadlines close. Counters enforce local CHECK constraints and transactional parent aggregates; a CHECK cannot alone enforce a cross-row sum. Time partitioning is used for `audit_event` retention and never to drop live authorization rows. Index due work by state/due_at/id and catalog by scope/time/id, artifact/capture and origin/artifact. Query plans, cardinality and bounded history retention are release evidence.

### SC-DB-002

Given duplicate requests, publications and completion notifications arrive concurrently, when committed, then one operation, one registration and one artifact slot exist. A reused idempotency key with another request digest is rejected; deleting configuration cannot cascade-delete accounting.

## REQ-DB-003 — Admission and publication transactions

An operation is authorized once before its transaction: identity, eligibility and recovery are observed once and carried as an immutable value valid until `min(observedAt + identity.AuthorityRecheckInterval, original deadlines)` ([ADR-311](../docs/decisions/311-operation-authority-recheck.md)). Hub admission then atomically checks SQL-native facts (revocation rows, fences, expiries), reserves grant action starts/bytes and capacity, inserts the immutable capture/action work with its optional sharing instruction (a policy capture claims a sharing slot of its acceptance), and writes its `audit_event` row and any outbox row. A pending raw-sharing approval does not block otherwise valid collection.

Use short transactions and conditional counter updates. Lock in this order: relevant config/cluster rows; grants by UUID; the capacity pool row only when burst applies, then workload accounts by UUID; the policy acceptance; share and artifact rows by UUID; operation/work rows. Revocation and publication use the same order on overlapping rows. Runtime transactions must not hold a lock across a Kubernetes/IdP/S3 call, upload, analysis or process pause. Expiry uses database time with the documented clock-skew policy; local deadlines remain monotonic.

Use Read Committed with explicit locks/conditional writes for known-row invariants, Serializable for predicates not protected by a designated locked parent row. Retry an entire aborted transaction, bounded to three attempts with jitter within the request deadline. Retry no external side effects. An unknown COMMIT outcome is resolved by the original operation ID, never a new one. Aggregate admission cannot use SKIP LOCKED or an asynchronously lagging replica. A transaction failure leaves no partial hub reservation; S3 and connector effects are resolved by operation ID.

Evaluate grant/configuration/permit expiry against current database time **after all potentially blocking locks needed for the decision**, including later capacity or artifact locks. PostgreSQL `now()`/`CURRENT_TIMESTAMP` are transaction-start timestamps, and `statement_timestamp()` precedes a statement's lock wait; they do not establish current eligibility after contention. Use a post-lock check with `clock_timestamp()` under the qualified clock-skew policy. Dispatch and delivery reuse the operation's authority value within its validity; a started stream runs to its original bounds ([ADR-312](../docs/decisions/312-started-downloads-run-to-original-bounds.md)). Transaction success does not extend a deadline.

Publication creates the sharing instruction's concrete shares in the catalog transaction after checking current manager authority (REQ-SHR-004) and writes their audit rows. Parent revocation commits a denial/revision before child cleanup; a new delivery checks parent/child/grant revocation rows when it starts. No claim of an atomic transaction across PostgreSQL, Kubernetes, IdP, object storage and a target process is permitted.

### SC-DB-003

Given two captures race for the last grant execution and protected capacity, or revoke races with publication, when transactions commit, then quotas do not overdraw and revoked scope cannot be newly disclosed. Serialization retry and lost COMMIT response neither duplicate an action nor release a reservation.

A test holds a later capacity/artifact lock until the relevant grant has expired. Admission and result publication that then acquire it must reject without spending or publishing a child; an implementation that checks expiry only at transaction start or before the later lock fails.

## REQ-DB-004 — Outbox, audit and delivery

A security-relevant operation writes one append-only `audit_event` row in the same transaction as its effect; the operation fails if the row cannot be written. A revocation or denial commits with its audit row and never waits for export. An exporter, woken by `NOTIFY`, ships committed rows in batches to the object store (encrypted per batch, Object Lock where the backend supports it) or a SIEM and records its export position; retention drops whole time partitions after export. Precedent: Kubernetes audit backends, GitLab `audit_events`.

Work and outbox writers issue `NOTIFY` in the writing transaction. Each consumer holds one `LISTEN` connection; after (re)connecting it runs one catch-up query for ready rows ordered by `due_at`. A timer exists only for the earliest known future `due_at` or claim expiry. Webhook delivery workers claim due rows with FOR UPDATE SKIP LOCKED in short transactions, set a claim expiry and release locks before side effects; existing weighted fair workload scheduling selects eligible work before claiming it, since SKIP LOCKED alone promises no fairness. Connector work follows REQ-FED-002: the replica marks it `Sent` with the connection epoch and resends non-terminal work on reconnect; the connector deduplicates by `workID`. Fencing rejects stale results but cannot undo a command already started; unknown starts become Indeterminate and stay charged until their outcome is known.

Each deployed process type (hub, key service, deletion worker, others as deployed) uses one non-administrator SQL login and one connection pool; schema changes use a separate migration owner. setup creates these logins with an administrator credential that only the setup Job mounts, or the operator pre-creates them and supplies their Secrets, in which case setup needs only the migration owner. Transactions acquire one connection and never a second pool connection. The chart sets each process's pool size; the defaults total at most 30 connections for the default replica counts (ADR-335 D11). PgBouncer or the CloudNativePG pooler serves scale-out. Initial budgets: <=100 rows per claim, <=5-second SQL statement timeout and <=1-second lock wait for online requests. Exhaustion returns actionable pressure and does not grow queues without limits. Ordinary completed work rows expire after the replay window; authoritative denial/accounting rows have dependency-aware retention.

### SC-DB-004

Given a hub replica dies after committing work and before sending it, when the connector reconnects to another replica, then that replica resends the non-terminal work, the connector returns the existing state for a known `workID` and an ambiguous dump is not rerun. A notification missed during a listener disconnect is recovered by the catch-up query. An audit row that cannot be written fails its operation; no action starts and no evidence is delivered.

With one runtime login per process, concurrent preparation still creates one immutable execution, and a revocation committed while preparation waits for a lock prevents its effect.

## REQ-DB-005 — Durability, outage and disaster recovery

Production requires a qualified primary/replica/failover profile preserving acknowledged security/accounting commits within its declared failure model, synchronous commit where required, durable storage and fencing of the old primary. Never silently fall back to asynchronous acknowledgement. Managed PostgreSQL or an operator-managed service is supported after qualification; CloudNativePG is optional. A single-instance evaluation deployment must clearly lack the production availability claim. No per-node or workload-cluster database is required. A PostgreSQL restart without restore needs no recovery step.

Primary unavailability denies new central authorizations, share publication and evidence disclosures. Already authorized local work continues only under the connector's budget lease and unexpired permits; retention deletion continues locally.

Restore uses the chart's `recovery` value and the [restore runbook](../docs/installation/helm.md#restore) (ADR-335 D10). With `recovery.enabled: true` and a `recovery.restorePoint`, `helm upgrade` scales hub-api, hub-worker and the local connector to zero replicas, restores bundled PostgreSQL from its pgBackRest repository to that point (an external database is restored with its provider's tooling first) and runs setup's recovery step. That step sets `installation_state = 'recovery_blocked'` and increments `fence_epoch`, which invalidates all outstanding connector budget leases and browser/MCP sessions. It re-applies the revocations, cluster revocations and deletions recorded in exported audit batches after the restore point. If the restore point is earlier than the latest committed state, it also invalidates every restored grant, share, policy acceptance and pending approval, which then require new review. It recomputes committed usage from the bucket inventory per workload prefix and marks artifacts whose objects are gone as deleted. It then clears the flag; an interrupted recovery step leaves the flag set and is resumed by the next run. A following `helm upgrade` without `recovery` starts the workloads. Components read `installation_state` and `fence_epoch` at startup and on `NOTIFY`, not per request, and refuse to serve while the flag is set. Reconnecting connectors report usage before receiving a new lease. Stored deletion deadlines keep expired evidence unavailable after restore. Never reconstruct live spend solely from stored artifacts.

SQL backups/WAL contain no evidence payload, extracted text or full manifests. Control rows are protected by volume and backup repository encryption (pgBackRest repository encryption), access limits, approved finite metadata retention and the backup retention (`services.postgres.bundled.backup.retention`, default 14 days). Deleting a row cannot erase old backups; privacy notices state the backup retention as the time deleted control data may persist (REQ-PRV-008). Restore excludes expired information before serving it, and expired backup sets are deleted by the repository's retention; do not claim GDPR compliance from encryption. Exported audit batches are retained at least as long as the backup retention, within their own approved finite purpose. Payload search stays in region under evidence expiry, outside ordinary PostgreSQL backups. Restore gating prevents disclosure but does not itself delete bytes from old backups.

Migrations run in the Helm `setup` Job with the migration owner role and an exclusive migration lock; runtime roles have no DDL/superuser rights. Use expand/backfill/validate/contract, resumable bounded batches and N/N-1 compatible reads, so the previous minor release runs on the current schema and `helm rollback` to it works. Destructive contraction follows that rollback window and verified backups. Readiness rejects an unsupported schema version. Database connections use TLS 1.2 or newer and verify the endpoint against the system trust store or the optional `caBundle`; credentials rotate through Secrets (REQ-DEP-005). Monitor connection pressure, lock waits, queue age, WAL/backup lag and backup age, replication durability, dead rows and database disk headroom, without evidence-bearing SQL logs.

### SC-DB-005

Given primary failover, an older backup or WAL archive replay, when recovery runs, then revocations recorded in exported audit after the restore point are re-applied, restored grants and shares older than the latest committed state require new review, outstanding connector leases are invalidated and reconciled from reported usage, accounting matches the bucket inventory and deleted/expired evidence stays unavailable. Serving resumes only after the recovery step has cleared `recovery_blocked` and `recovery` is unset; a failover without restore resumes without a recovery step.

## Capture history projection

[History](capture-history.md) is an access-controlled projection of accepted capture executions plus bounded settings snapshots, not a second capture authority. The snapshot is written in the capture's admission transaction. Index selector key, origin, accepted_at and capture ID for stable bounded pagination. The selector key includes namespace/workload incarnation; arbitrary labels and parameter equality use keyed lookup digests. Settings are returned only after authorization.

History-only caps/eviction cannot remove active accounting, approvals, restore denials or required audit. When an original history projection expires, non-authorizing repeat lineage may remain only within its own finite metadata lifetime; it cannot expose the source. Avoid a cascading foreign key from repeatedFromCaptureID to an evictable history row. Snapshots retain dependency digests and privacy lineage independently of mutable recipe CRDs; missing or disabled execution dependencies remain blockers.

## Capture-profile configuration and projections

Kubernetes is authoritative for CaptureProfile publication/availability; PostgreSQL stores bounded indexed source identity/digest/visibility projections and accepted-plan references. No second SQL editing API or runtime registry service is introduced. Accepted history retains profile composition provenance plus the expanded recipe as SQL rows; it cannot reconstruct authority from stale SQL availability after a restore. New permits use the current projection's source UID, visibility and disablement.

## Ongoing source bookkeeping

Store bounded source-session identity, plan/action/pod identity, hard end, readiness/coverage and active reservation references in existing service-owned work/accounting rows. Keep per-incident snapshot idempotency keys separate. Ring bytes remain on the collection node under privacy/resource limits, never in PostgreSQL or Kubernetes. Controller recovery reconciles sessions without creating one source per outstanding incident; snapshots with unknown outcomes keep their charges until resolved by snapshot ID. Source and snapshot cleanup follow [action lifecycles](action-lifecycle.md) and the restore rules above.

## Assessment retention

Persist acceptance/review assessment ID, plan/rule digests and bounded generic reason codes with existing operation/action records. Full explanations, when needed, are SQL rows under the same authorization. Metric samples, process facts and evidence-derived classifications are not copied into durable SQL/audit just to justify a forecast; their projections follow source/control-data deadlines and current audience checks. Artifact handling notices are current projections of authoritative lifecycle/classification decisions, not independent mutable retention promises. See [capture assessment](capture-assessment.md).

## Live-watch query state

The [live-watch contract](live-watch.md) adds a bounded `live_watch` runtime table, not a configuration CRD or evidence event log. Persist minimized viewer/client, exact scope digest, source/profile selection and display filter, revision, hard/idle deadlines, terminal state, opening idempotency key and query/output counters; the row is deleted at its control-data deadline. No per-row SQL write, row body, HTTP headers, syscall details or durable replay queue. Existing capacity transactions reserve independent view resources; replay/filter changes cannot reset counters. Source acquisition and incident reservations remain separate. Restore never revives an old watch, source or expired authority.

## Native artifact transfer state

`artifact_download` stores opaque session/artifact/actor-client references, immutable version, state, authority revision, deadline, read-work reservation reference and emitted byte counters. Uniqueness is actor/client plus idempotency key/request digest; repeating preparation cannot allocate new budget. C-14 owns transitions under the canonical lock order. Filename, native checksum and coverage remain in the protected artifact metadata, not a copied evidence payload. No per-range CRD or persistent byte cache. Deletion/restore ends incomplete transfers and never resurrects one; external local files have no managed-copy deletion state. [REQ-DLD-003](artifact-downloads.md) defines semantics.

## Combined investigation grants

AccessGrant retains optional accepted resultAccess (selected actions, operations, same-human registered clients, digest, finite output/count/operation pool, original expiry). Child rawQuery grants store resultOrigin and a parent foreign key. Add a bounded `grant_result_registration` relation keyed by parent, capture, artifact and client, referencing verified immutable artifact/digest and action provenance; distinct-artifact membership is unique at parent/artifact independently of client. This is an internal relation, not a new public aggregate or CRD. Parent resultAccessCounters and ordinary acquisition counters are separate.

Within the canonical transaction order, C-03 locks the parent decision/scope, validates trusted commit and current eligibility, registers/reuses the output, publishes exact child scope and writes audit/outbox rows. Downloads/queries reserve parent disclosure and child operation limits in the same authorization/capacity transaction. Never allocate an independent full parent allowance per child. A read checks the parent's revocation rows when it starts; cleanup delivery may lag. Restore does not recreate expired authority. Runtime concurrency, duplicate publication, interrupted delivery and parent revocation tests remain required under REQ-INV-002.
