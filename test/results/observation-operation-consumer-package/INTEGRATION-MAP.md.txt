# ADR150 v2 consumer integration map

Source-only proposal, 2026-10-13. Both concrete native operation primitives are now integrated. This map selects no runtime route and makes no native availability claim. No source/build changes accompany it.

The original counterexample remains the reason for this work: native first owner pair took 3.715292 seconds and 94 observer / 24 probe calls; the second pair was denied after 1.198731 seconds, leaving about 80.7 milliseconds of the original query interval. It was an expected-denial test, not a successful observation workflow. See `test/results/regional-observation-native-cost*`.

## Contract and version boundary

Use the already agreed, original installed `Observation.Format` literal `owner-observation/v2`, with an independently pinned regional `connector-observation/v2` selection. Console owns the single fresh owner2/worker2 producer, schema, journal and loader selection. No extra operator option, candidate-limit inference, negotiation or v1 fallback is added.

V1 `OwnerAuthenticator`, full source/attestation ports, constructors, wire encoders/decoders and callers keep their current semantics and bytes. V2 explicitly distinguishes an actual source-value read from an operation's two native guard/workload brackets. It does not implement a caching substitute for a v1 port.

Each v2 native operation is privately owned by one consumer operation. Its public proof envelope names an opaque, locally created bracket ID, original request ID/challenge/root, original start/end, exact installed pin, actual TLS channel and leaf/process, plus the initial/final phase. The ID is correlation only and grants no authority. A returned value cannot instantiate a private operation. Repeated request IDs cannot acquire another operation's state.

The metadata request/result and their canonical digest remain unchanged inside v2 envelopes. Keep four proof ordinals and the existing twelve-frame exchange. Add closed v2 own-proof, exchange, local and routing purpose constants/decoders; existing v1 decoders reject the v2 identifiers. The v2 proof payload can carry original bracket dates and actual value-read dates separately. No later source, SQL, TLS or final-bracket date may extend the original deadline.

## Exact ordering for one claimed conversation

1. HWORK starts one original at-most-five-second request. Read the finite, complete current SQL candidate set; the actual common-SNI leaf must belong to it. Take the selected-server initial native bracket and current registration/configuration/root checks **before reading/sending the projected HWORK token**.
2. Owner B verifies that token online and the independently installed HWORK chain. HWORK and owner are separate workloads; share a native guard read only where the actual client and complete original guard identity are identical. Keep the HWORK token local to B.
3. B's branch establishes its original native pair for B and contacted A. GET is common-SNI, purpose-fixed, actual mTLS. SQL candidate/Ready observations are routing provenance, not permission. Every contacted candidate costs its real native work; no truncation or implied latest-process choice.
4. A authenticates actual B, starts its original native pair, and records the exact public holder locator plus its private pending operation. A sends the locator under the original query/native/socket/leaf bound.
5. B selects one locator. A new actual exact-SNI TLS connection carries the sole claim. B and A recheck current SQL/configuration/roots/keys; A atomically spends the matching pending record before holder attachment or metadata work. Wrong/missing/replaced/expired records deny; no rebracketing or fallback.
6. A attaches to the exact retained regional socket. Its original hard socket end still caps everything. Four owner proof replies use the same private owner operation, actual current SQL/TLS/private keys each time. R accepts no metadata operation until its first two source-value replies and A's first exact SQL49 registry check have succeeded.
7. R performs the selected existing bounded metadata operation. The result remains private/bounded until all final checks and terminal completion.
8. For the final SQL49 check, ordinal 3 reads the source again. A performs its genuine final owner native bracket before creating ordinal 4's final own-owner proof. R then performs its genuine final native bracket **before the ordinal 4 source-value decode**, so a source change during the guard's own probe GET/denial cannot escape the final value comparison. R rechecks its current keys/leaf/process/issuer roots/time after that value read. A checks the exact final source value and SQL result under the original end.
9. Complete the existing exact Receipt and joined request/response EOF. The A receiver consumes the already-established final native snapshot; it does not call `Final` twice or claim another native read. It still checks current SQL/TLS/private-key/cancellation/time before output. Any detected change or terminal uncertainty suppresses the result.
10. B takes its independent final native pair/caller checks and verifies current SQL/TLS before replying. HWORK independently takes its final selected-server native bracket/current SQL/TLS check before using the response. These brackets keep original starts/ends. A final observation is not a new allowance.

The owner A pair is the same private operation for locator/claim and four own-owner proofs. Starting a separate own-owner operation would silently repeat the native work and break the count target. Its sharing is explicit in a concrete, bootstrap-owned per-claim coordinator. The regional process has its separate native operation; a remote value cannot replace the local owner guard.

## Pending locator ownership and delivery

The pending operation must not derive its lifetime from the GET handler context, which net/http cancels when the handler returns. Its context is a child of the handler/process root with an explicit immutable end equal to the earliest of the original accepted GET socket end, query end, native bracket end, sender/holder leaf ends and standby end. It cannot use a later POST's interval to extend any of those bounds.

Admission links GET cancellation to that finite operation until output ownership is explicitly transferred. The private state machine is `proving -> prepared -> delivery-started -> pending -> claimed -> closing -> joined` (failure can enter closing from any state). Count the operation in the existing per-process limit through pending, claimed and joined cleanup. The HTTP handler's own active work is also joined; releasing its network slot does not release the retained operation slot.

Before the first locator write, record `delivery-started` under the same mutex that protects claim/cancel. No write or flush proves peer receipt. If cancellation occurs before any possible delivery, close and join. Once delivery is possible, a lost/cancelled GET remains unknown and charged until exact claim or original expiry. Normal GET completion detaches only its joined setup callback; it does not cancel the already owned finite operation. Simultaneous claim and GET completion/failure have one atomic state winner. A duplicate GET cannot allocate another record for the same original query/sender; a duplicate or uncertain POST cannot retry it. Keep a spent marker in that same bounded record through its original end, including after successful joined completion, so a repeated GET cannot recreate an already consumed operation within its still-valid request interval. It occupies its original slot and adds no independently growing tombstone collection. Expiry/Close cancels and joins work before slot release; old cleanup compares the exact entry/sequence and cannot remove a replacement.

This adds no persistent route or authority journal. Restart loses the pending operation and the old claim fails. The caller can start a wholly new bounded metadata query through existing admission, but this implementation performs no automatic retry or unknown takeover.

## Proposed staged checkpoints and path ownership

The first consumer checkpoint is **the purpose-specific value/port bridge plus v2 source/registry semantics**, not a runtime selector. Exact new paths proposed:

- `internal/domain/fleet/observation_operation.go` and `_test.go`: native-only value types, explicit bracket/phase predicates and clone behavior; pure values only, no hashing/JSON/I/O.
- `internal/application/fleet/observation_operation.go`: narrowly typed owner/regional native operation ports and v2 source-value/registry ports. No configurable callbacks or generic cache.
- `internal/adapters/kubernetes/observation_operation_ports.go` and `_test.go`: concrete bridges to the two existing primitives. Existing primitive native value definitions can be aliases to the domain type; no change to their I/O or validity predicates.
- `internal/adapters/postgres/connector_observation_operation.go` and `_test.go`: fixed SQL49 v2 composition; narrow private extraction in `connector_registry.go` only if needed to avoid duplicated SQL validation. Old full-source path remains independently tested.

Then freeze a second bounded checkpoint for `internal/contracts/observation_operation.go` / tests and separate `mtls/{owner,connector}_observation_operation{,_wire,_source}.go` / targeted tests. Existing v1 files only receive mechanical private-helper extraction where exact byte/lifecycle parity is proved. The v2 mTLS constructor must accept the concrete bootstrap-provided native operation port, current registry, actual process credentials and installed pin. It cannot be selected by decoding a wire format alone.

Next checkpoints connect actual closed v2 stream framing/coordinator; finite pending locator/claim and matching forwarder; finally outer HWORK caller/client. Each will list exact files before its freeze, with source-count and closure regressions. Do not combine all these untested lifecycle changes into one large payload. The map covers the complete graph so passing one checkpoint cannot be mistaken for a usable route.

Workflow owns these new purpose-specific consumers, their tests and staged ADR150/architecture amendments. Console retains shared `OwnerObservationBootstrap`/OwnerDeployment/layout/schema/producer/reader selection and original receipt work. MCP retains CapacityLocalOwner/worker effect consumers and fixed SQL role inventory. Existing v1 source remains the default. Parent owns canonical integration, runtime selection review and actual native labs.

## Required evidence and known remaining gaps

- A v1-shaped consumer must fail the explicit v2 types/format/bracket semantics; wrong source/profile/leaf/channel/ordinal/phase/date/uint64 and unknown/duplicate fields deny. Metadata digest bytes and all four existing purpose payloads remain identical.
- The v2 registry test must show exactly two real source-value calls around each SQL call, one ordinal spent before each I/O, no SQL call after a bad first value, and denial after SQL revocation or final source/roles/backing change. The real SQL49 native fixture must remain required; a fake registry race test is not lock/fence qualification.
- Actual TLS tests cover current key/leaf renewal or closure, cancelled setup/read/final delivery, old candidate vs newly selected leaf, current accepted root/configuration change, mixed v1/v2, and final native mutation suppressing all metadata output. Close must join the native operation and actual transport work.
- Pending locator tests cover GET cancellation before write; lost reply after possible write; handler return without proof cancellation; original expiry despite a later POST; duplicate/concurrent claim; wrong sender/process/leaf/holder/sequence; stale cleanup; process shutdown; and no slot release before joined cleanup.
- HWORK tests must cover no token read/disclosure before complete selected-server proof; separate caller template/account/TokenReview mutation; outer deadline spent during candidate discovery; and final native/SQL denial before result use.
- Counts currently remain proposal: HWORK 28/6, B 48/6 plus separate candidate work, A 34/6, R 50/12 plus selected metadata, under their existing per-process clients. Neither loopback latency nor these counts proves full availability. Candidate branches/pages and legitimate background observers add work under the same bounds.
- Full native composition must use HWORK, two owners and regional process, actual API and SQL current checks, actual mTLS streams, all four metadata purposes, original finite pending and standby bounds, body-free per-leg timings and actual API/acquire counts. Success and final mutation/revocation/expiry/cancellation cases are required at original five seconds and 20 QPS. Until then v2 remains unselected, and installed multi-cluster observation availability is unqualified.
