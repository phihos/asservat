# Current peer identity

C-04/C-20/C-21/C-24 under I-01/I-02, TASK-03 and S-01. This implements certificate interpretation and current connector registration reads. It does not enroll a cluster, issue a certificate, attest a node or expose a listener.

## Internal certificate profile

Internal peer ingress uses TLS 1.3 with client-certificate chain verification. The initial profile uses one URI SAN, digital-signature usage and client-auth EKU only, explicit non-CA basic constraints, no common name, DNS, IP or email identities, and at most one hour from notBefore to notAfter. TLS server certificates remain separate. The [initial enrollment CSR profile](enrollment-claims.md) qualifies conventional Ed25519/ECDSA/RSA choices; the Ed25519 JWS choice does not dictate one PKI key algorithm.

The URI profile is `spiffe://asservat.<installation-uuid>/cluster/<cluster-uuid>/epoch/<issuer-epoch>/<role>/<peer-uuid>`. Role is `connector` or `node`; node identity appends `/uid/<node-uid>/boot/<boot-uuid>/collector/<collector-epoch>`. Exact canonical spelling and no query, fragment, encoded path, port or extra identity are accepted. IDs are assigned/verified by enrollment; a node name, client field or matching certificate alone cannot establish that enrollment. This uses SPIFFE ID syntax without introducing SPIRE, its Workload API or a new mandatory service.

`mtls.PeerVerifier` takes the actual server-side TLS state, requires a verified client chain and repeats current-time X.509 verification against explicitly supplied installation roots on each request. A reused connection cannot outlive its certificate. No forwarded-certificate/proxy-header fallback exists. The application then requires current peer registration, exact certificate digest/times and expected role/cluster/issuer epoch before returning a finite authenticated peer. The supplied root pool is copied; trust rotation requires replacing the verifier from current protected bootstrap, not mutating an incoming header.

## Current SQL registration

Migration 00006 supplies suspended/recovery-blocked `fleet_trust`, disabled-by-default `fleet_peer` and two bounded certificate slots. It supplies no enrollment writer. A future qualified enrollment/audit producer must bind the verified audit receipt and original authority before enabling a peer. Certificate renewal may overlap two slots; retiring a slot blocks the old certificate even while its CA signature remains valid. [One-use bootstrap claims](enrollment-claims.md) now have their own SQL boundary and tests; [claim/certificate audit, signing and activation](enrollment-activation.md) now compose in a tested coordinator. Token issuance, rotation writer, total registry/history limits and recovery checkpoints remain pending.

The SELECT-only registry adapter is scoped to one installation and connector peers. It reads from a primary connection, records database time before its statement and checks time afterward. Current trust observation is at most 30 seconds, and returned per-request authority is capped at five seconds and the earlier trust/registration deadline. Revocation, stale epoch, suspended root, recovery block, missing audit, expired registration or unknown certificate denies access. A blocked lookup cannot be stamped fresh after it returns. Node certificate parsing is implemented; node enrollment/local registration is not supplied by this hub reader.

The fixed `work-trust.json` protected ConfigMap contains one cluster/issuer epoch, a finite revision and at most eight public Ed25519 keys. The Kubernetes reader pins namespace and ConfigMap UID, validates the offline schema, canonical key/time encodings and complete unique key set, and preserves original read freshness. A signed envelope cannot select a URL or another configuration object. Current TLS enrollment and work-key trust are independent checks, and neither bypasses current authority/reference resolution or the local start journal.

## Verification and provenance

Actual TLS tests cover connector/node certificates, wrong installation/role/root, ambiguous identities, DNS/CN contamination, server/dual EKU, overlong lifetime, expiry on a live connection, missing client certificate and TLS 1.2. Application tests cover current revocation, epoch/digest mismatch, stale registry and expiry during lookup. Protected-key-reader tests cover replacement, malformed/duplicate keys, schema/case aliases, stale receivers and delayed API reads. A real Kubernetes run also passed pinned key lookup, rejected ConfigMap replacement and proved the reader cannot update trust (`test/results/peer-trust-kubernetes-check.log`). Race tests passed in `test/results/peer-identity-unit.log`.

The real PostgreSQL test uses separate read-only credentials and synthetic accepted-enrollment records. It covers current revocation, recovery/epoch/trust/registration expiry, certificate rotation, missing audit, wrong cluster and a blocked lookup. The expanded run passed with exit 0, unchanged source hashes and complete cleanup; `test/results/peer-registry-integration-check.log` and the custody environment report record the result. The initial run exposed a stale schema-version check in the capture-audit constructor; `test/results/peer-registry-migration-regression.log` preserves that failure, and the passing rerun includes its fix and all custody/authority/admission regressions. These tests do not qualify production PKI/enrollment, private-key custody, protected configuration writers, restoration or node process exclusion.

Primary references checked 2026-10-10: [Go TLS connection state](https://pkg.go.dev/crypto/tls#ConnectionState), [X.509 verification](https://pkg.go.dev/crypto/x509#VerifyOptions), and [SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/). The standard library verifies chains; current registration/revocation and this exact certificate profile are Asservat rules.
