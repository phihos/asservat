# ADR144 exact-holder forwarder component checkpoint-v1

This immutable eight-path package adds a concrete purpose-fixed forwarding component and two narrow supporting APIs. It does not select receiving routes or an installed runtime backend. Existing protocol bytes, four proof ordinals, permission-root/installation distinction, SQL roles and source/caller/socket deadlines remain unchanged.

The forwarder reads the original explicitly selected complete SQL candidate set, intersects it with one complete Ready endpoint observation, performs at most two read-only locator GETs concurrently and joins all outstanding GET work before one exact-holder claim POST. Actual common-SNI and exact-SNI TLS leaves receive independent current registry, accepted configuration/roots, Ready route, native guard and installed-template checks before and after each request. A failed or unknown POST is never replayed; no HWORK token is forwarded. Two process slots remain occupied through joined native proof, body and transport cleanup.

`ObserveOwnerClient` delegates the existing complete authenticator and private-key verifier. The exported locator mappings preserve the existing wire conversions and exact uint64 semantics. The existing public constructors and other routes are unchanged.

## Remaining scope and next work

No real SQL/Kubernetes/provider regional workflow, actual holder-stream attachment, installed multi-owner reachability or sustained five-second availability is qualified by these component tests. The prior candidate native SQL/S3 qualification is separate evidence. Local synthetic successful forwarding measured roughly 22–24 ms, but one success still invokes 16 registry checks, 16 guard checks, 10 route checks and 8 workload checks across both legs; these are structural component counters, not backend latency measurements.

The next separate package must compose the existing bounded listener with the closed common-SNI locator GET and exact-SNI claim POST, preserving accept-time bounds and proof/standby slot separation. Runtime selection must follow the original acknowledged backend receipt, with the actual regional producer/holder and dedicated HWORK path. Then an owned native multi-owner/two-cluster fixture must measure complete per-leg work within the same original five seconds. No shared installed-v2 producer, SQL grant, migration, field default or runtime selector is included here.
