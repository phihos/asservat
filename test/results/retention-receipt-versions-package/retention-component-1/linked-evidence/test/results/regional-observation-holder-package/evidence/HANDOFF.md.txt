## Behavior and boundaries

The handler reserves a process slot before Hello/factory work. Setup, idle, claimed, failed and closing work remain charged until admitted work joins. An exact claim includes root, cluster, exchange UUID and a monotonic local registration sequence; overflow denies. Repeated wire UUID and delayed old cleanup cannot claim or delete a replacement. Later distributed forwarding must additionally bind exact holder Pod/process.

Both handler and coordinator require the original finite socket context (at most 30 seconds); neither creates fallback residency. The request, locator, owner/connector proofs, certificate expiry, holder parent and caller only shorten this bound. No cache, signing/enrollment fallback, new frame, SQL table or credential is introduced.

The purpose-fixed bootstrap factory binds the actual receiving TLS stream to original installed profile, concrete owner ingress and separately scoped registry. The registry wrapper delegates to unchanged SQL49 current-leaf logic. Two registry reads obtain all four new numbered same-channel source replies, around one metadata exchange. Every own-owner proof retains current registry/route/native guard/workload reads. Revocation or changed source after metadata withholds Receipt/result.

Positive completion removes the exact entry from routing before Receipt, requires clean request EOF and joins coordinator/stream work before handler completion. Extra bytes, missing EOF, unknown final delivery or cancellation fail. The separate listener still owns and must join its actual raw socket; handler cleanup is not evidence of remote acknowledgement or socket closure. This checkpoint deliberately does not select that listener.
