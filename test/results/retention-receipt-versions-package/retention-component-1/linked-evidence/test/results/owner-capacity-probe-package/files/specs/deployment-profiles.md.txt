# Deployment profiles and internal dependency alternatives

The maintainer requires a small-deployment path that does not require separately operated SSO, KMS, S3 or PostgreSQL and has accepted the recommendations in [ADR-063](../docs/decisions/063-small-deployment-alternatives.md). The [research report](../docs/research/small-deployments.md) distinguishes selected choices from measured qualification. These requirements are planned behavior, not available chart settings.

## REQ-DEP-001 — Independently selectable infrastructure

[ADR-140](../docs/decisions/140-installed-public-runtime-producers.md) requires
fixed protected post-activation credential producers before installed public
startup. The retired initial SQL manager MUST NOT be reopened. The three
configuration-reconciler credential purposes MAY use independently current
guarded source/workload proof in place of expired stored source-observation
freshness, but MUST retain original positive installation activation, current
database incarnation/issuer/recovery/suspension checks and original bounded
one-use claims. Other public credential purposes MUST retain their independently
accepted current configuration requirement. Proof reuse MUST be local to one
original operation, recheck actual negative enforcement and canonical facts
before effects and after blocking locks, and never extend the earliest original
deadline. Unknown effects remain lookup-only. Immutable credential projections
confer no activation or current authority. Installed provisioning MUST validate
the full aggregate runtime/rollout/reconciler/verifier/installer PostgreSQL
connection budget; partial role inventories or isolated component tests do not
enable public serving. The command switch MUST be composed with its actual
protected projection producer and installed qualification.

Official Helm installation MUST offer explicit bundled and external choices for identity, key services, PostgreSQL and evidence storage. A small profile selects compatible internal/bundled defaults; administrators can override each provider independently. Deployment size is separate from hub/cluster topology and never introduces tenants. Workload-cluster enrollment MUST NOT install duplicate hub databases or identity services. Reuse existing configured infrastructure without taking ownership of it.

Preserve the same authorization, audit, retention, fair capacity and native-download contracts in both profiles. Do not require a broker, email service, external monitoring backend, paid service, licence key or runtime internet access. Existing Kubernetes and durable persistent storage remain explicit prerequisites. Offline analysis may be unavailable without qualified encrypted scratch under ADR-036; that MUST NOT disable independently usable collection, live projections or native downloads.

[ADR-137](../docs/decisions/137-official-helm-bootstrap.md) packages initial
bootstrap separately from runtime enablement. The official chart MUST preserve
one fixed original hook, successful-only automatic deletion, immutable public
revision inputs and all product-owned progress outside Helm. An explicit
terminal-only resume command MUST verify exact original template/input/UID/RV
and positive process termination before removal; timeout, disappearance or Helm
rollback MUST NOT confer recovery authority. Completed replay MUST work without
setup credential files. Operators provide static endpoints, ordinary PEM and
Secret references, not generated UID/OID/digest bundles. Optional registry auth
MUST remain closed, bounded and separately supplied, propagate to the exact
activation pull without entering its mounted seven-file projection, and share
the original positive managed-copy cleanup. Successful bootstrap MUST NOT be
reported as installed public-service readiness.

### SC-DEP-001

Given a fresh cluster with suitable persistent storage and trusted HTTPS configuration but no IdP, KMS, S3 or database service, when the administrator selects the qualified small profile, then the installer supplies the chosen internal services without asking application maintainers for infrastructure credentials. Adding another workload cluster reuses that hub. Unqualified or absent analysis scratch reports only the affected capability unavailable.

## REQ-DEP-002 — Local identity without a second permission system

Support local users, groups, login, invite/recovery, disable and session revocation using stable installation-issuer/subject/group identifiers. Password credentials MUST use a reviewed memory-hard hash, never reversible encryption. Local authentication MUST supply verified recent assurance for approval/administration where required, with bounded authentication resource usage. No default password, anonymous enrollment or mandatory email delivery. Account/group administration is separately authorized/audited; a group membership change may change existing rights and MUST show that consequence. Evidence ownership and immutable creators remain separate from account administration.

Use the existing Kubernetes permission resources for local and external identities. Do not infer Kubernetes exec rights by matching a local username; inheritance still needs a qualified explicit identity mapping. MCP and CLI login MUST use the reviewed OAuth discovery/code/PKCE/resource/client-bound flow without receiving the user's password. Local disable and membership/session changes MUST be enforced at current effect gates within the existing freshness bounds; cached tokens cannot extend them. Local identity outages fail closed for dependent interactive access. Team policy execution retains independently delegated workload authority, not a local user's perpetual refresh token.

### SC-DEP-002

Given a local developer authorized through a group AccessBinding and a separate authorized reviewer, when the developer connects an MCP client, then authentication uses browser login and scoped tokens, and the same evidence rules apply as with SSO. Removing group membership or disabling the account blocks dependent access within the specified freshness bounds. Recreating the same username does not inherit the deleted subject's grants, ownership or shares.

## REQ-DEP-003 — Local key services with unchanged evidence isolation

[ADR-126 connector process identity](../docs/architecture/connector-renewal.md)
MUST keep the logical installation/cluster/peer account stable across ordinary
Pod and process replacement. Fresh protected Pod/controller proof, distinct
client/server keys, bounded signing attempts and independent audit precede leaf
activation. Backing renewal MUST preserve original process/leaf dates and
uncertain spend; it cannot make a stale complete source current. Exact leaf
registration is required for peer use. Automatic replacement must not require
repeated administrator enrollment, and retiring an absent process must not
depend on that process supplying a live identity. Component tests do not qualify
installed renewal, backend costs or complete finite retirement.

Historical connector signing records MUST preserve a nonempty intersection of
their original request, identity, configuration and recovery observation
intervals. Sequential observations may begin after request entry; validating
their historical overlap MUST NOT move that request start, extend any deadline
or replace the current-time checks required for new effects.

[ADR-081 owner enrollment proof](../docs/architecture/owner-enrollment-proof.md) MUST verify the dedicated Pod-bound token online, exact live account/Pod/controller membership, identity-free CSR possession, current accepted configuration and independently qualified namespace protection before durable enrollment or signing. Allow scheduled Pending/Running Pods before readiness; retain Ready endpoints for actual forwarding. Repeat token/object checks, reject deletion and security-relevant mutation, and preserve the earliest original five-second/configuration/protection/token deadline. Structural checks MUST accept overlapping original observation intervals whether the nested configuration read predates or follows the proof start; they MUST NOT reset either start, extend a deadline or replace current-time effect checks. Keep tokens and full specs out of proof/audit payloads. Process uniqueness, bounded signing and activation remain separate durable responsibilities; this observation is not an evidence or issuance grant.

[ADR-080 private hub protection](../docs/architecture/owner-workload-protection.md) MUST prevent unrelated namespace writers from creating alternate workloads, forging privileged account ownership, minting tokens or injecting processes into the hub. Qualify native admission with exact pins and an independent RBAC-permitted dry-run denial, preserving the original deadline across all reads. Protect the dedicated namespace before credentials/workload installation and separately constrain credential reads; current admission alone cannot prove historical integrity. Keep application namespaces and acquisition workers outside this private scope, retain required qualified Kubernetes controller operations, and have the installer manage this boundary without developer approvals. Unsupported controller profiles fail closed. This prerequisite does not authorize enrollment or replace exact Pod/token/CSR and durable activation checks.

Provide a local static-key alternative for every required external key-service purpose: artifact key wrapping/unwrapping, protected application credentials, signatures and internal certificate issuance. Reuse established cryptographic implementations and the existing artifact format/bindings. Separate keys and authorization by purpose; collectors/publication are wrap-only, acquisition unwrap is scoped to current authorized evidence, and the hub has no raw-evidence unwrap authority. Static root keys MUST NOT be mounted into all application/collector pods to avoid implementing this boundary.

Keys MUST be random, versioned, initialized once and referenced from protected Secrets or an equivalently qualified local source. Protect the source and its backups at rest. Stable key/issuer/CA identities survive Helm upgrades, rollback and uninstall. Missing keys with existing installation state require recovery, never silent regeneration. Rotation preserves required old readers and finite recovery obligations without claiming selective erasure from shared-key deletion. Local keys do not remove TLS, peer identity or browser trust requirements.

The initial private wrapping/signing payload MUST follow [local-key-secret.schema.json](contracts/local-key-secret.schema.json) and [ADR-064](../docs/decisions/064-local-key-material.md): exact independently configured installation/purpose/key scope, bounded closed JSON, one active version and finite retained versions. References and associated data bind that scope, immutable version and the existing canonical caller binding. Replacing a Secret snapshot does not authorize rollback, retirement or additional operations. The protected service lifecycle MUST fence stale processes and enforce current scope before cryptographic effects. This payload is neither a public permission API nor a Helm value; its crypto backend cannot be mounted into consumer roles as a shortcut around the key-service boundary.

The [ADR-067 protected source and lifecycle](../docs/architecture/local-key-lifecycle.md) MUST bind the actual immutable Secret UID/digest to separately pinned configuration, current recovery and durable accepted version history. Cache only bounded public observations with their original deadlines; accept no stale fallback or deadline renewal. Check that same backend configuration before and after every authorized key effect. Initial rotation is additive; removal requires a separate retirement operation proving retained-data and recovery obligations, never automatic pruning.

The initial private remote facets follow [I-14](../docs/architecture/local-key-service.md) and [local-key-service.schema.json](contracts/local-key-service.schema.json): pinned mTLS identity, closed operation-specific requests, finite payload/concurrency/deadline limits and a current operation permit bound to the exact request and peer. A certificate role or caller-provided authority UUID MUST NOT confer authority. Current accepted artifact/session/signature scope, recovery generation and original deadlines remain mandatory after blocking checks and before output delivery. A working TLS/crypto fixture does not qualify the production resolver, issuer, Secret lifecycle or installer.

The initial local context-download resolver follows [ADR-066](../docs/decisions/066-download-key-authority.md): a private binding to the exact prepaid audited download batch and acquisition certificate, with one irreversible unwrap slot per physical-object key. Current parent/retention/recovery fences apply after locks. Binding retries and provider errors cannot refill slots, select another peer/artifact or lengthen the original lease. This implementation does not confer collection, raw-artifact access or authority for other key purposes.

[ADR-068 worker proofs](../docs/architecture/download-worker-attestation.md) additionally require a current Pod-bound token review and exact namespace/account/Job/Pod identities and approved spec digests from protected dispatch. Bind the original finite proof to the acquisition certificate and download; recheck after blocking SQL work. TokenReview and certificate roles alone grant no evidence authority. Never store the bearer token, renew an existing child through proof replacement or fabricate proofs for legacy rows. Enrollment and control mediation are internal operations, with no additional developer approval.

[ADR-069 dispatch](../docs/architecture/download-worker-dispatch.md) MUST journal a single-use, independently audited launch and pin the actual acquisition Pod. Unknown create outcomes cannot issue another create; another Pod cannot inherit identity. Persist known process termination before deleting the exact Job, and verify deletion before releasing worker capacity. Cancellation, expiry and a missing API object alone are insufficient cleanup proof. The fixed restricted template receives only bounded startup identity/public configuration; current evidence authority remains separate.

Worker installation MUST supply a pinned non-preempting PriorityClass; the initial dispatch profile fixes priority zero and refuses global-default or preempting classes. Polling/reconciliation MUST reuse exact acknowledged audit receipts without repeating encryption, while still checking current authority before effects. Reject unusably short worker reservations before charging capacity; never extend an evidence deadline to satisfy the scheduler.

[ADR-070 protected worker configuration](../docs/architecture/worker-configuration.md) MUST supply dispatch and worker-identity consumers with an independently pinned administrator source and an audited monotonic revision, never a constructor profile alone. Qualify the exact native admission protection with a separate non-administrator dry-run probe; RBAC denial alone is insufficient. Preserve the original observation deadline through SQL locks, Job operations and identity proofs. Unavailable, suspended, unaudited or superseded configuration denies new effects; rollout never renews evidence/session deadlines or refunds uncertain capacity. Historical termination and verified cleanup remain possible after revocation. Installation resolves these references for administrators; developers do not hand-author worker profiles or approve this internal operation.

[ADR-071 enrollment](../docs/architecture/worker-enrollment.md) MUST verify the exact admitted Pod/token and an identity-free signed CSR before its first certificate exists. Bind one public key per worker; keep its private key in that process. Separately audit enrollment, spend finite signing attempts before provider I/O, verify the actual issued identity/key/deadline, audit the certificate and activate it before use. CA validity alone does not establish a registered acquisition peer. Derive bounded renewal periods from the original worker start, retain uncertain attempts and preserve all download/worker deadlines; polling, token changes and reconnects cannot refill the signing budget. Trusted control retains human credentials and current download authority. No new developer approval is introduced.

[ADR-072 private credential transport](../docs/architecture/worker-credential-channel.md) MUST use independently pinned server and issuer trust, the existing dedicated projected Pod token, a process-owned CSR key and the closed [enrollment wire](contracts/worker-enrollment.schema.json). Reject worker-selected principals, human credentials, callback addresses or signing periods. Bind current authority to an active authenticated control operation of at most thirty seconds, preserving parent cancellation and exact worker identity. Reopen the fixed projected token for actual renewal, retain the process key and original certificate periods, and reject mismatched/expired response identities before use. Bound concurrency, bytes, deadlines and retries; no redirect, automatic POST replay, plaintext credential persistence or offline identity fallback. Closing the owner disables retained signers; current authority and registry checks remain mandatory on reused connections.

[ADR-073 worker startup](../docs/architecture/worker-startup.md) MUST verify the exact immutable [worker control payload](contracts/worker-control.schema.json), separate pinned CA sets, fixed paths and original identity/timing arguments before enrollment. The actual Pod UID comes from the downward API and remains subject to independent token/dispatch verification. Disable process core dumping before loading credentials; never change host core settings. Bound initial enrollment, renewal, backoff and status notifications by the original deadlines. A blocked observer MUST NOT delay credential closure. Credential readiness is not work readiness or download success. Historical cleanup MUST verify originally stored object identities/spec digests, while new admission still requires the current template; uncertain or extra Pods remain charged.

[ADR-074 active request routing](../docs/architecture/worker-request-routing.md) MUST bind each enrollment to its exact current authenticated owner and admitted worker, preserving original deadlines through registration I/O and response delivery. Bound registration, active owners and closing in-flight work together; closing a route cannot refund its local slot before that work returns. Concurrent workers MUST retain separate token readers and actor/client scope. Reject duplicate active ownership, and prevent old-handle cleanup from closing a replacement. Response cancellation/deadlines remain effective through write/flush, with callback cleanup completed before socket reuse. A process-local route is not cross-replica rendezvous, durable authorization or certificate revocation.

Shared worker request ownership follows [ADR-075](../docs/architecture/worker-owner-locator.md). Persist only minimized process/request IDs, finite original times and fencing state, never personal credentials, Pod tokens or endpoint URLs. Claim only for a current authorized request and exact admitted worker; repeat freshness checks after blocking locks. An active fence cannot be silently taken over or renewed. Late release MUST compare the exact original fence and leave replacements untouched. Locate metadata independently of authority; the receiving process MUST verify both the current shared owner and exact local handle before ordinary enrollment checks. Missing owners, uncertain claims and process restarts cannot invent authenticated human state. Metadata cleanup remains bounded and cannot refund worker/signing/evidence capacity.

[ADR-076 hub owner discovery](../docs/architecture/hub-owner-discovery.md) MUST resolve a request owner through the pinned hub-cluster Service/EndpointSlice/Pod/account/Deployment chain, with bounded complete observations and no worker-supplied endpoint. TLS MUST independently identify the exact installation, hub cluster, issuer epoch, Pod and process using current explicit-root verification. Discovery readiness is not identity or authority; source protection, issuer activation and exact current request ownership remain separately required. A restarted process or replacement Pod cannot inherit another process's active authenticated request. Verify the destination before forwarding credentials and preserve original deadlines through connection and delivery.

[ADR-077 protected owner configuration](../docs/architecture/owner-configuration.md) MUST supply the pool and public issuer roots from an independently pinned administrator-protected Kubernetes source, using [owner-configuration.schema.json](contracts/owner-configuration.schema.json). The payload cannot select its own administrator, protection, private issuer credential or callback endpoint. Qualification requires current exact admission protection and an independent non-administrator dry-run denial, not RBAC denial alone. Observe matching configuration before and after endpoint resolution; reject suspension, changes or unavailable roots and preserve the earliest original observation/root/request deadline. An observation is not durable configuration acceptance, recovery authority, certificate activation or an evidence grant.

### SC-DEP-003

Given retained evidence encrypted under local key version one, when the chart upgrades and version two becomes active, then old evidence remains readable only through authorized acquisition and new evidence uses the new version. A collector's wrap credential cannot unwrap either version. Losing the old Secret produces a specific recovery failure; reinstalling cannot make the old ciphertext appear successfully restored.

## REQ-DEP-004 — Bundled durable services and bounded operations

The bundled PostgreSQL and evidence-store modes MUST use persistent storage, authenticated encrypted transport, separate service roles, pinned maintained images and bounded resource/storage settings. Evidence remains encrypted before upload. Database, evidence, backup, system and cleanup capacity MUST be accounted separately; shared underlying storage requires backed limits before promising isolation. Preserve per-workload protected evidence allocations and physical headroom for compaction, temporary files, deletion and database/WAL operation.

Single-instance deployments MUST state downtime and failure-domain limitations. The support contract includes tested restart, backup/restore, capacity exhaustion, credential/certificate rotation, minor upgrades and explicit major migration. Database backups use finite encrypted base/WAL recovery; copying an active database directory or keeping a dump without a defined recovery objective is insufficient. Report stale/failed backups and threatened recovery objectives. Do not silently discard required WAL or evidence to keep service healthy. Same-disk backup copies are not independent disaster recovery. Retain persistent state on Helm uninstall; explicit removal workflows remain responsible for evidence deletion.

### SC-DEP-004

Given a small deployment with two workload allocations, when one workload reaches its evidence quota or the object disk becomes pressured, then expensive acquisition is suppressed before consuming another workload's protected allocation or database/system reserve. Restart preserves committed artifacts and accounting. Restore remains fenced until current revocations, expiries and deletion obligations are reapplied. Chart uninstall does not erase retained data or recovery keys.

## REQ-DEP-005 — Low-effort bootstrap and safe provider migration

[ADR-133 positive managed setup-copy closure](../docs/architecture/initial-bootstrap-copy-closure.md) MUST be selected by the installer only for a positively fresh v3 bootstrap. Existing v1/v2 identities, guard bytes and copy-deletion denial remain unchanged. Missing seed alone cannot select a new version: recover only an exact complete protected original prelude or fail unavailable. After independently verified original handover, activation history and positive manager credential/session retirement, retain one fifteen-minute cleanup claim across bounded two-minute command attempts and five-second current observations. Actual expiry requires separately qualified recovery, never a renewed claim or assumed completion.

Before deleting a managed SQL/provider input copy, independently qualify an additive permanent native tombstone that prevents recreation of its fixed name, preserve the original v3 guard, and retain the exact original copy UID/resourceVersion. Guard retention belongs to trusted Kubernetes administrator/RBAC authority: VAP cannot self-protect admission-policy/binding objects. Runtime/probe roles MUST NOT gain their mutation rights; missing/replaced guard identities or content MUST fail current effects and completed replay without recreation/adoption. Unknown create replies permit exact lookup only. Require positive guarded absence before atomically replacing the seed payload with fixed sanitized data and setting immutable. Completed replay MUST use only exact metadata and the retained history-only bundle before any setup-material read. This managed-copy removal does not remove operator-owned originals, revoke upstream credentials or claim control-plane/backup erasure; native enforcement and the complete installed command chain require separate qualification.

[ADR-102 preparation journal](../docs/architecture/initial-preparation.md) MUST persist bounded public create intent before subsequent setup effects, bind exact namespace/guard/journal identities and the original preparation request/plan, and retain one pending create at a time. Only an acknowledged first UID/resource-version-qualified update may reserve a fresh attempt; timeout, uncertain reply, conflict, failed final protection or replay MUST NOT renew it. Record only independently verified exact receipts and reject their replacement. Require current administrator identity and native staging proof within the original five-second/caller deadline. Credentials, secret-payload hashes and evidence MUST NOT enter the journal. Its state supplies no execution, SQL activation, historical-integrity or recovery authority; the supervisor remains responsible for exact target checks, initial root persistence and guarded handover.

[ADR-099 protected installer execution](../docs/architecture/initial-installer.md) MUST use a finite process and the closed [private startup document](contracts/initial-installer.schema.json). Establish namespace/source protection before exposing credentials; remove the exact Pod's scheduling gate only after qualification. Authenticate its Pod-bound writer online and compare the current Pod UID/specification, exact account UIDs and independently pinned native guards before SQL access and every witness operation. Preserve original protection deadlines through witness/source reads and SQL locks. No automatic Pod restart/replacement, unbound-token fallback, credential-bearing arguments, caller-selected activation flag or success exit on interruption. Use distinct finite preparation/audit/activation credentials and retire their actual provider authority after completion or abandonment. These internal steps add no developer approval; first installation cannot recover a restored database.

[ADR-100](../docs/decisions/100-temporary-initial-sql-credentials.md) requires independent random SQL passwords retained in the closed [private Secret state](contracts/initial-sql-credentials.schema.json) before role creation, bound to the full startup plan and original fifteen-minute interval. Plaintext passwords MUST NOT enter SQL DDL/bind parameters. Replays MUST verify exact direct and ambient authority and authenticate the retained secrets without renewing them. Retire new-login and existing-session effect privileges; password expiry or Secret deletion alone is insufficient. The maintenance capability remains separate from activation/runtime credentials. This refines REQ-DEP-005; the implementation/qualification record distinguishes the provider components from the unfinished installation supervisor.

The protected Secret producer MUST prove the exact administrator, independent native namespace protection, immutable startup configuration and original unscheduled/gated Pod before creation. Retain the original at-most-five-second deadline through writes and final checks. Send no uncertain POST replay; only exact caller-retained content can resolve a lost creation reply. Subsequent reads require the retained UID and unchanged protected plan. A same-named object, new passwords or a replacement Pod cannot silently resume an old attempt. Cleanup reads may outlive the Pod; removing its protection does not authorize secret disclosure. These remain internal installation steps, not another developer approval flow.

The activation executable MUST reject SQL credentials whose username does not match the installation UUID and assigned preparation/audit/activation purpose, before opening SQL or consuming the witness. It MUST require actual SCRAM-SHA-256 authentication rather than accepting trust, MD5 or cleartext-password fallback. Exact runtime names supplement the provisioner's grant/password checks and never replace credential retirement.

[ADR-101 staging](../docs/architecture/initial-namespace-staging.md) MUST establish namespace protection before future installer identities/workloads/provider credentials. A pre-namespace policy plan carries no fabricated UID; current observations bind the actual newly created namespace and exact guard identities. Create policy, binding and namespace in that order under current administrator identity, refusing an existing namespace and retaining acknowledged identities on partial failure. Unknown create replies MUST NOT cause automatic POST replay or adoption. Read-only resumption requires the original complete pins and preparation request; it cannot repair protection or prove historical cleanliness. Keep a distinct denied preparation probe and an explicitly nonpersistent final-input probe so the staging policy cannot mask the final guard. Preserve both protections during handover and keep the original Pod gated until the final guard is qualified. Current enforcement alone is not recovery authority. The durable bootstrap journal and handover supervisor remain separately implemented/qualified work under REQ-DEP-005.

[ADR-098 first-installation activation](../docs/architecture/initial-installation.md) MUST require an exact protected witness, current unsuspended fleet source, atomic eligible-database checks and independently verified encrypted attempt audit. Preserve a single finite attempt across retries and uncertain outcomes. Check every application table under locks before preparation and again before first activation; operational history, unknown/missing tables or row security forbid first installation. Use separate temporary preparation/audit/activation roles and retire them after installation. A completed-attempt replay MUST NOT clear later suspension/recovery, refresh observation or activate another database incarnation. This private coordinator is not restore approval or a runnable installer.

[ADR-097](../docs/decisions/097-one-use-installation-witness.md) supplies a one-use installation witness outside PostgreSQL. Retain independently pinned installation/epoch/namespace/object/writer identity across upgrades and ordinary uninstall until qualified retirement. Consume the exact existing record once by conditional UPDATE to an immutable finite claim; no runtime create-on-missing, reset, delete or replacement is allowed. Missing or replaced state requires recovery. Current writer identity, named RBAC and independent admission enforcement are mandatory. Witness consumption alone MUST NOT clear recovery or substitute for an atomic eligible-database check and durable encrypted activation audit. Installer provisioning and the activation coordinator remain separate requirements.

[ADR-095](../docs/decisions/095-hub-workload-garbage-collection.md) MUST preserve native foreground deletion of the protected Deployment chain. Permit the exact garbage collector's metadata maintenance only with unchanged workload spec, labels and annotations, and the assigned kubelet's final DELETE only after deletion has begun and the Pod is terminal. No generic controller/developer workload-write grant or fixture finalizer stripping may substitute for native lifecycle qualification. Keep current policy pins and kind-specific denial tests; wildcard type-check status is insufficient.

[ADR-094](../docs/decisions/094-native-hub-worker-projections.md) supplies installation-owned hub-worker objects. Native API credentials MUST be Pod-bound token projections for the process ServiceAccount, with bounded lifetime, current file rereads and the API audience. Keep purpose-specific clients, non-administrator source probes, exact RBAC/admission and separate SQL/key credentials. Separate files within one process do not imply isolated principals. Owner enrollment retains its distinct audience. Build the workload initially at zero replicas; protect its namespace and provide immutable startup inputs before launching it. Source-probe ConfigMaps MUST NOT alias startup configuration. Template generation and Pod readiness never clear recovery or confer evidence authority.

Use one-time, scoped bootstrap operations to create stable credentials and an administrator invitation, with idempotent create-if-absent behavior and recovery diagnostics. Secret bytes MUST NOT be supplied through Helm values, rendered Secret templates, release metadata or ordinary logs. Support existing Secret references. Do not rotate or recreate credentials merely because a template renders. No second privacy consent or per-maintainer infrastructure setup is introduced.

Expose independent dependency/capability status and exact remedies, distinguishing configured, qualified, unavailable and recovery-required states. Support documented provider migration with current authority, explicit stable identity mapping, preserved audit actors and native artifact hashes, copy-ledger accounting and unchanged absolute deletion deadlines. Do not link accounts automatically by email/name. Database/provider migration MUST fence old writers and authority; endpoint edits alone cannot authorize a second active installation or reset grants. Old key/store readers remain available until retained obligations are safely migrated or expire.

### SC-DEP-005

Given a working local installation, when SSO and external storage are adopted separately, then explicitly mapped users retain only reviewed access, audit actor history is unchanged, ongoing copies count against capacity and their deletion deadlines do not move. An interrupted migration can resume from recorded state without duplicating grants, silently replacing objects or erasing the old keys.

[ADR-078 owner acceptance](../docs/architecture/owner-configuration.md) MUST persist one pinned source per installation/hub cluster and monotonic immutable revision history before using pool/public-root changes. A newer unaudited revision invalidates the old projection immediately; only independently verified encrypted audit permits current use. Persist source failure watermarks even before first acceptance, commit known rollback/mutation fences, and prevent delayed results or late audit from reviving earlier trust. Preserve original source/root deadlines through SQL locks and restart, and require current matching installation recovery/issuer state. Replacing a source UID requires separately qualified recovery, not ordinary refresh. This internal lifecycle adds no developer setup or approval.

Owner leaf issuance follows [ADR-079](../docs/architecture/owner-issuance.md): require an identity-free CSR, exact Pod/process/purpose/key, accepted configuration/recovery, enrolled audit and durably spent bounded signing attempt. Use distinct server/client provider roles and absolute period expiry; a retry MUST NOT extend it. Verify actual output against both independently pinned and current accepted roots before separate encrypted certificate audit/activation. Twenty-minute UTC periods with one-minute advance renewal permit long-lived hubs; each renewal still requires current authority and bounded history. Provider issuance MUST NOT activate a peer or become a public enrollment shortcut. Private keys remain owned by the process; no automatic POST retries, provider key export or plaintext fallback.

The private owner lifecycle under [ADR-082](../docs/architecture/owner-registration.md) MUST durably bind exact Pod/process/purpose to its public key before signing. Independently verified encrypted enrollment and certificate audit precede separate activation. Spend attempts before provider I/O; pending/uncertain attempts survive restart and cannot refill in the same period. Stored results may finish audit using fresh proof/current roots without extending signing deadlines. Durable comparison MUST retain exact recovery identity/revision and wall-clock instants without depending on process-local monotonic clock data or time-zone representation. Bound retained registrations and renewal history; retirement fences use immediately but holds capacity through the last possible leaf expiry plus one minute. Current registry, actual TLS identity, protected workload routing and exact request ownership all remain necessary for forwarding; none substitutes for developer/evidence authority.

[ADR-083 current peer authentication](../docs/architecture/owner-authentication.md) MUST combine actual verified TLS with the exact active registration, currently accepted explicit roots, native private-workload protection and Ready routing before owner use. Repeat registration/protection around routing and recheck all original deadlines after blocking work; retain the earliest within an overall five-second interval. Reject source/root changes, retirement, unavailable protection, mismatched Pod/controller identity and deleted/unready Pods even on a reused TLS connection. Enrollment before readiness remains allowed. This peer identity is not a request locator, developer credential, evidence grant or authority to inherit another process's work.

[ADR-084 process-owned credentials](../docs/architecture/owner-credentials.md) MUST keep separate server/client private keys within the owning process and retain each original CSR through bounded enrollment/renewal. Bootstrap generates a fresh process epoch on restart; keys and active requests cannot be inherited. Independently verify actual certificate bytes, generated key, fixed UTC period, active registration and both pinned/current roots before installation. TLS snapshots preserve their original expiry and become unusable for signing when their owner closes. Supervise both purposes with finite initial enrollment/retries and renewal through the earlier original expiry; a partial renewal cannot extend that deadline. Identity notifications cannot block shutdown or grant readiness/authority. The runtime remains responsible for current peer checks, listener/socket closure, protected bootstrap and exact-request forwarding. No extra developer configuration or approval is introduced.

[ADR-085 private receiving](../docs/architecture/owner-relay.md) MUST authenticate actual client TLS and current local serving identity before accepting the bounded worker enrollment body, resolve the exact existing live registration, and repeat current identity checks before returning certificate bytes. Initial peer observations admit receipt only; independent operation authority remains mandatory throughout work. Preserve original locator/request/owner deadlines and cancellation through flush. Bound connections before TLS, disable resumption in the initial profile, enforce an absolute connection lifetime and close active sockets on shutdown. A wire locator grants no authority, and outbound transport MUST verify the exact discovered destination before transmitting a Pod token. This adds no user-visible configuration or approval.

[ADR-086 outbound transfer](../docs/architecture/owner-forwarding.md) MUST verify the exact currently accepted server process and local client identity before transmitting a Pod token/CSR, repeat the same locator check and retain original route/worker/setup deadlines. Use only qualified Pod IPs, explicit roots and one non-replayable HTTP exchange; never follow redirects, retry an uncertain POST, use an ambient proxy or take over another owner. Verify returned DER against the worker issuer, CSR and original identity/period, then repeat current peer/locator/worker checks. Socket ownership follows caller/root cancellation. A completed HTTP response MUST NOT be presented as a live remote `WorkerEnrollmentDelivery`; final downstream ownership and current operation authority remain mandatory.

[ADR-087 live forwarding](../docs/decisions/087-live-owner-delivery.md) supersedes the finite-only relay limitation. The private owner-relay/v2 receiver MUST retain the exact original operation through downstream delivery using one open authenticated response, never a completed reply or a renewed lease. The sender MUST reject fixed-length/v1 replies, clamp the advertised deadline to independent local limits, and cancel on EOF, any extra payload, transport failure or caller/root cancellation. Keep sender/receiver slots charged through cleanup and join the finite body monitor on Close. The worker handler retains the live delivery through its final write/flush. A silent partition is bounded by the original final identity interval, at most five seconds; delivered certificate bytes cannot be retracted and confer no evidence authority. No additional user configuration or approval is introduced.

[ADR-088 owner startup](../docs/decisions/088-owner-startup-readiness.md) MUST distinguish startup readiness from peer/request authority. Before Kubernetes Ready, validate exact current owned server/client keys, activated registration, accepted configuration and native Pod/token/CSR/protection proofs without requiring an already Ready route. Preserve all original intervals and the five-second/parent deadline. Request admission MUST continue requiring actual TLS and Ready routing. Runtime composition uses a fresh process epoch, process-local core suppression before key creation, exact protected pool/source and original roots, joined credential/listener/forwarding ownership and expiring readiness. A missing/failed observation cannot retain a stale ready hint. Close keys/sockets and bound shutdown; no startup path may clear RecoveryBlocked or substitute fixture authority.

[ADR-089 multi-cluster routing](../docs/architecture/worker-routing.md) MUST select each worker profile from current admitted SQL state under the configured installation/permission root. Resolve issuer roots only from an installation-supplied control document matching that exact profile digest and cluster; never merge issuer roots across profiles. Repeat current checks before token transmission and after receipt. Keep effect stores profile-scoped. Configuration/parent/caller expiry and cancellation during blocking reads deny routing. Installation supplies and synchronizes the same immutable control bytes; developers do not manage a duplicate trust list.

The [ADR-090 deployment loader](../docs/architecture/owner-deployment.md) MUST consume only fixed installation-owned projections under the private [deployment](contracts/owner-deployment.schema.json), [credential](contracts/owner-credentials.schema.json) and [worker bundle](contracts/owner-worker-trust.schema.json) contracts. Reject ambient provider credentials, secret-bearing DSNs, symlink escapes, non-regular or unbounded files, and stale-token fallback. Preserve current accepted source/recovery, native workload proof and purpose-specific provider roles; startup cannot grant itself acceptance. Read HTTP credentials per request and SQL credentials before new connections without changing the selected role. Current whole-bundle failure stops the owner subsystem; valid individual profile removal remains scoped. Installer-generated projections and native in-Pod operation require qualification before enabling the chart.

[ADR-091 reconciliation](../docs/architecture/configuration-reconciliation.md) MUST run with independent observation/audit roles under the private [hub worker deployment](contracts/hub-worker-deployment.schema.json) contract. Qualify fleet and owner source protection with pinned native admission and independent dry-run enforcement. Scheduling leases cannot clear recovery or replace per-observation freshness/SQL fencing. Bound independent source loops, cancel and join them on leadership loss, and never recreate a missing pinned Lease. Equal database observation timestamps cannot extend authority or undo a negative watermark.

[ADR-092](../docs/decisions/092-independent-source-admission-probes.md) requires independent source-guard qualification when namespace and source admission overlap. The private owner projection MUST carry a finite exact `configurationProbes` list. The workload guard may permit only listed same-namespace ServiceAccount/core ConfigMap pairs for explicitly nonpersistent dry-run UPDATE without subresources. Real writes, other actors/resources/operations and broad dry-run bypasses remain forbidden. The source guard MUST still supply the independently expected denial; unrelated denial or repeated lucky policy ordering is insufficient. Include the list in expected policy, protection digest and restart/requalification rules.

[ADR-093](../docs/decisions/093-bounded-hub-scheduling-permission.md) adds a required private `schedulingLeases` list of at most four exact same-namespace account/Lease pairs. The private namespace policy may permit only UPDATE on each named coordination Lease main resource for its exact account. RBAC MUST independently restrict runtime to named get/update; no create/delete, wildcard actor/resource or administrator grant may substitute. Scheduling MUST retain original namespace/Lease UID, CAS and finite record validation and confer no configuration/recovery/collection authority. Preserve explicit empty-list semantics, closed validation, copied input, digest coverage and restart/requalification on change.

## Original installed capacity probe

Under REQ-DEP-003 and ADR-145, the private namespace guard MAY carry the exact
original worker ServiceAccount name and UID for explicit dry-run main-resource
CREATE of the two v1alpha1 capacity configuration resources. The independent
capacity admission guard MUST still deny both operations; namespace or RBAC
denial alone is insufficient. No persistent write, other version, subresource,
actor or resource is exempted. Fresh installed inputs MUST derive this branch
and the fixed processing-source UPDATE probe before their original guard claims,
and preserve them through configuration role production, worker activation and
owner startup. Existing receipts MUST NOT be rewritten to adopt the new plan.
