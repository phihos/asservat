# Native fixture retention observation ownership

Four test-only paths; no production, SQL, authority, budget, socket or aggregate deadline changes. Integrate `manifest.json` only after verifying every base/payload and recording dependency changes separately.

The native download gate previously called `retentionEffectFixture.RetainedRetentionPolicies`, which writes `ObserveRetention` under an exclusive permission-stream lock before every accepted-source read. Publication used the same write-on-read pattern. The fixture already had a one-second source owner, but it began after publication/setup and renewed retention ownership without publishing its observations. The actual current-source consumer is now `AcceptedRetentionReader` for native cases, including the factory-captured `f.authority` closure and enrollment/control consumers. Ordinary fixture composition remains unchanged.

One joined native fixture owner starts immediately after the accepted capture scenario returns, before processing initialization, crypto preparation and catalog publication. It observes only the original explicitly synthetic fleet/permission/retention roots. Each original <=5-second refresh renews the existing source lease, publishes the retention observation and refreshes permissions; the already accepted worker configuration is attached later, once, without holding the registration mutex during I/O. No source observer can clear recovery, suspension, replace a revision or revive expired ownership. Failure cancels the shared fixture context and is reported when the owner joins. `t.Cleanup` covers early setup Goexit; an idempotent explicit Close joins before native phase pools close.

The capture scenario's already accepted admission, authority observations, human session, worker, encrypted artifacts and every native request keep their original dates. The source owner does not rerun capture admission or renew disclosure leases. Its early start does not synthesize production installation authority.
