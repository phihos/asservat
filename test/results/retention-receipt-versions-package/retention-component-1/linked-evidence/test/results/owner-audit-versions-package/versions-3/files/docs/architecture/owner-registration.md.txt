# Durable hub owner registration and certificate activation

[ADR-082](../decisions/082-durable-owner-enrollment.md) composes [pre-Ready enrollment proof](owner-enrollment-proof.md), [accepted owner configuration](owner-configuration.md) and [bounded provider issuance](owner-issuance.md). C-04 owns the coordinator/ledger/activation/registry/cleanup/verifier ports; C-11 owns separate encrypted audit writer/acknowledgement ports; C-21 owns SQL, object-store and crypto adapters; C-24 owns the immutable values. No public UI/MCP API changes.

## Values and persistence

`OwnerEnrollment` retains a generated registration UUID, exact installation/cluster/issuer/Pod/process binding, single server/client purpose, immutable public-key digest, pool/source pins, Pod/ReplicaSet provenance, initial token/workload/protection digests and original claim/hold times. Later fresh proofs must match identity, key, names, source and pool. Initial digests remain provenance; ordinary live workload changes require new proof, not equality to a perpetual Deployment-spec snapshot.

`OwnerCertificateAttempt` contains the immutable enrollment, the existing `OwnerCertificatePermit`, and original token/workload/protection digests and proof times. The permit contains the public configuration once; `Proof()` reconstructs the original complete observation without duplicating roots. Persist at most 64 KiB per attempt, 16 KiB per enrollment, 64 KiB per issued leaf/chain JSON and 8 KiB per receipt. These are explicit serialized bounds. Clear private keys, tokens, complete workload specs and CSR bytes do not enter SQL or durable audit.

Migration `00030_owner_enrollment.sql` adds `hub_owner_enrollment` and `hub_owner_certificate`. The registration has a unique exact binding/purpose, write-once enrollment audit, monotonic highest epoch/hold and irreversible retirement. Certificate attempts have unique registration/epoch/ordinal and unique leaf digest; result, acknowledgement and activation are write-once. Inserts start unaudited/unactivated. Triggers defend registration counts, current next signing ordinal, absolute expiry, immutable fields and no deletion before the last possible leaf plus grace. No destructive down is provided.

## Acquisition and retry

1. The coordinator validates the identity-free CSR, obtains a current trusted Pod proof and claims/reuses its exact registration. Claim/pruning/counting run under current matching accepted configuration and recovery.
2. If missing, write encrypted enrollment audit at `hub-owner-enrollment/v1/<installation>/<registration>`, conditionally create it, read back and decrypt/compare its entire frozen value. The independent audit SQL role records the exact receipt. An acknowledged retry does not repeat wrapping/object work.
3. Obtain fresh proof. Under recovery then configuration locks, validate original deadlines, exact configuration and unretired audited enrollment. Choose ADR-079's UTC epoch and consume at most two ordinals. Persist the complete attempt before any provider call. Concurrent callers get stored/pending progress, never another permission to reuse an attempt.
4. Sign only under the original permit deadline. Verify actual CSR/SPKI, purpose/identity, lifetime and both pinned/current roots. Store the immutable public result while the original proof and permit are still valid. Any possible provider call remains spent even if its response or storage fails.
5. Write/read-back/verify independent encrypted certificate audit at `hub-owner-certificate/v1/<installation>/<attempt>`, then acknowledge it through the audit role. Resume a stored result without signing again. Audit may finish after the signing deadline while the leaf is valid; current proof and crypto verification are still required.
6. With fresh Pod proof and current trust, use the separate activation SQL facet. Require exact stored result/audit/enrollment, unchanged recovery revision, live certificate and unretired registration. Return the independently checked certificate only while final proof/certificate deadlines remain valid.

The complete coordinator has a thirty-second operation bound. Individual SQL/provider/proof bounds remain shorter; the outer timeout never refreshes them. No remote I/O takes place while SQL is locked. Use `clock_timestamp()` after blocking locks; retain the initial observation through pool waits and aborted-transaction retries. A failed/uncertain COMMIT is not permission to resend a signing effect.

Proof structural checks require overlapping original proof/configuration intervals. A native configuration read may finish after the proof start, while a cached read may predate it. `OwnerEnrollmentProof.WellFormed` checks the earliest point in that overlap; it does not establish current authority. SQL still checks `Valid` against actual database time after locks and at completion, keeps the original proof deadline, and compares current accepted configuration. Never reset the start or extend freshness to accommodate I/O.

Attempt equality compares recovery identity/revision exactly and timestamps by their instants, including after durable JSON round trips. Process-local monotonic readings and time-zone representation are not persisted authority fields. Reject any actual deadline or identity change; do not mistake serialization's removal of monotonic clock data for a changed signing attempt.

## Current use and cleanup

`ReadOwnerRegistration` is an independently limited registry facet. It requires current accepted configuration/recovery, matching pool/source, unretired immutable enrollment, acknowledged enrollment and certificate audits, activated exact certificate digest/identity and matching issuance recovery revision. Its observation lasts no longer than five seconds or original configuration/recovery/certificate deadlines. This is registration evidence, not a TLS handshake. Forwarding must also validate the actual peer under current roots, current live workload routing and the exact request locator and developer authority. The registry does not grant download or takeover rights.

Retirement immediately fences one exact registration; retry is idempotent. It does not delete a possible live leaf or refund registration capacity. Initial hold and every signing attempt extend the hold through the full absolute certificate expiry plus one minute, up to 22 minutes from current preparation. Count all pending/uncertain/retired registrations: 1,024 per pool and 32 per Pod across purposes. One overloaded Pod cannot consume the entire pool. These are implementation ceilings; installation-wide admission/throughput qualification remains required.

Pruning deletes only certificate attempts whose expiry plus one minute is past. It preserves the parent's highest epoch until the entire expired registration can be removed, so historical cleanup cannot reset a current budget. Claim/preparation prunes the bounded pool; an explicit cleanup facet handles idle pools and source outages. A quiescent registration with no possible live leaf can be deleted without node-quiescence proof because this state accounts for certificate issuance, not running capture/Job capacity. Cleanup never releases evidence or worker reservations.

After pruning, a fresh enrollment receives a new audit ID even if a caller repeats an old process identifier. All former certificates/locators have expired; runtime startup still generates fresh process epochs. A late acknowledgement/retirement addressed to the old registration ID cannot change a replacement.

## Qualification

The real SQL/S3/OpenBao fixture composes the production coordinator, purpose-separated provider issuer and current crypto verifier. It covers missing audit, interrupted certificate audit after actual signing, retry after the original signing deadline, no duplicate provider call, key/process/purpose mismatch, concurrent irreversible attempts, bounded uncertain retry, post-lock expiry, separate role denials, retirement without refund, source/recovery fences, per-Pod capacity and expired restored-row cleanup. Initial Pod proof/recovery are explicitly synthetic; ADR-081 separately qualifies real Kubernetes proof. The historical cleanup seed uses only the fixture administrator's transaction; runtime roles cannot bypass triggers.

Current-root tests distinguish checking a stored certificate after a signing deadline from reviving a signing permit. Actual results, source hashes, failures and cleanup are recorded in [implementation progress](../implementation-progress.md). [ADR-083](owner-authentication.md) adds current peer authentication and the native proof-through-activation integration fixture; measured qualification is tracked in the progress record. Pending: long-duration renewal/restore and fleet sizing, protected owner issuer/transport/bootstrap, actual forwarding and public workflow. No claim of S-01/S-02 completion follows from these components.

All recognized active owner input formats require versioned audit stores for enrollment and certificate records. Current enrollment replay, signing preparation, audit acknowledgement, certificate activation and registry reads reject retained receipts with an empty or `null` version. Structural enrollment/attempt decoding and historical retirement/pruning remain separate: historical bytes and original attempts are never rewritten to restore authority. Native evidence download and acquisition-worker receipt formats are unchanged by this owner-specific requirement.
