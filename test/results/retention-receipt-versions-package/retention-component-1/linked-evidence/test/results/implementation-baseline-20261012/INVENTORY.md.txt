# Asservat feature and milestone baseline — 2026-10-12

This is a read-only inventory of the accepted first-release scope and evidence available at capture time. It supplies no overall percentage, remaining-effort weighting or delivery date. Stage labels describe evidence, not equal-sized units of work. Source digests and the exact evidence inputs are in `sources.json`; ongoing implementation can supersede this snapshot.

The defensible current position is: **the packaged initial bootstrap workflow has passed native Helm qualification; substantial authority, custody and bounded context components exist; a complete installed developer investigation service has not passed.** The breadth of the first release extends well beyond the current pod-status diagnostic. Most of that collector, recording, analysis and sharing breadth still needs product implementation and integration.

## How to read the inventory

- **Designed (D):** accepted requirements/contracts/architecture exist. A prototype or feasibility experiment is not implementation of the product feature.
- **Implemented component (C):** concrete product code exists with bounded component checks. This says nothing by itself about deployed authority or usability.
- **Integrated with synthetic authority (I):** concrete components communicate in a fixture, but one or more installation, identity, permission, source or backing facts are supplied by the fixture.
- **Native-qualified (N, named scope):** a recorded test passed against actual APIs/providers/SQL/TLS/browser/containers, with its stated synthetic boundaries. N and I can coexist; real transport does not make synthetic authority production authority.
- **Installed/user-usable (U, named scope):** the intended operator/developer can complete the specific workflow through the packaged product and its supported inputs. The bootstrap-only operator flow has native packaged evidence. The complete installed developer flow does not.
- **Production-qualified (P):** applicable release, failure, privacy, compatibility, scale, operational and usability criteria have passed for advertised profiles. No complete first-release feature set or S-09 exit has this evidence.

A row gives its highest evidenced **bounded scope**, followed by what prevents completion. “No product implementation identified” refers to the reviewed scope and current diagnostic/entrypoint inventory; it is not a claim that no reusable utility or domain type exists anywhere. Evidence keys link to concrete files below.

For a subsequent forecast, estimate bounded work packages behind these IDs separately: design decisions still open; implementation; integration with actual installed producers; native/failure qualification; and user/production acceptance. Record dependencies, reuse and measured effort on comparable completed packages before adding any weights or schedule. Count neither ADRs/migrations/tests nor checklist rows as equal progress units.
