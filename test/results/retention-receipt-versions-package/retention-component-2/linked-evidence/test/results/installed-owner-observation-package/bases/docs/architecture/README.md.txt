The vocabulary has four levels. An **application role** is a separately scheduled process/Job or host executable with its own authority. A **component** owns a cohesive responsibility and its state transitions. A **code module** is a package family implementing that component; it is not automatically a separate Go module or network service. An **interface** is a versioned network/IPC contract or a typed in-process port. Diagrams use C4-style levels in Mermaid; “application” avoids confusing the C4 term “container” with Kubernetes containers. Public collection and permission scope remains the whole pod.

## Selected shape

Use a modular Go hub with separately runnable API and worker roles. Workload clusters contain a connector/controller and privileged node collectors. A minimal Rust helper handles the host crash path. Evidence analysis uses separate acquisition, offline-analysis and publication Jobs. Share the reviewed Go codebase and role-selecting binary, while images, credentials and network policy enforce different execution authority. Inspektor Gadget is an explicit pinned external dependency. No component becomes a microservice solely because it appears in a diagram. The accepted React/TypeScript console is a static build served by the Go API role, with no production Node service.

PostgreSQL owns hub transactions; Kubernetes owns configuration and bounded local execution records; regional object storage owns encrypted evidence and immutable outcomes. Regional text indexes are rebuildable memory caches. Browser and MCP are adapters over the same application services. All external effects leave the hub transaction before execution and return through idempotent, fenced reconciliation.

## Authority of these artifacts

The behavioral requirements and canonical public schemas remain authoritative for user-visible semantics. [REQ-ARC-001–007](../../specs/implementation-architecture.md) specify this decomposition. The catalog is the canonical list of application/component IDs, dependency allowances, entity owners, requirement owners and interface endpoints. Prose explains their contracts; it does not create an independent API vocabulary.

Every existing requirement has one primary implementation owner in the catalog; collaborators may participate. Each domain entity has one lifecycle owner even when several application roles run its code. An owner is not necessarily the current execution location or the sole table in a SQL transaction. Current source authority in the domain model remains unchanged.

An implementation task should read its requirement, catalog owner, relevant component/interface, runtime flow and slice acceptance tests. It should not need the entire repository in one prompt. Empty package directories, illustrative Go signatures and successful schema validation are not evidence that a collector or security boundary works.

## Review outcomes

This pass resolves the competing package-layout sketches, places evidence-text search in its region, specifies collector-initiated local transport, separates durable command/control from transient live delivery, and makes transaction/fencing responsibilities explicit. It also prevents lease expiry from being interpreted as permission to replay an intrusive action.
