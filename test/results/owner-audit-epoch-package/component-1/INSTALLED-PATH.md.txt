# ADR156 concrete installed path, separate implementation proposal

This maps the staged values to the existing product implementation. No listed constructor, role, migration or runtime format is changed here. The existing full consumer map remains authoritative for the inventory of affected readers.

## Fixed object contract before adapter reuse

The proposed record type is `audit.OwnerConfigurationEpoch`, format `asservat-owner-configuration-epoch/v1`. Its complete JSON record includes epoch/attempt/ordinal, full protected semantic configuration, original reserve/source/store/root/qualification/policy and all original dates. The exact key is:

`hub-owner-configuration-epoch/v1/<installation UUID>/<cluster UUID>/<source UID>/<reserve UUID>/<positive decimal ordinal>/<epoch UUID>`

There is no trailing slash, generation alias, caller-selected prefix, latest pointer or partial matching. The new ciphertext domain/AAD format will be `asservat-owner-configuration-epoch-audit/v1`; its root is the original installation UUID and event is the exact key. Reuse `framed.sealControlAudit` and `verifyControlAudit` with a separate fixed wrapper, 64 KiB plaintext / 128 KiB ciphertext caps, and complete record equality. This proposal does not replace the existing `asservat-hub-owner-configuration-audit/v1` AAD or old key. The shared encryption primitive is reusable; old owner writer, old receipt lookup and old IAM prefix are not interchangeable with the new purpose.

The new adapter must take a concrete pre-admitted one-use epoch claim, not just a caller-made record. Under a spent claim it issues at most one original PUT and then verifies the immutable actual version independently. Unknown PUT results go to exact bounded inventory/reconciliation under the same retained record and charged attempt; never call the old writer again to search by repeated PUT. The generic `putControlAudit` behavior must be reviewed against this one-use claim before reuse. New exact-key IAM provisioning must be qualified for the selected provider. Parent-owned complete pagination and positive writer closure remain independent prerequisites for retirement.

## Deliverable sequence tied to current code

1. **Protected bootstrap reserve and narrow SQL plan.** Extend the actual initial-runtime installer between positive source14/store/account/physical backing production and immutable worker-input publication. Retain one original reserve identity and acknowledge real allocation. SQL54 capacity adoption refers to that allocation once. Preserve initial root totals; do not fabricate an artifact or add the same reserve twice. This work needs its own reviewed SQL/privilege plan before implementation.
2. **Persisted epoch claim/result/current selection.** Keep SQL29 source revisions and negative watermarks. Add distinct finite tables and purpose-separated facets as proposed in SQL-PLAN. The claim transaction locks recovery then source, reserve/head, and exact epoch, checks original source/cadence/capacity, commits full charge/one pending ordinal before I/O. Separate result recording preserves historical outcomes; selecting the head needs a currently complete source, original bounds and positive exact receipt. Unknown commit replies resolve exact stored state without new I/O or date changes.
3. **Worker producer first, with no owner dependency cycle.** The current `NewProviderInstalledHubWorkerDeployment` already starts independent fleet/source loops and `InstalledConfigurationProviderEffects` uses protected worker material plus `RecoveryReader`, rather than `OwnerConfigurations.ReadOwnerConfiguration`. Preserve that separation so it can produce the first epoch. Extend `OwnerConfigurationObserver` through a new explicitly selected epoch observer/ledger/writer graph: frequent source refresh remains inexpensive; the finite persisted cadence drives automatic one-use audit claims. The mailbox keeps immediate source-loss cancellation and no independent authority. Routine unchanged observations no longer skip a due epoch merely because SQL29 has a historical receipt.
4. **Explicit complete accepted and admitted consumer graph.** New `AcceptedOwnerAuditEpochReader` serves routes/discovery and new operation admission. `AdmittedOwnerAuditEpochReader` checks exact existing finite dependencies during their original intervals. Start with `OwnerEnrollments.current/withProof`, `ClaimOwnerEnrollment`, `BeginOwnerCertificate`, `StoreOwnerCertificate`, activation/registry and their domain proof/permit/receipt equality, then owner readiness/routes/authentication, provider gates and installer setup consumers identified in OWNER-AUDIT-EPOCH-CONSUMERS. Every effect stores its concrete effect ID and exact epoch before I/O. Pure X.509 checks may still use semantic configuration, but surrounding proof must retain epoch and original interval. An adapter that casts new accepted state back to old plain configuration is not a complete implementation.
5. **Automatic bounded retirement and restart.** A separate cleanup role joins actual writers, resolves all original dependencies, inventories every page/version/marker/upload under exact historical identity, deletes/aborts and positively verifies absence, then retires finite metadata/residual obligations. It cannot create new epochs or release because a source/receipt disappeared. New protected runtime format selects the complete producer/consumer/cleanup graph only after real service tests, including original installed worker rollover with unchanged semantic source. Old formats remain explicit old behavior; no silent fallback or mixed consumer graph.

No step asks a normal developer to manage epochs or renew an approval. The installer can expose administrator-selected qualified profiles and report original policy, measured usage, next automatic rollover, remaining headroom and a specific stopped condition. Failure messages distinguish insufficient configured slots, pending/uncertain writes, source unavailable, and physical cleanup not complete. There is no claim that the arithmetic lower bound proves cleanup will finish on time.

## Required next SQL review details

The next executable work should deliver named fixed tables/queries, lock order and actual narrow role permissions for reserve, source/epoch claim, exact receipt acknowledgement, selected read, finite purpose-owned dependency, inventory and retirement. The worker's source observation role must not gain reserve provisioning or deletion rights. The epoch audit acknowledgement role must not claim a second attempt or clear recovery. Read facets must verify actual full receipt bytes and policy, not accept a Boolean. No public EXECUTE, generic arbitrary-purpose insert or credential broker.

Actual qualification must include lost claim COMMIT, dropped PUT reply, versioned duplicate copies, changed source during audit, later head with valid original in-flight work, current retention shortening, restored ordinal rollback, exhausted uncertainty allowance, malformed policy minimum, positive writer closure, full paginated retirement and automatic steady-state rollover. Existing tiny inventory tests, pure values and accelerated clocks do not establish those runtime results.
